# Marketplace State Ownership

Marketplace installation separates plugin availability, activation, and refresh: Codex keeps available plugins in the selected `CODEX_HOME`, defaults their home activation to disabled, and lets trusted products enable their chosen skills through `.codex/config.toml`. Persistent refresh preserves each agent's selected plugin set and activation through native update operations, refreshing from the source the agent's own registry carries; isolated verification exercises installation in disposable homes. Marketplace-delivered Codex subagent definitions remain globally registered in the selected home, independently of product skill activation.

Persistent selection is bounded and ordered by each agent's committed marketplace catalog, and the marketplace's name is the one those catalogs declare. Claude Code supplies its installed inventory for that marketplace at project or local scope in the invocation checkout for bootstrap, and every project- or local-scope install record it reports on the machine for a cataloged plugin for refresh. The invocation checkout's own records move through the native plugin update. Every other project- or local-scope record of a cataloged plugin is brought to the target by rewriting its entry in the agent's install-record file to the target install path, version, and commit, so every Claude Code session on the machine starts and reloads at the head of the registered source's default branch. A record whose plugin the catalog does not carry, or whose scope is neither project nor local, is left unchanged and reported. No agent command runs with any checkout other than the invocation checkout as its working directory. Codex selection comes from the plugin keys declared in the selected home's configuration, including disabled entries and entries whose caches are absent; merged product overrides and cache presence do not choose that home-wide set. Every nonempty selection contains `spec-tree`. An empty selection supplies only `spec-tree` and a warning to choose additional plugins; an empty Codex home receives it disabled. Claude Code bootstrap preserves any declared project activation and defaults an undeclared bootstrap plugin to disabled. The supply and its warning are one act: an empty inventory proposes the bootstrap, and the plan the run carries decides it, so an agent whose bootstrap a later condition withholds installs nothing, warns of no first install, and is reported as installing nothing.

A Claude Code refresh run is one bounded pass over the install-record listing it reads at its start. The target is the head of the registered source's default branch after the native marketplace refresh: for each cataloged plugin, the manifest version at that commit and the cache directory that version names. That head is read from the location the registry records for the marketplace, so it resolves only where that location is a git working tree; a registration whose location is not one — a directory source registered from a plain directory — and a read that fails for any other reason resolve no head, and a run with no head reaches no target. That is the same no-target run the bootstrap and withheld-registration cases produce, not an operational failure that stops the run: every project- or local-scope record of a cataloged plugin the run carries is reported against no target with a blocking warning, and the run exits nonzero. The invocation checkout's records move through the native update; every other planned record is rewritten in the install-record file to the target, whatever version it held before and whether or not its project directory still exists, so records that entered the run at differing versions leave it at one version. The run holds no lock over the agent's record store and makes no second pass: a record another agent session creates or rewrites after the listing is read is outside the plan. Outside the plan means unplanned, never erased — the rewrite edits the document as it stands when the write happens, so such a record survives the write with every field the plan does not set and reaches the closing comparison, where it is reported like any other record. After execution the run reads the listing again and compares every project- or local-scope record of a cataloged plugin with the target; it reports each record's version before and after and exits nonzero when any such record is off the target. Currency is a property of the run that established it: between runs a record holds what its last native install, native update, or rewrite wrote, and a session that starts from that record loads that version until the next run.

The marketplace source is the entry the agent's own registry carries under the catalog's name, read through the agent's listing command; the run refreshes from that source and names it in its report, and no source is compared against a constant. A missing registration is the bootstrap case and is added from the invocation checkout's own declaration; that run has no registered clone when its plan is built, so it reports every other checkout's record as unrefreshed and exits nonzero, and the next run brings them to the target. Refresh updates every selected plugin, including disabled plugins, and repairs missing snapshots or caches without widening selection. Existing activation entries remain unchanged, including explicitly enabled home entries. Verification reports an unexpected selection or activation change as failure and preserves the diagnostic state; refresh never restores an old settings snapshot. A selected plugin absent from the registered source is pending publication only when that absence is established; a failed read of the registered location's head resolves no target and is reported as the no-target disposition; every other operational failure stops the run. Isolated verification registers the invocation checkout, where an absent declared plugin is terminal.

For an agent whose plugin manifest cannot declare agents, the build emits each plugin's agent definitions in that agent's native format inside the plugin's declared skill surface, and plugin installation carries them to the consumer. Every agent definition invokes its plugin's skills, so placement is derived, never chosen: a plugin's agent definitions live in the same scope as the skill content they invoke, and every marketplace-shipped operation that delivers or refreshes either carries both in the same run. Skills installed in the selected agent home place their agents in that home's agent directory; skill content a repository commits carries its agents committed beside it in that checkout. Placing a plugin's agent definitions into a checkout's agent directory is checkout materialization, and it is valid only where that checkout carries the plugin's invoked skill content. A split — agent definitions in one scope while the skills they invoke live in another — is a detected fault: placement reports the mismatched definitions and stops rather than refreshing around them, because a checkout definition shadows the home copy while the home skills underneath it move with every refresh. No installation run or generated instruction surface requires committing agent definitions into a consumer repository, and a checkout's agent directory changes only within the namespace the owning plugin controls.

## Rationale

Plugin availability lets several products share one installed cache while choosing their own skill context. Disabled home defaults make product activation explicit; preserving an existing enabled home entry respects the operator's choice. `spec-tree` is the minimum coherent selection because it supplies the marketplace's governing methodology. Selection declarations survive an interrupted installation or a missing cache, so Codex refresh reads them independently of installed-file discovery. Native update operations preserve activation without a compensating write that could erase failure evidence.

A persistent run installs from the registered marketplace source while bounding the installed inventory with the checkout catalog, so the two disagree precisely when a selected checkout catalog name is absent from the published source. Reporting that name as pending publication keeps the refresh accurate about what it installed, leaves the rest of the selected set installable, and preserves release handling for a checkout whose catalog leads the registered source. The distinction is the marketplace source, not the plugin: an isolated run registers the checkout itself, so the same absence there means the committed catalog and the built tree disagree, which is a defect and stays terminal.

Claude Code keys an install record by scope and project path, and every session reads its plugin version from that one file. One machine hosts many checkouts sharing one plugin cache, so a refresh confined to the invocation checkout leaves every other checkout's session at its first-install version. Moving the invocation checkout's own records through the native update is what fetches the target into the cache; every other record needs only its entry to name that cache, so the file rewrite is the whole operation and no command has to run inside another checkout, where it would mutate a repository the run does not own and could not run at all where the directory is gone. One listing read bounds the run because the agent's record store admits no lock from outside the agent and a run that re-lists until nothing changes is an open-ended wait; comparing the closing listing with the target and failing on any miss makes the miss visible in the run's own result rather than in an inventory read later. The registry, not a constant, names the source because the machine's registration is what every session resolves against; a constant second-guesses it. That also settles what a settings document declaring the same marketplace name at another scope can do to a run: the registry admits one entry per name and carries no scope of its own, the run takes that entry, and a settings document supplies only a bootstrap registration, so no declaration at any scope displaces a present entry or aims the run at a source other than the one the machine resolves. What such a declaration can change is which source that is, and the run follows it rather than diverging from it — following the machine's own registration is the whole reason the source comes from the registry. Because the run names the refreshed source in its report, a source other than the one the invocation checkout declares is reported rather than silent. Rejecting a run because another scope named the marketplace guarded an intent the run no longer holds: under a constant the run carried a source of its own to defend, and under the registry it carries none. A user-scope install record is a different subject and keeps its own disposition: it lies outside the project boundary and is reported rather than moved. A persistent install is an explicit request to refresh the selected project and agent home. Trusted Codex product configuration controls effective skill activation, while home configuration controls home-wide refresh selection. Native commands run with that same separation so merged product overrides cannot change the planned set. Isolated mode protects persistent installation state during verification.

Codex discovers home subagent definitions independently of plugin activation. A global registry keeps placement and ownership reconciliation bounded, while each product controls its skill context. The [native plugin manifest](https://github.com/openai/codex/blob/main/codex-rs/core-plugins/src/manifest.rs) supplies no agent-definition delivery field, so the plugin lifecycle's shipped placement script remains the bridge from packaged definitions to the home registry. Product activation neither generates a checkout registry nor prunes home definitions.

The [Codex configuration contract](https://learn.chatgpt.com/docs/config-file/config-reference) permits trusted-product overrides of local-marketplace plugin activation and refresh of configured disabled plugins. That separation supports a shared home cache with product-selected skills; preserving activation through recovery and excluding product overrides during refresh remain obligations of the marketplace installer.

Agent definitions are placed beside their skills because an agent whose plugin manifest declares only skills has no manifest path to its agents: that agent loads custom subagent definitions from its agent directories alone — the selected agent home and the checkout — so a plugin's agents reach a session only once something writes them into one of those. An agent definition is a pointer into its plugin's skill content, so the two are one versioned unit: the placement scope follows the skills, and every marketplace-shipped operation that refreshes the skills refreshes the agents in the same pass. Installation installs skills into the selected agent home, so home placement is what installation performs; a committed checkout copy is coherent only where the checkout also carries the skill content it invokes. The split placement is the failure the co-location rule exists to prevent — a checkout definition shadows the home copy while the home skills underneath it move with every refresh, and committing one machine's plugin state into repositories that do not own it multiplies that drift — so placement detects the split and stops with a report instead of writing around it. Conversion belongs to the build because it is a pure function of the agent source: running it once emits each agent's native artifact, so every consumer receives byte-identical definitions rather than whatever each machine's converter produced, and the placement a consumer performs stays a file copy rather than a second implementation of the mapping. Shipping those artifacts inside the plugin's own declared skill surface makes delivery contractual — a declared component the installer is obliged to carry — rather than depending on an undeclared directory surviving the copy. The rejected alternative defers conversion to each consumer, which multiplies a mapping implementation across machines and leaves the agent surface reachable only where that conversion runs.

## Invariants

- Every installation plan is bounded and ordered by the corresponding committed marketplace catalog.
- A persistent plan refreshes only the agent's pre-run selected catalog plugins, except that empty state selects only `spec-tree` and carries a warning.
- A nonempty persistent selection contains `spec-tree` or the run stops before its first state-changing command.
- Every entry a run reports names what its plan carries, never the observation that proposed it: the empty-selection supply, its warning, and the installed set the report names are raised from the plan, so an agent whose bootstrap the run withholds announces no first install and is named as installing nothing.
- Persistent Claude Code installation resolves only at project and local scope.
- Persistent Claude Code refresh reaches every project- and local-scope install record the agent reports on the machine for a cataloged plugin: the invocation checkout's records through the native plugin update, every other such record through a rewrite of its install-record entry to the target; a record whose plugin the catalog does not carry or whose scope is neither project nor local is reported and left unchanged; no agent command runs with another checkout as working directory.
- A Claude Code refresh run plans from one listing read at its start, brings every planned record to the head of the registered source's default branch, reads the listing again after execution, and exits nonzero when any project- or local-scope record of a cataloged plugin is off that target; it takes no lock and no second pass.
- Persistent Codex installation resolves only inside the selected `CODEX_HOME`.
- Codex home selection includes configured disabled plugins and survives missing installation caches; trusted product activation cannot widen or narrow that selection.
- Bootstrap defaults to disabled without changing an existing activation declaration; refresh preserves every pre-run activation entry.
- The registered marketplace entry carrying the catalog's name is the source the run refreshes from and reports; the run compares it against no constant, and a settings document is read only to supply a bootstrap registration, so no declaration at any scope displaces a present entry.
- A run that registers the marketplace itself has no target: it reports every other checkout's record as unrefreshed and exits nonzero, and the next run brings them to the target.
- The target's head is read from the location the registry records, so it resolves only where that location is a git working tree; a registration that is not one, and any other failed head read, leaves the run with no target rather than stopping it, and every project- or local-scope record of a cataloged plugin the run carries is reported against no target with a blocking warning that makes the exit nonzero.
- Isolated verification resolves installation and session state beneath caller-selected disposable homes. Subscription discovery alone may read and natively refresh the selected saved-login file, as governed by `spx/32-distribution.enabler/21-installation.enabler/21-repository-installation.enabler/21-installation-architecture.adr.md`.
- Successful persistent installation leaves pre-run plugin selection and activation unchanged, apart from the declared empty-selection bootstrap.
- Persistent installation reports established absence from the registered source as pending publication and continues with the remaining selected plugins until completion or the first other failure; isolated verification treats that absence as terminal.
- A plugin's agent definitions live in the same scope as the skill content they invoke, and every marketplace-shipped operation that delivers or refreshes either carries both in the same run; installation-delivered skills in the selected agent home carry their agent definitions into that home's agent directory.
- Placement never writes around a scope split: agent definitions found in a scope whose skill content lives elsewhere are reported as a fault and left for directed repair, never silently refreshed, pruned, or duplicated.
- Agent-home cleanup beyond one plugin's namespace is a marketplace-scope reconciliation, a distinct operation from any plugin's namespace-bounded placement; it prunes or overwrites only definitions under the marketplace's recorded ownership, and a colliding file outside that ownership is reported and left untouched.

## Verification

- ALWAYS: persistent selection uses Claude Code's inventory recorded for the invocation checkout at project or local scope and Codex's selected-home plugin declarations, including disabled entries, bounded and ordered by the corresponding committed catalog.
- ALWAYS: trusted product `.codex/config.toml` may enable chosen skills over disabled home defaults, while persistent Codex inspection and execution remain independent of product overrides.
- ALWAYS: empty persistent selection supplies only `spec-tree` with a warning, disabled where no activation is declared; an empty Codex home declares `spec-tree` disabled. An agent whose bootstrap the run withholds supplies nothing, raises no first-install warning, and is reported as installing nothing.
- ALWAYS: refresh uses native operations that preserve the selected set and activation, including disabled plugins, and verifies both after execution for the invocation checkout and the selected home; a mismatch is reported without restoring an older configuration snapshot. A recorded checkout elsewhere receives the install-record rewrite alone, which touches no settings document, so it carries no activation postcondition.
- NEVER: refresh resets an existing explicitly enabled home entry to the disabled default.
- ALWAYS: the run refreshes from the marketplace source the agent's registry carries under the catalog's name and names that source in its report.
- ALWAYS: recovery of a missing registration, snapshot, or selected plugin cache preserves the declared selection and activation, including a retry after interrupted installation.
- ALWAYS: Codex subagent definitions for home-selected plugins remain in the global selected-home registry independently of trusted-product skill activation; plugin lifecycle placement retains its namespace and digest-bound ownership checks.
- NEVER: product skill activation generates a checkout subagent registry or filters the home registry.

- ALWAYS: agent-home cleanup beyond one plugin's namespace runs as the marketplace-scope reconciliation, distinct from any plugin's namespace-bounded placement, and establishes marketplace-scoped ownership — an ownership record or content marker, never a filename prefix alone — before any prune or overwrite in the shared agent home, reporting a colliding foreign file and leaving it untouched ([compliance])

- ALWAYS: persistent installation reports established absence from the registered source as pending publication and continues with the remaining selected plugins until completion or the first other failure, while isolated verification treats the same absence as terminal at that plugin's operation ([compliance])

- ALWAYS: the registered marketplace entry carrying the catalog's name maps to the source the run refreshes from and names in its report; an absent entry maps to the bootstrap registration from the invocation checkout's own declaration ([mapping])
