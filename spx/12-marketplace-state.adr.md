# Marketplace State Ownership

The marketplace installation toolchain operates only on the repository checkout and caller-selected agent homes: it derives each agent's marketplace membership from the checkout's committed catalog — Codex in `.agents/plugins/marketplace.json` and Claude Code in `.claude-plugin/marketplace.json` — and never mutates a developer's ambient marketplace registrations, plugin caches, or agent directories. Claude Code's project-scope `.claude/settings.json` selects plugins for repository sessions, while Codex installation and enablement belong to the selected `CODEX_HOME`; repository `.codex/config.toml` is not Codex plugin-installation or enablement authority. For an agent whose plugin manifest cannot declare agents, the agent definitions a plugin provides are committed repository content under the checkout's agent directory, materialized there by that plugin's lifecycle skill: the build emits each plugin's agent definitions in that agent's native format inside the plugin's own declared skill surface, plugin installation carries them to the consumer, and the lifecycle skill places and prunes the checkout's agent directory within the namespace its plugin owns. A manifest that cannot declare agents leaves the runtime loading them only from an agent directory, so materializing them into the checkout is the sole path by which a plugin's agents reach a session. The guarantee that every catalog plugin installs and enables for every agent is established by an isolated installation harness that provisions each agent in a disposable home, not by mutating a maintainer's live installation.

## Rationale

A developer's user-scope marketplace and plugin state belongs to that developer; a repository-scoped tool that reaches into it strands running agent sessions, couples the tool to one machine's ambient configuration, and makes install verification depend on whatever that machine already holds. Bounding synchronization to the invocation checkout and establishing the every-plugin-installs guarantee in a disposable installation harness makes the tool safe to run from any worktree and the guarantee reproducible anywhere. The rejected alternative maintains the maintainer's user-scope caches and registrations in place, which entangles repository tooling with per-machine global state and forces cache-preservation machinery to protect the agent sessions that entanglement puts at risk. What the invariant forbids is the implicit reach: an install the developer names, targeting the home they name, carries none of that ambient coupling, so it stays available as an explicit operation while no automatic path resolves there.

Agent definitions are materialized into the checkout because an agent whose plugin manifest declares only skills has no manifest path to its agents: that runtime loads custom agents from an agent directory alone, so a plugin's agents reach a session only once something writes them there. Committing the result serves the environments where nobody runs that step. Conversion belongs to the build because it is a pure function of the agent source: running it once emits each agent's native artifact, so every consumer receives byte-identical definitions rather than whatever each machine's converter produced, and the placement a consumer performs stays a file copy rather than a second implementation of the mapping. Shipping those artifacts inside the plugin's own declared skill surface makes delivery contractual — a declared component the installer is obliged to carry — rather than depending on an undeclared directory surviving the copy. The rejected alternative defers conversion to each consumer, which multiplies a mapping implementation across machines and leaves the agent surface reachable only where that conversion runs.

## Invariants

- Repository installation derives each agent's complete plugin set from that agent's committed marketplace catalog.
- Codex installation and enablement resolve only inside the caller-selected `CODEX_HOME`.

## Verification

### Testing

- ALWAYS: for an agent whose plugin manifest cannot declare agents, that plugin's agent definitions ship inside the plugin's own declared skill surface and are materialized into the checkout's agent directory by the plugin's lifecycle skill — no manifest path delivers them ([compliance])
- ALWAYS: a plugin's lifecycle skill places and prunes only within the namespace its own plugin owns, leaving agent definitions authored by the developer or provided by another plugin untouched ([compliance])
- NEVER: a plugin's agent definitions ship through a directory the plugin manifest does not declare — an undeclared surface reaching the consumer is incidental, not contractual ([compliance])

- NEVER: repository installation mutates a path outside the invocation checkout and caller-selected disposable agent homes — a developer's ambient marketplace registrations, plugin caches, and agent directories are unchanged after every run ([compliance])
- ALWAYS: repository installation derives marketplace membership from committed per-agent catalogs — Codex in `.agents/plugins/marketplace.json` and Claude Code in `.claude-plugin/marketplace.json` ([conformance])
- NEVER: repository installation reads or writes repository `.codex/config.toml` to install or enable Codex plugins — effective Codex plugin state belongs to the caller-selected `CODEX_HOME` ([compliance])
- ALWAYS: for an agent whose plugin manifest cannot declare agents, converted agent definitions are committed repository content under that agent's directory in the checkout ([conformance])
- ALWAYS: marketplace-install diagnosis derives expected plugin state from the checkout's committed per-agent marketplace catalogs rather than from a plugin catalog embedded in shipped diagnostic output ([compliance])
- ALWAYS: install completeness — every catalog plugin installed and enabled for every agent the checkout registers — is verified by an isolated installation harness that provisions each registered agent in a disposable home and mutates no user-scope state ([compliance])
