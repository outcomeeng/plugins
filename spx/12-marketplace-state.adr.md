# Marketplace State Ownership

Marketplace installation has two explicit modes over one catalog-bounded operation model. Persistent installation targets Claude Code's project scope in the invocation checkout and Codex's selected `CODEX_HOME`; isolated verification targets caller-selected disposable agent homes. Before persistent mutation, each agent reports its installed `outcomeeng` plugin inventory. A nonempty inventory is valid only when it includes `spec-tree`, and installation refreshes exactly the installed names that the agent's committed catalog declares. An empty inventory bootstraps only `spec-tree` and reports that the operator probably wants to install more plugins. Isolated verification registers the invocation checkout in disposable homes and proves full-catalog, valid-subset, and invalid-subset behavior without mutating persistent state. Claude Code's persistent marketplace source is the project-scoped GitHub repository `outcomeeng/plugins`; any user-scoped `outcomeeng` marketplace registration is a collision that stops installation before mutation. Codex marketplace registration, installation, and enablement belong to the selected `CODEX_HOME`; repository `.codex/config.toml` has no plugin-installation or enablement semantics. A selected plugin the checkout declares ahead of the canonical marketplace is reported as pending publication and the run continues; because the checkout is isolated verification's marketplace, the same absence is terminal there. Where installation activates a plugin, persistent installation restores the scope's pre-run activation selection after refreshing the selected installed set.

For an agent whose plugin manifest cannot declare agents, the build emits each plugin's agent definitions in that agent's native format inside the plugin's declared skill surface, and plugin installation carries them to the consumer. Every agent definition invokes its plugin's skills, so placement is derived, never chosen: a plugin's agent definitions live in the same scope as the skill content they invoke, and every marketplace-shipped operation that delivers or refreshes either carries both in the same run. Skills installed in the selected agent home place their agents in that home's agent directory; skill content a repository commits carries its agents committed beside it in that checkout. Placing a plugin's agent definitions into a checkout's agent directory is checkout materialization, and it is valid only where that checkout carries the plugin's invoked skill content. A split — agent definitions in one scope while the skills they invoke live in another — is a detected fault: placement reports the mismatched definitions and stops rather than refreshing around them, because a checkout definition shadows the home copy while the home skills underneath it move with every refresh. No installation run or generated instruction surface requires committing agent definitions into a consumer repository, and a checkout's agent directory changes only within the namespace the owning plugin controls.

## Rationale

An installation refresh is maintenance of selected software, so it preserves the operator's installed set instead of widening it to the marketplace catalog. `spec-tree` is the marketplace's governing methodology and therefore the minimum coherent selection: an existing selection without it is rejected, while an empty state receives that minimum and an explicit prompt to choose additional plugins. Agent inventories remain separate because Claude Code project scope and the selected Codex home are separate ownership boundaries. Catalog order makes plans deterministic, while catalog membership bounds which installed names this marketplace refreshes. Restoring Claude Code's pre-run activation selection prevents install commands from activating plugins the project left disabled.

A persistent run installs from the canonical marketplace while bounding the installed inventory with the checkout catalog, so the two disagree precisely when a selected name exists in the checkout ahead of its published source — the state a changeset that adds a selected plugin occupies until it merges. Reporting that plugin as pending publication keeps the refresh accurate about what it installed while leaving the rest of the selected set installable, and it keeps the release action reachable from the changeset that introduces a plugin rather than requiring the plugin to be published before it can be merged. The distinction is the marketplace source, not the plugin: an isolated run registers the checkout itself, so the same absence there means the committed catalog and the built tree disagree, which is a defect and stays terminal.

A persistent install is an explicit request to refresh the selected project and agent home. Claude Code project scope makes the repository's plugin selection reproducible while preserving the developer's user scope as a separate ownership boundary. Refusing a same-name user registration prevents Claude's flattened marketplace resolution from silently selecting the wrong source. Codex has no repository plugin-installation scope, so the active `CODEX_HOME` is the persistent boundary and repository `.codex/config.toml` remains unrelated configuration. The isolated mode keeps release verification reproducible before merge and protects selected persistent homes from test execution.

Agent definitions are placed beside their skills because an agent whose plugin manifest declares only skills has no manifest path to its agents: that runtime loads custom agents from its agent directories alone — the selected agent home and the checkout — so a plugin's agents reach a session only once something writes them into one of those. An agent definition is a pointer into its plugin's skill content, so the two are one versioned unit: the placement scope follows the skills, and every marketplace-shipped operation that refreshes the skills refreshes the agents in the same pass. Installation installs skills into the selected agent home, so home placement is what installation performs; a committed checkout copy is coherent only where the checkout also carries the skill content it invokes. The split placement is the failure the co-location rule exists to prevent — a checkout definition shadows the home copy while the home skills underneath it move with every refresh, and committing one machine's plugin state into repositories that do not own it multiplies that drift — so placement detects the split and stops with a report instead of writing around it. Conversion belongs to the build because it is a pure function of the agent source: running it once emits each agent's native artifact, so every consumer receives byte-identical definitions rather than whatever each machine's converter produced, and the placement a consumer performs stays a file copy rather than a second implementation of the mapping. Shipping those artifacts inside the plugin's own declared skill surface makes delivery contractual — a declared component the installer is obliged to carry — rather than depending on an undeclared directory surviving the copy. The rejected alternative defers conversion to each consumer, which multiplies a mapping implementation across machines and leaves the agent surface reachable only where that conversion runs.

## Invariants

- Every installation plan is bounded and ordered by the corresponding committed marketplace catalog.
- A persistent plan refreshes only that agent's pre-run installed catalog plugins, except that empty state selects only `spec-tree` and carries a warning.
- A nonempty persistent selection contains `spec-tree` or the run stops before its first state-changing command.
- Persistent Claude Code installation resolves only at project scope after proving no user-scope `outcomeeng` registration exists.
- Persistent Codex installation resolves only inside the selected `CODEX_HOME`.
- Isolated verification resolves every agent state path beneath caller-selected disposable homes.
- Persistent installation leaves the checkout's committed plugin selection unchanged.
- Persistent installation reports a selected plugin the canonical marketplace has not published as pending publication and installs every other selected plugin; isolated verification treats that same absence as terminal.
- A plugin's agent definitions live in the same scope as the skill content they invoke, and every marketplace-shipped operation that delivers or refreshes either carries both in the same run; installation-delivered skills in the selected agent home carry their agent definitions into that home's agent directory.
- Placement never writes around a scope split: agent definitions found in a scope whose skill content lives elsewhere are reported as a fault and left for directed repair, never silently refreshed, pruned, or duplicated.
- Agent-home cleanup beyond one plugin's namespace is a marketplace-scope reconciliation, a distinct operation from any plugin's namespace-bounded placement; it prunes or overwrites only definitions under the marketplace's recorded ownership, and a colliding file outside that ownership is reported and left untouched.

## Verification

### Testing

- ALWAYS: for an agent whose plugin manifest cannot declare agents, that plugin's agent definitions ship inside the plugin's own declared skill surface and persistent installation places them in the selected agent home's agent directory — no manifest path delivers them ([compliance])
- ALWAYS: a plugin's lifecycle skill places and prunes only within the namespace its own plugin owns, leaving agent definitions authored by the developer or provided by another plugin untouched ([compliance])
- ALWAYS: agent-home cleanup beyond one plugin's namespace runs as the marketplace-scope reconciliation, distinct from any plugin's namespace-bounded placement, and establishes marketplace-scoped ownership — an ownership record or content marker, never a filename prefix alone — before any prune or overwrite in the shared agent home, reporting a colliding foreign file and leaving it untouched ([compliance])
- ALWAYS: placement derives each plugin's destination scope from where that plugin's skill content lives, and a scope split — agent definitions present in a scope whose invoked skill content lives elsewhere — is reported as a fault with no refresh, prune, or duplicate written across it ([compliance])
- NEVER: a plugin's agent definitions ship through a directory the plugin manifest does not declare — an undeclared surface reaching the consumer is incidental, not contractual ([compliance])

- ALWAYS: persistent installation inspects each selected agent state before mutation, orders the installed `outcomeeng` plugins by that agent's committed catalog, and installs only those names ([compliance])
- ALWAYS: empty persistent agent state selects only `spec-tree` and reports that the operator probably wants additional plugins ([compliance])
- NEVER: a nonempty persistent agent selection omitting `spec-tree` reaches a state-changing command ([compliance])
- ALWAYS: persistent installation reports a selected plugin the canonical marketplace has not published as pending publication and installs every other selected plugin, while isolated verification treats the same absence as terminal at that plugin's operation ([compliance])
- ALWAYS: persistent installation restores the checkout's committed plugin activation selection once installing completes, so refreshing an installed disabled plugin leaves that selection intact ([compliance])
- NEVER: a persistent installation run leaves the checkout's committed plugin selection changed ([compliance])
- NEVER: persistent installation mutates Claude Code user scope; a user-scoped `outcomeeng` marketplace registration stops the run before its first state-changing command ([compliance])
- ALWAYS: isolated verification confines `HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, and `CODEX_SQLITE_HOME` beneath caller-selected disposable state and leaves persistent homes unchanged ([compliance])
- ALWAYS: installation derives marketplace membership from committed per-agent catalogs — Codex in `.agents/plugins/marketplace.json` and Claude Code in `.claude-plugin/marketplace.json` ([conformance])
- NEVER: installation reads or writes repository `.codex/config.toml` to install or enable Codex plugins — effective Codex plugin state belongs to the selected `CODEX_HOME` ([compliance])
- ALWAYS: marketplace-install diagnosis derives expected plugin state from the checkout's committed per-agent marketplace catalogs rather than from a plugin catalog embedded in shipped diagnostic output ([compliance])
- ALWAYS: isolated installation verifies every catalog plugin, a generated valid subset containing `spec-tree`, and a generated invalid subset omitting `spec-tree` in disposable homes without mutating persistent state ([compliance])

### Audit

- ALWAYS: a checkout's agent directory receives a plugin's agent definitions only where that checkout also carries the skill content those definitions invoke — never as a required step of installation or of any generated instruction surface ([audit])
- NEVER: a generated instruction surface directs an agent session to commit agent definitions into a checkout — a missing agent role is repaired by refreshing the selected agent home and then reloading the harness plugin index or starting a new session, because a running session retains already-loaded plugin content ([audit])
