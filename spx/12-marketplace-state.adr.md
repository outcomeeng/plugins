# Marketplace State Ownership

Marketplace installation has two explicit modes over one catalog-derived operation model. Persistent installation targets Claude Code's project scope in the invocation checkout and Codex's selected `CODEX_HOME`; isolated verification targets caller-selected disposable agent homes. Both modes derive each agent's complete plugin set from the checkout's committed catalog — Codex in `.agents/plugins/marketplace.json` and Claude Code in `.claude-plugin/marketplace.json`. Claude Code's persistent marketplace source is the project-scoped GitHub repository `outcomeeng/plugins`; any user-scoped `outcomeeng` marketplace registration is a collision that stops installation before mutation. Codex marketplace registration, installation, and enablement belong to the selected `CODEX_HOME`; repository `.codex/config.toml` has no plugin-installation or enablement semantics. Persistent installation reconciles the selected Claude project and Codex home to the canonical GitHub source, refreshes it, and installs every catalog plugin. Where an agent activates a plugin by installing it into a scope, installation carries enablement with it, so persistent installation restores the scope's committed plugin selection once installing completes: every catalog plugin ends installed and available, and the selection the checkout declares is the selection that stays active. Isolated verification registers the invocation checkout in disposable homes and proves the same catalog and lifecycle contracts without mutating persistent state.

For an agent whose plugin manifest cannot declare agents, the build emits each plugin's agent definitions in that agent's native format inside the plugin's declared skill surface, and plugin installation carries them to the consumer. Persistent installation places those definitions in the selected agent home's agent directory beside the plugin content it installs, so a plugin's agents and the skills they invoke refresh in one operation. Materializing agent definitions into a checkout's agent directory is that plugin's lifecycle skill's explicit opt-in for a repository that chooses committed delivery; the lifecycle skill places and prunes within the namespace its plugin owns, and no installation run or generated instruction surface requires committing agent definitions into a consumer repository.

## Rationale

A checkout's plugin selection is committed, reviewed content that governs how every collaborator's agent behaves in that repository, so a refresh that silently widened it would change reviewed behavior without review. Installing every catalog plugin is still what a refresh is for: it makes the whole marketplace available locally, and availability costs a consumer nothing. Because installing into the scope also activates, the selection is restored from the committed declaration after installing rather than defended by installing less — the checkout owns that file, so the refresh ends with every plugin present and the file exactly as committed.

A persistent install is an explicit request to refresh the selected project and agent home. Claude Code project scope makes the repository's plugin selection reproducible while preserving the developer's user scope as a separate ownership boundary. Refusing a same-name user registration prevents Claude's flattened marketplace resolution from silently selecting the wrong source. Codex has no repository plugin-installation scope, so the active `CODEX_HOME` is the persistent boundary and repository `.codex/config.toml` remains unrelated configuration. The isolated mode keeps release verification reproducible before merge and protects selected persistent homes from test execution.

Agent definitions are placed in the agent home because an agent whose plugin manifest declares only skills has no manifest path to its agents: that runtime loads custom agents from its agent directories alone — the selected agent home and the checkout — so a plugin's agents reach a session only once something writes them into one of those. The home is the right default because it is the boundary installation already refreshes for skills: one operation keeps a plugin's agents and the skills they invoke at the same version, while a committed checkout copy freezes at placement time and drifts as installation refreshes the skills beside it. Committing agent configuration into every consumer repository also multiplies one machine's plugin state across repositories that do not own it; a repository that wants reviewed, committed agent definitions opts in through the lifecycle skill, and that opt-in is the only path by which installation-delivered content changes a checkout. Conversion belongs to the build because it is a pure function of the agent source: running it once emits each agent's native artifact, so every consumer receives byte-identical definitions rather than whatever each machine's converter produced, and the placement a consumer performs stays a file copy rather than a second implementation of the mapping. Shipping those artifacts inside the plugin's own declared skill surface makes delivery contractual — a declared component the installer is obliged to carry — rather than depending on an undeclared directory surviving the copy. The rejected alternative defers conversion to each consumer, which multiplies a mapping implementation across machines and leaves the agent surface reachable only where that conversion runs.

## Invariants

- Every installation mode derives each agent's complete plugin set from that agent's committed marketplace catalog.
- Persistent Claude Code installation resolves only at project scope after proving no user-scope `outcomeeng` registration exists.
- Persistent Codex installation resolves only inside the selected `CODEX_HOME`.
- Isolated verification resolves every agent state path beneath caller-selected disposable homes.
- Persistent installation leaves the checkout's committed plugin selection unchanged.
- Agent definitions installation delivers land in the selected agent home's agent directory; a checkout's agent directory changes only through the owning plugin lifecycle skill's explicit opt-in.

## Verification

### Testing

- ALWAYS: for an agent whose plugin manifest cannot declare agents, that plugin's agent definitions ship inside the plugin's own declared skill surface and persistent installation places them in the selected agent home's agent directory — no manifest path delivers them ([compliance])
- ALWAYS: a plugin's lifecycle skill places and prunes only within the namespace its own plugin owns, leaving agent definitions authored by the developer or provided by another plugin untouched ([compliance])
- NEVER: a plugin's agent definitions ship through a directory the plugin manifest does not declare — an undeclared surface reaching the consumer is incidental, not contractual ([compliance])

- ALWAYS: persistent installation reconciles Claude Code's project scope and the selected `CODEX_HOME` to the canonical GitHub marketplace `outcomeeng/plugins`, then installs every plugin declared by each agent's committed catalog ([compliance])
- ALWAYS: persistent installation restores the checkout's committed plugin selection once installing completes, so installing a plugin the selection omits leaves that selection intact ([compliance])
- NEVER: a persistent installation run leaves the checkout's committed plugin selection changed ([compliance])
- NEVER: persistent installation mutates Claude Code user scope; a user-scoped `outcomeeng` marketplace registration stops the run before its first state-changing command ([compliance])
- ALWAYS: isolated verification confines `HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, and `CODEX_SQLITE_HOME` beneath caller-selected disposable state and leaves persistent homes unchanged ([compliance])
- ALWAYS: installation derives marketplace membership from committed per-agent catalogs — Codex in `.agents/plugins/marketplace.json` and Claude Code in `.claude-plugin/marketplace.json` ([conformance])
- NEVER: installation reads or writes repository `.codex/config.toml` to install or enable Codex plugins — effective Codex plugin state belongs to the selected `CODEX_HOME` ([compliance])
- ALWAYS: marketplace-install diagnosis derives expected plugin state from the checkout's committed per-agent marketplace catalogs rather than from a plugin catalog embedded in shipped diagnostic output ([compliance])
- ALWAYS: install completeness — every catalog plugin installed and enabled for every agent the checkout registers — is verified by an isolated installation harness that provisions each registered agent in disposable homes and mutates no persistent state ([compliance])

### Audit

- ALWAYS: a checkout's agent directory receives a plugin's agent definitions only through that plugin's lifecycle skill's explicit opt-in — never as a required step of installation or of any generated instruction surface ([audit])
- NEVER: a generated instruction surface directs an agent session to commit agent definitions into a checkout — a missing agent role is repaired by refreshing the selected agent home and then reloading the harness plugin index or starting a new session, because a running session retains already-loaded plugin content ([audit])
