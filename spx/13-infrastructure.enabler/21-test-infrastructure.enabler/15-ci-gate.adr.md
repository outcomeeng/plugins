# CI Enforcement of the Quality Gate

The marketplace runs the full quality gate — the `just check-full` recipe, whose full wrapper runs preflight plus the validation and test primitive recipes — as a GitHub Actions job on `pull_request` and on push to `main`, so every change is gated by deterministic full-gate verification. Wiring that job as a required status check on `main` — so a red gate blocks the merge — is a branch-protection setting applied once the job exists on `main`. The job provisions the gate's full toolchain (just, uv, the Python version `pyproject.toml`'s `requires-python` declares, actionlint and ShellCheck for workflow and shell linting, dprint, git, the Claude Code CLI that the `manifests` step's `claude plugin validate` invocation and repository-installation evidence need, the Codex CLI that repository-installation evidence needs, the `spx` CLI the `markdown` step invokes, built from source as the next paragraphs declare, and an authenticated `gh` — the workflow token with `actions: read` — for the `[test]`-lane `l3` workflow-observability tests) and runs the `just check-full` recipe, never a reimplemented or filtered subset of the full gate recipe beyond the live-discovery selection [`spx/15-validation.enabler/65-gate.enabler/21-selected-gate.enabler/15-live-discovery.pdr.md`](spx/15-validation.enabler/65-gate.enabler/21-selected-gate.enabler/15-live-discovery.pdr.md) declares; every other gate step and test remains selected. The gate `check` job itself runs unconditionally: it is not gated out by a job-level `if:` and not soft-passed by a truthy job-level `continue-on-error`, just as its steps are neither — a condition on the enclosing job would skip the whole gate or let a failed job report success as surely as a soft-passed step.

The workflow pins the Codex CLI to the codex-cli version the maintainers' development host runs; the pin follows that host rather than the package registry, so hosted CI and the host exercise one Codex CLI, and the pin carries no registry-update annotation. The pin equals the host's codex-cli version in every changeset that changes the workflow file; a host update between such changesets leaves the pin unchanged until the next changeset that changes the workflow file, and no merge or schedule alone requires the pin to move.

Every job this repository defines with `runs-on` declares an explicit `timeout-minutes` bound at or below a declared maximum. A job that never terminates never reports a conclusion, so it blocks no merge while holding a hosted runner for the platform default of 360 minutes — the same non-gating end state a job-level `if:` or a truthy `continue-on-error` produces, reached by exhaustion rather than by configuration. A job that calls a reusable workflow through `uses` is outside the rule because the platform rejects `timeout-minutes` on such a job, permitting only `name`, `uses`, `with`, `secrets`, `needs`, `if`, and `permissions`; the gate's own workflow-linting step enforces that exclusion, and the bound for a called workflow's jobs is the calling repository's to pass as an input, not to declare.

The workflow provisions the `spx` CLI by building the `outcomeeng/spx` repository at one pinned commit of its `main` branch, never by installing an `@outcomeeng/spx` release from the npm registry. A changeset that depends on a newer spx capability advances the pin to a commit that contains that capability. The workflow checks out the `outcomeeng/spx` repository at the commit `SPX_COMMIT` pins, installs its dependencies from its lockfile, runs its `build` script, and puts its `bin/spx.js` entry on `PATH` as `spx`. The registry install of `@outcomeeng/spx` and the `SPX_VERSION` variable do not exist. `SPX_COMMIT` is a full 40-character commit SHA of the `outcomeeng/spx` `main` branch whose build reports a version at or above the declared floor, and the pin carries no registry-update annotation, because no registry carries the commit.

The gate also enforces a version floor on the `spx` CLI it runs: the marketplace declares a minimum spx version — the lowest version a build of spx reports whose capabilities the shipped skills and their co-located tests depend on — and a gate step fails when the version the provisioned build reports is below that minimum. The declared floor is the single source of truth that gate step reads, and the step reads the version from the `spx` CLI on the gate's `PATH`, the build the workflow provisions and the gate's other steps run.

No gate step, workflow, or repository rule waits for an `@outcomeeng/spx` release on the npm registry, and the floor names no release channel. A consumer repository meets the floor with any spx build that reports the floor version, from npm or from source, and no shipped skill names an npm release as a precondition.

## Rationale

The completion bound belongs to the same family for the same reason the job-level rules do. A gate earns its authority by reaching a conclusion the merge can read; a job that hangs reports nothing, so the merge sees a check that is forever pending rather than one that failed. Declaring the bound per job rather than trusting the platform default makes the failure loud and quick — a hung job fails the gate within the bound instead of holding a runner for six hours and leaving the pull request unresolvable. Setting one maximum in source, rather than a per-workflow number, keeps the bound reviewable in one place and lets the assertion read it rather than restate it.

CI full-gate parity is the point: any divergence between the CI gate and the full gate leaves open the path where a failing step reaches `main` unseen. Running `just check-full` (equivalently `python3 -m outcomeeng.validation check-full`) rather than enumerating steps in YAML keeps the CI gate in lockstep with the full gate recipe in `outcomeeng/validation/_steps.py`, including its preflight and primitive recipe composition. A subset that drops the workflow and shell linting steps leaves GitHub Actions syntax and embedded shell defects unguarded server-side; a subset that drops the `claude`-dependent `manifests` step leaves plugin-manifest schema and version-parity drift unguarded server-side; and a runner without both agent CLIs cannot execute the real repository-installation evidence. The full gate therefore provisions both agent CLIs and runs their evidence without filtering.

The spx version floor exists because the shipped skills and their tests invoke the `spx` CLI and assume the behavior of a specific version. A skill or test that assumes a capability absent from the build the gate runs ships a runtime contract the consumer's installed CLI cannot honor, and surfaces only as an opaque test failure against that build or as a consumer-side regression. Comparing the declared floor with the version the provisioned build reports, in the same `just check-full` CI runs before merge, makes that dependency explicit and fails fast, naming the gap ("skills require spx >= X, the pinned build reports Y") rather than leaving it to a downstream test assertion. The floor rises only when a skill begins to depend on a newer capability, and the pin advances to a commit that contains it; a floor above what the pinned build reports fails the gate.

Building a pinned commit makes a capability available the moment it reaches `outcomeeng/spx` `main` and the pin advances, so the Plugins product never waits on a registry release. A full-SHA pin keeps the build reproducible where a moving ref would not, and a floor expressed as a version stays checkable against any spx build, since every build reports its version, which keeps consumers free of any release-channel precondition.

### Testing

- ALWAYS: the workflow triggers on `pull_request` and on push to `main` — every path to `main` passes through the gate ([compliance])
- ALWAYS: the workflow runs the gate by invoking the `just check-full` recipe as a job step, never an inlined, re-enumerated, or filtered subset of the step list beyond the live-discovery selection [`spx/15-validation.enabler/65-gate.enabler/21-selected-gate.enabler/15-live-discovery.pdr.md`](spx/15-validation.enabler/65-gate.enabler/21-selected-gate.enabler/15-live-discovery.pdr.md) declares — divergence from the full gate step list reintroduces the unseen-failure gap ([compliance])
- ALWAYS: the workflow provisions Python at the version `pyproject.toml`'s `requires-python` declares — CI uses the project's interpreter contract ([compliance])
- NEVER: a gate step is marked `continue-on-error`, gated out by a step-level `if:`, or soft-passed by its `run:` shell — a non-blocking gate is not a gate ([compliance])
- NEVER: the `check` job is gated out by a job-level `if:` or soft-passed by a truthy job-level `continue-on-error` — a job-level condition could skip the entire gate on `pull_request` or let a failed job report success, defeating the gate as surely as a soft-passed step ([compliance])
- ALWAYS: every job this repository defines with `runs-on` declares an explicit `timeout-minutes` at or below the declared maximum — an unbounded job never reports a conclusion, so it blocks no merge while holding a runner for the platform default ([compliance])
- NEVER: a job that calls a reusable workflow through `uses` declares `timeout-minutes` — the platform rejects the key on such a job, so the bound for a called workflow's jobs is passed as an input rather than declared here ([compliance])
- ALWAYS: a gate step fails when the version the `spx` CLI the gate runs reports is below the declared minimum spx version, so a floor above what the pinned build reports fails the gate rather than shipping ([compliance])
