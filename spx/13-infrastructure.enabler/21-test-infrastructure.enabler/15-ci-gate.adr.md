# CI Enforcement of the Quality Gate

The marketplace runs the full quality gate — `just check`, every step in the `outcomeeng.validation.STEPS` tuple — as a GitHub Actions job on `pull_request` and on push to `main`, so every change is gated by the same deterministic verification a contributor runs locally. Wiring that job as a required status check on `main` — so a red gate blocks the merge — is a branch-protection setting applied once the job exists on `main`. The job provisions the gate's full toolchain (uv, the Python version `pyproject.toml`'s `requires-python` declares, dprint, git, the Claude Code CLI that the `manifests` step's `claude plugin validate` invocation needs, the `@outcomeeng/spx` CLI the `markdown` step invokes, and an authenticated `gh` — the workflow token with `actions: read` — for the `[test]`-lane `l3` workflow-observability tests) and runs the same `just check` recipe contributors run, never a reimplemented or filtered subset of steps. The gate `check` job itself runs unconditionally: it is not gated out by a job-level `if:` and not soft-passed by a truthy job-level `continue-on-error`, just as its steps are neither — a condition on the enclosing job would skip the whole gate or let a failed job report success as surely as a soft-passed step.

The gate also enforces a version floor on the `@outcomeeng/spx` CLI it provisions: the marketplace declares a minimum spx version — the lowest published version whose capabilities the shipped skills and their co-located tests depend on — and a gate step fails when the spx version the CI workflow pins falls below that minimum. The declared floor is the single source of truth a gate step reads; the workflow's pinned version (Renovate-advanced) must stay at or above it.

## Rationale

Parity with the local `REVIEW_READINESS` gate is the point: any divergence between the CI gate and the local gate leaves open the path where a failing step lands on `main` unseen. Running `just check` (equivalently `uv run python -m outcomeeng.validation`) rather than enumerating steps in YAML keeps the CI gate in lockstep with the `STEPS` tuple, which stays the single source of truth in `outcomeeng/validation/_steps.py`. A subset that drops the `claude`-dependent `manifests` step leaves plugin-manifest schema and version-parity drift unguarded server-side — the class of failure the gate exists to stop — so the full gate runs, `claude` CLI cost included.

The spx version floor exists because the shipped skills and their tests invoke the `@outcomeeng/spx` CLI and assume the behavior of a specific version. A skill or test that assumes a capability absent from the pinned spx version ships a runtime contract the consumer's installed CLI cannot honor, and surfaces only as an opaque test failure against the pinned CLI or as a consumer-side regression. Binding a declared floor to the pin and checking it in the gate makes that dependency explicit and fails fast — in the same `just check` a contributor runs before merge — naming the gap ("skills require spx >= X, CI pins Y") rather than leaving it to a downstream test assertion. The floor rises only when a skill begins to depend on a newer capability; because the pin can only reach a version published to the registry, the floor enforces publish-before-depend by construction — a floor set to an unpublished version cannot be matched by any installable pin.

## Verification

### Testing

- ALWAYS: the workflow triggers on `pull_request` and on push to `main` — every path to `main` passes through the gate ([compliance])
- ALWAYS: the workflow runs the gate by invoking the `just check` recipe (or `uv run python -m outcomeeng.validation`) as a job step, never an inlined, re-enumerated, or filtered subset of the step list — divergence from the local step list reintroduces the unseen-failure gap ([compliance])
- ALWAYS: the workflow provisions Python at the version `pyproject.toml`'s `requires-python` declares — CI uses the project's interpreter contract ([compliance])
- NEVER: a gate step is marked `continue-on-error`, gated out by a step-level `if:`, or soft-passed by its `run:` shell — a non-blocking gate is not a gate ([compliance])
- NEVER: the `check` job is gated out by a job-level `if:` or soft-passed by a truthy job-level `continue-on-error` — a job-level condition could skip the entire gate on `pull_request` or let a failed job report success, defeating the gate as surely as a soft-passed step ([compliance])
- ALWAYS: a gate step fails when the `@outcomeeng/spx` version the CI workflow pins is below the declared minimum spx version — the floor below which a shipped skill's assumed CLI capability is unavailable — so a skill or test depending on an unpinned (or unpublished) spx capability fails the gate rather than shipping ([compliance])
