# Prompt Caching

Eval execution amortizes the plugin-and-system prompt prefix by reusing one warm prefix across a run's cases on the subscription `claude --print` path — never by routing to a metered provider API. The prefix is held byte-identical and cache-warm by loading every plugin once into a base session and forking that base per case: the case-specific question is the only content that varies, so each case reads the large shared prefix from the server-side cache and writes only its short suffix, and each case stays independent because it forks the same clean base rather than accumulating prior cases. Each invocation remains one bounded `claude` subprocess (the single-bounded-invocation rule is owned by `spx/13-infrastructure.enabler/25-eval-harness.enabler/eval-harness.md`, per `spx/13-plugin-and-runtime-conventions.adr.md`) — cache warmth comes from the server-side prompt cache, never from a resident process this decision would otherwise tempt the harness to hold open.

## Rationale

The prompt prefix dominates a model invocation's token volume: a large plugin-and-system prefix far outweighs the case-specific suffix and the short structured-verdict output. Prompt caching prices a cold prefix write at several times a warm read of the same prefix, so a run's cost is governed by how many distinct prefixes it writes cold rather than reads warm. A live measurement over the harness's own `claude --print` invocation confirms the payoff of a fixed warm prefix: against a held-constant prefix the first call writes it cold and later calls read it warm at roughly a 5.4× lower per-call cost, projecting a 73–80% reduction across a 10–50-case suite (`prototypes/eval-cache-amortization/FINDINGS.md`).

Capturing that payoff requires the prefix sent for each case to be byte-identical, because the prompt cache matches the longest byte-exact prefix and recomputes everything after the first difference. The invocation shape decides whether the prefix stays identical:

- **Single-turn independent calls** — `claude --print --no-session-persistence`, one fresh conversation per case — do not hold the prefix identical. Claude Code places the cache breakpoint on the last system block (core system plus tool definitions) and injects skill, command, and plugin content after it as conversation messages; with a different question per case, that post-breakpoint plugin content differs every call and cold-writes. Measurement of this shape: a full CI run cold-wrote roughly half its cached-prefix traffic, and a per-case experiment cold-wrote the ~27k-token plugin prefix on every case while only the ~15k-token core system prefix stayed warm — zero plugin-prefix reuse, structural rather than time-to-live-driven. This is the harness's current invocation shape, and it captures no plugin-prefix amortization.
- **A fixed base session, forked per case** holds the prefix identical. Loading every plugin once into a base session places the plugin content in the conversation prefix; forking that base inherits its system prompt, tools, and history exactly, so each fork's first request reads the base's plugin prefix from the cache and the case question appends after it. Per Claude Code's caching model, skill, command, and plugin content a session has loaded is appended after the existing conversation, so the next request still reads everything before it from the cache — exactly the fork-per-case shape. Forking copies the history into a new session and leaves the base unchanged, so cases stay mutually independent.

The fork-per-case design runs entirely on the subscription `claude --print` path and needs no metered key. Routing eval calls to the direct Messages API or the Agent SDK to place an explicit cache breakpoint would convert a notional equivalent cost into a real per-token bill for control the subscription path already affords once invocations share one warm prefix. Subscription capacity and rate limits are opaque to the harness and are not a target it optimizes.

Realizing the lever is gated on an upstream CLI regression. Since v2.1.69, `claude --print --resume`/`--fork-session` fails to reuse the cached conversation history — only the core system prompt caches and all history cold-writes (`anthropics/claude-code#34629`, closed without resolution; the regression persists in current releases). Until that regression is resolved upstream — or worked around by pinning a pre-regression CLI or applying the published community cache fix — a forked case cold-writes the prefix exactly as single-turn mode does, so the harness keeps its current single-turn invocation and the captured saving stays pending the fix. The decision is which invocation shape to pursue, not whether to leave the subscription; the architecture and the substrate already support the lever.

The measurable signal is the per-run equivalent API cost the harness records — `total_cost_usd`, derived from the cache read and creation token aggregates (per `spx/13-infrastructure.enabler/25-eval-harness.enabler/eval-harness.md`); cache creation dominating cache reads across a run marks an un-amortized run, whether from the current single-turn shape, prefix divergence, or time-to-live expiry. Prefix reuse, not per-suite model tiering, is the cost lever: a cheaper model per suite trades verdict quality for a second-order saving while leaving the dominant prefix-write cost untouched.

## Verification

### Audit

- ALWAYS: the eval cost lever is prefix reuse captured on the subscription `claude --print` path via a base session loaded once with every plugin and forked per case — not a metered substrate and not per-suite model tiering; the harness's current single-turn invocation is the expected state while the fork-session cache regression persists (`anthropics/claude-code#34629`, closed without resolution), with the realization re-derivation tracked in `spx/31-outcomeeng.enabler/31-verification.enabler/21-agentic-verification.enabler/PLAN.md` ([audit])
- NEVER: eval calls are routed to a metered provider API — the direct Messages API or the Agent SDK — to place an explicit cache breakpoint; the subscription path captures the saving once invocations share one warm prefix, and metering converts a notional equivalent cost into a real per-token bill ([audit])
- ALWAYS: the per-run cache read and creation token aggregates the harness records — surfaced as `total_cost_usd`, `cost_summary`, and `history.jsonl` per `spx/13-infrastructure.enabler/25-eval-harness.enabler/eval-harness.md` — are the feedback signal for prefix-reuse effectiveness: cache creation dominating cache reads across a run marks an un-amortized run ([audit])
- ALWAYS: the harness accepts its model runner as a dependency-injected parameter implementing the `ModelRunner` Protocol, so a recording implementation substitutes the real `claude` runner and captures a run's invocations and their cache-token aggregates ([audit])
- NEVER: per-suite model-tier selection is the primary eval cost mechanism in place of prefix reuse — the dominant cost is the prefix write, not the base token rate ([audit])
