# Codex Cache Preservation Source

The preservation set is the union of plugin-version pairs that have appeared in `src/plugins/<plugin>/.claude-plugin/plugin.json` on the published branch within the last ten days, derived from `git log` of that manifest. The marketplace recipe `just push-marketplace` invokes the cache-preservation script, which accepts an injected plugin-history source exposing the working-tree plugin set and each plugin's versions published within the window — the default wrapping `git log` against the working tree's manifest — and computes the symlink set from that source's output rather than from a pre-upgrade cache snapshot. The compatibility-symlink target for each installed plugin is the one complete real cache directory whose name equals the version Codex reports as installed for that plugin through `codex plugin list --json --marketplace <marketplace>`; absent a complete real directory of that name after the upgrade, the recipe creates no compatibility symlink for the plugin and removes every non-target real version directory for that plugin.

Cache preservation acts only on plugins Codex considers installed for the marketplace. The installed set and resolved version are read from the Codex CLI itself via `codex plugin list --json --marketplace <marketplace>`, taking the `name` and `version` of each entry in the `installed` array. A plugin's cache directory is preserved only when the plugin is present in both the working tree and the installed set; a cache directory for any other plugin — absent from the working tree, or present in the working tree but absent from the installed set — is pruned in full. The preserved plugin set is therefore the intersection of the working-tree plugin set and the installed set, and the orphan prune that removes a working-tree-absent plugin's cache directory removes a not-installed plugin's cache directory by the same rule. A successful query that reports an empty installed set prunes every cache directory for the marketplace; a query that fails, returns an unrecognized shape, or omits a string installed version aborts the recipe without mutating the cache, so a degraded signal never drives a prune.

## Rationale

Two requirements collide: the preservation set must cover in-flight conversations, and the mechanism must survive a single missed invocation of the recipe. A set computed from the pre-upgrade cache snapshot satisfies the first only when every prior push captured its predecessor; a single push that bypasses the recipe drops the predecessor permanently. A set derived from git history satisfies both — every invocation recomputes from the published commits in the window, cache state is consequential output rather than input, and a bypassed push is repaired by the next invocation. The ten-day window covers a working week plus weekend margin while keeping the symlink set bounded. Pinning Codex resolution to the working tree diverges from the version-pathed lookup contract: a developer can run preservation from an older feature worktree while Codex has already installed a newer marketplace version, and using the worktree manifest as the target prunes or bypasses the compatibility paths active sessions still reference. Reading the installed version from Codex keeps the target aligned with live runtime resolution while git history still defines which older version paths stay available.

Scoping preservation to the installed set resolves the stale-leftover failure mode. `codex plugin marketplace upgrade` refreshes the marketplace clone and re-materializes the per-plugin cache only for plugins Codex tracks as installed, so a plugin installed at an older version and later dropped from the installed set leaves a stale real version directory the upgrade never advances. Validation that the current version is materialized then fails for a plugin Codex is not tracking. Treating "not installed" identically to "absent from the working tree" — pruning the whole cache directory — lets validation pass honestly: a plugin Codex does not install holds no cache presence to validate, and installing it later re-materializes the current version through `codex plugin add`. Reading the installed set and version from the CLI rather than from `~/.codex/config.toml` keeps a single authority for what is installed and which version Codex resolves. The config file's layered global-and-project semantics are Codex's to reconcile; re-deriving them in the recipe would drift the moment the schema changes, and the drift would be silent. A CLI query instead surfaces a changed contract as a parse failure that aborts the recipe, so the failure is detectable rather than a quiet misread that prunes the wrong set.

## Invariants

- For any installed plugin `P` with manifest version `V` published to the marketplace branch within the last ten days, `~/.codex/plugins/cache/<marketplace>/P/V/` resolves to the Codex-reported installed version directory or a direct symlink to it immediately after `just push-marketplace` completes — when the Codex-reported installed version exists as a complete real directory after the upgrade. When the Codex-reported installed version is absent as a complete real directory, no compatibility symlink exists for `P` (the next invariant governs) and `validate_install` reports the gap.
- For any version `V` that is neither the Codex-reported installed version nor present in the last ten days of `P`'s manifest history, `~/.codex/plugins/cache/<marketplace>/P/V/` does not exist after the recipe completes.
- For any installed plugin `P` whose Codex-reported installed version exists as a complete real directory after the upgrade, `~/.codex/plugins/cache/<marketplace>/P/` contains exactly one real version directory after the recipe completes: the Codex-reported installed version. Every other in-window version path is a direct symlink to that directory, and every other real version directory is removed. When that complete target is absent, no non-target real version directory remains.
- The post-recipe cache state is a pure function of the published git history, the working-tree manifests, and the Codex-reported installed versions, independent of the cache state observed before the recipe ran.
- The compatibility-symlink target for plugin `P` is the complete real cache directory named with `P`'s Codex-reported installed version; version identity selects the target, never directory modification time and never the local working-tree manifest. Absent that complete real directory after the upgrade, every compatibility symlink for `P` is removed and none is created, and every non-target real version directory is removed, so no version resolves to non-current content.
- The preserved plugin set is the intersection of the working-tree plugin set and the Codex installed set reported by `codex plugin list --json --marketplace <marketplace>`. For any plugin `P` outside that intersection, `~/.codex/plugins/cache/<marketplace>/P/` does not exist after the recipe completes — a not-installed plugin is pruned in full by the same rule as a working-tree-absent plugin.
- The installed set and installed versions are read from the Codex CLI's structured output. A query that fails or returns a payload without an `installed` array of named entries with string versions aborts the recipe with no cache mutation, so a degraded or changed CLI contract is surfaced rather than allowed to drive a prune against the wrong set or choose the wrong target. The query runs only after a zero-exit upgrade, so an upgrade that itself fails returns before the query is attempted, regardless of the installed provider.

## Verification

### Testing

- ALWAYS: the preservation script derives the preservation set per plugin from a published-versions callable parameterized by a time window — git history is authoritative, snapshot deltas are not ([property])
- ALWAYS: the default published-versions callable invokes `git log` against the working tree's manifest for the configured plugin, limited to a ten-day window ([compliance])
- ALWAYS: compatibility symlinks for plugin versions outside the window are pruned during the same recipe invocation that creates current-window symlinks ([property])
- ALWAYS: plugins absent from the working tree but present in cache have their entire cache directory pruned — orphaned plugins retain no compatibility paths ([property])
- ALWAYS: the compatibility-symlink target is the complete real cache directory whose name equals the plugin's Codex-reported installed version — version identity selects the target, never directory modification time or the local working-tree manifest ([property])
- NEVER: leave or create a compatibility symlink for a plugin whose Codex-reported installed version is absent as a complete real cache directory after the upgrade — every such symlink is removed, since a symlink to a non-current directory resolves a version to stale content ([compliance])
- ALWAYS: each installed plugin cache contains exactly one real version directory after preservation: the Codex-reported installed version; every other in-window version path is a direct symlink to it ([property])
- ALWAYS: incomplete in-window compatibility roots are replaced with direct symlinks to the complete Codex-reported installed version directory; an incomplete cache root cannot block recovery of an active older hook path ([property])
- ALWAYS: non-target real version directories are removed during preservation, so stale worktree versions cannot remain as selectable or partially repairable plugin roots ([property])
- NEVER: compute the preservation set solely from the pre-upgrade snapshot delta — bypass a single recipe invocation and the chain breaks permanently ([property])
- NEVER: skip preservation when the git-history callable returns an empty set for a plugin — the empty set entails the orphan-prune behavior, not a silent skip ([compliance])
- ALWAYS: a plugin present in the cache and the working tree but absent from the injected installed set has its entire cache directory pruned — not-installed is treated identically to working-tree-absent ([property])
- ALWAYS: a plugin present in both the working tree and the installed set is preserved — the preserved set is the intersection, so an installed plugin's cache survives while a not-installed sibling's is pruned in the same run ([property])
- ALWAYS: the installed set is parsed from `codex plugin list --json` output as the `name` and `version` of each entry in the `installed` array, scoped to the queried marketplace; a payload that is not an object, lacks an `installed` array of named entries, or omits a string version raises rather than yielding a silent empty set or stale target ([property])
- NEVER: mutate the cache when the installed-set query fails or returns an unrecognized shape — preservation aborts so a degraded signal cannot drive deletion ([compliance])
- ALWAYS: a dry run reports planned changes without invoking the installed-set query and without mutating the cache — the preview treats every working-tree plugin as wanted and requires no Codex CLI present ([property])
- NEVER: attempt the installed-set query when the upgrade exits non-zero — the upgrade failure short-circuits the recipe before the query is attempted, regardless of the installed provider ([property])

### Audit

- ALWAYS: the published-versions callable is injected as a Protocol parameter — enabling `l1` testing of preservation logic against controlled version sets without invoking real git ([audit])
- ALWAYS: each plugin's current working-tree version remains exposed through the injected plugin-history Protocol for published-window computation, while target selection uses the injected installed-version provider — enabling `l1` testing of both compatibility-set construction and live Codex target selection without invoking real git or the real Codex CLI ([audit])
- NEVER: substitute the published-versions callable in tests with `unittest.mock.patch` or framework mocks — dependency injection is the standard ([audit])
- NEVER: persist preservation state to disk outside the cache directory — git history is the source of truth; a sidecar file introduces drift ([audit])
- ALWAYS: the installed-set provider is injected as a Protocol parameter — enabling `l1` testing of the not-installed prune against controlled installed sets without invoking the real Codex CLI ([audit])
- NEVER: read the installed set by parsing `~/.codex/config.toml` directly — the Codex CLI's `plugin list` output is the single authority, so a config-schema change surfaces as a detectable query failure rather than a silent misread ([audit])
