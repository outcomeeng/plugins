# Installation

PROVIDES local plugin marketplace installation and update support for developer machines
SO THAT Codex and Claude Code users working from this repository
CAN refresh installed plugins without breaking active sessions, local tool state, or sibling agent sessions

## Assertions

### Scenarios

- Given a plugin's manifest has two marketplace-branch versions inside the publication compatibility window and the Codex plugin cache contains one complete real directory for the Codex-reported installed version, when the marketplace cache preservation step executes, then the older published version path resolves to a direct symlink pointing at the Codex-reported installed version directory ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given Codex reports an installed plugin version newer than the working-tree manifest version and the cache contains one complete real directory for that Codex-reported version, when the marketplace cache preservation step executes, then in-window compatibility paths from the working-tree history resolve to direct symlinks pointing at the Codex-reported installed version directory rather than to the stale working-tree version ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given an in-window compatibility path exists as an incomplete real plugin root and the cache contains one complete real directory for the Codex-reported installed version, when the marketplace cache preservation step executes, then the incomplete compatibility root is replaced by a direct symlink to the complete Codex-reported installed version directory ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given the Codex plugin cache contains more than one real version directory for an installed plugin, when the marketplace cache preservation step executes, then every non-Codex-reported real version directory is replaced by a direct symlink to the Codex-reported installed version directory, and the plugin cache retains exactly one real directory: the Codex-reported installed version ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a version path is present in the Codex plugin cache as a symlink while that version is outside the publication compatibility window and the cache contains one complete real directory for the Codex-reported installed version, when the marketplace cache preservation step executes, then the out-of-window symlink is retargeted to point directly at the Codex-reported installed version directory rather than removed — a version a live session advertises is never stranded by age ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a version path is present in the Codex plugin cache as a complete real directory while that version is outside the publication compatibility window and a newer version is the Codex-reported installed version with its own complete real directory, when the marketplace cache preservation step executes, then the out-of-window real directory is replaced by a direct symlink to the installed version directory rather than removed, so a session started on the older version keeps resolving its advertised skill cache path ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a preserved compatibility symlink whose modification time differs from the reconciliation timestamp, when the marketplace cache preservation step executes, then that symlink's modification time is updated to the reconciliation timestamp so a stale-symlink check measures reconciliation freshness rather than publication age ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a plugin cache directory contains a regular file (such as an OS metadata file) alongside its version entries, when the marketplace cache preservation step executes, then the regular file is left untouched and reconciliation completes — only versioned directories and symlinks are treated as cache entries ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a plugin directory exists in the Codex plugin cache and no corresponding manifest exists in the working tree, when the marketplace cache preservation step executes, then the entire cache directory for that orphaned plugin is removed ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given the Codex installed-set query fails or returns a payload without an `installed` array of named entries, when the marketplace cache preservation step executes, then no cache directory is pruned and the step surfaces the failure rather than pruning against a degraded signal ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a dry run and a plugin present in the working tree but absent from the Codex installed set with a stale cache directory, when the marketplace cache preservation step executes, then the installed-set query is not invoked and the plugin's cache directory is retained — the preview reports planned changes without requiring the Codex CLI present and mutates nothing ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a Codex plugin add exits non-zero during local refresh, when the marketplace cache preservation step executes, then the refresh return code is surfaced and no cache directory is pruned ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a plugin directory holding a stale real version directory exists in the Codex plugin cache and no corresponding generated Codex manifest exists under `dist/codex`, when the marketplace cache preservation step executes, then the entire cache directory for that unmanaged plugin is removed — the same prune as a working-tree-absent orphan ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a successful query reporting an empty Codex installed set and two working-tree plugins with generated Codex manifests, when the marketplace cache preservation step executes, then both generated plugins are refreshed with `codex plugin add <plugin>@outcomeeng` rather than pruning every cache directory ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a plugin manifest exists in the working tree and no directory exists for that plugin in the local Codex plugin cache, when the marketplace cache preservation step executes, then no warning is emitted and the script exits zero ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a local Codex refresh leaves only an older version as a real directory in a plugin's cache while the Codex-reported installed version is in the published window but absent as a real directory, when the marketplace cache preservation step executes, then every compatibility symlink for the plugin is removed and the older real directory is removed because it is not the Codex-reported installed version ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a local Codex refresh leaves the Codex-reported installed version absent as a complete real directory and strict current-cache mode is enabled, when the marketplace cache preservation step completes reconciliation, then the result reports a current-cache topology error so a caller with no later install validator can fail the run ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a plugin's Codex-reported installed version has no complete real directory in the cache while the cache holds compatibility symlinks for the plugin — at the Codex-reported installed version or at an older in-window version — pointing at a non-current real directory, when the marketplace cache preservation step executes, then every compatibility symlink for the plugin is removed so no version resolves to a non-current directory ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a working-tree plugin's current version cannot be determined from its manifest (the manifest is unreadable or declares no version string), when the marketplace cache preservation step executes, then every compatibility symlink for the plugin is removed, no compatibility symlink is created, and the step exits cleanly ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given Claude reports `outcomeeng` as a Directory marketplace source, Codex reports `outcomeeng` as a local marketplace source at the same path, and either runtime includes duplicate lower-priority sources for the same marketplace, when the source preflight executes, then the shared local marketplace root is selected and accepted for the refresh ([test](tests/test_marketplace_sources.conformance.l1.py))
- Given Claude reports `outcomeeng` as a Directory marketplace source and Codex reports `outcomeeng` as a Git-backed marketplace source, when the read-only source validator executes, then it fails loudly before any plugin add or cache prune occurs ([test](tests/test_marketplace_sources.conformance.l1.py))
- Given Claude and Codex report local marketplace sources for `outcomeeng` at different paths, when the read-only source validator executes, then it fails loudly and names both configured paths ([test](tests/test_marketplace_sources.conformance.l1.py))
- Given the Claude Code `outcomeeng` registration is a Directory source at the canonical root reported at user scope or without an explicit scope, when maintainer source reconciliation executes, then no Claude marketplace command is issued — a correct user-scope registration is accepted without repair ([test](tests/test_marketplace_sources.scenario.l1.py))
- Given the Claude Code `outcomeeng` registration is absent, or a user-scope or unscoped Directory source points at a non-canonical path, when maintainer source reconciliation executes, then reconciliation removes any stale user-scope registration and adds the canonical local source, issuing every Claude marketplace command at user scope and never at project or local scope ([test](tests/test_marketplace_sources.scenario.l1.py))
- Given the Claude Code `outcomeeng` registration is a read-only managed Directory source at any path and no user-scope source exists, when maintainer source reconciliation executes, then the managed source is left untouched and a user-scope registration at the canonical root is added ([test](tests/test_marketplace_sources.scenario.l1.py))
- Given the Codex `outcomeeng` registration is absent, Git-backed, scoped outside user registration, or pointed at a non-canonical local path, when maintainer source reconciliation executes, then editable stale registration is removed when needed and the canonical local source is added before refresh ([test](tests/test_marketplace_sources.scenario.l1.py))
- Given Claude Code reports installed `outcomeeng` plugins before maintainer source reconciliation, when a stale user-scope Claude marketplace source is repaired, then user-scope plugin selections are restored with their enabled state, project/local plugin selections are not restored by maintainer sync, idempotent user-scope install or state responses are accepted, and non-idempotent restore failures still surface as errors ([test](tests/test_marketplace_sources.scenario.l1.py))
- Given Codex reports installed plugins and the local marketplace root contains plugin manifests under `dist/codex`, when the Codex local refresh step executes, then the installed plugins discovered from `dist/codex` are reinstalled in deterministic manifest order via `codex plugin add <plugin>@outcomeeng` before cache reconciliation, and `codex plugin marketplace upgrade outcomeeng` is never invoked ([test](tests/test_codex_plugin_cache.scenario.l1.py))
- Given a working-tree plugin manifest matches the Codex-reported installed version for the same plugin and the local Codex marketplace cache directory is absent, when validate_install runs, then the missing Codex cache is reported as an error that names the missing installed version rather than passing with an empty Codex install section ([test](tests/test_validate_install.scenario.l1.py))
- Given a configured local Codex marketplace root and a stale Git marketplace clone under the Codex home directory, when validate_install reads the Codex marketplace version for a plugin, then it reads the configured local root's `dist/codex` manifest rather than the stale Git clone ([test](tests/test_validate_install.scenario.l1.py))
- Given a working-tree plugin is absent from the Codex installed set and no local Codex cache directory exists for it, when validate_install runs with the live installed-set signal, then the absent cache reports no error because Codex does not install that plugin ([test](tests/test_validate_install.scenario.l1.py))
- Given no live Codex installed-set signal is supplied and no local Codex cache directory exists for a working-tree plugin, when validate_install runs, then no Codex cache error or warning is reported because the validator has no installed Codex target to verify ([test](tests/test_validate_install.scenario.l1.py))
- Given a working-tree plugin manifest declares a newer version than the Codex marketplace clone's published manifest for the same plugin, when validate_install runs, then the absence of the newer version in the Codex cache is reported as a warning that names the plugin and both versions, and the script exits zero ([test](tests/test_validate_install.scenario.l1.py))
- Given a plugin directory exists in either the Claude Code or Codex plugin cache and no manifest exists for that plugin in the working tree, when validate_install runs, then the orphan is reported as a warning that names the plugin, and the script exits zero ([test](tests/test_validate_install.scenario.l1.py))
- Given a plugin's cache holds the version directories `0.9.0`, `0.10.0`, `0.17.6`, `0.17.10`, and `0.17.12`, when the cache listing is assembled, then the entries appear in numeric order — `0.9.0`, `0.10.0`, `0.17.6`, `0.17.10`, `0.17.12` — rather than the lexicographic order that would place `0.10.0` first and `0.9.0` last ([test](tests/test_validate_install.scenario.l1.py))
- Given a plugin's cache holds the numeric version directories `0.9.0` and `0.10.0` alongside an entry whose name is not a dotted-integer version (for example a stray directory named `snapshot`), when the cache listing is assembled, then the numeric versions sort first in numeric order and the non-numeric entry sorts last — the listing tolerates an unparseable entry rather than failing ([test](tests/test_validate_install.scenario.l1.py))
- Given the Claude Code cache, whose resolution is working-tree-pinned, and a plugin whose working-tree version is higher than every cached version directory, when the cache listing is rendered, then a synthesized row for the working-tree version is shown marked `← current` and annotated as resolving from the working tree, sorted into numeric position — a correctly-resolving install whose cache lags is not rendered as stale ([test](tests/test_validate_install.scenario.l1.py))
- Given the Codex cache, whose resolution tracks the marketplace version Codex publishes, when the cache listing is rendered, then the `← current` marker is placed on the version `codex plugin list --json` reports for that plugin — the version Codex actually resolves — rather than the local working-tree manifest version, which does not determine Codex resolution ([test](tests/test_validate_install.scenario.l1.py))
- Given the Codex cache and a plugin whose Codex-reported version has no cache directory, when the cache listing is rendered, then no `← current` marker is shown for that plugin — the Codex listing does not synthesize a row the way the working-tree-pinned Claude listing does, and the absent version is surfaced by validate_install separately ([test](tests/test_validate_install.scenario.l1.py))
- Given the Codex cache contains more than one real version directory for a plugin, when validate_install runs, then the extra real directory is reported as an error that names the plugin path ([test](tests/test_validate_install.scenario.l1.py))
- Given the Codex cache target version directory lacks the runtime manifest for that plugin root, when validate_install runs, then the incomplete target entry is reported as an error that names the plugin path ([test](tests/test_validate_install.scenario.l1.py))
- Given the Codex cache contains only a newer non-target real directory while the Codex-resolved target version is absent, when validate_install runs, then the cache topology error names the missing target path and the non-target real directory ([test](tests/test_validate_install.scenario.l1.py))
- Given the Codex cache contains a complete real target directory while a compatibility symlink points at an older real directory, when validate_install runs, then the cache topology error names the symlink path, its actual target, and the expected target directory ([test](tests/test_validate_install.scenario.l1.py))
- Given the Codex cache contains a complete real target directory while a compatibility symlink points at another compatibility symlink instead of directly at the target directory, when validate_install runs, then the cache topology error names the symlink path, its direct target, and the expected target directory ([test](tests/test_validate_install.scenario.l1.py))
- Given the Codex cache target version path is a symlink to an older real directory, when validate_install runs, then the cache topology error names the target path, its actual target, and the requirement for a complete real target directory ([test](tests/test_validate_install.scenario.l1.py))
- Given the working-tree manifest version is strictly ahead of the local Codex marketplace source version and differs from the Codex-resolved version, when validate_install runs, then the Codex cache check verifies the Codex-resolved version and reports the divergence as a warning rather than requiring the working-tree version to be materialized in the Codex cache ([test](tests/test_validate_install.scenario.l1.py))
- Given the local Codex marketplace source has already published the working-tree manifest version but Codex still resolves an older version, when validate_install runs, then the Codex cache check verifies the local marketplace source version, requires the older Codex-resolved version to remain available as a compatibility symlink, and reports the Codex-resolved version as lagging ([test](tests/test_validate_install.scenario.l1.py))

### Properties

- For every generated Codex plugin exposed by the canonical local source, after `codex plugin add <plugin>@outcomeeng` exits zero during local refresh, cache reconciliation targets the version declared by `dist/codex/<plugin>/.codex-plugin/plugin.json`: that version remains the complete real current directory, and any stale post-refresh Codex-reported version is a compatibility symlink to it ([test](tests/test_codex_plugin_cache.property.l1.py))

### Compliance

- ALWAYS: marketplace sync and direct-publish wrappers reconcile Claude Code and Codex `outcomeeng` marketplace registrations before deciding whether plugin distribution files changed ([review])
- ALWAYS: marketplace sync and direct-publish wrappers refresh installed plugins when the published range changes plugin distribution files under `src/`, `dist/`, `.claude-plugin/`, or `.agents/plugins`; spec-only and coordination-note-only commits do not refresh marketplace caches unless source reconciliation repaired runtime configuration in the same invocation ([review])
- ALWAYS: the Codex installed set is read from `codex plugin list --json --marketplace <marketplace>` and parsed as the `name` and `version` of each entry in the `installed` array, scoped to the queried marketplace; a payload that is not an object, lacks an `installed` array of named entries, or omits a string version raises rather than yielding a silent empty set or stale target, so a changed CLI contract is detected instead of misread ([test](tests/test_installed_set.conformance.l1.py))
- ALWAYS: the maintainer refresh reads the addable Codex plugin set from `dist/codex/*/.codex-plugin/plugin.json` rather than from a hardcoded plugin list ([test](tests/test_codex_plugin_cache.compliance.l1.py))
- NEVER: maintainer sync invokes `codex plugin marketplace upgrade outcomeeng`; Codex refresh is per generated Codex plugin through `codex plugin add <plugin>@outcomeeng` against the reconciled local marketplace source ([test](tests/test_codex_plugin_cache.compliance.l1.py))
