# Plugin Packaging and Execution Safety

Every plugin ships dual manifests (`.claude-plugin/plugin.json` and `.codex-plugin/plugin.json`) with version fields in lockstep, every skill conforms to `/skill-standards`, every script the plugin ships — skill helpers and hook contracts — is Python under a `scripts/` directory, every path inside skill content resolves via `${CLAUDE_SKILL_DIR}`, every tool grant a skill declares names only a path inside that skill's own directory — logic two skills share is owned by one provider skill and reached from the consumer's own script by a `__file__`-relative import, never by a grant that walks into the provider's directory — every scratch directory comes from a unique-per-invocation source (`tempfile.mkdtemp`, `mktemp -d`, or a test fixture) with caller-owned cleanup, and no plugin code spawns a long-lived subprocess, daemon, keep-alive, or open-ended watcher. Skills prefer stdin/stdout pipes between scripts over intermediate files when fanout does not demand a directory. The marketplace's sole user-facing invocation artifact is the skill — invocable as `/<skill-name>`, model-invocable, and carrying capabilities a command cannot: progressive disclosure, bundled references and `scripts/`, an `allowed-tools` restriction, and model-invocation control; user-facing functionality is authored as a skill, optionally fronted by a thin agent that holds no logic, declares the output contract it relays, and runs the skill autonomously for background or headless execution.

## Rationale

The dual-manifest lockstep exists because the Codex marketplace cache resolves plugin versions independently of the Claude Code cache, so a single-file version bump causes Codex cache drift; lockstep is the simplest mechanical guarantee. The `/skill-standards` conformance invariant holds because skill activation depends on directive descriptions, frontmatter discipline, and pure-XML structure — one non-conformant skill lowers the activation rate of the whole surface. Helpers are Python because the marketplace manages Python via `uv`, helpers cross the Codex and Claude Code surfaces unchanged, and shell portability consumes more author time than it saves; hook scripts are Python too, because consumers already run Python for every skill, so a Python hook adds no runtime requirement and needs neither a shell nor `jq` — a plugin-root `scripts/` directory holds them, run as `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/<name>.py` from inside the inline guard `spx/15-hook-safety.pdr.md` requires, so `scripts/` means Python across the plugin.

`${CLAUDE_SKILL_DIR}` is the only path expression that resolves to the skill directory when the agent runs a command through the Bash tool — `$0`-derived expressions resolve to the calling shell. The execution-safety invariants exist because the Bash tool does not reliably reap subprocess trees across turns, so streaming watchers, agent-owned polling, and open-ended subprocesses accumulate into host exhaustion. A foreground process the harness reaps when it exits is outside that prohibition and needs no exception; what such a process runs, and how its result is read, belong to the node that owns it. The scratch-storage invariants exist because hardcoded `/tmp/<fixed-name>/` paths collide under concurrent runs and `atexit` cleanup behaves inconsistently across coding agents, so the orchestrator that creates a scratch directory owns its removal. These conventions hold across every plugin, so leaving them implicit in `CLAUDE.md` and `/skill-standards` would force every node spec to restate them to make them testable. Reach is what earns a place here: a convention every plugin obeys belongs in this decision, while one operation's command, flags, and result handling belong to the node that owns it, where they reach only the contexts that load it.

A grant naming a path inside another skill's directory encodes that skill's name and internal layout into a permission string, which no import graph, type checker, or test can follow. Renaming the provider or moving its `scripts/` directory then breaks every such grant silently: the pattern stops matching and the call degrades to a permission prompt rather than failing. Ownership by a provider skill with a `__file__`-relative import from the consumer's own script keeps the coupling inside Python, where a moved module raises at load. It also keeps the grant stable while the shared surface evolves, and it settles the question without depending on whether an invoked skill's grants remain in force while it is active — a property neither agent harness states and both are free to change. The consumer's own script is what the grant names, so a consumer needing nothing but the provider's result still owns an entrypoint; that file is the price of not spelling a sibling's layout in a permission.

The skill subsumes the command: slash invocation, argument passing, and a curated prompt body are a subset of what a skill provides, and the skill adds model-invocability, progressive disclosure, bundled references and `scripts/`, and an `allowed-tools` restriction. Maintaining a command artifact alongside skills doubles the authoring and audit burden for one invocation surface and splits discovery across two catalogs, so the marketplace authors functionality once, as a skill. An agent fronting a skill carries no logic because a thin wrapper keeps a single source of behavior — the shape the verification wrappers already follow — so autonomous or background execution adds an invocation path, not a second implementation.

## Verification

### Testing

- NEVER: a skill's `allowed-tools` names a path inside another skill's directory — a grant that walks out of `${CLAUDE_SKILL_DIR}` encodes a sibling's name and layout where nothing can follow it ([compliance])

### Audit

- ALWAYS: logic two or more skills share is owned by one provider skill, and each consumer reaches it from the consumer's own `scripts/` entrypoint by a `__file__`-relative import ([audit])
- NEVER: a consumer skill re-implements or re-exports a provider skill's shared logic to avoid importing it ([audit])
- ALWAYS: each plugin ships `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json` with `version` fields in lockstep — a single-file bump causes Codex cache drift ([audit])
- ALWAYS: every skill conforms to `/skill-standards` — directive description, lowercase-hyphenated name matching its directory, pure-XML body with `<objective>` and `<success_criteria>`, restricted `allowed-tools` ([audit])
- ALWAYS: helpers under a skill's `scripts/` directory and hook contracts under the plugin-root `scripts/` directory are Python (`python3`, stdlib only); a hook command invokes its Python via `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/<name>.py` inside the inline guard `spx/15-hook-safety.pdr.md` requires, never as a bare unguarded invocation ([audit])
- ALWAYS: paths in skill content resolve via `${CLAUDE_SKILL_DIR}` — `$0`-derived expressions do not resolve to the skill directory under the Bash tool ([audit])
- ALWAYS: scratch directories come from a unique-per-invocation source, and the orchestrator that creates one removes it on every exit path including failure — helper modules register no `atexit` handlers ([audit])
- ALWAYS: skills prefer stdin/stdout pipes between scripts over intermediate files; an intermediate file is valid only when fanout demands a directory ([audit])
- ALWAYS: Python helper logic that invokes an external command or subprocess accepts a source-owned Protocol-typed collaborator; the entrypoint binds the production process adapter at the outer edge ([audit])
- NEVER: framework mocks replace external-command or subprocess collaborators; tests inject explicit collaborators only under a `/test` exception case ([audit])
- NEVER: a helper or skill instruction spawns a daemon, background keep-alive, streaming-log command, open-ended watcher, or agent-owned polling loop — unreaped process trees accumulate until host resources are exhausted ([audit])
- ALWAYS: author user-facing functionality as a skill — the marketplace's single user-facing invocation artifact, invocable as `/<skill-name>` ([audit])
- ALWAYS: an agent that fronts a skill is a thin wrapper holding no logic — its behavior lives entirely in the skill it invokes ([audit])
- ALWAYS: a thin agent fronting a skill declares the output contract it relays, so a caller reads that contract from the agent definition rather than inferring it from the skill or from sibling agents ([audit])
- NEVER: author a command (`commands/*.md`) — the skill is the marketplace's sole user-facing invocation artifact and carries every command capability ([audit])
