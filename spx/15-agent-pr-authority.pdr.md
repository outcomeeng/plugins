# Agent Authority over PR Lifecycle Actions

The PR-management skills declare exactly three gates, evaluated in order; one word — **gate** — names each lifecycle authorization, and every condition a gate reads is a **predicate**, never a gate. `REVIEW_READINESS` authorizes opening the PR; `MERGE_READINESS` together with `PRODUCTION_READINESS` authorizes merging. The agent performs two lifecycle transitions — opening and merging — and the merge carries a production-relevance permission. Every gate is decidable from observable PR state, so an independent reader inspecting the same PR with the same overlay reaches the same verdict.

**`REVIEW_READINESS`** holds when both predicates hold: deterministic verification passes (every validation and testing check the project's full verification command runs reports success) and the local `reviewing-changes` review has converged (iterated to leave no valid finding unaddressed — each applied in-PR or recorded as out-of-PR scope in the owning node's `ISSUES.md`/`PLAN.md`). The moment it holds, the PR opens `ready_for_review`, not draft; draft state is not a gating mechanism. Both predicates hold against the diff every push publishes, opening and follow-up alike, and the local reviewer is invoked at parity with the CI reviewer — the caller passes only the repository/worktree and the diff range, with no interpretive scope, severity pre-filter, or emphasis steering.

**`MERGE_READINESS`** holds when both predicates hold: a clean current-head CI review exists — one matching the reviewing shape, itself complete and valid, reporting no unresolved `BLOCKING` or `DEBT` finding (stated directly, or with every such finding individually assessed and dropped as unbacked; `FOLLOW-UP` tracked, never blocking), with the absence of a current-head review never satisfying this — and every other required check is terminal-green. It carries no time-based settle.

**`PRODUCTION_READINESS`** holds when either the change is not production-relevant per the project's recognition mechanism or the operator has explicitly approved the merge. The agent computes `MERGE_READINESS` identically for every PR and executes the merge only when `PRODUCTION_READINESS` also holds.

**terminal-green.** A required check is terminal when it has reached a final state (`status == COMPLETED`, or `state ∈ {SUCCESS, ERROR, FAILURE}`) and green when its conclusion is `SUCCESS` (or `state == SUCCESS`); terminal-green is both. A non-terminal, terminal-but-not-success, or absent required check is not terminal-green and blocks `MERGE_READINESS`.

**Acting on findings (validity and phase, never severity).** The agent acts on a review finding by its validity — the finding holds against its cited rule, product-local/language/spec-tree governance, and the PDR/ADR decisions, which the agent reads fresh and drops a finding they do not support — and by phase: at `REVIEW_READINESS` it applies every valid finding that belongs and splits out of the changeset any whose fix is too large to belong (recorded in `ISSUES.md`/`PLAN.md`); at `MERGE_READINESS` it fixes every valid in-scope finding and re-pushes, with no deferral of in-scope work, while a genuinely out-of-scope `FOLLOW-UP` is tracked, not a blocker. A finding's severity label never decides whether the agent acts on it, and the reviewer never decides whether the change merges. When the current-head CI review reports `conclusion: skipped` because the PR modifies the reviewer's own workflow file, the agent fires the mention-triggered reviewer with the project's configured trigger phrase (default `@spec-tree`) and treats its posted findings as the current-head review — this applies to that skip cause only.

## Rationale

Naming each lifecycle authorization a "gate" and every condition a "predicate" gives the model one word per concept; an overloaded vocabulary cannot be encoded once and reused. `REVIEW_READINESS` covers the local review and deterministic verification before the PR opens, so a draft phase adds no signal and only delays the CI reviews. `MERGE_READINESS` reads the review-landed and terminal-green events directly rather than waiting a fixed settle window, so a clean review merges quickly and a missing one keeps the gate open because the predicate is unmet. Severity is the reviewer's label; whether the agent acts turns on validity and phase, so a mislabeled finding neither blocks a sound change nor slips an in-scope fix. Production-relevance is a separate explicit gate because merge effort is identical for every PR and only execution waits. Collapsing the three into one gate hides that the agent authorizes three transitions; gating on severity lets a label decide what only the author can; a time-based settle delays clean PRs and gives no guarantee for slow ones.

## Product properties

1. The PR-management skills expose exactly three gates — `REVIEW_READINESS`, `MERGE_READINESS`, `PRODUCTION_READINESS` — named with the single word "gate"; every condition a gate reads is a predicate, never a gate.
2. `REVIEW_READINESS` holds from deterministic verification plus a converged local review; the PR opens `ready_for_review` the moment it holds, and draft state is not a gating mechanism.
3. The two conditions `REVIEW_READINESS` reads hold against the diff every push publishes, opening and follow-up alike; the local reviewer is invoked at parity with the CI reviewer, the caller passing only the repository/worktree and the diff range.
4. `MERGE_READINESS` and `PRODUCTION_READINESS` are decidable from observable PR state — an independent reader reaches the same verdict — and `MERGE_READINESS` carries no time-based settle.
5. The agent acts on a review finding by its validity, the current phase, and its scope, never by its severity label; a `FOLLOW-UP` is non-blocking because it is genuinely out of scope, and the reviewer never decides whether the change merges.
6. Production-relevance is project-declared; the agent executes a production-relevant merge only after explicit operator approval and carries no built-in rule that could silently authorize one.

## Verification

### Audit

- ALWAYS: the agent opens a PR `ready_for_review` once `REVIEW_READINESS` holds — deterministic verification reports success and the local `reviewing-changes` review has converged with no finding left unaddressed — and uses no draft phase as a gating mechanism ([audit])
- ALWAYS: before every push — opening and follow-up — the agent re-establishes both `REVIEW_READINESS` predicates on the diff that push would publish ([audit])
- ALWAYS: the agent invokes the local `reviewing-changes` gate at parity with the CI reviewer, passing only the repository/worktree and the diff range and letting the reviewer read the repository's full instructions and the shared taxonomy ([audit])
- ALWAYS: the agent merges a non-production-relevant PR without separate human instruction once `MERGE_READINESS` holds — a clean current-head CI review exists (absence never satisfying it) and every other required check is terminal-green ([audit])
- ALWAYS: the agent treats a required check as terminal-green only when it has reached a terminal state with a success conclusion; a non-terminal, terminal-but-not-success, or absent required check blocks `MERGE_READINESS` and carries no time-based settle ([audit])
- ALWAYS: the agent executes the merge only when `PRODUCTION_READINESS` also holds — the change is not production-relevant per the project's recognition mechanism, or the operator has explicitly approved ([audit])
- ALWAYS: the agent acts on each review finding by validity and phase — at `REVIEW_READINESS` applying every valid finding that belongs and splitting out fixes too large to belong, at `MERGE_READINESS` fixing every valid in-scope finding and re-pushing while tracking out-of-scope `FOLLOW-UP`s — never by the finding's severity label ([audit])
- ALWAYS: when no current-head review exists because the CI review reports `conclusion: skipped` from the PR modifying the reviewer's own workflow file, the agent fires the mention-triggered reviewer with the configured trigger phrase and treats its posted findings as the current-head review — for that skip cause only ([audit])
- NEVER: gate any of the three gates on a review finding's severity label — validity, phase, and scope decide; a `FOLLOW-UP` is non-blocking because it is genuinely out of scope, and the reviewer never decides whether the change merges ([audit])
- NEVER: narrow the local `reviewing-changes` invocation with caller-supplied interpretive scope, a severity pre-filter, or emphasis steering — narrowing diverges the local gate from the CI reviewer it parallels ([audit])
- NEVER: push to the PR — opening or follow-up — without re-establishing the local `reviewing-changes` review and deterministic verification on the diff being pushed ([audit])
- NEVER: use a time-based settle window as a `MERGE_READINESS` predicate — the gate reads the review-landed and terminal-green events directly ([audit])
- NEVER: open a PR as draft as a gating mechanism, or add a separate gated draft-to-ready promotion — the PR opens ready once `REVIEW_READINESS` holds ([audit])
- NEVER: execute a production-relevant merge from `MERGE_READINESS` alone — `PRODUCTION_READINESS` requires explicit operator approval ([audit])
- NEVER: treat an agent-inferred "the work looks done" as a gate, name a predicate a "gate", or introduce a fourth gate without amending this decision — a gate's predicates are observable or deterministically computed state, and the gate set is finite, ordered, and enumerated here ([audit])
