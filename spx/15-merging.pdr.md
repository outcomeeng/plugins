# Agent Authority over Merging

The agent integrates a verified changeset into the product's default branch on origin through `/merge` under exactly three gates — `REVIEW_READINESS`, `MERGE_READINESS`, `PRODUCTION_READINESS` — evaluated in order, each decidable from observable state with no time-based settle; one word, **gate**, names each authorization and every condition a gate reads is a **predicate**. A changeset is unfinished while its branch carries commits ahead of the resolved base: a clean working tree, a local commit, passing validation, passing tests, a converged review, or an audit approval is progress, not delivered value. `/merge` classifies the changeset, selects the project-selected transport, and drives the selected merge lifecycle until the changeset reaches the default branch on origin or stops at an explicit merge lifecycle gate. A review classifies each finding as `blocking` or `debt`, and the author judges disposition: every valid finding whose fix is bounded is fixed within the changeset, and a finding is deferred only when its fix is a separate, larger concern whose recorded reason names why it is large. The agent drives the lifecycle from a determined changeset to merge without an up-front operator proposal; a project whose operators want to confirm intent before any mutation opts into a **pre-mutation confirmation** through its merge overlay — the one operator touch-point the lifecycle adds ahead of the three gates, and never a gate itself.

## Rationale

Merging is the integration of a changeset into the default branch on origin; the authority, the gates, and the finding-disposition are properties of that integration, not of any one transport, so binding them to one hosted or local mechanism conflates policy with mechanism and excludes projects with other merge transports. Severity is the reviewer's label and scope is the author's judgment — a bounded fix such as a rename propagation, a cross-reference update, or a mechanical change is in-scope work the changeset carries, so deferral is reserved for a separate, larger concern and a label never decides what only the author can.

## Product properties

1. Delivered value is value merged to the default branch on origin through `/merge`; a branch with commits ahead of its resolved base is unfinished even when the working tree is clean and local validation, tests, review, or audit gates have passed.
2. The agent merges under exactly three gates — `REVIEW_READINESS`, `MERGE_READINESS`, `PRODUCTION_READINESS` — each decidable from observable state with no time-based settle; the merge transport is project-selected, and a transport binds only the predicates without adding, removing, or reordering a gate.
3. The agent drives the merge lifecycle from a determined changeset — branch, commit, push, publish, merge — without an up-front operator proposal by default; a project opts into a pre-mutation confirmation through its merge overlay, and only where it does does the agent present the changeset and intended lifecycle through the runtime's structured-question tool and wait for confirmation before the first mutating action. Status assessments may report local evidence, then continue through `/merge` when the branch carries committed changes and the user has not explicitly limited the task to local work; terse follow-ups such as "so?", "continue", "ship it", "finish", and "go on" mean continue the already-governed merge lifecycle. The pre-mutation confirmation is an opt-in touch-point ahead of the lifecycle, never a fourth gate, and leaves the three gates and the finding-disposition policy unchanged.

## Verification

### Audit

- ALWAYS: the merging skills expose exactly three gates — `REVIEW_READINESS`, `MERGE_READINESS`, `PRODUCTION_READINESS` — named with the single word "gate"; every condition a gate reads is a predicate, never a gate ([audit])
- ALWAYS: the three gates and the finding-disposition policy are transport-neutral — a project selects the merge transport, and the transport binds the gate predicates (which review attests `MERGE_READINESS`, which checks are required, how `REVIEW_READINESS` publishes the changeset) without changing the gate set or the disposition rule ([audit])
- ALWAYS: `REVIEW_READINESS` holds from deterministic verification reporting success plus a converged review-agent review with no valid finding left unaddressed; the moment it holds the changeset is published to its transport, and both predicates hold against the diff every publication republishes — re-established freshly when that republication changed the diff, or per the preservation assertion below when it only rebased an unchanged diff onto an advanced base ([audit])
- ALWAYS: when a publication republishes a diff unchanged from the one that last satisfied `REVIEW_READINESS` — a follow-up push that only rebased onto an advanced base — the predicates may be re-established from a deterministic base-sync preservation proof that shows the branch diff unchanged and the base movement unrelated, reusing the converged review and running only the narrower validation the base delta requires, rather than a forced full re-run; the proof scopes pre-push verification only and never relaxes `MERGE_READINESS`, whose current-head review and checks still decide it after the push ([audit])
- ALWAYS: delivered value exists only when a changeset reaches the default branch on origin through `/merge`; until then, a committed changeset ahead of its resolved base is unfinished, even when the working tree is clean and validation, tests, review, or audit gates pass ([audit])
- ALWAYS: the local review predicate of `REVIEW_READINESS` is satisfied only by a review agent — the changeset-review agent run in an isolated context — invoked at parity with the integration-time reviewer, passed only the repository/worktree and the diff range with no interpretive scope, severity pre-filter, or emphasis steering; a republication that only rebased a provably-unchanged diff onto an advanced base may reuse that agent's converged verdict rather than re-invoking it, the diff being the same diff the agent already judged ([audit])
- ALWAYS: `MERGE_READINESS` holds when a clean current-head review exists — present, complete, valid, reporting no unresolved `blocking` or `debt` finding (stated directly, or with every such finding individually dropped as unbacked; a `debt` finding the author tracks out of scope with a recorded reason is not unresolved), its absence never satisfying the predicate — and every required check the transport defines is terminal-green, with no time-based settle ([audit])
- ALWAYS: a required check is terminal-green only when it has reached a terminal state with a success conclusion; a non-terminal, terminal-but-not-success, or absent required check blocks `MERGE_READINESS` ([audit])
- ALWAYS: the agent merges without separate human instruction once `MERGE_READINESS` holds and `PRODUCTION_READINESS` also holds — the change is not production-relevant per the project's recognition mechanism, or the operator has explicitly approved ([audit])
- ALWAYS: the agent drives a determined changeset from intent to merge without an up-front operator proposal, unless the project's merge overlay opts into a pre-mutation confirmation; where the overlay opts in, the agent presents the changeset and intended lifecycle through the runtime's structured-question tool and obtains confirmation before the first mutating action ([audit])
- ALWAYS: when a status assessment finds committed changes ahead of the resolved base, it may report the local evidence it found, then continues through `/merge` when the user has not explicitly limited the task to proposal, review, analysis, or local-only work; local readiness is not a stopping point or a reason to ask what to do next ([audit])
- ALWAYS: terse follow-ups such as "so?", "continue", "ship it", "finish", and "go on" continue the already-governed merge lifecycle rather than opening a new operator decision ([audit])
- NEVER: treat the pre-mutation confirmation as a default or as a fourth authority gate — it is an opt-in overlay touch-point, absent unless the project declares it, and it leaves the three gates and the finding-disposition policy unchanged ([audit])
- ALWAYS: a review classifies each finding by exactly two severities — `blocking` for a merge-safety defect, `debt` for a real defect that does not jeopardize merge safety — and the reviewer judges finding validity and severity only, never scope or disposition ([audit])
- ALWAYS: the author judges disposition by scope — every valid finding whose fix is bounded is fixed within the changeset, and a finding is deferred only when its fix is a genuinely separate, larger concern (its own node or feature) recorded in the owning node's `ISSUES.md`/`PLAN.md` with a reason naming why it is large ([audit])
- ALWAYS: the agent acts on each finding by validity, phase, and scope — at `REVIEW_READINESS` applying every valid finding that belongs and splitting out only a fix too large to belong, at `MERGE_READINESS` fixing every valid in-scope finding and re-publishing while tracking only a genuinely-separate-larger-concern `debt` finding with a named reason — never by the severity label ([audit])
- NEVER: defer a finding whose fix is bounded — a rename propagation, a cross-reference update, a mechanical change, or a fix that merely touches another file — as out of scope; only a genuinely separate, larger concern is deferrable, and the recorded reason names why it is large ([audit])
- NEVER: gate any of the three gates on a finding's severity label, or use a time-based settle as a `MERGE_READINESS` predicate — validity, phase, and scope decide, and the gate reads the review-landed and terminal-green state directly ([audit])
- NEVER: a review carries a third scope-shaped severity (`follow_up`), a severity rank (`P0`–`P3`, `critical`/`high`/`medium`/`low`/`minor`/`nit`), or a legacy class label (`NEEDS-ANSWER`, `NOTE`) — the taxonomy is the two severities only, and open questions are reframed as findings ([audit])
- NEVER: satisfy a gate's review predicate with a review run by invoking a review skill in the working conversation, or with an agent-inferred "the work looks done" — the review predicate reads a review-agent verdict, and a gate's predicates are observable or deterministically computed state ([audit])
- NEVER: execute a production-relevant merge from `MERGE_READINESS` alone — `PRODUCTION_READINESS` requires explicit operator approval ([audit])
- NEVER: surface a base-sync rebase as an operator decision — a branch behind its base is rebased automatically from observable git state, and the only base-sync operator touch-point is a rebase conflict the agent cannot resolve autonomously ([audit])
- NEVER: bind the gate set to one transport's mechanism — a draft-to-ready promotion, a specific merge command, or a CI-reviewer skip rule is a transport specialization declared in that transport's spec, never in this decision ([audit])
- NEVER: introduce a fourth gate, name a predicate a "gate", or add a transport that changes the gate set or the disposition policy without amending this decision ([audit])
