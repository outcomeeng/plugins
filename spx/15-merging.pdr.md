# Agent Authority over Merging

The agent integrates a verified changeset into the product's default branch on origin through `/merge` and drives the ordered lifecycle `VERIFY -> PREVIEW -> MERGE -> DEPLOY -> RELEASE -> CLOSE`. The lifecycle is governed by four gates, evaluated in phase order: `VERIFICATION_READINESS`, `MERGE_READINESS`, `DEPLOYMENT_READINESS`, and `RELEASE_READINESS`. One word, **gate**, names each authorization point, and every condition a gate reads is a **predicate**. Review remains one verification type inside `VERIFICATION_READINESS`; the verification gate may also read validate, test, evaluate, and audit predicates. Deployment and release are separate phases because environment mutation and consumer-visible publication are distinct project boundaries. `PREVIEW`, `DEPLOY`, and `RELEASE` are no-op phases when the selected transport or project declares no action for them.

## Rationale

Merging is one phase in a broader delivery lifecycle. Separating verification, preview, merge, deployment, release, and close lets every transport bind its own predicates while preserving one portable phase order. `production` is not a portable project boundary, and review is only one verification type, so gate names follow the action they authorize rather than one consumer's environment or one verifier.

## Product properties

1. A default-branch-bound changeset is unfinished while its branch carries commits ahead of the resolved base; after merge, the lifecycle remains unfinished while any declared deploy or release phase still has authorized work to perform.
2. The agent drives four gates in order: `VERIFICATION_READINESS` authorizes publishing the verified changeset to the selected transport; `MERGE_READINESS` authorizes integrating the current head into the default branch on origin; `DEPLOYMENT_READINESS` authorizes declared environment mutation after merge; `RELEASE_READINESS` authorizes declared consumer-visible publication or refresh.
3. The agent drives the lifecycle from a determined changeset — branch, commit, push, publish, preview, merge, deploy, release, close — in the assigned worktree without an up-front operator proposal by default; a project opts into a pre-mutation confirmation through its merge overlay, and only where it does does the agent present the changeset and intended lifecycle through the runtime's structured-question tool and wait for confirmation before the first mutating action. The pre-mutation confirmation is an opt-in touch-point ahead of the lifecycle, never a gate.

## Verification

### Audit

- ALWAYS: the merging skills expose exactly four gates — `VERIFICATION_READINESS`, `MERGE_READINESS`, `DEPLOYMENT_READINESS`, `RELEASE_READINESS` — named with the single word "gate"; every condition a gate reads is a predicate, never a gate ([audit])
- ALWAYS: the phase sequence is `VERIFY -> PREVIEW -> MERGE -> DEPLOY -> RELEASE -> CLOSE`; transports bind predicates and actions for the phases without reordering the lifecycle ([audit])
- ALWAYS: `VERIFICATION_READINESS` holds from the selected transport's verification predicates over the changeset, drawn from the verification taxonomy in `spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md` — validate, test, evaluate, review, and audit — with concrete command and verifier choices left to the project or transport ([audit])
- ALWAYS: when a publication republishes a diff that matches the verification-ready diff — a follow-up push that only rebases onto an advanced base — the predicates may be re-established from a deterministic base-sync preservation proof that shows the branch diff unchanged and the base movement unrelated, reusing the converged agentic verification and running only the narrower validation the base delta requires, rather than a forced full re-run; the proof scopes pre-push verification only and never relaxes `MERGE_READINESS`, whose current-head review and checks decide the published head ([audit])
- ALWAYS: a branch with commits ahead of its resolved base remains unfinished until it reaches the default branch on origin through `/merge`; after merge, a declared deploy or release phase keeps the lifecycle unfinished until that phase completes or stops at its readiness gate ([audit])
- ALWAYS: the local review predicate inside `VERIFICATION_READINESS`, when a transport declares one, is satisfied only by a review agent — the changeset-review agent run in an isolated context — invoked at parity with the integration-time reviewer, resolving its own review scope (the worktree it runs in and the base/head diff) with no caller-supplied interpretive scope, severity pre-filter, or emphasis steering; a republication that only rebases a provably unchanged diff onto an advanced base may reuse that agent's converged verdict because the review subject is unchanged ([audit])
- ALWAYS: `MERGE_READINESS` holds when a clean current-head integration review exists — present, complete, valid, reporting no unresolved valid `blocking` or `debt` finding; a finding is resolved only when the defect class is repaired and the current head is re-reviewed, the finding is individually dropped as unbacked, the affected capability leaves the changeset and the current head is re-reviewed without the finding, or the operator explicitly waives that exact finding while accepting its stated consequence — and every required check the transport defines is terminal-green, with no time-based settle ([audit])
- ALWAYS: a required check is terminal-green only when it has reached a terminal state with a success conclusion; a non-terminal, terminal-but-not-success, or absent required check blocks `MERGE_READINESS` ([audit])
- ALWAYS: `DEPLOYMENT_READINESS` holds when every project- or transport-declared deployment predicate authorizes the environment mutation; when no deploy action is declared, the `DEPLOY` phase is a no-op and never blocks later phases ([audit])
- ALWAYS: `RELEASE_READINESS` holds when every project- or transport-declared release predicate authorizes the consumer-visible publication or refresh; when no release action is declared, the `RELEASE` phase is a no-op and never blocks `CLOSE` ([audit])
- ALWAYS: the agent drives a determined changeset from intent through the lifecycle without an up-front operator proposal, unless the project's merge overlay opts into a pre-mutation confirmation; where the overlay opts in, the agent presents the changeset and intended lifecycle through the runtime's structured-question tool and obtains confirmation before the first mutating action ([audit])
- ALWAYS: when a status assessment finds committed changes ahead of the resolved base, it may report the local evidence it found, then continues through `/merge` when the user has not explicitly limited the task to proposal, review, analysis, or local-only work; local readiness is not a stopping point or a reason to ask what to do next ([audit])
- ALWAYS: terse follow-ups such as "so?", "continue", "ship it", "finish", and "go on" continue the already-governed lifecycle rather than opening a new operator decision ([audit])
- NEVER: treat the pre-mutation confirmation as a default or as a fifth authority gate — it is an opt-in overlay touch-point, absent unless the project declares it, and it leaves the four gates and the finding-disposition policy unchanged ([audit])
- ALWAYS: a review classifies each finding by exactly two severities — `blocking` for a defect with a deterministic merge-safety consequence, `debt` for a real defect whose evidence does not establish that consequence — and the reviewer judges finding validity and severity only, never disposition ([audit])
- ALWAYS: the author validates each finding against its cited governance, repairs every valid finding as a defect class, and re-runs the review; when the required repair belongs to a capability too large for the changeset, that capability and the finding leave the changeset together before review reruns ([audit])
- ALWAYS: a coordination note may preserve work removed from a changeset, but recording a valid finding in `ISSUES.md`, `PLAN.md`, a pull-request comment, or another ledger never resolves that finding and never contributes to readiness ([audit])
- ALWAYS: an operator waiver identifies the exact finding and explicitly accepts its stated consequence; a general instruction to merge, an authorization conditioned only on severity, or permission to proceed when no finding is considered "truly blocking" waives no finding ([audit])
- NEVER: defer a valid finding while the changed diff still carries the cited defect or affected capability — the number of files, size of the repair, severity label, and availability of a tracking location do not change its unresolved state ([audit])
- NEVER: treat a finding's severity label as its disposition, or use a time-based settle as a readiness predicate — validity and explicit resolution evidence decide, and each gate reads observable state directly ([audit])
- NEVER: a review carries a third scope-shaped severity (`follow_up`), a severity rank (`P0`–`P3`, `critical`/`high`/`medium`/`low`/`minor`/`nit`), or a legacy class label (`NEEDS-ANSWER`, `NOTE`) — the taxonomy is the two severities only, and open questions are reframed as findings ([audit])
- NEVER: satisfy a gate's review predicate with a review run by invoking a review skill in the working conversation, or with an agent-inferred "the work looks done" — the review predicate reads a review-agent verdict, and a gate's predicates are observable or deterministically computed state ([audit])
- NEVER: surface a base-sync rebase as an operator decision — a branch behind its base is rebased automatically from observable git state, and the only base-sync operator touch-point is a rebase conflict the agent cannot resolve autonomously ([audit])
- ALWAYS: the agent conducts the changeset's git work in the assigned worktree, resolving a worktree or branch conflict by branching there and continuing, and never operates in a worktree a live agent holds, never creates a worktree, and never uses `git stash` ([audit])
- NEVER: bind the gate set to one transport's mechanism — a draft-to-ready promotion, a specific merge command, a CI-reviewer skip rule, a deploy provider, or a release command is a transport or project specialization, never the portable lifecycle itself ([audit])
- NEVER: introduce an additional gate, name a predicate a "gate", or add a transport that changes the gate set or the disposition policy without amending this decision ([audit])
