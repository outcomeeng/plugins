# Subprocess Execution in the Validation Package

The validation package exposes one subprocess seam per pattern, both passed through dependency injection. The gate orchestrator accepts a `ProcessSpawner` Protocol for subprocess creation and a `TextIO`-like sink for output; the orchestrator creates one temp log file per step, passes that path into the spawner, prints only recipe status and timing lines to the sink, removes successful step logs, reads a capped excerpt from the retained failing step log when a step fails, and writes a structured JSON summary for every run. Its recipe model exposes two primitive deterministic verification recipes: `validation` with `verification_type: validation` and `purpose: conformance`, and `test` with `verification_type: testing` and `purpose: correctness`. The `check` wrapper composes those primitive recipes in order, stops at the first failed primitive, reports aggregate primitive status, and carries no verification type of its own. Every primitive recipe runs preflight inside the orchestrator so preflight failure leaves the same retained log and structured summary as any other step failure.

The production entry point binds the spawner to `subprocess.Popen` with `stdin=subprocess.DEVNULL`, combined `stdout`/`stderr` redirected to the step log, `start_new_session=True`, and child-start signal-mask restoration that unblocks the forwarded signals before exec, while `l1` tests bind in-process recording spies/stubs under the `/testing` Stage 5 `Interaction protocols` exception to record invocations, write deterministic log content, and emit deterministic exit codes. When the orchestrator escalates an interrupted child to `SIGKILL`, it performs a bounded direct-child reap check before exiting so the direct child does not remain observable as a live PID. A capturing validator CLI runs each external process through a dependency-injected runner whose default bounds the wait with an explicit timeout, isolates the child's standard input, captures output without depending on a descendant closing an inherited stream, starts the child in its own process group, and `SIGKILL`s the group on expiry. No validation-package code performs an unbounded capture that blocks while a surviving descendant holds the stream, and the recipe step lists are module-level `tuple[Step, ...]` constants of `Step(label, argv)`.

## Rationale

A `ProcessSpawner` Protocol whose method returns a handle implementing `pid`, `poll`, `wait`, and a process-group signalling contract gives the orchestrator one observable seam; production binds it to a thin `subprocess.Popen` adapter and tests bind a recording spy/stub through the `/testing` Stage 5 `Interaction protocols` exception, so the signal-handling, step-iteration, summary-writing, and wrapper-stop paths all run without launching real validators. A per-step log path parameter keeps child output capture inside the same spawn boundary, so every command runs once and the live sink avoids high-volume child output. Successful logs are scratch data and are removed when their step passes; the failing log remains because the live output and structured summary cite its path for diagnosis. An output sink as a second injected dependency lets tests capture header and timing lines as strings. Primitive recipes stay module-level constants because steps are inert data and constants keep recipe composition falsifiable by reading them rather than running the orchestrator; the flat `STEPS` constant remains an aggregate compatibility surface over the primitive recipe step lists. A capturing runner that writes the child's output to a file rather than reading an inherited pipe makes the wait depend only on the invoked process exiting, and the timeout plus process-group `SIGKILL` bound the wait even when the child hangs or ignores `SIGTERM`. Framework replacement of `subprocess`, a full `Runner` Protocol owning the step loop, a TOML-driven recipe list, an unbounded `capture_output=True`, and a capture bounded only by `subprocess.run(timeout=...)` are each rejected — they violate the dependency-injection standard, move the logic-under-test behind an interface, add needless configurability, or fail to bound the wait when a descendant holds the stream.

## Verification

### Testing

- ALWAYS: on timeout, the capturing runner returns a non-zero result identifying the timed-out command — preserving the package's exit-code contract when a child fails to exit ([compliance])
- NEVER: a capturing validator CLI performs an unbounded capture that waits on pipe EOF — a surviving descendant holding the stream blocks the read without bound ([compliance])
- NEVER: a capturing CLI relies on `SIGTERM` alone to stop a child — a child that ignores the signal leaves the wait unbounded ([compliance])

### Audit

- ALWAYS: the orchestrator's step-execution function accepts the `ProcessSpawner` and the output sink as parameters — enabling `l1` verification of step ordering, header emission, timing summary, and exit-code propagation without launching real validators ([audit])
- ALWAYS: the `ProcessSpawner` Protocol method accepts the command argv and an orchestrator-created output path, then returns a handle exposing `pid: int`, `poll() -> int | None`, `wait() -> int`, and `send_signal_to_group(sig: int) -> None` — naming every observable the signal-handling path needs while keeping output capture inside the spawn boundary ([audit])
- ALWAYS: the production `ProcessSpawner` adapter passes `start_new_session=True` so `send_signal_to_group` can target the child's process group via `os.killpg` ([audit])
- ALWAYS: the production `ProcessSpawner` adapter unblocks the forwarded signals in the child before exec so the orchestrator's protected spawn window does not make validators inherit a blocked SIGTERM/SIGINT/SIGHUP mask ([audit])
- ALWAYS: the production `ProcessSpawner` adapter redirects combined child stdout/stderr to the orchestrator-created output path and isolates child stdin — passing gate output never streams through the live sink ([audit])
- ALWAYS: primitive recipe step lists are exposed as module-level `tuple[Step, ...]` constants importable by tests, and `STEPS` remains the aggregate compatibility tuple ([audit])
- ALWAYS: every run writes a structured JSON summary naming the recipe, phase, primitive recipe metadata, step commands, statuses, durations, exit codes, and retained log paths only for logs that remain available after the run ([audit])
- NEVER: the `check` wrapper declares a verification type — only primitive recipes declare verification type and purpose ([audit])
- ALWAYS: a capturing validator CLI runs each external-process invocation through a dependency-injected runner whose default bounds the wait with an explicit, overridable timeout, isolates stdin, captures output without depending on a descendant closing an inherited stream, and `SIGKILL`s the child's process group on expiry ([audit])
- ALWAYS: the capturing runner's wait-bound is a source-owned constant on the owning module, imported by tests rather than restated ([audit])
- NEVER: a gate orchestrator module (`_engine.py`, `_model.py`, `_spawner.py`, `_steps.py`, `__init__.py`, `__main__.py`) imports `subprocess` outside the production `_spawner.py` adapter ([audit])
- NEVER: tests for the orchestrator use `unittest.mock.patch`, `monkeypatch.setattr`, or `MagicMock` to replace `subprocess`, `os.killpg`, `time.monotonic`, or any module the orchestrator imports ([audit])
- NEVER: recipe step lists are loaded from a config file, environment variable, or plugin discovery mechanism — fixed tuples are the safeguard against gate-composition drift ([audit])
