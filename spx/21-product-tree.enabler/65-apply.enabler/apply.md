# Apply

PROVIDES the apply lifecycle — selecting the next executable observable slice, then driving each node in that slice through the per-node TDD flow — bounded by a whole-changeset review and a terminal merge-lifecycle gate
SO THAT all implementation agents
CAN turn an implementation plan into demonstrable value merged to the default branch, with each node conforming to its governing spec on the first pass

## Assertions

### Audit: work queue and completion

- work-queue: With a canonical full `spx/...` node-path argument the work queue is that single node, and with no argument it is derived from the conversation; when the conversation names no work, `/apply` reports "Nothing to apply" and stops.
- main-conversation-work: The main conversation runs per-node authoring, implementation and behavior-preserving simplification, and dispatches the auditors and reviewers its gates require.
- queue-order: A multi-node work queue runs in ascending numeric-index order, preserving each stabilized gate subject in a local checkpoint commit whose recorded verification state is `passing`, `failing`, or `not-run`; agentic gate dispatch still requires deterministic passing, and a node whose flow cannot converge stops the queue and reports the failed node and every node remaining in the queue.
- committed-head-gates: Every persisted audit or review gate binds to an exact committed head after deterministic verification passes; a rejected finding is repaired in a new local checkpoint before the gate reruns, while an audit over modified or untracked files is advisory and never satisfies a gate.
- full-gate-last: When the repository requires the full deterministic gate, run `just check-full` only after every applicable evidence audit, implementation audit, and whole-changeset review has converged, and run no agentic verification after it; any change after the full gate invalidates it and requires the agentic gates to converge again before a new full-gate run.
- whole-changeset-review: When the change touches files or specs beyond the target node, `/apply` runs the required evidence-auditor gates for the test and eval artifacts that the slugs of touched Test and Evaluate Assertions link before the whole-changeset review, runs the whole-changeset review through the `changes-reviewer` agent over the full diff, and points all audit handoffs at the whole changeset before declaring the flow complete, because per-node gates miss cross-node effects.
- merge-completes-flow: For default-branch work, the flow is incomplete until the change reaches the default branch on origin through `/merge`; an approved code audit, a converged whole-changeset review, passing tests, and a clean committed branch are local readiness, not completion — the flow continues into `/merge` unless the user explicitly scoped the work to a proposal, analysis, review, or local-only change, or an explicit lifecycle gate blocks with no independent local action remaining, per the `/understand` default-branch completion boundary.
- no-runtime-hook: No runtime hook enforces the audit gates; the gate reminders are skill prose, the product-tree plugin ships no `PostToolUse` hook, and enforcement is the flow's own discipline.

### Audit: verifier dispatch

- readiness-record: Every per-node and whole-changeset Verifier dispatch the apply lifecycle makes is preceded by the readiness record bound to the exact clean committed head.
- sync-before-verification: The apply lifecycle invokes `/sync-base` before every deterministic verification command and before every Verifier dispatch, records the `already_current` or `rebased` result for the exact head in the readiness record, and treats a Verifier's `stale-base` block as no verdict — it synchronizes, re-establishes the deterministic results on the rebased head, and dispatches again.
- defect-class-stop: A Verifier rejection belonging to a previously recorded defect class stops the work queue at the node that raised it until the widened repair, same-class scan, and governing-workflow, standard, or source-contract amendment land.
- bounded-projection: The apply lifecycle carries only the bounded projection of each Verifier result — the result reference, exact head, verdict, finding identifiers, defect classes, and next required action — reopening the complete result by reference.
- author-work-before-wait: The apply lifecycle finishes every independent Author-side inspection, repair, same-class scan, deterministic check, readiness-record update, and required commit before it starts a blocking check or Verifier wait.
- simplify-before-audits: After implementation and before the final implementation and evidence audits, the apply instructions run the detected language's `simplify-{lang}-code` skill in the main conversation, which verifies and checkpoints every resulting change before Verifier dispatch; a language that ships no simplification skill skips this stage.
- exact-subagent-target: Each audit or review step explicitly selects its exact configured subagent and supplies only the target path or scope. The skill owns these invocation instructions and does not obtain a subagent-specific prompt from the root guide. Accepted requirements are persisted in decisions and specs before dispatch. Each Verifier starts without authoring history and independently reads the target and configured instructions; the calling skill never appends an author-written context packet.
- one-native-launch: Invocation guidance requires exactly one native launch and analysis and reporting of a failed launch or unusable result without retry or substitution. Completed audit verdicts follow the existing gate and repair workflows.
- sealed-run-verdict: The apply lifecycle reads the verdict of each artifact auditor it launches — `adr-auditor`, `test-evidence-auditor`, `eval-evidence-auditor` and `implementation-auditor` — from the terminal status of the sealed run whose token the launch returns: a `rejected` run rejects whatever its finding count, a launch whose run spx refused a payload or the finish of is blocked, and no approval comes from a verdict object outside the run, a transcript, a task-output file or prose.
- class-repair: Each repair the apply lifecycle makes of a valid finding fixes the defect class the cited rule defines in the cited standard — every instance the cited clause covers and nothing the clause does not require — and the readiness record of the next Verifier dispatch names, for each repair, the clause it applies and the check that shows the class closed, while the gate reads that Verifier's verdict, never the check, per `defect-class-fix` in [`spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md`](spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md).

### Audit: gates and repairs

- gate-cap: `/apply` runs each audit or review gate on a node at most twice, counting rejections, and stops after the second rejection with the gate, its verdicts and the outstanding findings reported; the cap covers the whole-changeset review as well as the node audits, a rejection counts only as `rejection-count` in [`spx/31-outcomeeng.enabler/32-changes.enabler/65-change-application.enabler/change-application.md`](spx/31-outcomeeng.enabler/32-changes.enabler/65-change-application.enabler/change-application.md) states, and a review's `debt` finding on touched or invalidated text counts as no rejection and waits for its ruling.
- mechanical-repair: `/apply` repairs a finding of an audit run sealed `rejected`, or a valid `blocking` finding of the sealed whole-changeset review run, itself when the repair is a Mechanical Repair — a path or link, a typo, a wording the finding states, or a renamed identifier, never Decision Record text — then runs Validate and reruns every Test and Evaluate result the repair invalidates, and adds no Verifier pass of its own.
- fixer-handoff: `/apply` hands every other repair of a finding of an audit run sealed `rejected`, or of a valid `blocking` finding of the sealed whole-changeset review run, to a Fixer in an agent session of its own, independent of the Round's Author and launched from the definition that produces the subject the finding cites, with exactly the run file, unchanged, and the instruction "attend to every rule the run names and sweep each named class across the whole target"; the main conversation adds no summary, remedy, class name, or other interpretation of the findings, per `fixer-input` in [`spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md`](spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md).
- decision-line-repair: When a repair needs a Decision Record line that differs from the reviewed line, `/apply` makes no repair; it returns the Change it applies to Sliced with the new line written into the Change, for the Operator's review.
- no-main-conversation-repair: `/apply` makes no repair other than a Mechanical Repair in the main conversation; where the harness supplies no definition that produces the subject the finding cites, `/apply` stops with an unavailable result naming the run file and the missing definition.
