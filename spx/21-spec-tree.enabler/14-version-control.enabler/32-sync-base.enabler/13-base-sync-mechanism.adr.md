# Base Synchronization by Rebase

A branch behind its fetched base is brought current by rebasing the branch's own commits onto the remote-tracking base ref `origin/<base>`, never by resetting the branch pointer onto the base. Synchronization fetches the base, rebases only when the branch is behind it, and runs without operator interaction. The sole operator touch-point is a rebase conflict that cannot be resolved autonomously or a hard git failure; on conflict, synchronization leaves the rebase state active and reports structured conflict details — a human-readable summary, conflicted paths, relevant base and branch git facts, git's conflict text, and operator options to inspect, continue, or abort.

A working tree carrying uncommitted changes to tracked files is a precondition that blocks the rebase — git refuses to replay commits over a dirty index or work tree. Synchronization detects this state before rebasing and reports it as a distinct `dirty_tree` outcome: no rebase is attempted, the working tree is left untouched, and no conflict details are surfaced, because a dirty tree is not a rebase conflict and clearing it is not an operator decision. The caller clears the precondition by committing the changes through the commit workflow and re-running synchronization; synchronization never commits or stashes on the caller's behalf, so base-sync stays a single fetch-and-rebase operation and commit policy stays with the commit workflow. An untracked file does not block a rebase and is not a dirty tree, so the precondition check scopes to tracked changes; the one exception — an untracked file the base advance would overwrite, which git refuses to start the rebase over — is a separable detection concern tracked in this node's `ISSUES.md`, not folded into the tracked-file dirty check.

A detached HEAD — a worktree with no branch checked out, the normal parked state of a bare-repository worktree pool — is brought current by the same fetch-and-compare, not waved through as inapplicable. Synchronization fetches the base and compares the detached commit to the fetched `origin/<base>`. When the detached commit is an ancestor of the fetched base — strictly behind it or already equal to it — and the working tree is clean, synchronization advances the worktree to the base tip and reports `rebased` when the worktree moved or `already_current` when it already sat at the tip; a context load or session pickup then reads product truth from the current base rather than a stale detached commit. Advancing a clean, strictly-behind detached worktree is a fast-forward to commits it does not yet have, never the reset the mechanism rejects: it carries no commits the advance would lose. When the detached commit is behind the base but the working tree carries uncommitted tracked changes, synchronization reports `dirty_tree`, the same precondition the caller clears by committing. When the detached commit has diverged from the base — it carries commits the base does not — synchronization reports `git_failure` rather than advancing, because advancing would orphan those commits and a detached HEAD has no branch to rebase them onto; the commits need a branch before their work can be replayed. When no remote base resolves, the detached case stays `git_failure`. This narrows the prior "a detached HEAD is inapplicable — proceed" rule to its genuinely non-advanceable cases — divergence and no resolvable remote base — so a pool worktree parked at a stale commit behind the advanced base is brought current instead of seeding the whole change on superseded specs and decisions.

On a clean synchronization — `rebased` or `already_current` — synchronization emits a deterministic readiness-preservation proof alongside the status: a stable schema version, the full OIDs of the new base, the branch before and after, and the branch's fork point from the base; the base-delta paths the base advanced over since that fork point; the branch's changed paths against the fork point and the new base; whether those path sets overlap; and whether the branch's patch identity changed across the rebase. Anchoring the base delta at the fork point — the merge-base of the pre-rebase branch and the current base — keeps it accurate whether or not the caller already fetched the base, where a pre-fetch remote ref would equal the new base and report an empty delta. A caller reads this proof to decide which pre-push readiness predicates survive the base movement and how much validation is proportional, rather than treating every rebase as invalidating all local readiness. The proof scopes pre-push local work only: it never satisfies a merge gate. Current-head pull-request checks and the current-head CI review remain required predicates of `MERGE_READINESS` after every push, unchanged.

The proof carries portable git facts only. Deciding which deterministic command a base delta requires, and which files are governance surfaces whose change invalidates a prior local review, depends on a project's layout and tooling — knowledge a primitive shipped into unknown consumer repositories does not have. So the facts-to-command mapping and the governance-surface list live in the project's merge overlay (`spx/local/merging.md`), and a caller that cannot classify a base-delta path against that overlay falls back to the full deterministic gate. The primitive states facts; the project's policy maps them.

## Rationale

`git reset --hard origin/<base>` and `git reset --soft origin/<base>` repoint the branch to the advanced base while leaving the working tree at the old base, so the next commit silently reverts whatever the intervening merges changed, and `--hard` additionally discards uncommitted work. Rebase replays the branch's own commits onto the advanced base, preserving the branch's work while absorbing the base's movement. Composing the rebase target against the fetched `origin/<base>` through the shared `remote_tracking_ref` primitive fixes the target independent of a stale local ref, per `spx/21-spec-tree.enabler/14-version-control.enabler/15-changeset-scope.enabler/13-changeset-derivation.adr.md`.

Running synchronization without an operator prompt follows the product authority decided in `spx/15-merging.pdr.md`: a branch behind its base is rebased from observable git state, and the only base-sync operator touch-point is a conflict the agent cannot resolve autonomously. A routine, clean rebase is not an operator decision; surfacing one re-asks a question the product has already answered. A conflict handoff is not an opaque token: it names the active rebase state and the product-intent question the agent could not decide from specs, decisions, tests, session state, or deterministic git facts.

Bringing a detached HEAD current rather than waving it through closes a stale-base failure mode. A bare-repository worktree pool parks a free worktree detached, and that detached commit is current only when it sits at the advanced base tip; a stale checkout, or a worktree fast-forwarded earlier in a long session while the remote moved on, sits behind it. Reporting every detached HEAD as an inapplicable `git_failure` lets a context load or session pickup proceed on that stale commit, reading superseded specs and decisions, and the divergence surfaces only at merge as a heavy rebase against a base that moved underneath the whole change. Comparing the detached commit to the fetched base distinguishes the current and behind cases from the genuinely non-advanceable ones, so the common parked-worktree case is brought current and only divergence or a missing remote base stays a failure.

Rejected: `git reset` (either mode) as a synchronization mechanism — it advances the branch pointer while stranding the working tree at the old base, reverting merged work and, under `--hard`, destroying uncommitted changes; and a merge of the base into the branch — a merge commit pollutes the branch's own history, where rebase keeps the branch a clean sequence of its commits atop the current base. Also rejected: `git checkout .`, `git restore .`, blanket `git checkout --ours .`, blanket `git checkout --theirs .`, or `git rebase --abort` as the automatic handoff action for an unresolved conflict. Conflict stages are evidence; the operator may choose `git rebase --abort`, but synchronization does not erase the active state simply because autonomous reconciliation failed.

Rejected: synchronization committing or stashing the working tree to clear a dirty-tree precondition itself — committing belongs to the commit workflow with its message and version-bump rules, this product forbids stash, and absorbing either spreads commit policy into a version-control primitive while mutating the caller's uncommitted work outside the caller's control. Rejected: reporting a dirty tree as a conflict — it is a precondition the caller clears autonomously, not an unresolvable rebase conflict, and conflating the two re-surfaces an operator touch-point the product reserves for genuine conflicts.

Rejected: waving every detached HEAD through as inapplicable — a pool worktree parked at a commit behind the advanced base then loads context from superseded specs and decisions; the inapplicable detached cases are only the diverged HEAD and the no-resolvable-remote-base HEAD, not a clean behind-base one. Rejected: advancing a diverged detached HEAD — it carries commits the base lacks, and advancing the worktree to the base tip would orphan them; a detached HEAD with its own commits needs a branch before that work can be rebased, so it stays `git_failure` rather than risking a discard the mechanism exists to prevent.

Rejected: emitting a project-specific deterministic-command name (a `just check` recipe or test-path scope) from the portable synchronization primitive — command selection is repository-specific, so baking it into a primitive shipped into unknown consumer repositories breaks portability; the primitive emits git facts and the project's overlay maps them to commands. Rejected: a readiness-preservation proof satisfying any merge gate — the proof scopes pre-push local verification only, and `MERGE_READINESS` still requires current-head pull-request checks and a current-head CI review after every push. Rejected: keying local-review reuse on branch-path overlap alone — a base delta that changes a governance surface the reviewer reads (the repository's agent instructions, review template, or standards skills) moves the ruleset the review judged against, so review reuse also requires that the base delta touched no such surface.

### Testing

- ALWAYS: base synchronization rebases the branch's commits onto the remote-tracking base ref `origin/<base>`, preserving those commits ([compliance])
- ALWAYS: base synchronization derives the base ref and its remote-tracking form through the shared changeset-scope primitives, never re-deriving them, per `spx/21-spec-tree.enabler/14-version-control.enabler/15-changeset-scope.enabler/13-changeset-derivation.adr.md` ([compliance])
- ALWAYS: a clean synchronization completes with no operator interaction; the only operator touch-point is an unresolvable rebase conflict with active conflict state and structured details, or a hard git failure, per `spx/15-merging.pdr.md` ([compliance])
- ALWAYS: a behind-base branch whose working tree has uncommitted changes to tracked files is reported as the distinct `dirty_tree` outcome with no rebase attempted and the working tree left intact, never as a conflict — untracked files, which do not block a rebase, are not a dirty tree ([compliance])
- ALWAYS: a clean detached HEAD whose commit is an ancestor of the fetched base is advanced to the `origin/<base>` tip and reported as `rebased` when the worktree moved or `already_current` when it already sat at the tip, so context loading and session pickup read the current base rather than a stale detached commit ([compliance])
- ALWAYS: a detached HEAD behind the base whose working tree has uncommitted tracked changes is reported as `dirty_tree` with the worktree left untouched, never advanced ([compliance])
- NEVER: base synchronization advances a detached HEAD that has diverged from the base — one carrying commits the base lacks — it reports `git_failure`, because advancing would orphan those commits; only a clean, strictly-behind-or-equal detached HEAD is advanced, and a detached HEAD with no resolvable remote base also stays `git_failure` ([compliance])
- NEVER: base synchronization brings a behind-base branch current with `git reset` in any mode — the mechanism is rebase, which preserves the branch's commits ([compliance])
- NEVER: base synchronization commits, stashes, resets, or automatically aborts a conflicted rebase at operator handoff — it fetches, rebases, reports a dirty-tree precondition for the caller to clear through the commit workflow, and leaves an unresolvable conflict active for inspection ([compliance])
- ALWAYS: a clean synchronization (`rebased` or `already_current`) emits a readiness-preservation proof — a schema version, the full OIDs of the new base, the branch before and after, and the branch's fork point from the base, the base-delta paths, the branch's paths against the fork point and new base, path overlap, and whether the branch patch identity changed — computed from git facts alone ([compliance])
- ALWAYS: the readiness-preservation proof reports full, unabbreviated OIDs and carries no project-specific deterministic-command name — command selection and the governance-surface list are the project overlay's, not the primitive's ([compliance])
- NEVER: the readiness-preservation proof satisfies a merge gate — it scopes pre-push local verification only, leaving current-head pull-request checks and the current-head CI review as required `MERGE_READINESS` predicates after every push ([compliance])
