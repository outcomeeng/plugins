# Base Synchronization by Rebase

A branch behind its fetched base is brought current by rebasing the branch's own commits onto the remote-tracking base ref `origin/<base>`, preserving the branch's commits. The synchronization primitive owns fetch, topology-specific base movement, and Git-state reporting; the `/sync-base` skill owns recovery of an authorized dirty tree through `/commit-changes` and retries the primitive within the same invocation. A workflow composing `/sync-base` consumes its completed result without duplicating recovery or treating an intermediate primitive result as completion.

A working tree carrying uncommitted changes to tracked files blocks a behind-base rebase. The primitive detects this precondition before rebasing and reports `dirty_tree`, preserving HEAD, index, and tracked content and carrying no conflict details. The skill establishes ownership and existing write authority for the exact paths, creates an owning branch in the assigned worktree when needed, and delegates an atomic checkpoint commit to `/commit-changes`. A checkpoint commit preserves a coherent concern and records verification as `passing`, `failing`, or `not-run`; it neither requests approval nor establishes verification readiness. Commit policy, hooks, and proof that HEAD changed belong to `/commit-changes`. Only a successful checkpoint permits the skill to retry the primitive. The primitive itself never commits or stashes.

Existing authorization remains effective within its stated scope until the operator changes it. Session-owned work covered by that authority proceeds without another permission question, including when verification is failing or has not run. Operator-owned or unknown work requires authority covering those paths before mutation. A missing authority, a failed checkpoint, a hard Git failure, and an unresolved product-intent conflict are reported as separate conditions, with the exact blocked action and evidence. An analysis or interview label supplies neither new mutation authority nor a waiver of an unfinished prerequisite. The skill resumes a composing workflow only after `already_current` or `rebased` establishes base currency for the same checkout; a successful checkpoint alone does not establish currency.

The primitive's dirty-tree check covers tracked changes only. Non-colliding untracked files allow base movement. An untracked path the base would overwrite requires separate collision handling, tracked in this node's `ISSUES.md`. `already_current` establishes that the checkout contains the fetched base; it does not certify that the index or working tree is clean, so a current checkout's pending edits alone require no recovery checkpoint.

The following topology and preservation contract describes the primitive; its caller is the `/sync-base` skill.

A detached HEAD — a worktree with no branch checked out, the normal parked state of a bare-repository worktree pool — is brought current by the same fetch-and-compare, not waved through as inapplicable. Synchronization fetches the base and compares the detached commit to the fetched `origin/<base>`. When the detached commit is an ancestor of the fetched base — strictly behind it or already equal to it — and the working tree is clean, synchronization advances the worktree to the base tip and reports `rebased` when the worktree moved or `already_current` when it already sat at the tip; a context load or session pickup then reads product truth from the current base rather than a stale detached commit. Advancing a clean, strictly-behind detached worktree is a fast-forward to commits it does not yet have, never the reset the mechanism rejects: it carries no commits the advance would lose. When the detached commit is behind the base but the working tree carries uncommitted tracked changes, synchronization reports `dirty_tree`, the same precondition the caller clears by committing. When the detached commit has diverged from the base — it carries commits the base does not — synchronization reports `git_failure` rather than advancing, because advancing would orphan those commits and a detached HEAD has no branch to rebase them onto; the commits need a branch before their work can be replayed. When no remote base resolves, the detached case stays `git_failure`. A pool worktree parked behind the fetched base is brought current before product context is loaded.

On a successful synchronization — `rebased` or `already_current` — synchronization emits a deterministic readiness-preservation proof alongside the status: a stable schema version, the full OIDs of the new base, the branch before and after, and the branch's fork point from the base; the base-delta paths the base advanced over since that fork point; the branch's changed paths against the fork point and the new base; whether those path sets overlap; and whether the branch's patch identity changed across the rebase. Anchoring the base delta at the fork point — the merge-base of the pre-rebase branch and the current base — keeps it accurate whether or not the caller already fetched the base, where a pre-fetch remote ref would equal the new base and report an empty delta. A caller reads this proof to decide which pre-push readiness predicates survive the base movement and how much validation is proportional, rather than treating every rebase as invalidating all local readiness. The proof scopes pre-push local work only: it never satisfies a merge gate. Current-head pull-request checks and the current-head CI review remain required predicates of `MERGE_READINESS` after every push, unchanged.

A branch stacked on a predecessor branch — its commits sit atop the predecessor's commits rather than the default branch's — carries a stack record in the repository's git configuration: `branch.<name>.stackPredecessor`, the predecessor's branch name, and `branch.<name>.stackTip`, the full OID of the predecessor tip the branch last sat on. The primitive writes the record from git facts at the two moments the relation is knowable. When a synchronization rewrites an attached branch and reports `rebased`, every ref under `refs/heads/` other than the rebased branch that contains the pre-rebase head receives a record naming the rebased branch and that pre-rebase head, because a branch containing the old head sat on it. When a caller-supplied `--base <predecessor>` synchronizes a branch onto a predecessor, the synchronized branch receives a record naming the predecessor and the tip it now sits on. No other caller input writes the record; the record lives in the pool's shared configuration and is removed with its branch.

A synchronization without `--base` of a branch that carries a record takes the recorded predecessor as its base. After fetching the predecessor with pruning, the predecessor's state selects the movement. `origin/<predecessor>` present, containing the recorded tip, and not reachable from `origin/<default>`: the predecessor is open and unchanged beneath the branch, so the branch rebases onto `origin/<predecessor>` as an ordinary behind-base rebase, and the recorded tip becomes the predecessor's tip. `origin/<predecessor>` present without the recorded tip and not reachable from `origin/<default>`: the predecessor was rewritten and is still open, so the branch replays only the commits above the recorded tip onto it — `git rebase --onto origin/<predecessor> <recorded tip>` — and the recorded tip becomes the predecessor's tip. `origin/<predecessor>` absent after the pruning fetch, or present but reachable from `origin/<default>`: the predecessor has merged, so the branch replays only the commits above the recorded tip onto `origin/<default>` — `git rebase --onto origin/<default> <recorded tip>` — and both keys are removed. Each movement is a rebase of the branch's own commits; the recorded tip is what bounds them. A rebase that replays a stale predecessor's commits against their rewritten form conflicts on the first of them, which is the failure the record exists to prevent. A restack reports `rebased`; its proof names the recorded tip as `old_base_oid` and the target tip as `new_base_oid`, and carries `stack_predecessor`, `stack_tip_before`, and `stack_tip_after` — the latter null once the record is cleared.

A branch that carries no record and receives no `--base` is checked against local topology before the plain rebase. The candidates are the refs under `refs/heads/` other than the branch and the default branch that do not contain HEAD, whose merge-base with HEAD is a proper descendant of HEAD's merge-base with `origin/<default>`: the branch forked from each of them after they forked from the default. The candidate whose merge-base with HEAD descends from every other candidate's is the predecessor; the primitive writes the record naming it and that merge-base and proceeds by the predecessor states above. Two candidates whose merge-bases are unordered yield no predecessor and no record. When no record exists and no predecessor derives, the plain rebase runs as before, and a conflict report lists among its operator options the restack form `git rebase --onto origin/<default> <fork>`, whose fork the operator names.

The proof carries portable git facts only. Deciding which validation lane a base delta requires, and which files are governance surfaces whose change invalidates a prior local review, depends on a project's layout and tooling — knowledge a primitive shipped into unknown consumer repositories does not have. So the facts→lane mapping and the governance-surface list live in the project's merge overlay (`spx/local/merging.md`), and a caller that cannot classify a base-delta path against that overlay falls back to the full deterministic gate. The primitive states facts; the project's policy maps them.

## Rationale

`git reset` moves the branch pointer without replaying its own commits. `--hard` also replaces the index and tracked working tree, discarding pending tracked work; `--soft` preserves the old index and working tree against the new HEAD, allowing a later commit to reverse changes from the advanced base. Rebase replays the branch's own commits onto the advanced base, preserving the branch's work while absorbing the base's movement. Composing the rebase target against the fetched `origin/<base>` through the shared `remote_tracking_ref` primitive fixes the target independent of a stale local ref, per `spx/21-spec-tree.enabler/14-version-control.enabler/15-changeset-scope.enabler/13-changeset-derivation.adr.md`.

Running a routine rebase without an operator prompt follows `spx/15-merging.pdr.md`. Permission to commit particular dirty paths is a separate prerequisite: existing authority settles it, and absent authority stops that mutation. Keeping authority, checkpoint success, base currency, and verification readiness distinct prevents an interview or a failing test from silently becoming a new approval requirement. A conflict handoff is not an opaque token: it names the active rebase state and the product-intent question the agent could not decide from specs, decisions, tests, session state, or deterministic git facts.

Bringing a detached HEAD current rather than waving it through closes a stale-base failure mode. A bare-repository worktree pool parks a free worktree detached, and that detached commit is current only when it sits at the advanced base tip; a stale checkout, or a worktree fast-forwarded earlier in a long session while the remote moved on, sits behind it. Reporting every detached HEAD as an inapplicable `git_failure` lets a context load or session pickup proceed on that stale commit, reading superseded specs and decisions, and the divergence surfaces only at merge as a heavy rebase against a base that moved underneath the whole change. Comparing the detached commit to the fetched base distinguishes the current and behind cases from the genuinely non-advanceable ones, so the common parked-worktree case is brought current and only divergence or a missing remote base stays a failure.

Rejected: `git reset` (either mode) as a synchronization mechanism — it moves the branch pointer without replaying the branch's commits, with `--hard` additionally discarding pending tracked work; and a merge of the base into the branch — a merge commit pollutes the branch's own history, where rebase keeps the branch a clean sequence of its commits atop the current base. Also rejected: `git checkout .`, `git restore .`, blanket `git checkout --ours .`, blanket `git checkout --theirs .`, or `git rebase --abort` as the automatic handoff action for an unresolved conflict. Conflict stages are evidence; the operator may choose `git rebase --abort`, but synchronization does not erase the active state simply because autonomous reconciliation failed.

Rejected: the synchronization primitive committing or stashing the working tree itself. Commit policy belongs to `/commit-changes`, and the primitive has no authority to choose a commit's scope. Also rejected: requiring every workflow that composes `/sync-base` to implement checkpointing and retry. That duplicates recovery policy and lets an intermediate `dirty_tree` escape as a completed operation. The skill composes the primitive with the commit workflow while preserving their separate responsibilities.

Rejected: waving every detached HEAD through as inapplicable — a pool worktree parked at a commit behind the advanced base then loads context from superseded specs and decisions; the inapplicable detached cases are only the diverged HEAD and the no-resolvable-remote-base HEAD, not a clean behind-base one. Rejected: advancing a diverged detached HEAD — it carries commits the base lacks, and advancing the worktree to the base tip would orphan them; a detached HEAD with its own commits needs a branch before that work can be rebased, so it stays `git_failure` rather than risking a discard the mechanism exists to prevent.

Git keeps no link between a rewritten commit and its original. A stale predecessor commit fails every stateless test — patch-id matching, rebase's drop-if-empty, and reflog fork-points all miss a commit that was rebased and then edited — and the similarity pairing behind `git range-diff` is a heuristic. A restack therefore needs recorded state, and what makes it dependable is who writes the state and when: the primitive, at the moment it rewrites a branch, from `git for-each-ref --contains` over the pre-rebase head, so no caller has to remember that a stack exists. Branch configuration is the home because it is shared by every worktree in a pool, needs nothing outside git, and dies with the branch. The topology fallback covers a stack made without the primitive while the predecessor's local branch survives; the ambiguity rule refuses to guess between unordered candidates. Rejected: a record in the coordination store — it couples base synchronization to a Change and leaves a stack without one unprotected. Rejected: topology derivation alone — the merge lifecycle deletes the predecessor's local branch right after merging it, which is when the restack is needed. Rejected: a distinct `restacked` status — the movement is a rebase and the status set is fixed; the proof states the facts.

Rejected: emitting a project-specific validation-lane name (a `just check` lane, a test-path scope) from the portable synchronization primitive — lane taxonomy is repo-specific, so baking it into a primitive shipped into unknown consumer repositories breaks portability; the primitive emits git facts and the project's overlay maps them to lanes. Rejected: a readiness-preservation proof satisfying any merge gate — the proof scopes pre-push local verification only, and `MERGE_READINESS` still requires current-head pull-request checks and a current-head CI review after every push. Rejected: keying local-review reuse on branch-path overlap alone — a base delta that changes a governance surface the reviewer reads (the repository's agent instructions, review template, or standards skills) moves the ruleset the review judged against, so review reuse also requires that the base delta touched no such surface.
