# Base Synchronization by Rebase

A branch behind its fetched base is brought current by rebasing the branch's own commits onto the remote-tracking base ref `origin/<base>`, never by resetting the branch pointer onto the base. Synchronization fetches the base, rebases only when the branch is behind it, and runs without operator interaction; the sole operator touch-point is a rebase conflict that cannot be resolved autonomously or a hard git failure, surfaced as the `SYNC_BASE` action token.

A working tree carrying uncommitted changes to tracked files is a precondition that blocks the rebase — git refuses to replay commits over a dirty index or work tree. Synchronization detects this state before rebasing and reports it as a distinct `dirty_tree` outcome: no rebase is attempted, the working tree is left untouched, and the `SYNC_BASE` conflict token is not surfaced, because a dirty tree is not a rebase conflict and clearing it is not an operator decision. The caller clears the precondition by committing the changes through the commit workflow and re-running synchronization; synchronization never commits or stashes on the caller's behalf, so base-sync stays a single fetch-and-rebase operation and commit policy stays with the commit workflow. An untracked file does not block a rebase and is not a dirty tree, so the precondition check scopes to tracked changes; the one exception — an untracked file the base advance would overwrite, which git refuses to start the rebase over — is a separable detection concern tracked in this node's `ISSUES.md`, not folded into the tracked-file dirty check.

On a clean synchronization — `rebased` or `already_current` — synchronization emits a deterministic readiness-preservation proof alongside the status: a stable schema version, the full OIDs of the new base, the branch before and after, and the branch's fork point from the base; the base-delta paths the base advanced over since that fork point; the branch's changed paths against the fork point and the new base; whether those path sets overlap; and whether the branch's patch identity changed across the rebase. Anchoring the base delta at the fork point — the merge-base of the pre-rebase branch and the current base — keeps it accurate whether or not the caller already fetched the base, where a pre-fetch remote ref would equal the new base and report an empty delta. A caller reads this proof to decide which pre-push readiness predicates survive the base movement and how much validation is proportional, rather than treating every rebase as invalidating all local readiness. The proof scopes pre-push local work only: it never satisfies a merge gate. Current-head pull-request checks and the current-head CI review remain required predicates of `MERGE_READINESS` after every push, unchanged.

The proof carries portable git facts only. Deciding which validation lane a base delta requires, and which files are governance surfaces whose change invalidates a prior local review, depends on a project's layout and tooling — knowledge a primitive shipped into unknown consumer repositories does not have. So the facts→lane mapping and the governance-surface list live in the project's merge overlay (`spx/local/merging.md`), and a caller that cannot classify a base-delta path against that overlay falls back to the full deterministic gate. The primitive states facts; the project's policy maps them.

## Rationale

`git reset --hard origin/<base>` and `git reset --soft origin/<base>` repoint the branch to the advanced base while leaving the working tree at the old base, so the next commit silently reverts whatever the intervening merges changed, and `--hard` additionally discards uncommitted work. Rebase replays the branch's own commits onto the advanced base, preserving the branch's work while absorbing the base's movement. Composing the rebase target against the fetched `origin/<base>` through the shared `remote_tracking_ref` primitive fixes the target independent of a stale local ref, per `spx/21-spec-tree.enabler/14-version-control.enabler/15-changeset-scope.enabler/13-changeset-derivation.adr.md`.

Running synchronization without an operator prompt follows the product authority decided in `spx/15-merging.pdr.md`: a branch behind its base is rebased from observable git state, and the only base-sync operator touch-point is a conflict the agent cannot resolve autonomously. A routine, clean rebase is not an operator decision; surfacing one re-asks a question the product has already answered.

Rejected: `git reset` (either mode) as a synchronization mechanism — it advances the branch pointer while stranding the working tree at the old base, reverting merged work and, under `--hard`, destroying uncommitted changes; and a merge of the base into the branch — a merge commit pollutes the branch's own history, where rebase keeps the branch a clean sequence of its commits atop the current base.

Rejected: synchronization committing or stashing the working tree to clear a dirty-tree precondition itself — committing belongs to the commit workflow with its message and version-bump rules, this product forbids stash, and absorbing either spreads commit policy into a version-control primitive while mutating the caller's uncommitted work outside the caller's control. Rejected: reporting a dirty tree as a `SYNC_BASE` conflict — it is a precondition the caller clears autonomously, not an unresolvable rebase conflict, and conflating the two re-surfaces an operator touch-point the product reserves for genuine conflicts.

Rejected: emitting a project-specific validation-lane name (a `just check` lane, a test-path scope) from the portable synchronization primitive — lane taxonomy is repo-specific, so baking it into a primitive shipped into unknown consumer repositories breaks portability; the primitive emits git facts and the project's overlay maps them to lanes. Rejected: a readiness-preservation proof satisfying any merge gate — the proof scopes pre-push local verification only, and `MERGE_READINESS` still requires current-head pull-request checks and a current-head CI review after every push. Rejected: keying local-review reuse on branch-path overlap alone — a base delta that changes a governance surface the reviewer reads (the repository's agent instructions, review template, or standards skills) moves the ruleset the review judged against, so review reuse also requires that the base delta touched no such surface.

## Verification

### Testing

- ALWAYS: base synchronization rebases the branch's commits onto the remote-tracking base ref `origin/<base>`, preserving those commits ([compliance])
- ALWAYS: base synchronization derives the base ref and its remote-tracking form through the shared changeset-scope primitives, never re-deriving them, per `spx/21-spec-tree.enabler/14-version-control.enabler/15-changeset-scope.enabler/13-changeset-derivation.adr.md` ([compliance])
- ALWAYS: a clean synchronization completes with no operator interaction; the only operator touch-point is an unresolvable rebase conflict or a hard git failure, surfaced as the `SYNC_BASE` action token, per `spx/15-merging.pdr.md` ([compliance])
- ALWAYS: a behind-base branch whose working tree has uncommitted changes to tracked files is reported as the distinct `dirty_tree` outcome with no rebase attempted and the working tree left intact, never as a `SYNC_BASE` conflict — untracked files, which do not block a rebase, are not a dirty tree ([compliance])
- NEVER: base synchronization brings a behind-base branch current with `git reset` in any mode — the mechanism is rebase, which preserves the branch's commits ([compliance])
- NEVER: base synchronization commits or stashes the working tree — it only fetches and rebases, reporting a dirty-tree precondition for the caller to clear through the commit workflow ([compliance])
- ALWAYS: a clean synchronization (`rebased` or `already_current`) emits a readiness-preservation proof — a schema version, the full OIDs of the new base, the branch before and after, and the branch's fork point from the base, the base-delta paths, the branch's paths against the fork point and new base, path overlap, and whether the branch patch identity changed — computed from git facts alone ([compliance])
- ALWAYS: the readiness-preservation proof reports full, unabbreviated OIDs and carries no project-specific validation-lane name — lane mapping and the governance-surface list are the project overlay's, not the primitive's ([compliance])
- NEVER: the readiness-preservation proof satisfies a merge gate — it scopes pre-push local verification only, leaving current-head pull-request checks and the current-head CI review as required `MERGE_READINESS` predicates after every push ([compliance])
