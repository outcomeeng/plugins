# Sync Base

PROVIDES automatic base synchronization with authorized checkpoint recovery, a deterministic Git primitive, and a completed currency result
SO THAT context loading, the merge lifecycle, and session pickup
CAN read product truth, verify, and integrate against a current base without re-deriving base operations or surfacing a routine rebase as an operator decision

## Assertions

### Scenarios

These assertions exercise the bundled synchronization primitive. The `/sync-base` skill owns recovery from its intermediate results.

- Given a branch whose HEAD is behind its fetched base, when the synchronization primitive runs, then the branch's own commits are replayed onto `origin/<base>` and the changes already merged into the base are present in the working tree ([test](tests/test_sync_base.scenario.l1.py))
- Given a branch already current with its fetched base, when the synchronization primitive runs, then it performs no rebase and reports the branch already current ([test](tests/test_sync_base.scenario.l1.py))
- Given a rebase that conflicts and cannot be resolved autonomously, when the synchronization primitive runs, then it stops with the rebase state active and reports structured conflict details — summary, conflicted paths, base and branch git facts, git's conflict text, and operator options to inspect, continue, or abort — rather than aborting the rebase or emitting an opaque action token ([test](tests/test_sync_base.scenario.l1.py))
- Given a behind-base branch whose working tree has uncommitted changes to tracked files, when the synchronization primitive runs, then it reports the distinct `dirty_tree` outcome without attempting the rebase, leaving the working tree untouched and emitting no conflict details — the skill owns checkpoint recovery and retry ([test](tests/test_sync_base.scenario.l1.py))
- Given a behind-base branch whose only working-tree change is a non-colliding untracked file, when the synchronization primitive runs, then it rebases normally rather than reporting `dirty_tree` — a non-colliding untracked file does not block a rebase and is not a dirty tree ([test](tests/test_sync_base.scenario.l1.py))
- Given a base ref that does not resolve, when the synchronization primitive runs, then it reports a hard git failure rather than rebasing onto an unresolved target ([test](tests/test_sync_base.scenario.l1.py))
- Given a clean detached HEAD whose commit is an ancestor of the fetched base and is behind it, when the synchronization primitive runs, then it advances the worktree to the `origin/<base>` tip and reports `rebased`, with the base advance present in the working tree — a parked pool worktree is brought current rather than waved through on a stale commit ([test](tests/test_sync_base.scenario.l1.py))
- Given a clean detached HEAD already at the fetched base tip, when the synchronization primitive runs, then it performs no advance and reports `already_current` ([test](tests/test_sync_base.scenario.l1.py))
- Given a detached HEAD behind the base whose working tree has uncommitted changes to tracked files, when the synchronization primitive runs, then it reports the `dirty_tree` outcome without advancing, leaving the working tree untouched — the skill owns checkpoint recovery and retry ([test](tests/test_sync_base.scenario.l1.py))
- Given a detached HEAD that has diverged from the base — carrying commits the base lacks — when the synchronization primitive runs, then it reports a hard git failure rather than advancing, because advancing would orphan those commits and a detached HEAD has no branch to rebase them onto ([test](tests/test_sync_base.scenario.l1.py))
- Given a detached HEAD with no resolvable remote base, when the synchronization primitive runs, then it reports a hard git failure rather than attempting to advance ([test](tests/test_sync_base.scenario.l1.py))
- Given a clean detached HEAD behind the base whose only working-tree change is a non-colliding untracked file, when the synchronization primitive runs, then it advances the worktree rather than reporting `dirty_tree` — a non-colliding untracked file does not block the advance and is not a dirty tree ([test](tests/test_sync_base.scenario.l1.py))
- Given a caller-supplied base branch name, when the synchronization primitive runs, then it synchronizes onto that base's remote-tracking ref `origin/<base>` rather than the `origin/HEAD` default — so a stacked changeset rebases onto its actual base ([test](tests/test_sync_base.scenario.l1.py))
- Given a clean rebase whose base advance changed only files the branch does not touch, when the synchronization primitive runs, then the readiness-preservation proof reports no path overlap between the base delta and the branch's changed paths and an unchanged branch patch identity — the signal a caller reads to reuse a prior local review ([test](tests/test_sync_base.preservation.l1.py))
- Given a clean rebase whose base advance changed a file the branch also changed, when the synchronization primitive runs, then the readiness-preservation proof reports the path overlap, so a caller does not reuse a prior local review or a narrowed validation lane ([test](tests/test_sync_base.preservation.l1.py))
- Given a branch already current with its base, when the synchronization primitive runs, then the preservation proof reports an empty base delta and an unchanged branch patch identity, so a caller preserves all prior readiness ([test](tests/test_sync_base.preservation.l1.py))
- Given a caller that already fetched the base before the synchronization primitive runs, when a clean rebase completes, then the proof reports the base advance in `base_delta_paths` — anchored at the branch's fork point rather than the pre-fetch remote ref — so the base delta stays accurate and the caller's lane mapping is not misled by an empty delta ([test](tests/test_sync_base.preservation.l1.py))
- Given a clean detached HEAD advanced to the base tip, when the synchronization primitive runs, then it emits a readiness-preservation proof reporting the base advance in `base_delta_paths`, no path overlap, and an unchanged branch patch identity — a parked worktree carries no branch work the advance invalidates ([test](tests/test_sync_base.preservation.l1.py))
- Given a clean detached HEAD already at the base tip, when the synchronization primitive runs, then it emits a preservation proof reporting an empty base delta and an unchanged branch patch identity ([test](tests/test_sync_base.preservation.l1.py))
- Given a clean rebase whose base advance renames a file, when the synchronization primitive runs, then the proof reports both the old and the new path in `base_delta_paths` — a base rename is not collapsed to the new name, so a base rename of a path the branch also changed surfaces as a path overlap rather than hiding ([test](tests/test_sync_base.preservation.l1.py))

### Compliance

- ALWAYS: the synchronization primitive resolves the base ref and its remote-tracking form `origin/<base>` through the shared changeset-scope primitives, never re-implementing base, remote-tracking, or branch derivation ([test](tests/test_sync_base.compliance.l1.py))
- NEVER: the synchronization primitive brings a behind-base branch current with `git reset` in any mode — it rebases, preserving the branch's commits, per `spx/21-spec-tree.enabler/14-version-control.enabler/32-sync-base.enabler/13-base-sync-mechanism.adr.md` ([test](tests/test_sync_base.compliance.l1.py))
- NEVER: the synchronization primitive requests an operator decision for a routine behind-base rebase; it returns Git-state outcomes for the skill to act on ([test](tests/test_sync_base.compliance.l1.py))
- NEVER: the synchronization primitive commits or stashes the working tree, aborts a conflicted rebase at operator handoff, or surfaces a dirty tree as a conflict — a dirty tree is a distinct precondition the skill resolves through the commit workflow, per `spx/21-spec-tree.enabler/14-version-control.enabler/32-sync-base.enabler/13-base-sync-mechanism.adr.md` ([test](tests/test_sync_base.compliance.l1.py))
- ALWAYS: `src/plugins/spec-tree/skills/sync-base/SKILL.md` assigns authorized dirty-tree recovery to `/sync-base`: objective work stays on its owning branch, unrelated coordination work follows its own merge route, and `/commit-changes` owns checkpoint policy and proof of success before the primitive is retried within the same invocation ([audit])
- ALWAYS: the recovery contract applies existing authority to the exact changed paths, records checkpoint verification as `passing`, `failing`, or `not-run`, and names the blocked action and evidence separately for absent authority, failed checkpoint, hard Git failure, or unresolved product intent ([audit])
- NEVER: the recovery contract treats an analysis or interview label as a change in authorization or a waiver of an unfinished prerequisite; explicit operator limits govern mutation ([audit])
- NEVER: the skill hands an intermediate authorized `dirty_tree` back as completed synchronization, treats a checkpoint as proof of base currency, or treats `already_current` as proof that the working tree is clean ([audit])
- ALWAYS: the synchronization primitive brings a clean detached HEAD whose commit is an ancestor of the fetched base current by advancing the worktree to `origin/<base>`, never waving it through as a hard failure, per `spx/21-spec-tree.enabler/14-version-control.enabler/32-sync-base.enabler/13-base-sync-mechanism.adr.md` ([test](tests/test_sync_base.compliance.l1.py))
- NEVER: the synchronization primitive advances a detached HEAD behind the base whose working tree has uncommitted tracked changes — it reports `dirty_tree` and leaves the worktree untouched ([test](tests/test_sync_base.compliance.l1.py))
- NEVER: the synchronization primitive advances a diverged detached HEAD — one carrying commits the base lacks — it reports `git_failure` and preserves those commits rather than orphaning them, per `spx/21-spec-tree.enabler/14-version-control.enabler/32-sync-base.enabler/13-base-sync-mechanism.adr.md` ([test](tests/test_sync_base.compliance.l1.py))
- ALWAYS: the readiness-preservation proof carries a schema version and reports the old and new base and branch OIDs as full unabbreviated hashes, and carries no project-specific validation-lane name — lane mapping is the project overlay's, per `spx/21-spec-tree.enabler/14-version-control.enabler/32-sync-base.enabler/13-base-sync-mechanism.adr.md` ([test](tests/test_sync_base.preservation.l1.py))
