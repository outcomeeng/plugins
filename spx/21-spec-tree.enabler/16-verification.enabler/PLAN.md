# PLAN: Verification run-journal migration

## Why

`spx/21-spec-tree.enabler/16-verification.enabler/13-run-journal.adr.md` replaces the prior shared-architecture decision (universal thread-store persistence, an end-of-run JSON result, and the verdict toolchain) with the append-only run-journal contract: a run is one event journal that is its sole source of truth, every surface is a projection rendered from the journal, and the skill emits through one backend-neutral channel that binds the backend — a local run-journal file on a developer machine, a hosted pull-request comment under CI — at the edge. The journal and its backends are owned by the `spx` CLI's local state store and its `spx journal` verbs. This node's children and the entangled auditing decision still declare the superseded stack; truth flows down, so align them to the new contract.

## Gate status — UNBLOCKED (spx 0.6.0 published)

`@outcomeeng/spx@0.6.0` is published to npm (`latest`) and ships the `spx journal` channel — one **type-agnostic** run journal with verbs `open`, `append`, `read --from <cursor>`, `seal`, `render`, where the verification kind (`auditing`/`reviewing`) is an opaque `<type>` scope segment. Events are **CloudEvents** (`spx` owns the event schema — `append` rejects input "missing a required CloudEvents field"); a run's journal file lives at `.spx/branch/<slug>/<type>/runs/run-*.jsonl`. Verified live on 0.6.0: `open` returns `{runToken,runFile}`, `seal` returns `{"sealed":true}`, and `read`/`render` stream the event-prefix projection. There is no separate `spx review`/`spx audit` channel — auditing and reviewing drive the same `spx journal`, differing only by `<type>`.

The migration is therefore **unblocked** per the published-capability rule. The one remaining gate step lands in the first changeset that binds the channel: advance `REQUIRED_SPX_VERSION` (`outcomeeng/validation/spx_version.py`) and the CI `SPX_VERSION` pin (`.github/workflows/check.yml`) from `0.5.6` to `0.6.0`.

**The channel (`spx journal`, the type-agnostic run journal):**

| Verb                   | Contract role (per `13-run-journal.adr.md`)                                                                                                                                  |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `open`                 | open the journal for a `<type>`-scoped run on a branch/head — `<type>` is the opaque verification-kind segment (`auditing`/`reviewing`); the run is its sole source of truth |
| `append`               | append one domain event (scope entered, finding reported, run completed) carrying a strictly increasing, contiguous sequence number                                          |
| `read --from <cursor>` | resume reads of the event history from a cursor — the read surface that supersedes the audit-era `status`/`list`                                                             |
| `seal`                 | terminal seal: make the run's sequence final, after which no append succeeds                                                                                                 |
| `render`               | render a projection (markdown report, PR comment, findings JSON, check summary) as a pure function of the event prefix — the verdict projection a sealed journal produces    |

Backend selection is **edge-resolved from the environment** — override `SPX_VERIFY_BACKEND`, scope `SPX_VERIFY_BRANCH` — so the wrapper agent names no backend: a local run-journal file + stdout on a dev machine, GitHub Snapshot persistence + PR-comment under CI.

`13-run-journal.adr.md` already phrases the contract in exactly these terms (append / read-from-cursor / seal / render; backend bound at the edge; type-agnostic over reviewing and auditing), so **the ADR needs no change** — it matches published `spx journal`.

**CORRECTION — supersedes the earlier "verdict.py becomes the projection" framing and PR #300.** `spx journal render` *is* the projection renderer and CloudEvents *is* the event schema, so the entire `verdict.py` toolchain (`verdict.py` + `emit_verdict.py`/`read_verdict.py`/`aggregate_verdicts.py`/`pass_results.py`) is **redundant and must be removed**, not reframed. The Python does not "become the projection" and is not "the verdict projection a sealed journal renders" — `spx journal render` replaces it. Any earlier guidance in this plan to keep the toolchain as a projection (and PR #300, which did exactly that) is wrong; see corrected item 1.

## Downstream work (lower layers now lag the ADR) — sequenced

Truth flows down from `13-run-journal.adr.md`. Each item below is a node-level change with its own audit gate; sequence them so a superseded surface is never left half-migrated. **`/contextualize` each target node before editing it.** Every item is also gated on the spx-journal release per the gate-status section above: author the spec-leading alignment when the migration runs, but bind the live `spx journal` channel only once the release publishes and the floor advances.

1. **Remove `15-verdict-toolchain.enabler` (the Python toolchain) and drive `spx journal` directly.** `spx journal` subsumes every job the Python toolchain does: CloudEvents events replace the `verdict.py` schema; `spx journal render` replaces `emit_verdict.py`; `spx journal read` replaces `read_verdict.py`; `spx journal render` over the event prefix replaces `aggregate_verdicts.py`'s rollup; appended events replace `pass_results.py`. So **delete the toolchain and its tests** and rewire the ~20 consumers — the `/audit` skill; the `auditor` and `pr-review-orchestrator` agents; every `audit-{lang}` / `audit-{lang}-architecture` skill across python/typescript/rust; `audit-adr`/`audit-pdr`/`audit-specs`/`audit-tests`; `develop`'s `audit-skills`/`audit-commands`/`audit-subagents`; and `review-changes` (`review_result.py`) — to `open`/`append`/`seal`/`render` through `spx journal`. This is the substance of the migration and touches the whole audit + review surface; sequence it as several PRs, and advance the floor/pin (gate-status above) in the first one. `13-run-journal.adr.md` needs no change.

   ⚠️ **PR #300 (merged `7ab9ba66`) did the OPPOSITE and is wrong-direction work to undo.** It kept all five Python scripts, reworded `verdict-toolchain.md` to declare the Python "the verdict projection a sealed journal renders," and renamed its 5 tests `*.scenario.l1.py` → `*.compliance.l1.py` (with the 17 `[test]` links + docstrings). It changed no behavior; it only cemented code that must be deleted. **Revert or supersede #300** as part of this removal. (Aside, now moot since the node is being deleted: the evidence-type relabel in #300 was also wrong — per `/test` routing these assertions are mapping-dominant with conformance/property and only ~2 compliance, not uniform compliance.)

2. **Decide `21-thread-store.enabler`'s fate.** Its CRUD-overwrite facade (`write` overwrites; `read`/`delete`/`list`) does not match the append/sequence/cursor/seal journal contract. `review-changes` persists through it today and works — leave reviewing intact until it migrates. Choose: (a) supersede thread-store with the `spx journal` channel and migrate `review-changes` onto `spx journal` under reviewing's `<type>` segment, or (b) reframe thread-store as one Appendable backend bound at the edge. Recommendation: (a) — the channel is the new source of truth; thread-store's branch-slug derivation already re-exports from `14-version-control.enabler/15-changeset-scope.enabler`, so nothing unique is lost, and reviewing drives the same `spx journal` channel as auditing (no separate `spx review` surface exists — the kind is the `<type>` segment). Backend selection stays edge-resolved (`SPX_VERIFY_BACKEND` override, `SPX_VERIFY_BRANCH` scope); the wrapper agent names no backend. **Safety property the replacement MUST preserve:** the review-result head-identity gap tracked in `spx/21-spec-tree.enabler/68-reviewing.enabler/21-reviewing-changes.enabler/ISSUES.md` (a `review-result.json` keyed by branch slug alone, with no head/base OID, lets a reused-worktree or stale-branch read return the wrong diff's record) — whatever supersedes thread-store must key records by review-diff identity (head/base OID), not branch slug alone. Gate with `/audit-adr`/`/audit-tests`.

3. **Rework `spx/21-spec-tree.enabler/17-auditing.adr.md` onto the journal.** It still encodes the old machinery end to end: the `verdict.py` toolchain, the `.spx/audits/<lang>/<branch-slug>.md` orchestrator state + lockfile, the PR-comment-as-database recovery (`AUDIT_VERDICT_JSON_BEGIN` delimiter), and the four `/audit`-family wrapper agents that drive them.
