# PLAN: Verification run-journal migration

## Why

`spx/21-spec-tree.enabler/16-verification.enabler/13-run-journal.adr.md` replaces the prior shared-architecture decision (universal thread-store persistence, an end-of-run JSON result, and the verdict toolchain) with the append-only run-journal contract: a run is one event journal that is its sole source of truth, every surface is a projection rendered from the journal, and the skill emits through one backend-neutral channel that binds the backend — a local run-journal file on a developer machine, a hosted pull-request comment under CI — at the edge. The journal and its backends are owned by the `spx` CLI's local state store and its `spx journal` verbs. This node's children and the entangled auditing decision still declare the superseded stack; truth flows down, so align them to the new contract.

## Gate status — BLOCKED pending the `spx journal` release

The `spx` CLI run-journal channel is `spx journal`, one **type-agnostic** channel with verbs `open`, `append`, `read --from <cursor>`, `seal`, `render`. The verification kind — `auditing` or `reviewing` — is an opaque `<type>` scope segment the caller passes; `spx` carries no `audit`/`review` vocabulary of its own. Auditors and reviewers drive the SAME `spx journal` channel, differing only by their `<type>` label. There is no separate `spx review` (or `spx audit`) channel.

This channel is **not yet published**. It lives on the `spx` `work/journal` branch, unmerged. The currently published and installed `spx 0.5.6` ships the now-removed `spx audit init|progress|close|status|list` lifecycle — a different, superseded surface — and `REQUIRED_SPX_VERSION` (`outcomeeng/validation/spx_version.py`) and the CI `SPX_VERSION` pin (`.github/workflows/check.yml`) both sit at `0.5.6`. So the earlier premise — "unblocked because `spx 0.5.6` published the audit run-journal verbs" — is **false**: those verbs are being removed, and the channel this migration binds is unpublished.

Per the published-capability rule (`AGENTS.md` "Depend on an `spx` CLI capability only after it is PUBLISHED and the floor is advanced"), this migration is unblocked only by the forthcoming **spx-journal release**: (1) an `@outcomeeng/spx` release that ships `spx journal` is published to npm, (2) `REQUIRED_SPX_VERSION` is advanced to that version (above `0.5.6`), and (3) the CI `SPX_VERSION` pin is bumped to a published version at or above the floor. The floor must target that future spx-journal release, **not** `0.5.6`. Until all three hold, the marketplace skills cannot bind the channel.

Sequencing is one-directional, and the `spx` merge is **not** gated on this plugin work: this repo invokes the channel in zero executable paths — its live verification model is still thread-store + `verdict.py` — so `spx` publishes `spx journal` first, and THEN this migration adopts it.

**The channel (`spx journal`, the type-agnostic run journal):**

| Verb                   | Contract role (per `13-run-journal.adr.md`)                                                                                                                                  |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `open`                 | open the journal for a `<type>`-scoped run on a branch/head — `<type>` is the opaque verification-kind segment (`auditing`/`reviewing`); the run is its sole source of truth |
| `append`               | append one domain event (scope entered, finding reported, run completed) carrying a strictly increasing, contiguous sequence number                                          |
| `read --from <cursor>` | resume reads of the event history from a cursor — the read surface that supersedes the audit-era `status`/`list`                                                             |
| `seal`                 | terminal seal: make the run's sequence final, after which no append succeeds                                                                                                 |
| `render`               | render a projection (markdown report, PR comment, findings JSON, check summary) as a pure function of the event prefix — the verdict projection a sealed journal produces    |

Backend selection is **edge-resolved from the environment** — override `SPX_VERIFY_BACKEND`, scope `SPX_VERIFY_BRANCH` — so the wrapper agent names no backend: a local run-journal file + stdout on a dev machine, GitHub Snapshot persistence + PR-comment under CI.

`13-run-journal.adr.md` already phrases the contract in exactly these terms (append / read-from-cursor / seal / render; backend bound at the edge; type-agnostic over reviewing and auditing), so **the ADR needs no change** — it matches `spx journal` as published-to-be. What changes shape is the verdict-attach mechanism: instead of the audit-era `close --verdict-path <file>`, the `verdict.py` schema + renderer becomes a journal **projection** rendered via `spx journal render`, and the run closes via `spx journal seal`. The "verdict-toolchain → projection" re-scope intent below (item 1) is unchanged; only the attach/seal mechanism differs.
