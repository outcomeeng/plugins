# PLAN: Verification run-journal migration

## Why

`spx/21-spec-tree.enabler/16-verification.enabler/13-run-journal.adr.md` replaces the prior shared-architecture decision (universal thread-store persistence, an end-of-run JSON result, and the verdict toolchain) with the append-only run-journal contract: a run is one event journal that is its sole source of truth, every surface is a projection rendered from the journal, and the skill emits through one backend-neutral channel that binds the backend — a local run-journal file or a hosted pull-request comment — at the edge. The journal and its backends are owned by the `spx` CLI's local state store and its run-journal verbs (`append`, `read --from <cursor>`, `seal`, `render`), landing separately in the `spx` CLI. This node's children and the entangled auditing decision still declare the superseded stack; truth flows down, so align them to the new contract.

## Downstream work (lower layers now lag the ADR)

1. **Replace `spx/21-spec-tree.enabler/16-verification.enabler/15-verdict-toolchain.enabler`.** Its `verdict.py` end-of-run schema and the `emit_verdict.py` / `read_verdict.py` / `aggregate_verdicts.py` surface CLIs are the projection of the old single-result model. Under the run-journal contract the canonical run state is the event journal and every surface is a render. Re-scope or prune this node: the marketplace skill stops shipping its own verdict schema and surface toolchain and emits events through the `spx` run-journal channel; the rollup and the resolved/reopened diff become journal projections the channel renders. Sequence with `/refactoring`.
2. **Decide the fate of `spx/21-spec-tree.enabler/16-verification.enabler/21-thread-store.enabler`.** Its CRUD-overwrite facade (`write` overwrites; `read`/`delete`/`list`) does not match the append-only / sequence / cursor / seal journal contract. Reviewing persists through it today and works — leave reviewing's behavior intact until it migrates. Either (a) supersede thread-store with the `spx` run-journal channel and migrate reviewing onto it, or (b) reframe thread-store as one Appendable backend bound at the edge. The branch-slug derivation it re-exports already has its canonical home in `15-changeset-scope.enabler`.
3. **Rework `spx/21-spec-tree.enabler/17-auditing.adr.md`.** "Auditing Architecture" still encodes the old machinery end to end: the `verdict.py` toolchain, the `.spx/audits/<lang>/<branch-slug>.md` orchestrator state with a lockfile, the PR-comment-as-database recovery (the `AUDIT_VERDICT_JSON_BEGIN` delimiter), and the four wrapper agents that drive them. Realign it to the run-journal contract — orchestrator state, CI state, and the PR comment all become journal and projections through the `spx` channel, and the wrapper agents append events rather than persisting verdicts. This is a node-level decision rework via `/aligning` then `/audit-adr`.
4. **`spx/21-spec-tree.enabler/16-verification.enabler/15-changeset-scope.enabler` survives unchanged** — the run-journal contract still derives branch, slug, base ref, and the changed-file set from it.
5. **Re-home the verdict-vocabulary reference in `spx/21-spec-tree.enabler/76-merging.enabler/merging.md`.** Its in-slice-unresolved-work assertion cites `15-verdict-toolchain.enabler/verdict-toolchain.md` for the `REJECTED` / `UNKNOWN` / `FAIL` / `REJECT` tokens — the accurate current authority. When item (1) replaces the verdict toolchain, the result vocabulary is defined by the journal's terminal event and projection; update the merging assertion to cite that authority then.
6. **Decide reviewing's result-delivery governance.** `spx/15-audit-result-delivery.pdr.md` decides observable result delivery — incremental reveal, same shape on local and PR surfaces — for **audit** runs, while `13-run-journal.adr.md` applies the run-journal contract to **both** agentic verification types. A reviewing run is equally minutes-long and reveals incrementally through its own surface, but no PDR declares that observable behavior. This effort is deliberately audit-scoped — reviewing's implementation is left intact — so the choice (broaden `15-audit-result-delivery.pdr.md` to an "agentic verification result delivery" decision covering both types, or author a separate reviewing-result-delivery decision) is recorded here rather than made in this changeset.

## Deferred

The verdict-terminology follow-up carried in the removed `spx/21-spec-tree.enabler/PLAN.md` (align the overall-verdict token `REJECT` → `REJECTED` to the `verdict-toolchain.md` `Status` enum) is deferred until item (1) replaces the verdict toolchain. While the toolchain remains live — shipped, tested, and cited by `merging.md` and `spx/21-spec-tree.enabler/17-auditing.adr.md` — the `REJECT` → `REJECTED` alignment still applies to it; it is subsumed only when the journal's terminal event and its projection define the result vocabulary in place of the `verdict.py` `Status` / `Severity` enums.

## Dependency

Items (1)–(3) depend on the `spx` CLI exposing the run-journal verbs (`spx audit` and `spx review` with `append`, `read --from <cursor>`, `seal`, `render`) over the new local state store. Until those land the marketplace skills cannot bind the backend-neutral channel, so `13-run-journal.adr.md` declares the contract ahead of that implementation as future product truth.
