# Audit

The marketplace ships one implementation-audit wrapper surface in the spec-tree plugin: an `implementation-auditor` agent invoking skill-owned orchestration that resolves, for each changed path, the registered artifacts whose detection matches it and the audit skills they name, from the artifact registry the build renders beside its provider skill's reader, which the scope resolver imports; validates that each selected skill is installed; passes the supplied scope unchanged to each selected skill that follows the concern contract; aggregates their projections; and records one audit verification run. Each concern skill owns language-specific applicability and claims the subject paths it audits or returns not applicable; a resolved path no registered artifact matches, a matched path whose selected skill returns not applicable, and a path whose registered artifact's audit skill follows another contract remain outside implementation-audit coverage and stay with their artifact-type auditor and the whole-changeset review, while the run records each as an accounting record — an optional, skipped coverage-gap unit carrying no language partition and, for a path whose registered artifact's audit skill follows another contract, naming that skill — so a sealed run's recorded path subjects equal the changed-path inventory its own start input carries, while a missing selected skill is recorded as a required unit naming that skill rather than a path. Audit consumes the shared agentic-verification run journal and projection governed by [`spx/21-spec-tree.enabler/16-verification.enabler/13-run-journal.adr.md`](spx/21-spec-tree.enabler/16-verification.enabler/13-run-journal.adr.md) and `spx/21-spec-tree.enabler/16-verification.enabler/18-journal-projection.enabler`; those shared layers own storage, backend selection, event ordering, streaming, sealing, projection rendering, wrapper-agent shape, and changeset-scope derivation. The implementation-audit orchestration dispatches only the selected skills that follow the concern contract — for a language, its code, tests, and architecture concerns — and never runs deterministic validation, test, or eval commands, which remain the main agent's changeset responsibility and CI's repository responsibility per [`spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md`](spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md). Eval-evidence audits run through a separate artifact-type auditor, not as a fourth implementation-audit phase.

Every language plugin ships implementation-audit intelligence as skills only; no language-specific auditor agent exists. This is the audit case of the rule in [`spx/15-subagent-execution.pdr.md`](spx/15-subagent-execution.pdr.md) that every subagent definition is language-neutral. The implementation-audit surface is one spec-tree-owned `implementation-auditor` wrapper agent that owns the isolated verifier context and composes the implementation concern skills inside that one subagent invocation. The launcher exposes one subagent level, so nested composition happens by invoking skills from the dispatched implementation-auditor context rather than by launching a second layer of agents. The implementation-auditor invokes the relevant `audit-{lang}-{code|tests|architecture}` skill set for each language partition and composes their validated projections into one audit verification run. Keeping composition inside that one verifier context avoids an unmaintainable fleet of single-skill agents such as `{lang}-code-auditor`, `{lang}-test-auditor`, or `{lang}-architecture-auditor`.

The marketplace's other auditor agents are artifact-type-scoped: each covers a single artifact type — a decision record or test evidence, for example — reading it against its governing standards, and each is owned by whichever plugin governs that artifact type. An artifact-type auditor with language-specific concerns composes the matching implementation-audit skill set, partitioned by the language detected in scope. Section structure, atemporal voice, and tag validity for decision records are judged by the artifact-type auditor reading the canonical decision templates; composed language architecture skills carry only language-specific architecture concerns and never re-judge those generic decision-record rules from copied template prose. Wrapper agents never construct a path into `scripts/`; implementation-audit persistence goes through `spx verification run`.

Declaration audits distinguish authoring form from evidence completeness. The canonical templates admit untagged rules directly under `## Verification` and untagged assertions directly under `## Assertions` while verification selection is pending. These declarations may coexist with routed subsections. Auditors derive the form from the artifact without a caller identity or phase argument. Draft declarations receive the applicable structure, voice, specificity, and consistency checks; routed content retains its tag and grouping checks. Approval establishes declaration quality only and supplies no evidence that an untagged claim holds or that its node is Passing.

## Rationale

The audit-specific decision lives here because neither shared verification nor review decides how audit partitions scope, which language skill names must exist, which artifact-type auditors compose language concerns, or which wrapper agents expose audit surfaces. Keeping those rules in the audit decision leaves the shared run-journal and projection architecture in `spx/21-spec-tree.enabler/16-verification.enabler/` and keeps review free to consume the same architecture with its own policy.

The implementation-audit orchestration embeds no language-specific knowledge beyond the rendered registry and the `audit-{lang}-{code|tests|architecture}` dispatch template. The rendered registry establishes which artifacts the marketplace governs and how a path selects them; each read-only concern skill owns its language's applicability within its selected match; the installed skill inventory establishes only whether a selected skill can run. This keeps documentation, manifests, and other artifact classes from becoming fabricated language partitions while still requiring complete implementation coverage for paths a language concern claims.

Accounting for a path is not auditing it. A sealed run that is silent about a resolved path cannot be read as either covering that path or deliberately leaving it to another auditor, and silence is the shape a narrowed inspection takes: a run that stopped after its first finding is indistinguishable from one that finished. Recording every unclaimed path as an optional, skipped coverage-gap unit with no language partition keeps artifact classes out of language partitions while making the sealed run self-describing — its recorded subject set equals the inventory its start input carries, and any reader reproduces that equality from the run alone rather than from the auditor's account of it. Reconciliation therefore compares the run against its own sealed inventory rather than against the plan the run driver holds, because a plan narrowed before enumeration reconciles with itself, and it runs as a bundled command whose exit code carries the verdict, because a reconciliation the run driver performs in prose is one it can omit without leaving a trace. Selection runs in the scope resolver against the rendered registry and is recorded in the run's start input, because a selection the run driver performs in prose is one it can omit without leaving a trace, and a selection driven by the installed inventory loads every installed kind for every changeset and hides a kind the consumer has not installed; the inventory decides only audited against `missing-skill`, and it is read from the dispatched context rather than probed, because a failed probe is one step from a manufactured `missing-skill` unit. Validating that each selected skill is installed before dispatch makes a missing skill a pre-execution failure. Skills own policy and the agents are thin wrappers because skills are the shared behavior surface across Claude Code-authored source and generated Codex output and are the only surface where `${CLAUDE_SKILL_DIR}` resolves. The registry is rendered rather than imported because a shipped script runs in a consumer checkout that carries no `outcomeeng` package, per `spx/12-shipped-scripting.adr.md`; its reader is one provider skill the scope resolver imports, because logic one skill owns and another executes has one owner, per `spx/13-plugin-and-runtime-conventions.adr.md`.

## Verification

### Audit

- ALWAYS: declaration audits recognize the canonical untagged authoring form from the artifact itself, including drafts alongside routed content, without requiring a caller identity or phase argument ([audit])
- ALWAYS: declaration audits check every draft claim for its applicable declaration-quality rules and preserve tag, grouping, and evidence-fit checks for routed claims ([audit])
- NEVER: approval of an untagged declaration establishes evidence completeness, implementation correctness, or Passing state ([audit])
- ALWAYS: the implementation-audit wrapper agent contains zero language-specific tokens beyond the dispatch template `audit-{lang}-{code|tests|architecture}` ([audit])
- ALWAYS: every marketplace plugin that defines a programming language ships `audit-{lang}-code`, `audit-{lang}-tests`, and `audit-{lang}-architecture` skills ([audit])
- NEVER: the spec-tree plugin ships multiple implementation-audit wrapper agents; implementation audit has one wrapper, `implementation-auditor` ([audit])
- ALWAYS: every auditor agent is generic and artifact-type-scoped, never language-scoped — the one spec-tree-owned `implementation-auditor` composes the per-language implementation code, test, and architecture skills, and every other artifact type is covered by a single artifact-type auditor owned by the plugin that governs that artifact type; language audits ship as skills with no language-specific auditor agent ([audit])
- ALWAYS: the `implementation-auditor` runs all implementation concern composition inside its one isolated verifier context because the main conversation agent launches only one subagent level ([audit])
- ALWAYS: an artifact-type auditor with language-specific concerns composes them by invoking the matching `audit-{lang}-{code|tests|architecture}` skill set, partitioned by the language detected in scope ([audit])
- ALWAYS: section structure, atemporal voice, and tag validity for a decision record are judged by the artifact-type auditor reading the canonical decision template; the composed `audit-{lang}-architecture` skill carries only language-specific concerns ([audit])
- ALWAYS: audit wrapper agents reach audit policy and the audit verification run only by invoking audit skills; review agents reach review policy and the review journal only by invoking the `review-changes` skill ([audit])
- ALWAYS: the main conversation reaches an implementation audit only by dispatching the `implementation-auditor` wrapper agent — the dispatched agent's isolated context produces the verdict, per [`spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md`](spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md) ([audit])
- ALWAYS: the `implementation-auditor` supplies its run-driver producer identity as explicit request data; `audit-implementation` accepts that identity generically and never names, detects, or otherwise depends on the agent, skill, or context that invokes it ([audit])
- ALWAYS: orchestration dispatches the audit skills the scope resolver selected by matching each changed path, an advisory audit's live paths included, against the rendered artifact registry, most specific match within a kind and kinds in declaration order, and dispatches only the selected skills that follow the concern contract; it never selects from the installed inventory or invents an artifact for an unmatched path ([audit])
- ALWAYS: a registry-selected concern skill absent from the installed inventory is a required `missing-skill` unit naming that skill ([audit])
- ALWAYS: a sealed implementation-audit run's recorded path subjects equal the changed-path inventory its own start input carries, so a reader establishes the inspection's completeness from the run rather than from the run driver's account of it ([audit])
- ALWAYS: orchestration records every resolved path no registered artifact matched, every matched path whose selected skill returned not applicable, and every path whose registered artifact's audit skill follows another contract, as an accounting record — an optional, skipped coverage-gap unit — that names the audit skill of a registered artifact which follows another contract ([audit])
- ALWAYS: implementation-audit reconciliation compares the run against the inventory its own start input sealed, and runs as a bundled command whose exit code carries the verdict ([audit])
- NEVER: an accounting record for an unclaimed path carries a language partition, a required coverage requirement, or a final coverage status — it records that the path was considered and left to another auditor, never that it was audited ([audit])
- NEVER: implementation-audit orchestration runs the project's validation or test commands (or any deterministic verification) — it dispatches only the agentic concern audits, the main agent having passed deterministic verification on the changeset before dispatch and CI re-running it over the whole repository, per [`spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md`](spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md) ([audit])
- NEVER: a language-specific auditor agent (`{lang}-architecture-auditor`, `{lang}-code-auditor`, `{lang}-test-auditor`) exists — language concerns reach an audit through skills composed inside the `implementation-auditor`, not a per-language agent ([audit])
- NEVER: an audit skill judges decision-record section structure, voice, or tag validity from a transcribed copy of the canonical template — the copy drifts from and contradicts the template ([audit])
- NEVER: the main conversation invokes an implementation-audit skill in place to produce a verdict — the isolated wrapper-agent context, not the main conversation, is where an audit runs ([audit])
- NEVER: introduce language-specific examples, file extensions, validation commands, test commands, or evidence patterns into implementation-audit orchestration or the audit wrapper agents — that content belongs in the corresponding `audit-{lang}-{code|tests|architecture}` skill ([audit])
- NEVER: ship per-language audit-orchestration agents such as `typescript-audit-orchestrator` — the implementation-auditor context serves every language by skill dispatch ([audit])
- NEVER: embed deterministic shell pipelines (git diff, base-ref detection, scope partitioning) directly in the wrapper agent prompts — the implementation-audit orchestration skill prose owns these pipelines ([audit])
- NEVER: reference `scripts/` from an agent prompt by `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_SKILL_DIR}`, or a hard-coded relative path — neither variable is substituted in an agent prompt body ([audit])
- NEVER: add a per-skill self-description block to `audit-{lang}-{code|tests|architecture}` skills declaring file globs, configs, gate commands, or test commands — the dispatch contract is the skill name ([audit])
- NEVER: place the consumer-side projection helper at a plugin-root location — the marketplace co-locates Python under the consuming skill ([audit])
- NEVER: the implementation audit's orchestration or its wrapper agent carries its own copy of the artifact kind list — each reads the rendered registry ([audit])
