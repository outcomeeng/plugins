# Audit

The marketplace target ships one implementation-audit wrapper surface in the spec-tree plugin: an `implementation-auditor` agent invoking skill-owned orchestration that dispatches language partitions to `audit-{lang}-code`, `audit-{lang}-tests`, and `audit-{lang}-architecture` skills, aggregates their projections, and records one audit verification run. Audit consumes the shared agentic-verification run journal and projection governed by `spx/21-spec-tree.enabler/16-verification.enabler/13-run-journal.adr.md` and `spx/21-spec-tree.enabler/16-verification.enabler/18-journal-projection.enabler`; those shared layers own storage, backend selection, event ordering, streaming, sealing, projection rendering, wrapper-agent shape, and changeset-scope derivation. The implementation-audit orchestration dispatches only its three language-partition concerns — code, tests, and architecture — and never runs deterministic validation, test, or eval commands, which remain the main agent's changeset responsibility and CI's repository responsibility per `spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md`. Eval-evidence audits run through the sibling `eval-evidence-auditor` artifact-type wrapper, not as a fourth implementation-audit phase.

Every language plugin ships implementation-audit intelligence as skills only; no language-specific auditor agent exists. The target implementation-audit surface is one spec-tree-owned `implementation-auditor` wrapper agent that owns the isolated verifier context and composes the implementation concern skills inside that one subagent invocation. The launcher permits the main conversation agent to launch one level of subagents: nested composition happens by invoking skills from the dispatched implementation-auditor context, not by launching a second layer of agents. The implementation-auditor invokes the relevant `audit-{lang}-{code|tests|architecture}` skill set for each language partition and composes their validated projections into one audit verification run. Keeping composition inside that one verifier context avoids an unmaintainable fleet of single-skill agents such as `{lang}-code-auditor`, `{lang}-test-auditor`, or `{lang}-architecture-auditor`.

The marketplace's other auditor agents are artifact-type-scoped: `adr-auditor`, `pdr-auditor`, `test-evidence-auditor`, and `eval-evidence-auditor` for decision, test-evidence, and eval-evidence audits; and the instructions-owned `skill-auditor` and `subagent-auditor` for skill-content and subagent-configuration audits when the instructions plugin is installed. An artifact-type auditor with language-specific concerns composes the matching implementation-audit skill set, partitioned by the language detected in scope. Section structure, atemporal voice, and tag validity for decision records are judged by the artifact-type auditor reading the canonical decision templates; composed language architecture skills carry only language-specific architecture concerns and never re-judge those generic decision-record rules from copied template prose. Wrapper agents never construct a path into `scripts/`; implementation-audit persistence goes through `spx verification run`.

## Rationale

The audit-specific decision lives here because neither shared verification nor review decides how audit partitions scope, which language skill names must exist, which artifact-type auditors compose language concerns, or which wrapper agents expose audit surfaces. Keeping those rules in the audit decision leaves the shared run-journal and projection architecture in `spx/21-spec-tree.enabler/16-verification.enabler/` and keeps review free to consume the same architecture with its own policy.

The implementation-audit orchestration embeds no language-specific knowledge beyond the `audit-{lang}-{code|tests|architecture}` dispatch template, so a partial multi-language audit reports the right language without product detection. Validating the language trio at marketplace-validation time makes a missing skill a pre-execution failure. Skills own policy and the agents are thin wrappers because skills are the shared behavior surface across Claude Code-authored source and generated Codex output and are the only surface where `${CLAUDE_SKILL_DIR}` resolves.

## Verification

### Testing

- ALWAYS: every marketplace plugin that defines a programming language ships `audit-{lang}-code`, `audit-{lang}-tests`, and `audit-{lang}-architecture` skills ([compliance])

### Audit

- ALWAYS: the implementation-audit wrapper agent contains zero language-specific tokens beyond the dispatch template `audit-{lang}-{code|tests|architecture}` ([audit])
- ALWAYS: every marketplace plugin that defines a programming language ships `audit-{lang}-code`, `audit-{lang}-tests`, and `audit-{lang}-architecture` skills ([audit])
- ALWAYS: the marketplace's auditor agents are generic and artifact-type-scoped — one spec-tree-owned `implementation-auditor` for implementation code, tests, and architecture, plus `adr-auditor`, `pdr-auditor`, `test-evidence-auditor`, and `eval-evidence-auditor`, and the instructions-owned skill and subagent auditors when that plugin is installed; language audits ship as skills with no language-specific auditor agent ([audit])
- ALWAYS: the `implementation-auditor` runs all implementation concern composition inside its one isolated verifier context because the main conversation agent launches only one subagent level ([audit])
- ALWAYS: an artifact-type auditor with language-specific concerns composes them by invoking the matching `audit-{lang}-{code|tests|architecture}` skill set, partitioned by the language detected in scope ([audit])
- ALWAYS: section structure, atemporal voice, and tag validity for a decision record are judged by the artifact-type auditor reading the canonical decision template; the composed `audit-{lang}-architecture` skill carries only language-specific concerns ([audit])
- ALWAYS: audit wrapper agents reach audit policy and the audit verification run only by invoking audit skills; review agents reach review policy and the review journal only by invoking the `review-changes` skill ([audit])
- ALWAYS: the main conversation reaches an implementation audit only by dispatching the `implementation-auditor` wrapper agent — the dispatched agent's isolated context produces the verdict, per `spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md` ([audit])
- ALWAYS: implementation-audit orchestration partitions multi-language scopes by file extension and runs the orchestration protocol once per language partition ([audit])
- NEVER: implementation-audit orchestration runs the project's validation or test commands (or any deterministic verification) — it dispatches only the agentic concern audits, the main agent having passed deterministic verification on the changeset before dispatch and CI re-running it over the whole repository, per `spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md` ([audit])
- NEVER: a language-specific auditor agent (`{lang}-architecture-auditor`, `{lang}-code-auditor`, `{lang}-test-auditor`) exists — language concerns reach an audit through skills composed inside the `implementation-auditor`, not a per-language agent ([audit])
- NEVER: an audit skill judges decision-record section structure, voice, or tag validity from a transcribed copy of the canonical template — the copy drifts from and contradicts the template ([audit])
- NEVER: the main conversation invokes an implementation-audit skill in place to produce a verdict — the isolated wrapper-agent context, not the main conversation, is where an audit runs ([audit])
- NEVER: introduce language-specific examples, file extensions, validation commands, test commands, or evidence patterns into implementation-audit orchestration or the audit wrapper agents — that content belongs in the corresponding `audit-{lang}-{code|tests|architecture}` skill ([audit])
- NEVER: ship per-language audit-orchestration agents such as `typescript-audit-orchestrator` — the implementation-auditor context serves every language by skill dispatch ([audit])
- NEVER: embed deterministic shell pipelines (git diff, base-ref detection, scope partitioning) directly in the wrapper agent prompts — the implementation-audit orchestration skill prose owns these pipelines ([audit])
- NEVER: reference `scripts/` from an agent prompt by `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_SKILL_DIR}`, or a hard-coded relative path — neither variable is substituted in an agent prompt body ([audit])
- NEVER: add a per-skill self-description block to `audit-{lang}-{code|tests|architecture}` skills declaring file globs, configs, gate commands, or test commands — the dispatch contract is the skill name ([audit])
- NEVER: place the consumer-side projection helper at a plugin-root location — the marketplace co-locates Python under the consuming skill ([audit])
