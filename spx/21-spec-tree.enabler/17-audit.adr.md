# Audit

The marketplace ships one generic `/audit` skill in the spec-tree plugin that owns audit-specific orchestration: language-partition dispatch to `audit-{lang}`, `audit-{lang}-tests`, and `audit-{lang}-architecture` skills, aggregation into one wrapper verdict, artifact-type auditor composition, and audit wrapper boundaries. Audit consumes the shared agentic-verification run journal and projection governed by `spx/21-spec-tree.enabler/16-verification.enabler/13-run-journal.adr.md` and `spx/21-spec-tree.enabler/16-verification.enabler/18-journal-projection.enabler`; those shared layers own storage, backend selection, event ordering, streaming, sealing, projection rendering, wrapper-agent shape, and changeset-scope derivation. The generic `/audit` skill dispatches only its three language-partition concerns — implementation, test evidence, and ADR/PDR architecture — and never runs deterministic validation, test, or eval commands, which remain the main agent's changeset responsibility and CI's repository responsibility per `spx/14-verification.pdr.md`. Eval-evidence audits run through the sibling `eval-evidence-auditor` artifact-type wrapper, not as a fourth `/audit` phase.

Every language plugin ships the `audit-{lang}` trio as skills only; no language-specific auditor agent exists. The marketplace's auditor agents are generic and artifact-type-scoped: the `/audit` family (`auditor`, `audit-orchestrator`) for code-and-scope audits, plus `adr-auditor`, `pdr-auditor`, `test-evidence-auditor`, and `eval-evidence-auditor` for decision, test-evidence, and eval-evidence audits. An artifact-type auditor with language-specific concerns composes the matching `audit-{lang}*` skill, partitioned by the language detected in scope. Section structure, atemporal voice, and tag validity for decision records are judged by the artifact-type auditor reading the canonical decision templates; composed `audit-{lang}-architecture` skills carry only language-specific architecture concerns and never re-judge those generic decision-record rules from copied template prose. The audit skill resolves script paths through `${CLAUDE_SKILL_DIR}`; wrapper agents never construct a path into `scripts/`.

## Rationale

The audit-specific decision lives here because neither shared verification nor review decides how audit partitions scope, which language skill names must exist, which artifact-type auditors compose language concerns, or which wrapper agents expose audit surfaces. Keeping those rules in the audit decision leaves the shared run-journal and projection architecture in `spx/21-spec-tree.enabler/16-verification.enabler/` and keeps review free to consume the same architecture with its own policy.

The orchestrator embeds no language-specific knowledge beyond the `audit-{lang}*` dispatch template, so a partial multi-language audit reports the right language without product detection. Validating the language trio at marketplace-validation time makes a missing skill a pre-execution failure. The skill owns policy and the agents are thin wrappers because the skill is the shared behavior surface across Claude Code-authored source and generated Codex output and is the only surface where `${CLAUDE_SKILL_DIR}` resolves.

## Verification

### Testing

- ALWAYS: the consumer-side adapter maps audit run metadata and each streamed child verdict onto journal events whose terminal completion event carries the core journal run-state identity — branch name, branch slug, head SHA, base ref, base SHA, config digest, participants, path-filter scope, timestamps, and output paths — and whose rolled-up overall equals the verdict toolchain's rollup over the corresponding wrapper; a failing or rejecting row or child yields a rejecting run, an unknown row or child absent any rejection yields an unknown run with a core terminal status of `failed`, and an all-passing wrapper yields an approved run, so streaming the verdict through the journal never changes its verdict outcome and still produces terminal evidence the `spx journal` fold can key by head/base identity ([test](tests/test_audit_journal_emit.mapping.l1.py))
- Given a regenerated or re-severitied finding with the same `(file, line, rule, message)` tuple as a prior finding, when the consumer-side resolved-and-reopened projection computes finding identity, then the finding matches its prior counterpart by content, excluding any assigned id and severity ([scenario](68-audit.enabler/tests/test_auditing.scenario.l1.py))
- ALWAYS: a regression — the same finding content returning after a resolved-then-reopened cycle across the run set — is reported as reopened rather than as a new finding ([compliance])

### Audit

- ALWAYS: the `/audit` skill and the `auditor` and `audit-orchestrator` agents contain zero language-specific tokens beyond the dispatch template `audit-{lang}*` ([audit])
- ALWAYS: every marketplace plugin that defines a programming language ships `audit-{lang}`, `audit-{lang}-tests`, and `audit-{lang}-architecture` ([audit])
- ALWAYS: the marketplace's auditor agents are generic and artifact-type-scoped — the `/audit` family plus `adr-auditor`, `pdr-auditor`, `test-evidence-auditor`, and `eval-evidence-auditor`; language audits ship as `audit-{lang}*` skills with no language-specific auditor agent ([audit])
- ALWAYS: an artifact-type auditor with language-specific concerns composes them by invoking the matching `audit-{lang}*` skill, partitioned by the language detected in scope ([audit])
- ALWAYS: section structure, atemporal voice, and tag validity for a decision record are judged by the artifact-type auditor reading the canonical decision template; the composed `audit-{lang}-architecture` skill carries only language-specific concerns ([audit])
- ALWAYS: the audit wrapper agents reach the audit policy and the audit journal only by invoking the `/audit` skill; review agents reach review policy and the review journal only by invoking the `review-changes` skill ([audit])
- ALWAYS: the main conversation reaches a generic audit only by dispatching an audit wrapper agent — the dispatched agent's isolated context produces the verdict, per `spx/14-verification.pdr.md` ([audit])
- ALWAYS: the `/audit` skill partitions multi-language scopes by file extension and runs the orchestration protocol once per language partition ([audit])
- NEVER: the `/audit` skill runs the project's validation or test commands (or any deterministic verification) — it dispatches only the agentic concern audits, the main agent having passed deterministic verification on the changeset before dispatch and CI re-running it over the whole repository, per `spx/14-verification.pdr.md` ([audit])
- NEVER: a language-specific auditor agent (`{lang}-architecture-auditor`, `{lang}-code-auditor`, `{lang}-test-auditor`) exists — language concerns reach an audit through the composed `audit-{lang}*` skill, not a per-language agent ([audit])
- NEVER: an audit skill judges decision-record section structure, voice, or tag validity from a transcribed copy of the canonical template — the copy drifts from and contradicts the template ([audit])
- NEVER: the main conversation invokes the `/audit` skill in place to produce a verdict — the isolated wrapper-agent context, not the main conversation, is where an audit runs ([audit])
- NEVER: introduce language-specific examples, file extensions, validation commands, test commands, or evidence patterns into the `/audit` skill or the audit wrapper agents — that content belongs in the corresponding `audit-{lang}*` skill ([audit])
- NEVER: ship per-language audit-orchestration skills or agents such as `typescript-audit-orchestrator` — the generic skill serves every language by dispatch ([audit])
- NEVER: embed deterministic shell pipelines (git diff, base-ref detection, scope partitioning) directly in the wrapper agent prompts — the `/audit` skill prose owns these pipelines ([audit])
- NEVER: reference `scripts/` from an agent prompt by `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_SKILL_DIR}`, or a hard-coded relative path — neither variable is substituted in an agent prompt body ([audit])
- NEVER: add a per-skill self-description block to `audit-{lang}*` skills declaring file globs, configs, gate commands, or test commands — the dispatch contract is the skill name ([audit])
- NEVER: place the consumer-side projection helper at a plugin-root location — the marketplace co-locates Python under the consuming skill ([audit])
