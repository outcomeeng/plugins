# Auditing Architecture

## Purpose

This decision governs the architecture of audit orchestration in the marketplace — how the generic `/auditing` skill dispatches to language-specific audit skills, how the agent wrappers (`auditor`, `audit-orchestrator`, `pr-reviewer`, `pr-review-orchestrator`) relay and combine its verdict, where the supporting deterministic computations live, where stateful agents persist their working set (worktree-local for the local agent, in the PR comment thread for the CI orchestrator), and which naming patterns the dispatch model requires across plugins.

## Context

**Business impact:** Audit orchestration runs the audit-skill family on TypeScript, Python, Rust, and any future language plugin, locally and in CI. Without a uniform pattern, each language plugin grows its own orchestrator that drifts in protocol, embeds language-specific knowledge in the wrong place, and duplicates the determinism contract (frozen scope, scope hash, frozen concerns, frozen findings). Audit verdicts become incomparable across languages; bug fixes in one orchestrator do not propagate to the others; and the cost of adding a new language scales linearly rather than as a no-op. A second failure mode appears when agent wrappers reach into the skill's `scripts/` directory by path: an agent prompt — unlike skill content — has neither `${CLAUDE_SKILL_DIR}` nor `${CLAUDE_PLUGIN_ROOT}` substituted, so a path expression in an agent prompt resolves to nothing and the helper invocation silently fails.

**Technical constraints:** The marketplace has a precedent for generic-to-language-specific dispatch: `spx/21-spec-tree.enabler/65-applying.enabler/` defines `/applying`, which detects language by project-file presence and dispatches to `coding-{lang}` and `testing-{lang}` via a hardcoded skill map. LLMs running an orchestrator skill cannot reliably execute deterministic shell computations in-process — base-ref detection, git diff parsing, scope hashing all need a Python helper module. Plugin consumers do not receive `outcomeeng/scripts/`; that path is repo-internal marketplace tooling. Plugins ship their Python helpers strictly co-located with the skill that consumes them — every existing Python file in `plugins/` lives under a specific skill's `scripts/` or `references/` directory (see `spx/13-plugin-and-runtime-conventions.adr.md`). And `${CLAUDE_SKILL_DIR}` is substituted only in skill content (SKILL.md and its `!`-injection lines), `${CLAUDE_PLUGIN_ROOT}` only in hook command fields and MCP server configs — neither is substituted in an agent definition's prompt body, and neither is exported to the Bash tool in a normal session.

## Decision

The marketplace ships a single generic `/auditing` skill in the spec-tree plugin that owns the audit policy: the six-phase run, language-partition dispatch to `auditing-{lang}*` skills via template substitution from the language detected in scope, aggregation, and JSON-verdict emission through the verdict toolchain. Agent wrappers hold no audit policy of their own and invoke nothing the skill does not already resolve: the `auditor` agent runs `/auditing` as a one-off and forwards the caller's requested surface form to the skill; the `audit-orchestrator` agent runs `/auditing` once per commit and drives the state machinery through the same skill so finding identities, regressions, and resolutions carry across runs; the `pr-reviewer` agent runs `/auditing` alongside the established PR-review prompt (wrapped as a skill) and posts one combined comment. Every language plugin MUST ship `auditing-{lang}`, `auditing-{lang}-tests`, and `auditing-{lang}-architecture`. The deterministic git and scope computations the skill's Phase 0 depends on — base-ref detection, branch-scope enumeration, diff-range expansion, scope hashing — plus the stateful helpers used by `audit-orchestrator` (file-based `RunLock`, `AuditState` persistence, monotonic finding-ID assignment, regression detection via `(file_line, root_cause)` identity, and the composed `state_transition` operation) live in a Python helper module co-located with the `/auditing` skill at `plugins/spec-tree/skills/auditing/scripts/audit_orchestrator.py`. The same module exposes a stdlib `argparse` CLI (`base-ref`, `current-branch`, `branch-slug`, `scope-hash`, `branch-scope`, `modified-since`, `sha-reachable`, `acquire-lock`, `release-lock`, `state-transition`) so the skill can drive every helper from shell. The canonical verdict schema and rollup live in the sibling `verdict.py`, and the surface-rendering toolchain in `emit_verdict.py` / `read_verdict.py` / `aggregate_verdicts.py`. The skill resolves those paths via `${CLAUDE_SKILL_DIR}`; agents never construct a path into `scripts/`.

Stateful agents partition their working set under `.spx/audits/<lang>/<branch-slug>.md` in the worktree, with the lock file living at `<state-file>.lock`. The `.spx/` root is gitignored so audit state is local development scratch — not product truth — and never enters the commit history. The state file carries one frontmatter block plus two markdown tables (`## Open findings`, `## Resolved findings`); `save_state` writes through `<state-file>.tmp` + `os.replace` so a crash mid-write leaves the prior state intact. The lock contract is TTL-bounded: a lock with mtime inside the configured TTL refuses concurrent acquisition, and a lock older than the TTL is treated as stale (left by a crashed run) and overwritten. `RunLock`'s context manager removes the lock on every exit path so a crashed run does not block the next run for a full TTL window.

The `pr-review-orchestrator` agent uses a different state surface: the pull-request comment thread itself. The `/auditing` skill exposes two PR-thread modes (`MODE: prior-verdict-read` and `MODE: with-prior-verdict`) keyed on an explicit `MODE:` line — drift in calling-agent wording surfaces as an error rather than as silent default. `MODE: prior-verdict-read` finds the most recent comment on the target PR carrying the `<!-- AUDIT_VERDICT_JSON_BEGIN -->` delimiter, extracts the JSON via `read_verdict.py`, and returns the parsed prior verdict (or a no-prior marker for first runs). `MODE: with-prior-verdict` runs the standard six-phase audit, then drives `audit_orchestrator.py verdict-diff` to populate the wrapper verdict's `resolved` and `reopened` arrays by content identity `(file, line, rule, message)`. The orchestrator supersedes the prior audit comment (edit-last when possible, post + delete otherwise) so the thread carries exactly one delimiter-bearing audit comment per agent at any time. PR-thread mode never writes to `.spx/audits/`; the worktree-local state surface belongs exclusively to the local `audit-orchestrator` agent.

## Rationale

The factoring rule that the orchestrator never embeds language-specific knowledge follows directly from `/applying`'s working precedent. `/applying` detects language by project-file presence and dispatches to `{verb}-{lang}` skills; the generic skill itself contains zero language-specific tokens beyond the dispatch template. `/auditing` adopts the same model with one refinement appropriate to its scope: where `/applying` operates on a whole TDD flow rooted in a project, `/auditing` operates on a frozen file list (the audit scope), so language detection happens at scope-partition time rather than at project-detection time. The LLM running the orchestrator reads the file extensions in scope (`*.ts`, `*.tsx`, `*.py`, `*.rs`), partitions by language, and runs the orchestration loop once per partition. No detection helper or required argument is needed — file-extension recognition is trivial training-time knowledge for any LLM that can run the orchestrator at all.

The naming convention as a hard invariant follows from the dispatch model. Template substitution requires that `auditing-{lang}` resolve to a real skill; any missing skill in the trio halts the orchestrator mid-audit with an error the caller cannot work around. Validating the trio at marketplace-validation time rather than at first-audit time makes the failure mode loud and immediate.

The skill-owns-policy / agents-are-wrappers split exists because the skill is the only surface both runtimes share. Codex and Claude Code both invoke skills; agent definitions are a Claude Code construct, and even there an agent prompt body does not get the `${CLAUDE_SKILL_DIR}` substitution that skill content gets. An agent that reached into `scripts/` by path would therefore work nowhere — not on Codex (no agents), not on Claude Code (no substitution in the prompt body). So the agents carry no policy: `auditor` and `pr-reviewer` invoke `/auditing` (and, for `pr-reviewer`, the review-prompt skill), and the skill — which can resolve `${CLAUDE_SKILL_DIR}` — runs every `scripts/` invocation. The agent's only job is to relay the rendered output (`auditor`) or to combine the audit verdict with the review prose into one PR comment (`pr-reviewer`). Naming the bare audit-runner `auditor` parallels `/applying` and `applier`; `pr-reviewer` is review-flavoured because the audit sits inside the PR review surface.

The Python helper module's placement under the `/auditing` skill's `scripts/` directory follows the marketplace-wide co-location convention. Every existing Python file in `plugins/` lives under a specific skill: excalidraw's `references/render_excalidraw.py` (with its own `pyproject.toml`), creating-skills' `scripts/init_skill.py`, github-actions' `scripts/workflow_inspect.py`. None lives at plugin root. The `/auditing` skill is the helper module's exclusive consumer; co-location matches the consumer, mirrors precedent, and avoids inventing a new "shared infrastructure" plugin-root convention solely to host one module.

Alternatives considered:

- **Per-language orchestration skills and agents** (`typescript-audit-orchestrator`, `python-audit-orchestrator`, `rust-audit-orchestrator`). Rejected: the protocol is identical across languages; per-language wrappers duplicate it and drift. Language-specific content accumulates in the wrapper instead of in the corresponding `auditing-{lang}*` skill, and bug fixes to the protocol must be ported across every wrapper rather than landing once.
- **Audit-skill self-description block** declaring file globs, configs, gate command, test command. Rejected: `/applying` works without one. The dispatch contract is the skill name, not the skill's metadata. Adding a descriptor pattern would create a new authoring obligation for every language audit skill that solves a problem the dispatch does not have.
- **Agents invoke `audit_orchestrator.py` directly** via `${CLAUDE_PLUGIN_ROOT}/skills/auditing/scripts/...`. Rejected: `${CLAUDE_PLUGIN_ROOT}` is not substituted in an agent prompt body and is not a Bash environment variable in a normal session, so the path resolves to nothing; the invocation fails on first use. Routing the script invocations through the `/auditing` skill — which does get `${CLAUDE_SKILL_DIR}` substituted — is the only resolution that works on both runtimes.
- **Plugin-root Python scripts** (`plugins/spec-tree/scripts/audit_orchestrator.py`). Rejected: contradicts every existing precedent in the marketplace. Would require establishing "shared infrastructure scripts at plugin root" as a new convention solely to host one helper module.
- **Project-file detection like `/applying`** (`tsconfig.json` → TypeScript) instead of scope-extension partitioning. Rejected for `/auditing`'s use case: an audit may be invoked on a strict subset of a multi-language repo; project-file detection at the repo level reports the wrong language for partial audits. Scope-extension partitioning correctly identifies the language under audit and naturally handles mixed scopes by running the audit once per language partition.

## Trade-offs accepted

| Trade-off                                                                                                    | Mitigation / reasoning                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Language plugins MUST ship the auditing-{lang}* trio or the orchestrator halts mid-audit                     | Marketplace validation pipeline enforces the trio at install/check time; failure is loud and pre-runtime rather than mid-audit                                                                                                                                      |
| LLM extension partitioning relies on the orchestrator's LLM correctly recognizing file extensions            | File extensions are unambiguous training-time knowledge; the orchestrator already reads the scope in Phase 0 to compute the scope hash, so partitioning adds no new I/O                                                                                             |
| Helper module is co-located with the consumer skill rather than reusable across other spec-tree concerns     | The `/auditing` skill is its sole consumer today; if a second consumer appears, the module migrates to a shared location at that time rather than speculatively                                                                                                     |
| Agents carry no audit policy, so adding a new agent-level behaviour means extending the skill, not the agent | The skill is the only surface both runtimes share and the only place `${CLAUDE_SKILL_DIR}` resolves; concentrating policy there keeps the agents thin and portable                                                                                                  |
| Mixed-language scopes still require per-language audit dispatch                                              | The orchestrator dispatches one `auditing-{lang}*` per partition, collects each verdict, and aggregates via `aggregate_verdicts.py` into one wrapper verdict whose `children` array carries the per-language verdicts; rollup logic lives once in `verdict.roll_up` |

## Compliance

### Recognized by

The spec-tree plugin ships exactly one orchestration skill (`/auditing`) that embeds no language-specific tokens beyond the dispatch template `auditing-{lang}*`, and the agent wrappers (`auditor`, `audit-orchestrator`, `pr-reviewer`, `pr-review-orchestrator`) that hold no audit policy. Each language plugin ships exactly the trio `auditing-{lang}`, `auditing-{lang}-tests`, `auditing-{lang}-architecture`. The `/auditing` skill's `scripts/` directory owns the deterministic git/scope helpers, the state-machinery helpers, the verdict-diff helper, and the CLI exposed by `audit_orchestrator.py`, plus the verdict toolchain (`verdict.py`, `emit_verdict.py`, `read_verdict.py`, `aggregate_verdicts.py`); the skill references those by `${CLAUDE_SKILL_DIR}/scripts/...`, and no agent prompt contains a path into `scripts/`. Worktree-local audit state for the local `audit-orchestrator` agent lives under `.spx/audits/<lang>/<branch-slug>.md` with the lock at `<state-file>.lock`; `.spx/` is gitignored and never committed. CI-side audit state for the `pr-review-orchestrator` agent lives in the pull-request comment thread, recovered each run by `read_verdict.py` matching the `<!-- AUDIT_VERDICT_JSON_BEGIN -->` delimiter; PR-thread state never touches `.spx/audits/`.

### MUST

- The `/auditing` skill and the `auditor`, `audit-orchestrator`, `pr-reviewer`, and `pr-review-orchestrator` agents contain zero language-specific tokens beyond the dispatch template `auditing-{lang}*` — prevents the language-leakage failure mode where per-language wrappers absorb content that belongs in the corresponding `auditing-{lang}*` skill; the orchestrator is dispatch, not domain knowledge ([review])
- Every marketplace plugin that defines a programming language ships `auditing-{lang}`, `auditing-{lang}-tests`, and `auditing-{lang}-architecture` — the orchestrator's dispatch is template substitution; the trio's existence is the contract that makes dispatch resolvable ([review])
- The deterministic git, scope, lock, and state-transition computations invoked during an audit run live in `plugins/spec-tree/skills/auditing/scripts/audit_orchestrator.py` and the canonical verdict schema and rollup live in the sibling `verdict.py` — LLMs cannot reliably run git plumbing, hash scopes, manage file locks, or maintain finding-ID monotonicity in-process, and the verdict contract must validate against one shared schema; these modules are the boundaries that make the computations testable ([review])
- The `auditor`, `audit-orchestrator`, `pr-reviewer`, and `pr-review-orchestrator` agents reach the audit policy, the `scripts/` toolchain, and the `audit_orchestrator.py` CLI only by invoking the `/auditing` skill (and, for `pr-reviewer`, the review-prompt skill) — the skill resolves `${CLAUDE_SKILL_DIR}`, which an agent prompt cannot, so the skill is the only surface that can drive the scripts on both runtimes ([review])
- The `/auditing` skill partitions multi-language scopes by file extension and runs the orchestration protocol once per language partition — handles mixed-language repos without requiring callers to filter the scope and without halting on plurality ([review])
- The `audit-orchestrator` agent persists its working set under `.spx/audits/<lang>/<branch-slug>.md` and acquires `<state-file>.lock` before reading or writing state — partitioning by language and branch slug keeps state stable across runs, and the lock prevents concurrent runs on the same partition from corrupting each other's state file ([review])
- `save_state` writes the state file atomically (`<state-file>.tmp` plus `os.replace`) and `RunLock` releases its lock on every context-manager exit path including exceptions — atomicity protects the file across crashes; lock release on exception protects the next run from a full TTL wait after a failed predecessor ([test](../21-spec-tree.enabler/68-auditing.enabler/tests/test_auditing.scenario.l1.py))
- A regression — the same `(file_line, root_cause)` returning after a resolved-then-reopened cycle — reopens the original finding ID and does NOT advance `next_finding_id` — preserves cross-run referential identity so external comments and notes that reference a finding ID continue to resolve to the same defect across runs ([test](../21-spec-tree.enabler/68-auditing.enabler/tests/test_auditing.scenario.l1.py))
- The `pr-review-orchestrator` agent persists no on-disk audit state — its durable cross-CI-run surface is the PR comment thread, recovered each run by `read_verdict.py` matching the `<!-- AUDIT_VERDICT_JSON_BEGIN -->` delimiter; CI runners that exit between iterations preserve no state outside the PR thread itself ([review])
- `compute_verdict_diff` keys finding identity on the tuple `(file, line, rule, message)` — `id` and `severity` are excluded so a regenerated finding with a fresh producer-assigned ID, or one whose severity is upgraded or downgraded across runs, matches its prior counterpart by content rather than by accident-of-numbering ([test](../21-spec-tree.enabler/68-auditing.enabler/tests/test_auditing.scenario.l1.py))

### NEVER

- Introduce language-specific examples, file extensions, validation commands, test commands, failure-mode prose, or evidence patterns into the `/auditing` skill or the `auditor`, `audit-orchestrator`, `pr-reviewer`, or `pr-review-orchestrator` agents — that content belongs in the corresponding `auditing-{lang}*` skill; cross-cutting placement is the failure mode this ADR exists to prevent ([review])
- Ship per-language audit-orchestration skills or agents such as `typescript-audit-orchestrator` or `python-audit-orchestrator` — the generic skill serves every language by dispatch; per-language wrappers reintroduce the duplication and drift this decision rejects ([review])
- Embed deterministic shell pipelines (git diff, base-ref detection, scope hashing, lock acquisition, state transition, verdict diffing) directly in the `auditor`, `audit-orchestrator`, `pr-reviewer`, or `pr-review-orchestrator` agent prompts — inline shell in agent prompts relies on Bash invocation discipline LLMs cannot guarantee, and the agents have no path-substitution surface to reach the helper module; the `/auditing` skill prose owns these pipelines because it is the only surface that resolves `${CLAUDE_SKILL_DIR}` ([review])
- Reference `plugins/.../scripts/` from an agent prompt by `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_SKILL_DIR}`, or a hard-coded relative path — neither variable is substituted in an agent prompt body and neither is a Bash environment variable, so the path resolves to nothing; agents reach `scripts/` (and the `audit_orchestrator.py` CLI) only by invoking a skill that resolves the path ([review])
- Add a per-skill self-description block (YAML, XML, or otherwise) to `auditing-{lang}*` skills declaring file globs, configuration files, gate commands, or test commands — the `/auditing` skill's dispatch contract is the skill name; metadata blocks add an authoring surface that solves no dispatch problem ([review])
- Place the audit-orchestrator Python helper module at `plugins/spec-tree/scripts/` or any other plugin-root location — the marketplace co-locates Python under the consuming skill (see `spx/13-plugin-and-runtime-conventions.adr.md`); plugin-root scripts are not an established convention ([review])
- Persist audit state inside `spx/` or any other tracked product directory — the durable map is product truth; the only sanctioned audit-state surfaces are the worktree-local `.spx/audits/` partition (for the local `audit-orchestrator` agent) and the PR comment thread (for the CI-side `pr-review-orchestrator` agent) ([review])
- Write to `.spx/audits/` when running `/auditing` in either PR-thread mode (`MODE: prior-verdict-read` or `MODE: with-prior-verdict`) — the PR-thread state surface is the PR comment thread itself; cross-pollinating the worktree-local state file with CI-side runs corrupts the local agent's open/resolved tracking ([review])
- Reissue a finding ID once it has been assigned — `next_finding_id` strictly exceeds every ID ever allocated on the branch (open and resolved) so a regression reopens its original ID rather than seeing a duplicate allocation; reuse would break cross-run referential identity ([review])
