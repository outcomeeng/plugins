# Auditing Architecture

The marketplace ships a single generic `/audit` skill in the spec-tree plugin that owns the audit policy — language-partition dispatch to `audit-{lang}*` skills via template substitution from the language detected in scope, aggregation, and the run's record. The audit dispatches only the agentic concern audits — implementation, test evidence, and ADR/PDR architecture — and never runs the project's validation or test commands: deterministic verification (validate, test, evaluate) is the main agent's responsibility on the changeset before it dispatches the audit, and CI's over the whole repository, per `spx/14-verification.pdr.md`. Every audit run is one `spx journal` run on the append-only run-journal channel of `spx/21-spec-tree.enabler/16-verification.enabler/13-run-journal.adr.md` under audit's opaque verification-type segment: the skill opens a run, appends domain events as the run advances — scope entered, gate evaluated, finding reported, partition completed, run completed — and seals it, and the journal is the run's sole source of truth. Every audit surface — the markdown report, the pull-request comment, the findings JSON, the check summary, the resolved-and-reopened rollup across a run set — is a projection of the journal's event prefix computed consumer-side: the channel's render returns the event prefix unchanged and the type-agnostic channel carries no verification-kind-specific rendered surface, so the verdict rollup and the human-readable surface are rendered by a consumer-side projection rather than by the channel. The skill addresses the journal through the one backend-neutral channel and hard-codes no storage path, backend, or surface; backend selection is bound at the edge — a local run-journal file on a developer machine, the pull-request backend under CI — and is swappable without changing the skill. The agent wrappers hold no audit policy and invoke nothing the skill does not resolve: `auditor` runs `/audit` once and forwards the caller's requested surface form; `audit-orchestrator` runs it once per commit and carries open and resolved findings across commits as a projection over the run set; `pr-reviewer` runs it alongside the review-prompt skill and posts one combined comment; `pr-review-orchestrator` runs it against the PR diff and supersedes the prior audit on the pull-request thread. Every language plugin ships `audit-{lang}`, `audit-{lang}-tests`, and `audit-{lang}-architecture` as skills only — no language-specific auditor agent exists. The marketplace's auditor agents are generic and artifact-type-scoped: the `/audit` family (`auditor`, `audit-orchestrator`, `pr-reviewer`, `pr-review-orchestrator`) for code-and-scope audits, and `adr-auditor`, `pdr-auditor`, and `test-evidence-auditor` for decision and test-evidence audits. An artifact-type auditor that has language-specific concerns composes them by invoking the matching `audit-{lang}*` skill, partitioned by the language detected in scope — the same dispatch the `/audit` skill performs. Section structure, atemporal voice, and tag validity for a decision record are owned by the artifact-type auditor reading the canonical decision template from the understanding skill (`spx/21-spec-tree.enabler/21-templates.enabler`); the composed `audit-{lang}-architecture` skill carries only language-specific concerns (dependency-injection mandates, mocking prohibitions, execution-level accuracy) and never re-judges section structure, voice, or tag validity from a transcribed copy of the template. The shared git-derivation primitives — base-ref detection, current-branch detection, branch-scope, diff-range expansion, and slug — live in the changeset-scope skill's `changeset_scope.py` per `spx/21-spec-tree.enabler/14-version-control.enabler/15-changeset-scope.enabler/13-changeset-derivation.adr.md`; the `/audit` skill consumes the shared consumer-side projection governed by `spx/21-spec-tree.enabler/16-verification.enabler/18-journal-projection.enabler` — building its journal event inputs from a run's results and rendering its rollup and human-readable surface from the event prefix — rather than re-implementing that projection, which the run-journal architecture declares shared across audit and review. The skill resolves script paths via `${CLAUDE_SKILL_DIR}`, and agents never construct a path into `scripts/`. The journal is the run's durable state on every backend — a local audit streams to the local run-journal file the channel binds and a CI audit streams to the pull-request backend — so no audit writes a separate `.spx/audits` state file, holds a state-file lock, or recovers prior state by parsing a delimiter from a rendered comment.

## Rationale

The orchestrator embeds no language-specific knowledge, following the working precedent of `/apply`, which dispatches to `{verb}-{lang}` skills and contains zero language tokens beyond the dispatch template; `/audit` partitions by file extension at scope-partition time rather than project-detection time so a partial multi-language audit reports the right language. The naming convention is a hard invariant because template substitution requires `audit-{lang}` to resolve, and validating the trio at marketplace-validation time makes a missing skill a loud pre-execution failure. The skill owns policy and the agents are thin wrappers because the skill is the shared surface across Claude Code-authored source and generated Codex output and is the only surface where the generated skill-directory token resolves — an agent prompt body receives neither `${CLAUDE_SKILL_DIR}` nor `${CLAUDE_PLUGIN_ROOT}`, so an agent that reached into `scripts/` by path would work nowhere.

The journal is the run's single source of truth because a contract phrased in append, read, cursor, seal, and render survives backend substitution: the same audit is observable in the same shape whether it streams to a local file or a pull-request comment, and the channel's append and seal return an exit code that keeps record validity a deterministic signal rather than a second model judgment over the events the model just produced. Separating the canonical event history from its projections keeps a mutable, size-bounded display surface from contaminating the run's source of truth, and the channel's render returning the event prefix unchanged is deliberate — a verification-kind-specific rendered surface cannot live in a type-agnostic channel, so the rollup and the human-readable surface are consumer-side projections, pure functions of the event prefix that the consumer computes. The consumer-side projection is a shared primitive governed by `spx/21-spec-tree.enabler/16-verification.enabler/18-journal-projection.enabler` and consumed by `/audit` rather than re-implemented in it, because the run-journal architecture is declared shared across audit and review; a shared primitive lives in one home both consumers import, as the git-derivation primitives shared with the review-changes and manage-thread-store skills do in their changeset-scope home. Routing durable state through the channel rather than a separate `.spx/audits` state file, a state-file lock, and a pull-request-comment-as-database recovery removes a second state model that drifts from the journal and a delimiter-parse recovery that reads authoritative state from a rendered surface; the channel owns concurrency and persistence on each backend. Per-language orchestration wrappers, a skill self-description block, and agents invoking the helper or the channel directly are rejected because each reintroduces the duplication, the authoring obligation, or the unresolved-path failure this decision exists to prevent.

## Verification

### Testing

- ALWAYS: the consumer-side adapter maps an audit wrapper verdict onto journal events whose terminal completion event carries the core journal run-state identity from the wrapper metadata — branch name, branch slug, head SHA, base ref, base SHA, config digest, participants, path-filter scope, timestamps, and output paths — and whose rolled-up overall equals the verdict toolchain's rollup over that wrapper; a failing or rejecting row or child yields a rejecting run, an unknown row or child absent any rejection yields an unknown run with a core terminal status of `failed`, and an all-passing wrapper yields an approved run, so routing the verdict through the journal never changes its verdict outcome and still produces terminal evidence the `spx journal` fold can key by head/base identity ([test](tests/test_audit_journal_emit.mapping.l1.py))
- ALWAYS: the consumer-side resolved-and-reopened projection keys finding identity on the tuple `(file, line, rule, message)`, excluding any assigned id and severity so a regenerated or re-severitied finding matches its prior counterpart by content ([property])
- ALWAYS: a regression — the same finding content returning after a resolved-then-reopened cycle across the run set — is reported as reopened rather than as a new finding ([compliance])

### Audit

- ALWAYS: every audit run is one `spx journal` run under audit's verification-type segment, opened, appended to as the run advances, and sealed, with the journal as the run's sole source of truth ([audit])
- ALWAYS: every audit surface — markdown report, pull-request comment, findings JSON, check summary, resolved-and-reopened rollup — is a projection of the journal's event prefix, computed consumer-side ([audit])
- ALWAYS: the verdict rollup and the human-readable surface are rendered by a consumer-side projection, never read back as channel-rendered output — the channel's render returns the event prefix unchanged ([audit])
- ALWAYS: the `/audit` skill and the wrapper agents address the journal through the one backend-neutral channel and hard-code no storage path, backend, or surface — backend selection is bound at the edge and swappable without changing them ([audit])
- ALWAYS: the `/audit` skill consumes the shared consumer-side projection governed by `spx/21-spec-tree.enabler/16-verification.enabler/18-journal-projection.enabler` to build journal event inputs and render the rollup, rather than re-implementing event construction, rollup, or rendering ([audit])
- ALWAYS: the `/audit` skill and the `auditor`, `audit-orchestrator`, `pr-reviewer`, and `pr-review-orchestrator` agents contain zero language-specific tokens beyond the dispatch template `audit-{lang}*` ([audit])
- ALWAYS: every marketplace plugin that defines a programming language ships `audit-{lang}`, `audit-{lang}-tests`, and `audit-{lang}-architecture` ([audit])
- ALWAYS: the marketplace's auditor agents are generic and artifact-type-scoped — the `/audit` family plus `adr-auditor`, `pdr-auditor`, and `test-evidence-auditor`; language audits ship as `audit-{lang}*` skills with no language-specific auditor agent ([audit])
- ALWAYS: an artifact-type auditor with language-specific concerns composes them by invoking the matching `audit-{lang}*` skill, partitioned by the language detected in scope ([audit])
- ALWAYS: section structure, atemporal voice, and tag validity for a decision record are judged by the artifact-type auditor reading the canonical decision template; the composed `audit-{lang}-architecture` skill carries only language-specific concerns ([audit])
- ALWAYS: the audit run's record validity is the channel's append and seal exit code, never a second model judgment over the events the run just produced ([audit])
- ALWAYS: the four wrapper agents reach the audit policy and the journal only by invoking the `/audit` skill (and, for `pr-reviewer`, the review-prompt skill) ([audit])
- ALWAYS: the main conversation reaches a generic audit only by dispatching one of the four wrapper agents — the dispatched agent's isolated context produces the verdict, per `spx/14-verification.pdr.md` ([audit])
- ALWAYS: the `/audit` skill partitions multi-language scopes by file extension and runs the orchestration protocol once per language partition ([audit])
- NEVER: the `/audit` skill runs the project's validation or test commands (or any deterministic verification) — it dispatches only the agentic concern audits, the main agent having passed deterministic verification on the changeset before dispatch and CI re-running it over the whole repository, per `spx/14-verification.pdr.md` ([audit])
- ALWAYS: the `audit-orchestrator` agent carries open and resolved findings across commits as a projection over the run set on the journal, and the `pr-review-orchestrator` agent supersedes the prior audit on the pull-request thread, both reading prior state from the journal rather than from a separate state file or a rendered comment ([audit])
- NEVER: an audit writes a separate `.spx/audits` state file, holds a state-file lock, or recovers prior state by parsing a delimiter from a rendered comment — the channel owns persistence and concurrency on each backend ([audit])
- NEVER: a language-specific auditor agent (`{lang}-architecture-auditor`, `{lang}-code-auditor`, `{lang}-test-auditor`) exists — language concerns reach an audit through the composed `audit-{lang}*` skill, not a per-language agent ([audit])
- NEVER: an audit skill judges decision-record section structure, voice, or tag validity from a transcribed copy of the canonical template — the copy drifts from and contradicts the template ([audit])
- NEVER: the main conversation invokes the `/audit` skill in place to produce a verdict — the isolated wrapper-agent context, not the main conversation, is where an audit runs ([audit])
- NEVER: introduce language-specific examples, file extensions, validation commands, test commands, or evidence patterns into the `/audit` skill or the four wrapper agents — that content belongs in the corresponding `audit-{lang}*` skill ([audit])
- NEVER: ship per-language audit-orchestration skills or agents such as `typescript-audit-orchestrator` — the generic skill serves every language by dispatch ([audit])
- NEVER: embed deterministic shell pipelines (git diff, base-ref detection, scope partitioning) directly in the wrapper agent prompts — the `/audit` skill prose owns these pipelines ([audit])
- NEVER: reference `scripts/` from an agent prompt by `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_SKILL_DIR}`, or a hard-coded relative path — neither variable is substituted in an agent prompt body ([audit])
- NEVER: add a per-skill self-description block to `audit-{lang}*` skills declaring file globs, configs, gate commands, or test commands — the dispatch contract is the skill name ([audit])
- NEVER: place the consumer-side projection helper at a plugin-root location — the marketplace co-locates Python under the consuming skill ([audit])
