# Auditing Architecture

The marketplace ships a single generic `/auditing` skill in the spec-tree plugin that owns the audit policy — the six-phase run, language-partition dispatch to `auditing-{lang}*` skills via template substitution from the language detected in scope, aggregation, and JSON-verdict emission through the verdict toolchain. The agent wrappers hold no audit policy and invoke nothing the skill does not resolve: `auditor` runs `/auditing` once and forwards the caller's requested surface form; `audit-orchestrator` runs it once per commit and drives the state machinery through the skill; `pr-reviewer` runs it alongside the review-prompt skill and posts one combined comment; `pr-review-orchestrator` runs it against the PR diff and supersedes the prior audit comment in the PR thread. Every language plugin ships `auditing-{lang}`, `auditing-{lang}-tests`, and `auditing-{lang}-architecture`. The deterministic git, scope, lock, and state-transition helpers live in `plugins/spec-tree/skills/auditing/scripts/audit_orchestrator.py`, with the canonical verdict schema and rollup in the sibling `verdict.py` and the surface toolchain in `emit_verdict.py` / `read_verdict.py` / `aggregate_verdicts.py`; the skill resolves those paths via `${CLAUDE_SKILL_DIR}`, and agents never construct a path into `scripts/`. Worktree-local audit state for the local `audit-orchestrator` lives under `.spx/audits/<lang>/<branch-slug>.md` with the lock at `<state-file>.lock` (`.spx/` is gitignored); CI-side state for `pr-review-orchestrator` lives in the pull-request comment thread.

## Rationale

The orchestrator embeds no language-specific knowledge, following the working precedent of `/applying`, which dispatches to `{verb}-{lang}` skills and contains zero language tokens beyond the dispatch template; `/auditing` partitions by file extension at scope-partition time rather than project-detection time so a partial multi-language audit reports the right language. The naming convention is a hard invariant because template substitution requires `auditing-{lang}` to resolve, and validating the trio at marketplace-validation time makes a missing skill a loud pre-execution failure. The skill owns policy and the agents are thin wrappers because the skill is the shared surface across Claude Code-authored source and generated Codex output and is the only surface where the generated skill-directory token resolves — an agent prompt body receives neither `${CLAUDE_SKILL_DIR}` nor `${CLAUDE_PLUGIN_ROOT}`, so an agent that reached into `scripts/` by path would work nowhere. The helper module is co-located under the consuming skill because every Python file in `plugins/` lives under a specific skill, not at plugin root. Per-language orchestration wrappers, a skill self-description block, and agents invoking the helper directly are rejected because each reintroduces the duplication, the authoring obligation, or the unresolved-path failure this decision exists to prevent.

## Verification

### Testing

- ALWAYS: `save_state` writes the state file atomically (`<state-file>.tmp` plus `os.replace`) and `RunLock` releases its lock on every context-manager exit path including exceptions ([compliance])
- ALWAYS: a regression — the same `(file_line, root_cause)` returning after a resolved-then-reopened cycle — reopens the original finding ID and does not advance `next_finding_id` ([scenario])
- ALWAYS: `compute_verdict_diff` keys finding identity on the tuple `(file, line, rule, message)`, excluding `id` and `severity` so a regenerated or re-severitied finding matches its prior counterpart by content ([property])

### Audit

- ALWAYS: the `/auditing` skill and the `auditor`, `audit-orchestrator`, `pr-reviewer`, and `pr-review-orchestrator` agents contain zero language-specific tokens beyond the dispatch template `auditing-{lang}*` ([audit])
- ALWAYS: every marketplace plugin that defines a programming language ships `auditing-{lang}`, `auditing-{lang}-tests`, and `auditing-{lang}-architecture` ([audit])
- ALWAYS: the deterministic git, scope, lock, and state-transition computations live in `audit_orchestrator.py` and the canonical verdict schema and rollup in the sibling `verdict.py` — the boundaries that make the computations testable ([audit])
- ALWAYS: the four wrapper agents reach the audit policy, the `scripts/` toolchain, and the `audit_orchestrator.py` CLI only by invoking the `/auditing` skill (and, for `pr-reviewer`, the review-prompt skill) ([audit])
- ALWAYS: the `/auditing` skill partitions multi-language scopes by file extension and runs the orchestration protocol once per language partition ([audit])
- ALWAYS: the `audit-orchestrator` agent persists its working set under `.spx/audits/<lang>/<branch-slug>.md` and acquires `<state-file>.lock` before reading or writing state ([audit])
- ALWAYS: the `pr-review-orchestrator` agent persists no on-disk audit state — its durable cross-CI-run surface is the PR comment thread, recovered each run by `read_verdict.py` matching the `<!-- AUDIT_VERDICT_JSON_BEGIN -->` delimiter ([audit])
- NEVER: introduce language-specific examples, file extensions, validation commands, test commands, or evidence patterns into the `/auditing` skill or the four wrapper agents — that content belongs in the corresponding `auditing-{lang}*` skill ([audit])
- NEVER: ship per-language audit-orchestration skills or agents such as `typescript-audit-orchestrator` — the generic skill serves every language by dispatch ([audit])
- NEVER: embed deterministic shell pipelines (git diff, base-ref detection, scope hashing, lock acquisition, verdict diffing) directly in the wrapper agent prompts — the `/auditing` skill prose owns these pipelines ([audit])
- NEVER: reference `plugins/.../scripts/` from an agent prompt by `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_SKILL_DIR}`, or a hard-coded relative path — neither variable is substituted in an agent prompt body ([audit])
- NEVER: add a per-skill self-description block to `auditing-{lang}*` skills declaring file globs, configs, gate commands, or test commands — the dispatch contract is the skill name ([audit])
- NEVER: place the audit-orchestrator helper module at `plugins/spec-tree/scripts/` or any plugin-root location — the marketplace co-locates Python under the consuming skill ([audit])
- NEVER: persist audit state inside `spx/` or any tracked product directory — the only sanctioned surfaces are the worktree-local `.spx/audits/` partition and the PR comment thread ([audit])
- NEVER: write to `.spx/audits/` when running `/auditing` in either PR-thread mode — the PR-thread state surface is the comment thread itself ([audit])
- NEVER: reissue a finding ID once assigned — `next_finding_id` strictly exceeds every ID ever allocated on the branch, so a regression reopens its original ID ([audit])
