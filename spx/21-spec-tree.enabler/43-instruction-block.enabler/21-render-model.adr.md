# Instruction Block Render Model

The product's Spec Tree instructions are a generated managed instruction block in the product's root agent-harness instruction files — `CLAUDE.md` read by Claude Code and `AGENTS.md` read by Codex — because root instruction files are retained across context compaction while `spx/` subdirectory instruction files disappear from the compacted conversation. Each root file's managed surface is three region kinds: a generated **router block**, named **per-product command slots**, and the product's own **out-of-block prose**. The writer removes `spx/CLAUDE.md` and `spx/AGENTS.md` so the root managed surface is the only instruction surface. Existing root instruction-file content outside every managed fence is preserved verbatim.

The **router block** is delimited by a single opening marker `<!-- SPEC-TREE v{template_version} langs:{enabled-languages} -->` and a closing `<!-- /SPEC-TREE -->`. It carries the product-neutral WHEN-to-invoke routing, filtered to the product's enabled languages and to the reading harness. Its opening marker carries only the two fields staleness reads — the dotted template version and the recorded enabled-language list — and no invariant field, because the template source is always the methodology's own and a recorded copy of it would change no comparison. Both instruction blocks originate from one authored template, but generation reads the rendered harness templates committed under `dist/claude/` and `dist/codex/`; the build resolves runtime-token macros before generation, then the writer filters the remaining per-harness spans and enabled-language blocks per root output. The two router blocks differ only in the spans the template marks for a harness and in their own root filename. The router block is regenerated in full on every update; a re-render overwrites any hand-edit inside it. A markerless root instruction block recognized as the generated Spec Tree instructions from the retired full-file surface, and a block delimited by the retired `BEGIN MANAGED SPEC TREE INSTRUCTIONS` / `END MANAGED SPEC TREE INSTRUCTIONS` markers with their metadata comment lines, are both generated content: the writer replaces either with the current router block and its compressed marker rather than preserving it.

The **named per-product command slots** are delimited by `<!-- SPEC-TREE:{slot} -->` and `<!-- /SPEC-TREE:{slot} -->` over a fixed, methodology-defined slot set — `author`, `verify`, `gate`, and `merge`. Each slot holds one product's operational command for a spec-tree phase: `author` the command that rebuilds or regenerates artifacts after a create, update, or delete on a spec, test, or implementation file; `verify` the deterministic check command over a single node and over the changeset; `gate` the full deterministic bundle; `merge` the transport command. `/apply` decomposes into `author` and `verify` and so earns no slot of its own. A slot's body is product-owned and preserved verbatim across every re-render — the generator never authors slot content, only recognizes the fences and carries the body through — while the router block references a slot by name, so a phase's routing resolves to the product's own command without the router carrying a product-specific string itself. When a slot fence is absent, the writer scaffolds it with a placeholder body marking it unfilled, so the fixed slot set is always present and the router's by-name references never dangle; the drift gate therefore requires each fixed slot's fence, filled or placeholder. A slot's body is identical in both root files, because a spec-tree phase runs the same command whichever harness reads it: the writer fills an empty or placeholder slot in one root file from the sibling root file's filled slot, and a slot filled differently in the two files is drift the gate reports and the update skill reconciles.

Generation is deterministic end to end and needs no agent judgment for the router and the mechanical slot cases: the enabled-language list is read from the product's test-file extensions under `spx/**/tests/`, staleness is a dotted-version and language-set comparison, the router render is a pure string transformation, and slot handling is fence recognition plus verbatim carry-through with sibling fill. The parse, version-compare, language-filter, harness-filter, router replacement, slot preservation, sibling-fill, and render functions are pure over content strings; language detection, filesystem reads, symlink replacement, obsolete `spx/` instruction-file removal, and the two root file writes live only at the writer's thin CLI edge and the gate that drives it. If a repository has only one root harness instruction file, the missing file is created from the present file's body before its harness-specific router block is inserted; if a root harness instruction file is a symlink to the other, the symlink is replaced by a regular file copy before insertion, because harness-specific router blocks are impossible through a symlink and replacing it by a copy is lossless. The one reconciliation the generator does not resolve deterministically — a slot filled differently in the two root files — is left for the update skill, whose git-recency judgment is the reconcile path the deterministic gate cannot supply. The authored template has one source home — the understanding skill's `templates/` — and the writer consumes only the built harness copies under `dist/`.

## Rationale

One repository is worked by several agents at once, and each agent harness reads a root instruction filename before it reads any `spx/` subdirectory instruction file. Context compaction preserves root instructions but drops loaded subdirectory content, so putting the Spec Tree router only under `spx/` leaves the resuming agent dependent on remembering a rule that is no longer in context. A root managed surface keeps the router in the instruction surface the harness already retains. Two blocks from one authored source keep the shared body in one place while per-harness spans render for each output and each file takes its own filename — the single-source per-harness-divergence discipline the build already applies to plugin content (`spx/18-plugin-build.enabler/15-build-architecture.adr.md`); a forked pair of whole templates would drift. The writer reads `dist/` rather than `src/` because authored templates can contain build-time macros such as runtime-token calls, valid source but invalid instruction-block output; consuming rendered harness templates makes the build output the authority for what a block may contain, and an unresolved-macro guard fails generation when `dist/` is stale or malformed.

The compressed marker exists because a four-line header — a begin marker plus three metadata comment lines — records one invariant field the staleness check never reads. Version and language set are the only fields a re-render compares; folding them into one opening line and dropping the template-source line removes a line per marker without losing anything the check consumes.

The named command slots exist because the router is product-neutral by construction, yet the facts an agent most needs after compaction — how this product rebuilds artifacts, runs its checks, gates, and merges — are exactly the facts that vary per product. A product-neutral router cannot carry a product's own commands, so without slots those commands live in hand-maintained prose that drifts; a preserved slot holds each command in the compaction-surviving surface instead. A slot is preserved rather than rendered because its content is the product's, not the methodology's: the block cannot both track template-version truth and merge arbitrary in-place edits from two inputs alone, so the router is rendered and the slots are preserved as data. The slot set is fixed and named after spec-tree phases rather than free-form because the router references slots by name, so a phase's routing resolves to a known slot; a free-form set the router could not reference by role would carry commands the router cannot point at. `/apply` is not a slot because it decomposes into `author` and `verify` — it orchestrates create/update/delete on artifacts and then runs the verification commands — so a slot for it would duplicate those two. A slot's cross-file identity is required because a spec-tree phase's command is harness-neutral: the same build or merge command serves Claude Code and Codex, so a slot filled in one root file and empty in the other would deny a harness the command it needs post-compaction. Filling an empty slot from its sibling extends the existing missing-file seeding to slot granularity; the only case the deterministic generator cannot resolve — two filled slots that differ — is a genuine reconcile the update skill owns, because choosing which side is current needs the git-recency judgment a pure string transformation cannot make.

The gate requires each fixed slot's fence, even when its body is an unfilled placeholder, so the router's by-name references always resolve and a product cannot silently drop a phase's command surface. Detecting the language list deterministically from the product's own test-file extensions keeps the router honest as those languages change and removes the only router step that ever read as agent work. `just build-instructions` is the agent-facing writer and `just instructions-check` is the drift gate; Python modules and scripts are recipe internals. The renderer uses stdlib-parseable fence delimiters rather than a third-party templating engine, because the generator ships as a stdlib-only script per `spx/13-plugin-and-runtime-conventions.adr.md`. The accepted cost is that a re-render does not preserve unmodeled hand-prose edits inside the router block; this is acceptable because the router is generated boilerplate, and the product's durable truth lives in its specs and decisions, its preserved command slots, and its root instruction-file content outside every fence.

## Verification

The behavioral rules of the three region kinds — marker format, slot-fence recognition, verbatim slot preservation, sibling-fill identity, placeholder scaffolding, drift reporting, legacy-marker and markerless replacement, obsolete `spx/` removal, and unresolved-delimiter refusal — are declared and tested as `[test]` assertions on the sibling spec `spx/21-spec-tree.enabler/43-instruction-block.enabler/instruction-block.md`. The rules below are the architectural constraints no deterministic test falsifies: the region model, the source-of-content boundaries, the purity and thin-CLI-edge placement, and the deterministic-no-agent-judgment discipline.

### Audit

- ALWAYS: the product's Spec Tree instructions are a generated managed surface in the root harness instruction files — `CLAUDE.md` for Claude Code and `AGENTS.md` for Codex — because each agent harness retains its root instruction file across compaction ([audit])
- ALWAYS: each root file's managed surface is three region kinds — a generated router block, named per-product command slots, and product-owned out-of-block prose ([audit])
- ALWAYS: generation reads the rendered harness templates committed under `dist/claude/` and `dist/codex/` rather than the authored `src/` template, because authored templates can carry build-time macros that are valid source but invalid instruction-block output ([audit])
- ALWAYS: the parse, version-compare, language-filter, harness-filter, router replacement, slot preservation, sibling-fill, and render functions are pure — content strings in, content strings out — with no filesystem, environment, or subprocess access ([audit])
- ALWAYS: language detection, filesystem reads, symlink replacement, obsolete `spx/` instruction-file removal, and the two root file writes live only in the writer's thin CLI edge and the gate that drives it ([audit])
- ALWAYS: the one reconciliation the deterministic generator does not resolve — a command slot filled with different bodies in the two root files — is the update skill's git-recency judgment, the reconcile path a pure string transformation cannot supply ([audit])
- ALWAYS: the authored template has one source home — the understanding skill's `templates/` — and generation consumes the rendered copies under `dist/` ([audit])
- NEVER: the generator depends on a third-party templating engine — language-conditional, harness-conditional, and slot fences use stdlib-parseable delimiters, and the dotted version is parsed with the standard library only ([audit])
- NEVER: an agent judges which languages a product uses or whether a router block is stale by reading and comparing versions in the conversation — both are computed by the deterministic checker (the generator's `--check`), which the gate runs ([audit])
