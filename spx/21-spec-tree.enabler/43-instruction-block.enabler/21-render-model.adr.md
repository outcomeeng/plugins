# Instruction Block Render Model

The product's Spec Tree instructions are a generated managed instruction block in the product's root agent-harness instruction files — `CLAUDE.md` read by Claude Code and `AGENTS.md` read by Codex — because root instruction files are retained across context compaction while `spx/` subdirectory instruction files disappear from the compacted conversation. The writer removes `spx/CLAUDE.md` and `spx/AGENTS.md` so the root instruction block is the only instruction surface. Both instruction blocks originate from one authored template in the understanding skill, but instruction-block generation reads the rendered harness templates committed under `dist/claude/` and `dist/codex/`. The build resolves runtime-token macros before instruction-block generation, then the instruction-block writer filters the remaining per-harness spans and enabled-language blocks for each root output. The two instruction blocks differ only in the spans the template marks for a harness and in their own root filename, which is the file the writer writes, not a span of the shared body. Existing root instruction-file content outside the block markers is preserved verbatim. A markerless root instruction block recognized as the generated Spec Tree instructions from the retired full-file surface is generated content, not product-owned prose, so the writer replaces it with the new instruction block rather than preserving it ahead of the block. If a repository has only one root harness instruction file, the missing harness instruction file is created from the present file's body before its harness-specific instruction block is inserted. If a root harness instruction file is a symlink to the other, the symlink is replaced by a regular file copy before insertion; preserving the symlink would make harness-specific instruction blocks impossible, and replacing a symlink by a copy is lossless for the existing body. The only per-product variation inside the instruction block is the enabled-language list; every other line, including the product's own name, is template content identical across products. Generation is deterministic end to end and needs no agent judgment: the enabled-language list is read from the product's test-file extensions under `spx/**/tests/`, staleness is a dotted-version and language-set comparison, and the render is a pure string transformation. An update re-renders both instruction blocks from the rendered harness templates with the recorded language list, so template additions propagate, disabled-language blocks stay out, and each block's `template_version` metadata is set to the rendered template version. A gate regenerates both root files and fails on drift — the same regenerate-and-diff contract the build's `dist/` sync uses — so no agent invocation maintains the instruction block. The parse, version-compare, language-filter, harness-filter, instruction-block replacement, and render functions are pure over content strings; language detection, filesystem reads, symlink replacement, obsolete `spx/` instruction-file removal, and the two root file writes live only at the writer's thin CLI edge and the gate that drives it. The authored template has one source home — the understanding skill's `templates/` — and the instruction-block writer consumes only the built harness copies under `dist/`.

## Rationale

One repository is worked by several agents at once, and each agent harness reads a root instruction filename before it reads any `spx/` subdirectory instruction file. Context compaction preserves root instructions but drops loaded subdirectory content, so putting the Spec Tree router only under `spx/` leaves the resuming agent dependent on remembering a rule that is no longer in context. A root instruction block keeps the router in the instruction surface the harness already retains. A single instruction block, or a symlink collapsing the two root files, hands every agent the same managed content and denies a harness the instructions it alone needs. Two instruction blocks from one authored source keep the shared body in one place while per-harness spans render for each output and each file takes its own filename, the single-source per-harness-divergence discipline the build already applies to plugin content (`spx/18-plugin-build.enabler/15-build-architecture.adr.md`); a forked pair of whole templates would drift. The instruction-block writer reads `dist/` rather than `src/` because authored templates can contain build-time macros such as runtime-token calls. Those macros are valid source but invalid instruction-block output. Consuming rendered harness templates makes the build output the authority for what an instruction block may contain, and an unresolved-macro guard fails instruction-block generation when `dist/` is stale or malformed.

An instruction block cannot both track template version truth and preserve arbitrary in-place edits inside that block from two inputs alone — "block absent from the product" is ambiguous between template addition and user deletion — so the customization is modeled as data and the block body is rendered: there is nothing to merge inside the markers. Root instruction-file content outside the markers belongs to the product and is preserved verbatim. The render substitutes no product-specific string into the instruction-block body — not even the product name — because the instruction block lives inside the product's own repository, where every reader already holds the product's identity, so a substituted name would change no routing and teach nothing. The one per-product customization that earns the render is the enabled-language list: the methodology ships reference blocks for several languages, and a single-language project should not carry the others as bloat, so a disabled language is an omission from the rendered block rather than prose surgery.

Detecting that list deterministically from the product's own test-file extensions keeps the instruction block honest as those languages change and removes the only step that ever read as agent work: nothing about reading metadata, comparing versions, filtering language or harness blocks, or writing two instruction blocks requires interpretation, so the whole generation runs through the repository command surface beside the build's `dist/` sync. `just build-instructions` is the agent-facing writer and `just instructions-check` is the drift gate; Python modules and scripts are recipe internals. The accepted cost is that a re-render does not preserve unmodeled hand-prose edits inside the instruction block; this is acceptable because the block is generated boilerplate, and the product's durable truth lives in its specs and decisions plus its root instruction-file content outside the block markers. The renderer uses stdlib-parseable block delimiters rather than a third-party templating engine, because the generator ships as a stdlib-only script per `spx/13-plugin-and-runtime-conventions.adr.md`. One authored template home avoids the drift a per-skill copy would invite, while consuming `dist/` avoids treating build macros as instruction-block text.
