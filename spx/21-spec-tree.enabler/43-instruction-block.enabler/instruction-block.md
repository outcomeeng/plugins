# Instruction Block

PROVIDES deterministic generation of a managed Spec Tree instruction surface in a product's root agent-harness instruction files — `CLAUDE.md` for Claude Code and `AGENTS.md` for Codex — composed of a generated router block rendered from the harness templates committed under `dist/`, product-owned command slots preserved across re-render, and product prose outside every managed fence, scoped to the project's enabled languages and rendered per agent harness
SO THAT every agent working a spec-tree project
CAN retain the Spec Tree routing instructions and the product's own phase commands across compaction while preserving the product's other root instructions

## Assertions

### Scenarios

- Given a template with language blocks and per-harness blocks, when the managed surface is generated for an enabled-language set, then both `CLAUDE.md` and `AGENTS.md` are written, each preserving root content outside every managed fence and containing, inside the router block, exactly the enabled languages' blocks and only its own harness's blocks ([test](tests/test_instruction_block.scenario.l1.py))
- Given a generation over a file with a filled command slot and product prose, when the managed surface is written, then the router block is re-rendered from the template, each command-slot body is preserved verbatim, and product prose outside every fence is preserved verbatim ([test](tests/test_instruction_block.scenario.l1.py))
- Given the router block, when it is written, then its opening marker is `<!-- SPEC-TREE v{template_version} langs:{enabled-languages} -->` carrying only the version and the recorded enabled-language list, its closing marker is `<!-- /SPEC-TREE -->`, and no template-source field is recorded ([test](tests/test_instruction_block.scenario.l1.py))
- Given the `CLAUDE.md` and `AGENTS.md` outputs of one generation, when they are compared, then they share every line except the per-harness spans the template marks and their own filename; the router content, command-slot bodies, and out-of-fence prose are otherwise identical ([test](tests/test_instruction_block.scenario.l1.py))
- Given a newer template that adds a section, when the managed surface is updated, then both re-rendered router blocks contain the new section, still carry the recorded enabled languages, and preserve every command-slot body ([test](tests/test_instruction_block.scenario.l1.py))
- Given a `--template` argument that is a symlink or does not resolve to an existing regular file, when the CLI runs, then the path is validated and rejected before any read, so a faulty argument cannot escape into an unintended file ([test](tests/test_instruction_block.scenario.l1.py))
- Given a router block whose `template_version` is not parseable as dotted integers, when staleness is checked, then it is treated as stale rather than raising, so a re-render normalizes it to the installed version ([test](tests/test_instruction_block.scenario.l1.py))
- Given root `CLAUDE.md` is a symlink to `AGENTS.md`, when `--write` updates the managed surface, then `CLAUDE.md` becomes a regular file copy and both root instruction files preserve the shared root body outside their harness-specific router blocks ([test](tests/test_instruction_block.scenario.l1.py))
- Given a root instruction file contains a markerless generated Spec Tree instruction block from the retired full-file surface, when `--write` updates the managed surface, then the generated legacy body is replaced rather than preserved ahead of the router block ([test](tests/test_instruction_block.scenario.l1.py))
- Given product prose that quotes the literal router marker as an inline example before the managed block, when `--write` updates the managed surface, then only the marker on its own fence line opens the block, so the inline example prose is preserved rather than replaced through the real closing fence ([test](tests/test_instruction_block.scenario.l1.py))
- Given a root instruction file carries a managed block delimited by the retired `BEGIN MANAGED SPEC TREE INSTRUCTIONS` / `END MANAGED SPEC TREE INSTRUCTIONS` markers and their metadata comment lines, when staleness is checked, then it reports `stale`, and when `--write` updates the managed surface, then the legacy-marker block is replaced in place with the compressed `SPEC-TREE` router marker rather than duplicated ([test](tests/test_instruction_block.scenario.l1.py))
- Given a fixed command slot whose fence is absent from a root file, when `--write` updates the managed surface, then the writer scaffolds the slot fence with a placeholder body marking it unfilled ([test](tests/test_instruction_block.scenario.l1.py))
- Given a root instruction file whose out-of-fence product prose carries a run of blank lines and whose command-slot fences are absent, when `--write` scaffolds the slots, then the blank-line run in the prose is preserved verbatim rather than collapsed ([test](tests/test_instruction_block.scenario.l1.py))
- Given a fixed command slot with a malformed fence — an open marker and a real body but no matching close marker — when `--write` updates the managed surface, then the fence is repaired into a well-formed one whose body is the recovered product command, not a placeholder ([test](tests/test_instruction_block.scenario.l1.py))
- Given a fixed command slot filled in one root file and a placeholder or empty in the other, when `--check` runs, then it reports `stale` — the two slot bodies are not yet identical and the next `--write` resolves them by sibling-fill ([test](tests/test_instruction_block.scenario.l1.py))
- Given a fixed command slot that is filled in one root file and empty or placeholder in the other, when `--write` updates the managed surface, then the empty or placeholder slot is filled from the sibling root file's filled body ([test](tests/test_instruction_block.scenario.l1.py))
- Given a fixed command slot unfilled in both root files but carrying divergent placeholder bodies, when `--check` runs it reports `stale`, and when `--write` updates the managed surface, then both bodies are normalized to the canonical placeholder so the two files never carry different bodies for an unfilled slot ([test](tests/test_instruction_block.scenario.l1.py))
- Given a fixed command slot filled with different bodies in the two root files, when the managed surface is checked, then the difference is reported as drift and the generator leaves both bodies unchanged rather than choosing between them ([test](tests/test_instruction_block.scenario.l1.py))
- Given a fixed command slot filled with different bodies in the two root files, when `--fill-slot {slot} --from {harness}` runs, then both root files' slot bodies become the named harness's body — the deterministic write the update skill applies after its git-recency judgment picks the more recent side ([test](tests/test_instruction_block.scenario.l1.py))
- Given a `--fill-slot` reconcile whose root instruction file is a symlink resolving outside the repository root, when the CLI runs, then the symlink target is rejected before any write, so a reconcile cannot escape into an unintended file ([test](tests/test_instruction_block.scenario.l1.py))
- Given a `--fill-slot` reconcile where a target root instruction file is absent, when the CLI runs, then it fails with an error rather than filling only the present file, so a partial reconcile is never written ([test](tests/test_instruction_block.scenario.l1.py))
- Given a root file missing a fixed command slot's fence, when `--check` runs, then it reports `stale` — the shipped check verb verifies each fixed slot's fence presence directly, not only through the regenerate-and-diff gate ([test](tests/test_instruction_block.scenario.l1.py))

### Mappings

- Over the languages the template defines blocks for, a language's block appears in a rendered router block when the language is in the detected enabled set and is omitted otherwise ([test](tests/test_instruction_block.mapping.l1.py))
- A test-file extension present under `spx/**/tests/` maps to the language it denotes, and the detected enabled-language set is the set of those mappings ([test](tests/test_instruction_block.mapping.l1.py))
- Each name in the fixed command-slot set — `author`, `verify`, `gate`, `merge` — maps to its recognized `<!-- SPEC-TREE:{slot} -->` fence, and a name outside the set maps to no recognized slot ([test](tests/test_instruction_block.mapping.l1.py))
- The `--check` verb maps a router-block state to its report: a missing block to `absent`, a version-behind block to `stale`, a version-current block to `current`, and a detected-language set differing from the recorded set to `stale` ([test](tests/test_instruction_block.mapping.l1.py))

### Properties

- After generation, each router block's `template_version` equals the installed template version ([test](tests/test_instruction_block.property.l1.py))
- Every rendered managed surface ends with exactly one trailing newline ([test](tests/test_instruction_block.property.l1.py))
- Staleness ordering matches dotted-numeric version order: a product version is stale exactly when it is numerically below the installed template version ([test](tests/test_instruction_block.property.l1.py))
- After a write that resolves command slots by sibling-fill, each fixed slot's body is byte-identical in `CLAUDE.md` and `AGENTS.md` ([test](tests/test_instruction_block.property.l1.py))

### Compliance

- ALWAYS: generation writes the managed surface in both root `CLAUDE.md` and root `AGENTS.md`, never one without the other — each agent reading the same repository gets its own harness router block in the root instruction file it retains across compaction ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: instruction-block generation reads the harness-specific templates from `dist/claude/` and `dist/codex/`, so the update surface consumes the same rendered output this product ships as installed plugin trees ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: instruction-block writing is exposed to agents through the repository Justfile recipe `just build-instructions`; `just instructions-check` is the drift gate over the same writer ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: the pre-commit hook regenerates the root managed surface through `just build-instructions` — the rendered-`dist/` template writer — never by invoking the generator directly against the authored `src/` template ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: the drift gate reports missing root instruction-file paths as drift and marks only existing generated instruction-file paths with `--intent-to-add`, so deleted obsolete `spx/` instruction files are reported by `git diff` without causing a missing-path failure ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: the drift gate requires each fixed command slot's fence — filled or placeholder — in each root file, so the router's by-name slot references never dangle ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: the refresh workflow regenerates skill output and the root managed surface, then opens or updates a pull request only when git drift exists ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: the refresh workflow checks out the default branch `main`, so its regeneration and drift comparison run against the published tree ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: the refresh workflow verifies the pinned `just` download against its recorded SHA-256 checksum before installing it, so a tampered or moved release fails the run rather than executing ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: the refresh workflow provisions `dprint` before regenerating skill output, because `just build-skills` formats generated `dist/` output with `dprint` and fails without it ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: regenerating a drifted router block overwrites the drift — a re-render restores the template's content over any hand-edit, the basis of the regenerate-and-diff gate that keeps both files current without an agent invocation ([test](tests/test_instruction_block.compliance.l1.py))
- ALWAYS: the router block references a command slot by name, so a spec-tree phase's routing resolves to the product's own command without a product-specific string in the router ([test](tests/test_instruction_block.compliance.l1.py))
- NEVER: the render substitutes a product-specific string into the router block — a brace-delimited token in the template passes through unchanged, and per-product commands live only in the preserved slots ([test](tests/test_instruction_block.compliance.l1.py))
- NEVER: the generator authors, edits, or overwrites a command slot's product-owned body — an update preserves it and only fills an empty or placeholder slot from its filled sibling ([test](tests/test_instruction_block.compliance.l1.py))
- NEVER: an update keeps an unmodeled hand-prose edit inside the router block — a re-render reflects only the template, the recorded enabled languages, and the harness, while command slots and out-of-fence prose are preserved ([test](tests/test_instruction_block.compliance.l1.py))
- NEVER: any rendered router block contains the session-result archive instruction token or the `result` session frontmatter field token ([test](tests/test_instruction_block.compliance.l1.py))
- NEVER: instruction-block generation writes output from a harness template that still contains unresolved build-template delimiters such as `{{! ... !}}` ([test](tests/test_instruction_block.compliance.l1.py))
- NEVER: `spx/CLAUDE.md` or `spx/AGENTS.md` remain after generation — the root managed surface is the canonical instruction surface ([test](tests/test_instruction_block.compliance.l1.py))
