# Guide Render Model

The product's spx-level agent guide is two generated files in the product's own `spx/` directory — `CLAUDE.md` read by Claude Code and `AGENTS.md` read by Codex — because one repository is worked by both agents at once and each reads its own filename from the same fixed directory. Both files originate from one authored template in the understanding skill, but product-guide generation reads the rendered runtime templates committed under `dist/claude/` and `dist/codex/`. The build resolves runtime-token macros before guide generation, then the guide writer filters the remaining per-runtime guide blocks and enabled-language blocks for each output. The two outputs differ only in the spans the template marks for a runtime and in their own filename, which is the file the writer writes, not a span of the shared body. The only per-product variation is the enabled-language list; every other line, including the product's own name, is template content identical across products. Generation is deterministic end to end and needs no agent judgment: the enabled-language list is read from the product's test-file extensions under `spx/**/tests/`, staleness is a dotted-version and language-set comparison, and the render is a pure string transformation. An update re-renders both files from the rendered runtime templates with the recorded language list, so template additions propagate, disabled-language blocks stay out, and each output's `template_version` is set to the rendered template version. A gate regenerates both files and fails on drift — the same regenerate-and-diff contract the build's `dist/` sync uses — so no agent invocation maintains the guide. The parse, version-compare, language-filter, runtime-filter, and render functions are pure over content strings; language detection, filesystem reads, and the two file writes live only at the writer's thin CLI edge and the gate that drives it. The authored template has one source home — the understanding skill's `templates/` — and the product-guide writer consumes only the built runtime copies under `dist/`.

## Rationale

One repository is worked by several agents at once, and `spx/` is a fixed on-disk directory rather than a per-runtime plugin render, so each agent's guide must be a real file present beside the other. A single guide, or a symlink collapsing the two, hands every agent the same content and denies a runtime the guidance it alone needs. Two files from one authored source keep the shared body in one place while per-runtime spans render per output and each file takes its own filename, the single-source per-runtime-divergence discipline the build already applies to plugin content (`spx/18-plugin-build.enabler/15-build-architecture.adr.md`); a forked pair of whole templates would drift. The guide writer reads `dist/` rather than `src/` because authored templates can contain build-time macros such as runtime-token calls. Those macros are valid source but invalid product-guide output. Consuming rendered runtime templates makes the build output the authority for what product guides may contain, and an unresolved-macro guard fails guide generation when `dist/` is stale or malformed.

A guide cannot both track template version truth and preserve arbitrary in-place edits from two inputs alone — "section absent from the product" is ambiguous between template addition and user deletion — so the customization is modeled as data and the body is rendered: there is nothing to merge. The render substitutes no product-specific string into the body — not even the product name — because the guide lives inside the product's own repository, where every reader already holds the product's identity, so a substituted name would change no routing and teach nothing. The one per-product customization that earns the render is the enabled-language list: the methodology ships reference blocks for several languages, and a single-language project should not carry the others as bloat, so a disabled language is an omission from the rendered guide rather than prose surgery.

Detecting that list deterministically from the product's own test-file extensions keeps the guide honest as those languages change and removes the only step that ever read as agent work: nothing about reading frontmatter, comparing versions, filtering language or runtime blocks, or writing two files requires interpretation, so the whole generation runs through the repository command surface beside the build's `dist/` sync. `just build-guides` is the agent-facing writer and `just guide-check` is the drift gate; Python modules and scripts are recipe internals. The accepted cost is that a re-render does not preserve unmodeled hand-prose edits to either guide file; this is acceptable because the guide is generated boilerplate, and the product's durable truth lives in its specs and decisions, not in the directory guide. The renderer uses stdlib-parseable block delimiters rather than a third-party templating engine, because the generator ships as a stdlib-only script per `spx/13-plugin-and-runtime-conventions.adr.md`. One authored template home avoids the drift a per-skill copy would invite, while consuming `dist/` avoids treating build macros as product-guide text.

## Verification

### Audit

- ALWAYS: the product's spx-level guide is two generated files in `spx/` — `CLAUDE.md` for Claude Code and `AGENTS.md` for Codex — both present and neither a symlink to the other, because one repository is worked by both agents and each reads its own filename ([audit])
- ALWAYS: both guide files originate from one authored template, but product-guide generation reads the rendered runtime templates committed under `dist/claude/` and `dist/codex/` ([audit])
- ALWAYS: build-time runtime-token macros are resolved by the plugin build before product-guide generation, and remaining guide runtime blocks are filtered by the product-guide writer per output file ([audit])
- ALWAYS: the only per-product variation is the enabled-language list declared in frontmatter; every other line, including the product name, is template content identical across products ([audit])
- ALWAYS: generation is deterministic and needs no agent judgment — the enabled-language list is read from the product's `spx/**/tests/` test-file extensions, staleness is a dotted-version and language-set comparison, and the render is a pure string transformation ([audit])
- ALWAYS: an update re-renders both files from the rendered runtime templates with the recorded language list, so template additions propagate and the language selection is preserved ([audit])
- ALWAYS: a gate regenerates both guide files and fails on drift; guide maintenance needs no agent invocation ([audit])
- ALWAYS: the parse, version-compare, language-filter, runtime-filter, and render functions are pure — content strings in, content strings out — with no filesystem, environment, or subprocess access ([audit])
- ALWAYS: language detection, filesystem reads, and the two file writes live only in the generator's thin CLI edge and the gate that drives it ([audit])
- ALWAYS: `template_version` comparison parses the dotted-numeric version with the standard library only ([audit])
- ALWAYS: `just build-guides` is the agent-facing write command for product guide files, and `just guide-check` is the drift gate over the same writer ([audit])
- ALWAYS: the authored template has one source home — the understanding skill's `templates/` — and product guide generation consumes the rendered copies under `dist/` ([audit])
- NEVER: product guide generation writes output from a runtime template that still contains unresolved build-template delimiters such as `{{! ... !}}` ([audit])
- NEVER: the render substitutes a product-specific string into a guide body — the guide carries no per-product tokens, only template content, language filtering, and per-runtime spans ([audit])
- NEVER: the generator depends on a third-party templating engine — language-conditional and runtime-conditional blocks use stdlib-parseable delimiters ([audit])
- NEVER: an update hand-merges or section-diffs a product's body against the template — re-render is the update mechanism ([audit])
- NEVER: an agent judges which languages a product uses or whether a guide is stale by reading and comparing versions in the conversation — both are computed by the deterministic checker (the generator's `--check`), which the gate runs ([audit])
