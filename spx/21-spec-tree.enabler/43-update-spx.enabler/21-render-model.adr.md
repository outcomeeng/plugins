# Guide Render Model

The product's Spec Tree agent guide is a generated managed section in the product's root runtime instruction files — `CLAUDE.md` read by Claude Code and `AGENTS.md` read by Codex — because root instruction files are retained across context compaction while `spx/` subdirectory guides disappear from the compacted conversation. The writer removes `spx/CLAUDE.md` and `spx/AGENTS.md` so the root managed section is the only guide surface. Both managed sections originate from one authored template in the understanding skill, but product-guide generation reads the rendered runtime templates committed under `dist/claude/` and `dist/codex/`. The build resolves runtime-token macros before guide generation, then the guide writer filters the remaining per-runtime guide blocks and enabled-language blocks for each root output section. The two managed sections differ only in the spans the template marks for a runtime and in their own root filename, which is the file the writer writes, not a span of the shared body. Existing root guide content outside the managed markers is preserved verbatim. If a repository has only one root runtime guide, the missing runtime guide is created from the present guide's body before its runtime-specific managed section is inserted. If a root runtime guide is a symlink to the other, the symlink is replaced by a regular file copy before insertion; preserving the symlink would make runtime-specific managed sections impossible, and replacing a symlink by a copy is lossless for the existing body. The only per-product variation inside the managed section is the enabled-language list; every other line, including the product's own name, is template content identical across products. Generation is deterministic end to end and needs no agent judgment: the enabled-language list is read from the product's test-file extensions under `spx/**/tests/`, staleness is a dotted-version and language-set comparison, and the render is a pure string transformation. An update re-renders both managed sections from the rendered runtime templates with the recorded language list, so template additions propagate, disabled-language blocks stay out, and each section's `template_version` metadata is set to the rendered template version. A gate regenerates both root files and fails on drift — the same regenerate-and-diff contract the build's `dist/` sync uses — so no agent invocation maintains the guide. The parse, version-compare, language-filter, runtime-filter, managed-section replacement, and render functions are pure over content strings; language detection, filesystem reads, symlink replacement, obsolete `spx/` guide removal, and the two root file writes live only at the writer's thin CLI edge and the gate that drives it. The authored template has one source home — the understanding skill's `templates/` — and the product-guide writer consumes only the built runtime copies under `dist/`.

## Rationale

One repository is worked by several agents at once, and each runtime reads a root instruction filename before it reads any `spx/` subdirectory guide. Context compaction preserves root instructions but drops loaded subdirectory content, so putting the Spec Tree router only under `spx/` leaves the resuming agent dependent on remembering a rule that is no longer in context. A root managed section keeps the router in the instruction surface the runtime already retains. A single guide, or a symlink collapsing the two root files, hands every agent the same managed content and denies a runtime the guidance it alone needs. Two managed sections from one authored source keep the shared body in one place while per-runtime spans render per output and each file takes its own filename, the single-source per-runtime-divergence discipline the build already applies to plugin content (`spx/18-plugin-build.enabler/15-build-architecture.adr.md`); a forked pair of whole templates would drift. The guide writer reads `dist/` rather than `src/` because authored templates can contain build-time macros such as runtime-token calls. Those macros are valid source but invalid product-guide output. Consuming rendered runtime templates makes the build output the authority for what product guides may contain, and an unresolved-macro guard fails guide generation when `dist/` is stale or malformed.

A managed section cannot both track template version truth and preserve arbitrary in-place edits inside that section from two inputs alone — "section absent from the product" is ambiguous between template addition and user deletion — so the customization is modeled as data and the section body is rendered: there is nothing to merge inside the markers. Root guide content outside the markers belongs to the product and is preserved verbatim. The render substitutes no product-specific string into the managed section body — not even the product name — because the guide lives inside the product's own repository, where every reader already holds the product's identity, so a substituted name would change no routing and teach nothing. The one per-product customization that earns the render is the enabled-language list: the methodology ships reference blocks for several languages, and a single-language project should not carry the others as bloat, so a disabled language is an omission from the rendered section rather than prose surgery.

Detecting that list deterministically from the product's own test-file extensions keeps the guide honest as those languages change and removes the only step that ever read as agent work: nothing about reading metadata, comparing versions, filtering language or runtime blocks, or writing two managed sections requires interpretation, so the whole generation runs through the repository command surface beside the build's `dist/` sync. `just build-guides` is the agent-facing writer and `just guide-check` is the drift gate; Python modules and scripts are recipe internals. The accepted cost is that a re-render does not preserve unmodeled hand-prose edits inside the managed section; this is acceptable because the section is generated boilerplate, and the product's durable truth lives in its specs and decisions plus its root guide content outside the managed markers. The renderer uses stdlib-parseable block delimiters rather than a third-party templating engine, because the generator ships as a stdlib-only script per `spx/13-plugin-and-runtime-conventions.adr.md`. One authored template home avoids the drift a per-skill copy would invite, while consuming `dist/` avoids treating build macros as product-guide text.
