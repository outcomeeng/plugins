# Guide Render Model

The product's spx-level directory guide is generated from the installed template, not hand-merged, and carries no substituted strings. Its only per-product variation is the enabled-language list declared in frontmatter: the body is rendered from the template with the blocks for disabled languages omitted, and every other line — including the product's own name — is template content, identical across products. An update re-renders the new template with the guide's recorded language list, so new template content propagates and disabled-language blocks stay out while `template_version` is set to the installed version. The enabled-language list is detected from the project's languages in use — by `/understand` or the calling flow — rather than hand-authored in the guide; `/update-spx` renders the guide from the template and that list. The parse, version-compare, language-filter, and render functions are pure over content strings; language detection and filesystem reads and writes live only at the skill script's thin CLI edge and the read-only `/understand` pass. The canonical template has one home — the understanding skill's `templates/` — read by `/understand` from its own template directory and by `/update-spx` through it.

## Rationale

A guide cannot both stay current with the template and preserve arbitrary in-place edits from two inputs alone — "section absent from the product" is ambiguous between new-in-template and user-deleted — so the customization is modeled as data and the body is rendered: there is nothing to merge. The render substitutes no product-specific string into the body — not even the product name — because the guide lives inside the product's own repository, where every reader already holds the product's identity, so a substituted name would change no routing and teach nothing. The one customization that earns the render is the enabled-language list: the methodology ships reference blocks for several languages, and a single-language project should not carry the other languages' tables as bloat, so a disabled language is an omission from the rendered guide rather than prose surgery. Detecting the list from the project's own languages in use keeps the guide honest as those languages change, without a hand-maintained declaration. The accepted cost is that a re-render does not preserve unmodeled hand-prose edits to the guide body; this is acceptable because the guide is generated boilerplate, and the product's durable truth lives in its specs and decisions, not in the directory guide. The renderer uses stdlib-parseable block delimiters rather than a third-party templating engine, because plugin scripts run in consumer environments with no third-party packages, per `spx/13-plugin-and-runtime-conventions.adr.md`. One template home avoids the drift a per-skill copy would invite, and mirrors how `/author` reads the spec-artifact templates from `../understand/templates/`.

## Verification

### Audit

- ALWAYS: the guide's only per-product variation is the enabled-language list declared in frontmatter; every other line, including the product name, is template content identical across products ([audit])
- ALWAYS: an update re-renders the new template with the guide's recorded language list, so new template content propagates and the language selection is preserved ([audit])
- ALWAYS: the enabled-language list is detected from the project's languages in use — by `/understand` or the calling flow — not hand-authored in the guide ([audit])
- ALWAYS: the parse, version-compare, language-filter, and render functions are pure — content strings in, content strings out — with no filesystem, environment, or subprocess access ([audit])
- ALWAYS: language detection and filesystem reads and writes live only in the skill script's thin CLI edge and the read-only understanding pass ([audit])
- ALWAYS: `template_version` comparison parses the dotted-numeric version with the standard library only ([audit])
- ALWAYS: the canonical template has one home — the understanding skill's `templates/` — and consuming skills read it through that path ([audit])
- NEVER: the render substitutes a product-specific string into the guide body — the guide carries no per-product tokens, only template content and language filtering ([audit])
- NEVER: the renderer depends on a third-party templating engine — language-conditional blocks use stdlib-parseable delimiters ([audit])
- NEVER: an update hand-merges or section-diffs the product's body against the template — re-render is the update mechanism ([audit])
