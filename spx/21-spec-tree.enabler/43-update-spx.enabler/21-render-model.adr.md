# Guide Render Model

The product's spx-level agent guide is two generated files in the product's own `spx/` directory — `CLAUDE.md` read by Claude Code and `AGENTS.md` read by Codex — because one repository is worked by both agents at once and each reads its own filename from the same fixed directory. Both files render from one canonical template: the body is shared, and the one span that differs by agent runtime — the auditor-subagent mandate Codex requires — is authored once as a per-runtime block and rendered into each file by the generator, the same way the enabled-language blocks are filtered. The two outputs differ only there and in their own filename, which is the file the generator writes, not a span of the shared body. The only per-product variation is the enabled-language list; every other line, including the product's own name, is template content identical across products. Generation is deterministic end to end and needs no agent judgment: the enabled-language list is read from the product's test-file extensions under `spx/**/tests/`, staleness is a dotted-version and language-set comparison, and the render is a pure string transformation. An update re-renders both files from the current template with the recorded language list, so new template content propagates and disabled-language blocks stay out while each output's `template_version` is set to the installed version. A gate regenerates both files and fails on drift — the same regenerate-and-diff contract the build's `dist/` sync uses — so no agent invocation keeps the guide current. The parse, version-compare, language-filter, runtime-filter, and render functions are pure over content strings; language detection, filesystem reads, and the two file writes live only at the generator's thin CLI edge and the gate that drives it. The canonical template has one home — the understanding skill's `templates/` — read by the generator and the gate through that path.

## Rationale

One repository is worked by several agents at once, and `spx/` is a fixed on-disk directory rather than a per-runtime plugin render, so each agent's guide must be a real file present beside the other. A single guide, or a symlink collapsing the two, hands every agent the same content and denies a runtime the guidance it alone needs — Codex keeps working in the main context unless its guide mandates spawning the auditor subagent. Two files from one source keep the shared body in one place while the per-runtime block — the subagent mandate — renders per output and each file takes its own filename, the single-source per-runtime-divergence discipline the build already applies to plugin content (`spx/18-plugin-build.enabler/15-build-architecture.adr.md`); a forked pair of whole templates would drift. The split is the generator's own concern, not the build's: the build bakes plugin content into `dist/claude` and `dist/codex` at build time, but both guide files land in one consumer repository regardless of which plugin a consumer installed, so the generator filters comment-delimited runtime blocks the build passes through untouched — the same mechanism that filters the language blocks.

A guide cannot both stay current with the template and preserve arbitrary in-place edits from two inputs alone — "section absent from the product" is ambiguous between new-in-template and user-deleted — so the customization is modeled as data and the body is rendered: there is nothing to merge. The render substitutes no product-specific string into the body — not even the product name — because the guide lives inside the product's own repository, where every reader already holds the product's identity, so a substituted name would change no routing and teach nothing. The one per-product customization that earns the render is the enabled-language list: the methodology ships reference blocks for several languages, and a single-language project should not carry the others as bloat, so a disabled language is an omission from the rendered guide rather than prose surgery.

Detecting that list deterministically from the product's own test-file extensions — not from agent judgment — keeps the guide honest as those languages change and removes the only step that ever read as agent work: nothing about reading frontmatter, comparing versions, filtering language or runtime blocks, or writing two files requires interpretation, so the whole generation runs as a gate beside the build's `dist/` sync rather than as a skill an agent must remember to invoke. The accepted cost is that a re-render does not preserve unmodeled hand-prose edits to either guide file; this is acceptable because the guide is generated boilerplate, and the product's durable truth lives in its specs and decisions, not in the directory guide. The renderer uses stdlib-parseable block delimiters rather than a third-party templating engine, because the generator ships as a stdlib-only script per `spx/13-plugin-and-runtime-conventions.adr.md`. One template home avoids the drift a per-skill copy would invite, and mirrors how `/author` reads the spec-artifact templates from `../understand/templates/`.

## Verification

### Audit

- ALWAYS: the product's spx-level guide is two generated files in `spx/` — `CLAUDE.md` for Claude Code and `AGENTS.md` for Codex — both present and neither a symlink to the other, because one repository is worked by both agents and each reads its own filename ([audit])
- ALWAYS: both guide files render from one canonical template; the per-runtime block that differs by agent runtime — the auditor-subagent mandate — is authored once and rendered into each file, and the two outputs otherwise differ only in their own filename, which is the output path the generator writes ([audit])
- ALWAYS: the per-runtime blocks are comment-delimited markers the plugin build passes through untouched and the guide generator filters per output file — the split is the generator's concern, not a build-time `target` conditional ([audit])
- ALWAYS: the only per-product variation is the enabled-language list declared in frontmatter; every other line, including the product name, is template content identical across products ([audit])
- ALWAYS: generation is deterministic and needs no agent judgment — the enabled-language list is read from the product's `spx/**/tests/` test-file extensions, staleness is a dotted-version and language-set comparison, and the render is a pure string transformation ([audit])
- ALWAYS: an update re-renders both files from the current template with the recorded language list, so new template content propagates and the language selection is preserved ([audit])
- ALWAYS: a gate regenerates both guide files and fails on drift; keeping the guide current needs no agent invocation ([audit])
- ALWAYS: the parse, version-compare, language-filter, runtime-filter, and render functions are pure — content strings in, content strings out — with no filesystem, environment, or subprocess access ([audit])
- ALWAYS: language detection, filesystem reads, and the two file writes live only in the generator's thin CLI edge and the gate that drives it ([audit])
- ALWAYS: `template_version` comparison parses the dotted-numeric version with the standard library only ([audit])
- ALWAYS: the canonical template has one home — the understanding skill's `templates/` — and the generator and gate read it through that path ([audit])
- NEVER: the render substitutes a product-specific string into a guide body — the guide carries no per-product tokens, only template content, language filtering, and per-runtime spans ([audit])
- NEVER: the generator depends on a third-party templating engine — language-conditional and runtime-conditional blocks use stdlib-parseable delimiters ([audit])
- NEVER: an update hand-merges or section-diffs a product's body against the template — re-render is the update mechanism ([audit])
- NEVER: an agent judges which languages a product uses or whether a guide is stale by reading and comparing versions in the conversation — both are computed by the deterministic checker (the generator's `--check`), which the gate runs ([audit])
