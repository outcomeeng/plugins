# Script Decomposition for Reviewing Changes

The review-changes skill decomposes into one policy module plus two single-purpose CLI scripts under `plugins/spec-tree/skills/review-changes/scripts/`. The policy module `review_result.py` declares the canonical schema — `SCHEMA_VERSION`, the `Severity`/`Concern` enums, the frozen `Finding` and `ReviewResult` dataclasses, the `ReviewResultValidationError` exception, and the `parse_json` / `parse_finding_json` / `to_json_dict` / `from_json_dict` entry points; a review carries findings only — no `summary`, acknowledgement, `decision`, or verdict field — so each consumer applies its own policy. The review streams its events live rather than building one batch from a finished result: `journal_emit.py` exposes one builder per domain event — `scope-entered`, `scope-advanced`, `finding-reported`, `run-completed` — and the skill appends each the moment the run reaches it, per `spx/21-spec-tree.enabler/16-verification.enabler/13-run-journal.adr.md`. `journal_emit.py finding-reported` parses each finding through `review_result.parse_finding_json` and exits non-zero on any violation before printing the event, so the per-finding parse is the live validity gate, matching the audit kind. `compute_diff.py` resolves `base_ref`/`head_ref` through their precedence chains — a git-derived `base_ref` composed to the remote-tracking form `origin/<base>` via `changeset_scope.remote_tracking_ref` per `spx/21-spec-tree.enabler/14-version-control.enabler/15-changeset-scope.enabler/13-changeset-derivation.adr.md` so a stale local branch ref cannot widen the diff — then emits labeled sections for `git diff <base_ref>...<head_ref>` (committed three-dot merge-base), `git diff --cached` (staged), `git diff` (unstaged), and `git ls-files --others --exclude-standard` plus `git diff --no-index` (untracked files). For reviewer fanout and random access, `compute_diff.py --bundle-dir <dir>` writes the same review input as a caller-owned scratch bundle: `diff.md` plus `manifest.json` containing refs, the diff hash, byte count, section spans, and changed files. `journal_emit.py` derives run metadata from the current worktree and env refs, maps each validated finding into the shared run-journal projection as the run raises it, derives the terminal status from the streamed event prefix, and renders the human-readable surface from the sealed review event prefix — the run journal is the review's sole source of truth, and the surface is a projection of its sealed events, the same shape the audit kind produces, so no second renderer reads a review-result JSON to produce a parallel surface. The swappable review prompt lives at `references/review-prompt.md` loaded via `${CLAUDE_SKILL_DIR}`; scripts use stdin/stdout pipes when no fanout is required and caller-owned scratch files when the diff input must be available by path; and the wrapper agent reaches the scripts only by invoking the skill, the `journal_emit.py finding-reported` parse being the validity gate before each journal append.

## Rationale

A separate policy module from the CLI scripts because the canonical schema — enum membership, required keys, the path-style `rule` citation form — is what the skill validates; `parse_finding_json` enforces it for the one finding a streaming run raises, making validation total over every entry path, and `journal_emit.py finding-reported` surfaces that parse result as an exit code the wrapper agent reads before each append — the same validity model the audit kind uses. Per-event builders rather than one batch builder because the run-journal contract requires events to stream as the run advances, so a reader resuming from a cursor watches the review in flight rather than waiting for one result at the end; a single builder that emitted a finished review's whole event sequence is the opaque-run shape `spx/15-audit-result-delivery.pdr.md` forbids. Dataclasses plus enums over a JSON Schema document because the marketplace's `verdict.py` sets that stdlib precedent and a second representation invites drift. Frozen dataclasses because instances cross the parse boundary as values. `compute_diff` auto-derives `base_ref` through a precedence chain rather than taking a flag because a flag is extra state three surfaces would drift on, composes the git-derived base to its remote-tracking form so the committed diff is taken against the fetched `origin/<base>` rather than a bare local ref that can lag in a multi-worktree checkout, and appends staged, unstaged, plus untracked diffs so local review covers the full working changeset. The optional diff bundle exists because reviewer input has fanout and random-access needs: the prompt, reviewer, and changed-file progress loop all consume the same potentially large diff, and a path-addressable `diff.md` prevents the agent transcript from becoming the only copy. The manifest gives deterministic section spans and hashes without becoming review state; the caller owns the scratch directory and cleanup, while durable facts remain on the sealed review journal prefix. `journal_emit` consumes the shared run-journal projection instead of carrying a review-specific event model because audit and review share the run-state contract; the adapter owns only review-result-to-projection translation, and it renders the human-readable surface from the sealed event prefix so the journal is the run's sole source of truth — a second renderer reading the review-result JSON would produce a parallel surface that drifts from the journal and forces the caller to stage the JSON in a file the renderer can reach, the exact coupling the run-journal contract removes. Pipes remain preferred between scripts when fanout does not require a directory.

## Verification

### Testing

- ALWAYS: the policy module `review_result.py` declares `SCHEMA_VERSION`, frozen `Finding` and `ReviewResult` dataclasses, the `Severity`/`Concern` enums, the `ReviewResultValidationError` exception, and the `parse_json` / `parse_finding_json` / `to_json_dict` / `from_json_dict` entry points ([compliance])
- ALWAYS: the review-result schema carries findings only — no `summary`, acknowledgement, `decision`, or verdict field — and each consumer applies its own policy by validity and phase ([compliance])
- ALWAYS: `journal_emit.py` exposes one builder per domain event — `scope-entered`, `scope-advanced`, `finding-reported`, `run-completed` — that the streaming skill appends as the run advances, never a single builder emitting a finished review's whole event sequence ([compliance])
- ALWAYS: `journal_emit.py finding-reported` parses one finding through `review_result.parse_finding_json` and exits non-zero on any violation before printing the event — the per-finding parse is the validity gate and no separate CLI re-implements schema knowledge ([compliance])
- ALWAYS: `compute_diff.py` resolves `base_ref` and `head_ref` through their precedence chains — a git-derived `base_ref` is composed to the remote-tracking form `origin/<base>` via `changeset_scope.remote_tracking_ref` so a stale local branch ref cannot widen the diff — and emits labeled sections for committed merge-base, staged, unstaged, and untracked diffs — no `base_ref` source means a non-zero exit naming the env and git sources; `--bundle-dir` writes those sections into caller-owned scratch `diff.md` plus `manifest.json` for random access ([compliance])
- ALWAYS: `journal_emit.py` derives metadata through the shared changeset-scope primitives, maps each finding into the shared run-journal projection as it is raised, emits the terminal `com.outcomeeng.spx.journal.run.completed` event via `run-completed` carrying `headSha`, `baseRef`, `baseSha`, `branchSlug`, `configDigest`, `scope`, and a `status` derived from the streamed event prefix, and renders the human-readable surface from the sealed event prefix read on stdin ([compliance])
- ALWAYS: the human-readable review surface is rendered only from the sealed run-journal event prefix — no script renders a parallel surface from the review-result JSON payload ([compliance])
- ALWAYS: the swappable review prompt at `references/review-prompt.md` is loaded by skill prose via `${CLAUDE_SKILL_DIR}/references/review-prompt.md` — the prompt is data the skill loads, never code ([compliance])
- ALWAYS: the wrapper agent at `plugins/spec-tree/agents/changes-reviewer.md` reaches the scripts only by invoking the skill — its prose contains no `${CLAUDE_SKILL_DIR}`, no `${CLAUDE_PLUGIN_ROOT}`, and no hard-coded path into `scripts/` ([compliance])
- ALWAYS: frozen dataclasses are used for `Finding` and `ReviewResult` — instances are values that cannot be mutated between parse and emit ([compliance])
- NEVER: a CLI script under `scripts/` writes durable review state outside `spx journal`; scripts may read the payload and the prompt file, and `compute_diff.py` may write caller-owned scratch review-input bundle files, but durable run state is the sealed review journal prefix ([compliance])
- NEVER: a second representation of the schema is authored — `review_result.py` is the canonical schema ([compliance])
- NEVER: the review prompt is embedded inside `SKILL.md` or any `*.py` file — it is one standalone markdown file at the declared reference path ([compliance])
- NEVER: a script under `scripts/` imports a third-party package, depends on `uv` at runtime, or imports any `outcomeeng_*` module — stdlib only ([compliance])

### Audit

- NEVER: the reviewer emits a `decision`/verdict, or a surface posts an `APPROVE`/`REQUEST_CHANGES` review on the reviewer's behalf — a review produces findings only; the consumer applies its own policy by validity and phase, never by severity ([audit])
- NEVER: the wrapper agent hand-validates JSON it just emitted by re-checking enum membership or required keys in agent prose — the `journal_emit.py finding-reported` per-finding parse is the validity gate ([audit])
- NEVER: an intermediate file is used between two scripts in the chain when stdin/stdout suffices — pipes over files when fanout does not demand a directory ([audit])
