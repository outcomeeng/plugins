# Merging

PROVIDES the transport-neutral delivery policy — the ordered `VERIFY -> PREVIEW -> MERGE -> DEPLOY -> RELEASE -> CLOSE` lifecycle, the four readiness gates, the finding-disposition rule, and the delivered-value boundary — and the `/merge` transport dispatcher
SO THAT every product that installs the spec-tree plugin
CAN drive a changeset from verified local readiness through merge, declared deploy, declared release, and close under one policy, routed to the project's selected transport, per `spx/15-merging.pdr.md`

## Assertions

### Scenarios

- Given a feature branch whose local base lags its remote-tracking base and whose working tree contains an uncommitted path, when `/merge` classifies the changeset, then it includes the feature and working-tree paths and excludes the path already merged into the remote-tracking base ([test](tests/test_classify_changeset.scenario.l1.py))
- Given a modified coordination note under a path containing a space, when `/merge` classifies the working tree, then the path stays unquoted and is recognized as a coordination note ([test](tests/test_classify_changeset.scenario.l1.py))
- Given a repository whose remote default branch is unconfigured, when `/merge` classifies the changeset, then the classifier exits nonzero with an operator-facing base-ref configuration error and no Python traceback ([test](tests/test_classify_changeset.scenario.l1.py))

### Mappings

- Empty, coordination-note-only, mixed, and duplicate path collections map to total and non-coordination-note counts over their unique paths ([test](tests/test_classify_changeset.mapping.l1.py))
- Every source-owned coordination-note basename maps to recognition at the repository root and below generated directory paths, while source-derived case variants, suffixed names, and truncated-and-relettered names map to rejection at both depths ([test](tests/test_classify_changeset.mapping.l1.py))
- A declared deploy action with an unsatisfied authorization predicate maps to `DEPLOYMENT_READINESS = WITHHOLD` and `delivery_action = AWAIT_DEPLOYMENT_AUTHORIZATION`; an absent deploy declaration maps to `DEPLOY = SKIP` and never blocks release or close ([test](tests/test_merge_gate_policy.mapping.l1.py))
- A declared release action with an unsatisfied authorization predicate maps to `RELEASE_READINESS = WITHHOLD` and `delivery_action = AWAIT_RELEASE_AUTHORIZATION`; an absent release declaration maps to `RELEASE = SKIP` and never blocks close ([test](tests/test_merge_gate_policy.mapping.l1.py))
- A required check's `statusCheckRollup` status and conclusion map to terminal-green only when terminal (`status == COMPLETED`, or `state ∈ {SUCCESS, ERROR, FAILURE}`) and successful (`conclusion == SUCCESS` or `state == SUCCESS`); a `SKIPPED`, `NEUTRAL`, `FAILURE`, `ACTION_REQUIRED`, `CANCELLED`, `TIMED_OUT`, still-running, or absent required check maps to a blocking classification and withholds `MERGE_READINESS` ([test](tests/test_merge_gate_policy.mapping.l1.py))
- A review-kind check's status and conclusion map to `WAIT_FOR_REVIEW` when absent or non-terminal, `INSPECT_REVIEW_SURFACES` when successful, `MENTION_REVIEW_NEEDED` when skipped because the PR modifies the reviewer's own workflow file and no current-head review exists, `INSPECT_REVIEW_SURFACES` when that self-modifying skip occurs with a current-head review present, `MERGE_BLOCKED:review-check-skipped` when skipped for any other cause, and `MERGE_BLOCKED:review-check-failed` when terminal but failed, cancelled, timed out, action-required, or neutral ([test](tests/test_merge_gate_policy.mapping.l1.py))
- An auditor verdict surfaced while the merging flow drives review feedback maps to in-slice unresolved work when the overall verdict is `REJECTED` or `UNKNOWN`, a row status is `FAIL` or `UNKNOWN`, or a finding verdict is `REJECT`; out-of-PR verdicts map to `TRACK_OUT_OF_PR`, and non-blocking in-PR verdicts map to `NO_REPAIR` ([test](tests/test_merge_gate_policy.mapping.l1.py))

### Compliance

- ALWAYS: the `/merge` dispatcher ships as a user-invocable `SKILL.md` under `plugins/spec-tree/skills/merge/`, with no command wrapper, so it activates on both runtimes per `spx/13-plugin-and-runtime-conventions.adr.md` ([audit])
- ALWAYS: the shipped `merging-standards` skill text preserves the deployment-readiness, release-readiness, terminal-green, and auditor-verdict policy clauses that the deterministic merge-policy helper maps, so the mapping evidence stays coupled to the installed flow ([audit])
- ALWAYS: the `/merge` dispatcher remains user-invocable as the product's merge entry point ([audit])
- NEVER: the `/merge` dispatcher re-derives the base ref or diff range inline; its co-located classifier consumes the canonical `changeset_scope` primitives per `spx/21-spec-tree.enabler/14-version-control.enabler/15-changeset-scope.enabler/13-changeset-derivation.adr.md` ([audit])
- ALWAYS: `/merge` reads the changeset, takes the `spx/local/merging.md` transport selector when the overlay declares one, and selects exactly one transport per the precedence (overlay-declared, else coordination-note-only → direct-push, else GitHub-PR), and — on the direct-push path it executes itself — presents a pre-mutation confirmation before the first mutation only when the overlay opts into it, otherwise states the selection and proceeds autonomously ([eval](evals/transport-selection/eval.toml))
- ALWAYS: `/merge` routes each changeset to the selected transport's skills — the GitHub-PR transport to `/manage-github-pr`, the direct-push transport to its own lifecycle — rather than handling the changeset under the wrong transport, per `spx/15-merging.pdr.md` ([eval](evals/transport-selection/eval.toml))
- ALWAYS: `/merge` never reimplements a transport's internal protocol inline — the GitHub-PR lifecycle (commit → open → manage → close) is `/manage-github-pr`'s, and the direct-push lifecycle invokes `/commit-changes` and the `changes-reviewer` review, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: `/merge` treats a branch with committed changes ahead of its resolved base as unfinished and drives the selected transport until the changeset reaches the default branch on origin, then through any declared deploy and release phases before close, or stops at an explicit lifecycle gate; a clean working tree or passing local gate is progress, not completion ([eval](evals/local-completion-boundary/eval.toml))
- ALWAYS: the `CLOSE` phase for every merge transport is satisfied by continuing remaining in-scope work or invoking `/handoff` plain for operator-useful closeout and continuation disposition after the selected transport reaches the default branch and declared deploy/release phases complete or no-op; merge lifecycle skills build an explicit branch-state closeout record, delete a local feature branch whose remote ref is absent, which no live worktree checks out, and whose work is fully upstream — its tip an ancestor of `origin/<base>`, or every branch commit patch-equivalent to an `origin/<base>` commit (`git cherry` reports no `+` commit, the state a rebase merge or single-commit squash leaves behind; a multi-commit squash collapses its patches into one upstream commit that no per-commit patch-id matches, so that branch stays retained) — regardless of upstream configuration, retain a branch carrying any commit that is neither an ancestor nor patch-equivalent with that commit's evidence, include a compact Remaining Branches report, never replace closeout with a receipt-only final response, and never pass `--no-session` on automation's behalf ([audit])
- ALWAYS: the merge lifecycle establishes occupancy before it removes any ref, remote or local, and takes two proofs — the worktree list naming a worktree that holds the branch, and `git status` in every worktree sitting at the branch tip; a worktree detached at that tip carries no branch line and `git branch --merged` hides its uncommitted work, so status is the only proof for it, and a removed remote ref cannot be restored from a retained local branch alone ([audit])
- ALWAYS: once the changeset reaches the default branch on origin and before any declared deploy or release action, every transport fast-forwards the base branch's checkout to the published tip, resolving that one valid checkout and its occupancy from `spx` rather than a ref scan, and skipping with a named reason when the pool reading is absent or non-compliant, when a live session holds that checkout, when it carries uncommitted work, or when its branch is not an ancestor of the published tip ([audit])
- NEVER: a merge-lifecycle skill pre-authorizes the base-checkout refresh's out-of-worktree commands in its tool grants — a write outside the session's declared working directory is the operator's to approve per write, and a grant over a path resolved at run time would cover every path the resolver can report ([audit])
- NEVER: the merge lifecycle refreshes the base branch's checkout by checking that branch out in another worktree, by resetting it, by any advance other than a fast-forward in place, or while a live session holds it — a clean working tree never proves a checkout is free, and a checkout that fails any predicate is left exactly as found and reported, because the merged base on origin leaves every consumer of the local base branch reading a stale commit until that one checkout moves ([audit])

- ALWAYS: the merging skills expose exactly four gates — `VERIFICATION_READINESS`, `MERGE_READINESS`, `DEPLOYMENT_READINESS`, `RELEASE_READINESS` — named with the single word "gate"; every condition a gate reads is a predicate, never a gate, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: the merging policy — the phase sequence, four gates, and finding-disposition rule — is transport-neutral, and `/merge` selects the transport per the precedence, reading `spx/local/merging.md` as an optional overlay only when present (absent → the defaults apply, never a blocker; merge behavior is never reconstructed from incidental docs nor changed by editing a generated guide): a coordination-note-only changeset routes to the direct-push transport, an overlay-declared transport is honored, else the GitHub-PR transport is the default; `/merge` then delegates to that transport's skills, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: the merge-lifecycle skills conduct the changeset's git work in the assigned worktree, resolving a worktree or branch conflict by branching there and continuing, and never operate in a worktree a live agent holds, never create a worktree, and never `git stash`, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: this product's `spx/local/merging.md` runs the default `spx diagnose` machine report before each merge-lifecycle entry's first checkout-sensitive mutation, repeats it immediately before the merge command, and runs it after feature-worktree cleanup; requires the named `worktree-pool` check to report a readable designated main checkout attached to the resolved default branch; refuses to run the merge lifecycle from that designated checkout; permits detach-based cleanup only for a feature worktree proven distinct from it; deletes the remote feature branch only after the post-cleanup predicates pass; and runs persistent marketplace installation from the assigned checkout after it reaches merged `origin/main` ([audit])
- ALWAYS: each transport binds the gate predicates — which verification predicates establish `VERIFICATION_READINESS`, which checks are required, how `VERIFICATION_READINESS` publishes the changeset, and which deploy or release actions exist — without adding, removing, reordering, or renaming a gate or changing the disposition rule, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: `MERGE_READINESS`, `DEPLOYMENT_READINESS`, and `RELEASE_READINESS` are decidable from observable state — an independent reader reaches the same verdict — and carry no time-based settle, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: the agent acts on each review finding by validity, phase, and scope across the union of current-head review surfaces and reviewers — at `VERIFICATION_READINESS` applying every valid finding that belongs and splitting out only a fix too large to belong, at `MERGE_READINESS` fixing every valid in-scope finding and re-publishing; a clean review, passing check, or approved audit does not cancel a separate valid finding — and a bounded fix (a rename propagation, a cross-reference update, a mechanical change, a fix that merely touches another file, or a deeper variant of the same defect class surfaced by a later review round) is in scope and fixed in the changeset; a `DEBT` finding is deferred only when its fix is a separate larger concern recorded in `ISSUES.md` / `PLAN.md` with a reason naming why it is large, per `spx/15-merging.pdr.md` ([audit])
- NEVER: relabel a defect the changeset's own edits introduced — a stale claim, dead code, a broken cross-reference, a falsified spec — as a separate larger concern to escape a review-convergence loop; a self-caused defect is in scope however many files its fix touches, and a separate larger concern exists independently of this changeset, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: an auditor verdict surfacing while the merging flow drives review feedback — an overall `REJECTED` or `UNKNOWN` verdict, a row `FAIL` or `UNKNOWN`, or a finding `REJECT` — is in-slice unresolved work the flow fixes or resolves before merge, never deferred `ISSUES.md` / `PLAN.md` work, per `spx/21-spec-tree.enabler/16-verification.enabler/15-verdict-toolchain.enabler/verdict-toolchain.md` and `spx/15-merging.pdr.md` ([audit])
- ALWAYS: the merging skills re-establish the transport's `VERIFICATION_READINESS` predicates before every push — opening and follow-up — running the declared deterministic and agentic verification on the diff that push would publish, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: when a transport requires the full deterministic bundle, the merging skills run it only after all applicable evidence audits and agentic reviews converge on the same clean committed head, never before agentic verification or concurrently with another heavy command; any later change invalidates the full-gate result and reopens the affected agentic predicates before the next full-gate run ([audit])
- ALWAYS: the merging skills bring a behind-base branch current through sync-base (`spx/21-spec-tree.enabler/14-version-control.enabler/32-sync-base.enabler/sync-base.md`) — an automatic rebase from observable git state with no operator prompt; the only touch-point is an unresolvable conflict surfaced as a structured `conflict` report with active rebase state, while a `dirty_tree` outcome is cleared by committing through `/commit-changes` then re-syncing, never stashed and never surfaced as a conflict, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: after a clean rebase the merging skills either re-establish `VERIFICATION_READINESS` predicates on the rebased diff before pushing, or carry sync-base's readiness-preservation proof — reusing converged agentic verification only when the branch patch is unchanged and the base delta neither overlaps the branch's paths nor touches a governance surface named in `spx/local/merging.md`, and running only that overlay's narrowest validation lane covering the base delta, falling back to the full deterministic gate when any base-delta path is unclassified; the proof never satisfies `MERGE_READINESS`, whose current-head check and review predicates still hold after the push, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: the merging flow drives a determined changeset from intent to merge without an up-front operator proposal by default; a project opts into a pre-mutation confirmation through `spx/local/merging.md`, and only then does the flow present the changeset and intended lifecycle through the runtime's structured-question tool and wait before the first mutation, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: local-readiness status assessments may report the evidence they found, then continue through `/merge` when committed changes remain ahead of the resolved base, unless the user explicitly limited the task to local-only work or an explicit lifecycle gate blocks continuation, per `spx/15-merging.pdr.md` ([eval](evals/local-completion-boundary/eval.toml))
- NEVER: treat the pre-mutation confirmation as a default or a fifth gate — it is an opt-in overlay touch-point that leaves `VERIFICATION_READINESS`, `MERGE_READINESS`, `DEPLOYMENT_READINESS`, `RELEASE_READINESS`, and the finding-disposition rule unchanged, per `spx/15-merging.pdr.md` ([audit])
- ALWAYS: the merging skills invoke the local `changes-reviewer` review at parity with the integration-time reviewer — the review resolves its own scope (the worktree it runs in and the base/head diff), and the caller adds no interpretive scope, severity pre-filter, or emphasis steering — per `spx/15-merging.pdr.md` ([audit])
- NEVER: gate any of the four gates on a review finding's severity label, or use a time-based settle as a readiness predicate — validity, phase, and scope decide; a `DEBT` finding the author records as a separate larger concern is non-blocking because of scope, not its label, per `spx/15-merging.pdr.md` ([audit])
- NEVER: treat an agent-inferred "the work looks done" as a gate, or satisfy a gate's review predicate by invoking a review skill in the working conversation rather than the `changes-reviewer` agent — a gate's predicates are observable or deterministically computed state, per `spx/15-merging.pdr.md` ([audit])
