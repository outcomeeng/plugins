# Test Verification

PROVIDES Outcome Engineering governance for deterministic test evidence, test-infrastructure ownership, source testability, property-test reproducibility, and full-chain test-evidence audits
SO THAT methodology tests, plugin tests, runtime validation, and language-specific test standards
CAN prove spec assertions through source-coupled evidence without laundering domain truth through test files or helper modules

This node is the single language-neutral superset of the test-evidence seam rules. Every rule any language test-standard node enforces is asserted here once; a language node cites this node and `spx/31-outcomeeng.enabler/31-verification.enabler/31-test-verification.enabler/15-test-infrastructure.pdr.md` and declares only its language delta — assertion API, binding forms, generator libraries, test-infrastructure home, and runner specifics — never restating these rules or weakening them.

## Assertions

### Compliance

- ALWAYS: harness, generator, fixture, source-contract, test-infrastructure-home, and full-chain audit semantics derive from `spx/31-outcomeeng.enabler/31-verification.enabler/31-test-verification.enabler/15-test-infrastructure.pdr.md` ([audit])
- ALWAYS: source modules expose the observable contracts tests need — pure functions, typed dependency parameters, interfaces, protocols, traits, registries, constructors, schemas, enums, or typed factories — so behavior is testable through the production API, and the source contract is improved before a test accepts a workaround ([audit])
- ALWAYS: command and script entrypoints stay thin boundaries around imported orchestrators or domain modules; tests verify parsing and dispatch at the boundary while deeper behavior is tested through reusable modules ([audit])
- ALWAYS: behavior crossing a process, filesystem, clock, network, database, or service boundary is reached through typed interfaces, context managers, or injected collaborators so evidence stays coupled to real behavior without framework replacement mocks — dependency injection over mocking, because reality is the oracle ([audit])
- ALWAYS: a controlled implementation or recording collaborator conforms to the production dependency's typed boundary, preserves behavior-relevant state, and exposes observations while the linked test owns every predicate ([audit])
- ALWAYS: the linked executed test owns every behavioral predicate and assertion API call; harnesses, generators, fixtures, and controlled collaborators expose observations, handles, generated values, or resource lifecycles and never accept an expected outcome, return a verdict, call an assertion API, or expose a verdict-shaped helper ([eval](../../../21-spec-tree.enabler/68-audit.enabler/32-audit-tests.enabler/evals/full-chain-ownership/eval.toml))
- ALWAYS: a test-file binding is valid when it only receives or renames an observation, source-owned contract, generated value, harness handle, or fixture path introducing no data or policy, and belongs to its semantic owner when it chooses a case, expected result, runner or seed configuration, setup policy, generator domain, fixture content, or verdict rule ([audit])
- ALWAYS: every case — input and expected output — derives from a source independent of the test author's invention: the spec scenario, a finite source-owned enumeration, a generator over a domain, an external conformance oracle, the governing compliance rule, or an inert whole-payload fixture, so every case is auditable to a source outside the author's head ([audit])
- ALWAYS: values the source owns or imports come from the runtime, framework, protocol package, or production module through registries, enums, constructors, typed factories, schemas, dataclasses, tuples, or structured metadata; tests consume those contracts rather than defining local stand-ins or duplicating them ([audit])
- ALWAYS: a symbol is source-owned when a contract outside the test tree requires it — production consumes it, emits it, publishes it as API, registers it, or serializes it against a declared schema — so the source improvement a weak test demands is a contract the product already owes rather than one minted to give the test a citable address ([audit])
- ALWAYS: values only the test needs are generated when they represent a variable input domain — paths, names, identifiers, option sets, contents, encodings, counts, or product shapes — and generators vary, compose, shrink, or explore more than one meaningful value beyond naming a constant ([audit])
- ALWAYS: expected outputs for generated inputs derive from the input, an independent oracle, or a source outside the module under test, never through the same implementation path that produces the actual output ([eval](../../../21-spec-tree.enabler/68-audit.enabler/32-audit-tests.enabler/evals/full-chain-ownership/eval.toml))
- ALWAYS: every scenario, mapping, property, conformance, and compliance case has assertion-type-appropriate provenance and an oracle independent of the implementation path under test; inverting the linked test's predicate changes only that test, and mutating or disabling the production behavior makes the evidence fail ([audit])
- ALWAYS: property-based tests run through spec-governed harnesses that own seed selection, run count, replay input, and failure diagnostics so a failing property run is reproducible from the reported evidence, and the executed test does not own property-run configuration ([audit])
- ALWAYS: harnesses manage setup, teardown, cleanup, dependency checks, lifecycle, and access to real resources or behavior, preserving coupling to the behavior an assertion verifies ([audit])
- ALWAYS: fixtures are inert whole-payload inputs read from disk, copied into temporary products, or passed by path to the code or tool under test; executed tests never import fixtures as modules or consume fixture exports ([audit])
- ALWAYS: test-evidence audits inspect the executed test file and every imported or referenced test-infrastructure artifact before approving evidence, naming the exact artifact and evidence property affected by any finding ([audit])
- ALWAYS: an absent in-repository caller opens the ownership question rather than settling it, so a test-evidence audit inspects dynamic registration, the published package surface, generated and reflective use, and consumers outside the checkout before classifying a symbol as laundered ([audit])
- ALWAYS: a language-specific test-standard spec node cites this node and `spx/31-outcomeeng.enabler/31-verification.enabler/31-test-verification.enabler/15-test-infrastructure.pdr.md` by full path and declares only its language delta — the assertion API, binding forms, generator libraries, test-infrastructure home, and runner specifics for that language — never restating or weakening the language-neutral seam rules this node owns ([audit])
- NEVER: accept a test whose only path to passing is copying source literals, pinning arbitrary example objects, mocking the behavior under test, or storing isolated strings in fixture files — those patterns expose a missing source contract, and the source is improved before the test is accepted ([audit])
- NEVER: preserve hard-to-test source shape as a constraint on test design — the spec governs source design and the implementation complies ([audit])
- NEVER: use a hand-picked case based on the author's understanding of what would exercise the code — the author encodes the model the code embodies, and every future run confirms that shared model rather than the spec ([audit])
- NEVER: use shared test-owned constant bags — named example collections standing in for source-owned values — as a fix for duplicated literals; moving a hand-picked value behind a name adds no evidence ([audit])
- NEVER: a case, example, or expectation table sits inside a module under test so a test can cite a production path as its provenance — a symbol whose existence is explained only by the test that reads it is not a source contract however public its name or address ([audit])
- NEVER: a generator whose whole behavior is a constant-only wrapper for a source-owned singleton shape — the owning source module provides the constructor, registry, enum, or schema ([audit])
- NEVER: a harness replaces the behavior under test with a mock, fake, stub, monkeypatch, intercepted response, or equivalent while the assertion claims to verify that behavior ([audit])
- NEVER: a harness, generator, fixture, controlled implementation, or recording collaborator encodes the linked test's predicate through a boolean verdict, expected-value parameter, assertion call, matcher, or verdict-shaped method ([audit])
- NEVER: a fixture file stores isolated strings, numbers, protocol tokens, expected outputs, command names, status values, or edge-case sets as test data, and executed tests never import or consume fixture exports ([audit])
