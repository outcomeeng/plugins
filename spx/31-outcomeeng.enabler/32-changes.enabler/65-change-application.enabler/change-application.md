# Change Application

PROVIDES the Application of one Applicable Change by its Applier — confirming the claim, running each round's producing skills and Verifiers in agent sessions of their own, integrating the changeset, and closing or releasing the Change
SO THAT an Applier session started for a Change
CAN deliver the Change's Output while producing no artifact itself other than a mechanical repair

The product-tree plugin ships one subagent definition per skill an Applier session or its rounds run: `change-applier` fronts `/apply-change`, `change-author` fronts `/author`, `change-verifier` fronts `/verify`, `change-tester` fronts `/test`, `change-implementer` fronts `/implement-change`, `change-skill-author` fronts `instructions:author-skill`, and `change-subagent-author` fronts `instructions:author-subagent`. Each Fixer is a fresh session of the definition its round's Author used, per [`spx/15-agent-terminology.pdr.md`](spx/15-agent-terminology.pdr.md).

## Assertions

### Audit: Application

- claude-code-only: ALWAYS: the seven definitions ship for Claude Code only, and `/apply-change` on Codex returns an explicit unavailable result

- claim-confirmed: ALWAYS: `/apply-change` confirms that the winning Claim names its worktree root and loads the latest Handoff before it starts, and applies only an Applicable Leaf whose blockers are resolved, and refuses a Parent
- application-check: ALWAYS: before the first Declarations subsection, `/apply-change` runs the Application check against the current default branch plus the effects of the Change's earlier subsections in Application order; a failed check lowers the Applicable Change to Sliced, the Applier starts no subsection, writes a Handoff and releases the Change, and while a blocking Change is not yet delivered the Applier waits and the Change keeps its Maturity
- work-branch: ALWAYS: an Applier whose record and newest Handoff name no working branch works on the branch its assigned worktree has checked out only when that branch is not the default branch and its name ends with the Change number with no digit before it, as `work/change-<N>` and `applier-<N>` do and `work/change-1<N>` does not; otherwise the worktree counts as naming no branch, and the Applier creates the work branch `work/change-<N>` from the Change's number and starts there; a branch the record or the newest Handoff names stays the working branch
- round-sessions: ALWAYS: the Applier launches, for every round, one agent session of the kind that produces the subsection's result — decisions and specs, verification evidence, tests, implementation, a skill surface, or a subagent definition — and launches each Fixer as a fresh session of the same kind, handed exactly the rejected run's sealed run file, unchanged, and the instruction "attend to every rule the run names and sweep each named class across the whole target"
- fixer-input-plain: NEVER: the Applier adds a summary, a remedy, a class name, or any other interpretation of the findings to a Fixer's input
- surface-rounds: ALWAYS: a subsection whose Node's result is a skill surface — a skill's instructions, another file in a skill directory, or an authored shared fragment — runs as a round of the skill-surface producing kind judged by the skill auditor, and a subsection whose result is a subagent definition runs as a round of the subagent-definition producing kind judged by the subagent auditor; the Applier launches that Verifier after the round returns, as the merge composition of merging-standards names it, and the round launches none
- subsection-order: ALWAYS: the Applier takes the Declarations subsections in Application order, derives each subsection's results and Verifiers from the merge composition of merging-standards for the Node's malleability after and the verification type each Assertion's group heading names, and records its progress only in its Handoff; a round session never writes the Change record, and the Applier writes it only to make a Transition, to lower its Applicable Change to Sliced and write a changed decision line, or to write a reopened judgment's question and submit the Change
- round-launches-none: NEVER: a round session launches a Verifier; the Applier launches every Verifier that the merge composition of merging-standards selects for the subsections
- changelog-in-round: ALWAYS: a plugin changelog entry is produced in the round that produces the skill or subagent surface it records
- missing-skill-blocked: ALWAYS: a round whose fronted skill is not installed returns a `blocked` result naming that skill
- implement-change-skills: ALWAYS: `/implement-change` finds the installed `author-{lang}-architecture`, `author-{lang}-code` and `simplify-{lang}-code` skills and runs the target language's skills in its one session — `author-{lang}-architecture` for a language decision, `author-{lang}-code` for implementation, then `simplify-{lang}-code` where the language ships one — and launches no subagent
- configured-verifiers: ALWAYS: `/apply-change` launches its Verifiers from the configured auditor and reviewer definitions, each named exactly and each with a target-only prompt
- applier-mechanical-only: NEVER: the Applier produces an artifact of a round other than a mechanical repair — a fix of a finding that changes no behavior or decision, covering a path or link, a typo, a wording the finding states, or a renamed identifier, and never decision-record text — which it makes directly with no Fixer round; it takes the Declarations subsections in Application order, integrates the changeset, and closes the Change or releases it with a Handoff, per [`spx/15-agent-terminology.pdr.md`](spx/15-agent-terminology.pdr.md)
- repair-reruns: ALWAYS: after a mechanical repair the Applier runs Validate and every Test and Evaluate result the repair invalidates again; the repair launches no Verifier and counts toward no gate's cap, and the next Verifier the merge composition of merging-standards selects judges it, per [`spx/15-merging.pdr.md`](spx/15-merging.pdr.md)
- override-read: ALWAYS: a rejection the operator overrides counts toward no gate's cap, and the Applier reads the override from the verification run that names its actor, the subject commit, the artifacts judged, and the verdict set aside, never from a message or a comment; no override applies to a Deterministic result, per [`spx/15-merging.pdr.md`](spx/15-merging.pdr.md)
- gate-cap: ALWAYS: an Applier launches each gate at most twice per Change, counting every rejection from any session, including those of a Fixer round and of the reviewers and auditors `/merge` launches; after the second rejection it releases the Change with both rejections named by gate and run token in the Hazards line of the Handoff, and a third launch of that gate on that Change is refused with the count
- no-repeat-gate: NEVER: an Applier repeats a gate until it approves
- rejection-count: ALWAYS: a rejection counts when a `blocking` finding, or a `debt` finding an audit raises, sits on a line the changeset changed or is caused by its edit, and a complete `BLOCKED` diagnostic from an audit gate counts as a rejection with no finding to read; a `debt` finding a review raises, a filed finding, a stale finding and a finding on untouched text count for nothing, a launch that seals no run counts for nothing, and a published revision of the record's body restarts the count
- debt-ruling: ALWAYS: an Applier passes each new `debt` finding a review raises on text the changeset touches or invalidates up the chain of positions for its ruling and acts on the finding only as the ruling directs, per [`spx/15-merging.pdr.md`](spx/15-merging.pdr.md)
- cap-agentic-only: ALWAYS: the cap covers agentic gates only; a deterministic command that fails runs again after its Fixer round outside the cap, and one that fails again after that round releases the Change
- thin-definitions: ALWAYS: `change-applier`, `change-author`, `change-verifier`, `change-tester`, `change-implementer`, `change-skill-author` and `change-subagent-author` each front exactly one skill, hold no logic, and inherit the invoking session's execution policy
- foreground-load-gated: ALWAYS: a load-gated command `/implement-change` runs stays in the foreground, and the skill reports its result only after every such command has exited
- sealed-verdicts: ALWAYS: `/apply-change` reads the verdict of each `adr-auditor`, `pdr-auditor`, `spec-auditor`, `test-evidence-auditor`, `eval-evidence-auditor`, `changeset-coherence-auditor`, `implementation-auditor`, `assertion-auditor`, `skill-auditor` and `subagent-auditor` launch from the sealed run whose token the launch returns, and takes the run file from the launch's result: a `rejected` run rejects whatever its finding count, a launch whose run spx refused a payload or the finish of is blocked, and a verdict read from a verdict object outside the run, a transcript, a task-output file, or text parsed into a scratch file is an unusable result
- assertion-auditor-verifier: ALWAYS: `/apply-change` launches `assertion-auditor` as the Verifier for an evidence obligation on a node's Audit Assertions
- fixer-repair-scope: ALWAYS: a Fixer round repairs each valid finding across every instance the cited clause covers and nothing the clause does not require, and returns with its result, for each repair, the clause it applies and the check that shows the class closed, with that check's result; the Applier reads the gate's next verdict from the Verifier it launches, never from that check, per [`spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md`](spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md)

### Probe: definition invocation

- definition-invocation: ALWAYS: each of the seven definitions, as the Claude Code build emits it, loads natively, starts as the child session of one launch by its exact name, and returns a result its fronted skill or its own workflow declares ([probe](probes/definition-invocation/probe.md))
