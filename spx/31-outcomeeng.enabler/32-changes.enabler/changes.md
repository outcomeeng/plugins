# Changes

PROVIDES the Change coordination contract for defining, maturing, persisting, authoring, and auditing one intended Output
SO THAT product engineers and agent sessions coordinating work
CAN move a prioritized Output from proposal to executable work without placing mutable work state in product truth

## Assertions

- A Change record has YAML front matter with the closed key set `title`, `product`, `maturity`, `lifecycle`, `predecessors`, `blocked_by`, and `parent`, plus a body that opens with `## Intent` and adds the sections each Maturity requires in the final format; every key is required, and an unknown key is a defect ([audit:record-front-matter]).
- `change-standards` carries one independently loadable Definition of Ready for each Maturity level: Proposed, Framed, Sliced, and Executable ([audit:dor-per-maturity]).
- No Definition of Ready requires an operator review statement at Proposed, and each Definition of Ready is the complete criterion set for its Maturity ([audit:dor-no-review-statement]).
- The change audit judges each section against the Definition of Ready for the declared Maturity, including that every Governance entry carries the verdict `in line`, `amended`, or `new`, that every amended or new record has a Governance mutations block, and that every Spec mutations block opens with its Node's malleability before and after, and from Executable on with its required state ([audit:final-format-sections]).
- `change-standards` selects the 4.0 Change chapter — `versions/4.0/methodology/change/changes.md` inside the declared `methodology.source` — for a `methodology.version` declaration of `4.0` or `4.0.N` with `N` a non-negative integer, states that comparison, and rejects every other declaration ([audit:methodology-chapter-selection]).
- `author-change` runs one workflow per Maturity level; each workflow loads only that level's Definition of Ready and advances Maturity only when the Definition of Ready holds and the store shows the Product's Maintainer's move of the Change out of `Submitted` at the Maturity it leaves, which is the authority for that Maturity ([audit:maturity-workflows]).
- The change audit raises no `## Artifacts` finding on an Executable record whose section is empty or links only some of its records and Nodes, and rejects a link that names no record or Node of the record's mutations or pins no commit ([audit:executable-artifacts-per-round]).
- Change authoring at Executable writes no result or Verifier into the record, and execution derives them from the merge composition ([audit:executable-derivation-at-execution]).
- ALWAYS: `author-change` checks every same-class site and every section a repair changes before it dispatches a new change audit ([audit])
- `audit-change` reads the complete record front matter first, judges one record against the Definition of Ready for its declared Maturity, and emits a structured Agentic verdict under [`spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md`](spx/31-outcomeeng.enabler/31-verification.enabler/14-verification.pdr.md), whose result carries the run token, the rendered projection's run-level fields, every finding payload verbatim, and the one command that reproduces the complete rendered projection from the sealed run ([audit:audit-verdict-contract]).
- ALWAYS: `audit-change` treats a new record as touched text in full, and a revision as touched text in each revised section and each section the revision invalidates ([audit])
- ALWAYS: `audit-change` reaches the candidate, every repository path, and the SPX store only through its bundled Python runner, and never invokes `rm`, `mktemp`, a shell redirect to a file, or one of its scripts other than as the runner invocation the skill prescribes ([audit:runner-only-access]).
- ALWAYS: `audit-change` issues each runner invocation as its own command, never chained with `&&` or `;` and never piped into another command, and a nonzero runner exit stops the audit with a blocked result naming the request and the exit status ([audit:one-command-per-invocation]).
- NEVER: `audit-change` or its `change-auditor` wrapper writes a file; every payload passes over stdin and stdout, and the SPX run journal holds the run ([audit:auditor-writes-no-file]).
- Persistence writes each front-matter field to its one home in the configured store and reads each back unchanged; the store body carries the Intent and the sections its Maturity adds, without front matter, no field is written to a second home, a store limit never shapes the record, and the persistence skill instruction selects the client for the configured store ([audit:persistence-field-homes]).
- A record whose front matter does not carry the contract's closed key set is outside the contract; it receives no migration, alias, inferred front matter, body-line lineage interpretation, or audit verdict, and the Auditor reports it as outside the contract ([audit:outside-contract-record]).
- `claim-change` claims only an `Available` record whose Product is the configured Product, or a root that carries no Product: it adds the holder, records the Claim naming the claiming session and the worktree root the Change is claimed for — the session's own assigned root, or a root it names — and moves Lifecycle `Available` to `Claimed`, writing neither Maturity nor any body section; any other Lifecycle, an existing holder, or a field mismatch is reported without mutation ([audit:claim-change-contract]).
- Claiming a Change returns the newest Handoff's `Branch or PR` line and continues execution from the Handoff's next block, or from the first block with no Artifacts link when no Handoff exists ([audit:claim-resume]).
- Releasing a Change writes the Handoff into the Change — branch or changeset, the completed Governance mutations and Spec mutations blocks and the next one, blockers, and hazards, never a secret — removes the holder, moves Lifecycle `Claimed` to `Available`, or to `Submitted` when the release submits the Change, and leaves Maturity unchanged, so any agent session may claim an `Available` Change next; it runs only for a session whose assigned worktree root equals the winning Claim's, and reports any other caller without mutation ([audit:release-contract]).
- Closing a Change takes one terminal Lifecycle value, refuses any value outside `Applied` and `Abandoned`, refuses `Applied` for a Leaf while a record or Node the Change adds, modifies, or implements has no `## Artifacts` link, an Artifacts link is not integrated, a Node is off the state the record requires for it, or the Intent's Evidence is unmet, refuses `Applied` for a Parent while a child is open or its last child closed other than `Applied`, closes a root only on the operator's direction, and moves `Claimed` to the named value after writing the terminal record; it runs only for a session whose assigned worktree root equals the winning Claim's, and reports any other caller without mutation ([audit:close-contract]).
- The plugin ships no `/pickup`, `/handoff`, or `/issue` skill and no session-queue entry path; a follow-up is a Proposed Change created through `author-change` ([audit:no-pickup-handoff-issue]).
- Change authoring writes each record from its Maturity's template in the final format, one template per Maturity, and no template carries `## Nodes`, `## Assertion operations`, `## Decisions`, `## Mutations`, or `## Activities` ([audit:maturity-templates]).
- The change audit counts the Intent's words deterministically and rejects an Intent over 60 words, naming the section, the limit, and the count ([audit:intent-word-limit]).
- Change authoring splits a Sliced Change by creating children that name it in `parent` and removing its own Governance mutations and Spec mutations, merges two Changes by closing the absorbed one `Abandoned` and adding it to the survivor's `predecessors`, and reframes a Change in place, lowering its Maturity to `Proposed` ([audit:split-merge-reframe]).
- The change audit rejects a record that carries a Governance mutations or Spec mutations block while another Change names it in `parent`, and a Parent at Executable ([audit:parent-child-rejections]).
- After `close-change` closes a Change `Applied` whose Parent has a Parent and no open child, the same session claims that Parent through `claim-change` and closes it `Applied` through `close-change`, repeating upward; it never closes a root this way, and a Parent whose last child closed `Abandoned` stays open ([audit:parent-cascade-close]).
- `close-change` establishes that an Artifacts link is integrated by `git merge-base --is-ancestor` of the merge commit the link pins and the default branch exiting zero; before a new decision merges, `author-change` posts its content as a comment on the Change's issue with `gh issue comment --body-file`, and `## Artifacts` links that comment ([audit:artifacts-integration-check]).

### Compliance

- NEVER: the bundled Python runner of `audit-change` writes a file; each invocation reads one JSON request on stdin and writes one JSON result on stdout, and the SPX run journal is the only state that persists between requests ([test](tests/test_audit_change_run.compliance.l1.py))
- `confirm-change` moves a `Submitted` Change to `Available`, posting one comment that records the confirmation or the rejection with its reason and names the delegate, the operator it acts for, its agent harness, and its agent session; it writes no Maturity and no body section, and reports any other Lifecycle without mutation ([audit]).
- `audit-change` reads every authority event from the store's field-change events and confirmation comments, never from the body, and judges a record carrying body authority text as defective ([audit]).
- The `audit-change` runner's `read-authority` operation reads a Change's field-change events and comments at 100 per page and at most 10 pages, and returns a blocked result naming the bound when the read fills it ([test](tests/test_audit_change_authority.compliance.l1.py)).
- ALWAYS: `author-change` launches its `change-auditor` at most twice on one candidate, re-audit before publication included, and ends after the second rejection, reporting the outstanding defect class; a re-read before publication that changes the candidate after the second launch withholds publication and reports the intervening edit ([audit])
- ALWAYS: `audit-change` judges a revision of a published record only on the sections the revision changes and on unchanged text the revision makes false, reading the published body from the store; a finding on any other section is recorded as debt, a run whose findings are all debt finishes rejected, and that rejection blocks neither publication nor the gate count; a record with no published body is judged whole ([audit])
- ALWAYS: `author-change` publishes a revision whose sealed change-audit run is rejected with no blocking finding and every finding at debt, and treats every other rejection as a rejection; it dispatches the `change-auditor` for a revision of a stored Change with the candidate path and the canonical `<owner>/<repo>#<N>` store reference in the task message, and the `change-auditor` sets the `audit-change` request's `issue` from that reference and from nothing else ([audit])
- ALWAYS: the `read-published` operation of the `audit-change` runner takes exactly an operation name and a canonical `<owner>/<repo>#<N>` issue identity, reads that issue's body from the store through one `gh` query, writes nothing, and returns the body, the empty string when the store holds none; a malformed request is `invalid-request`, a failed or unrunnable `gh` call is `command-failed`, and a store answer without a body string is `unreadable-output` ([test](tests/test_audit_change_published.compliance.l1.py))
