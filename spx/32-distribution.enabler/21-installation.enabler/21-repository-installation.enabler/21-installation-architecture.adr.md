# Repository Marketplace Installation Architecture

Marketplace installation uses a Python ports-and-adapters boundary: typed observations become an immutable preflight report and plan, agent-specific adapters execute that plan through injected Protocols, and the CLI entry point binds the real subprocess runner. Persistent planning separates selected plugins, activation, registration source, and cache availability so refresh preserves the state contract in `spx/12-marketplace-state.adr.md`. Isolated planning redirects installation state into disposable homes and registers the invocation checkout.

Persistent preflight reads each agent's marketplace registry through the agent's own listing command, taking the entry that carries the committed catalog's name as the source the run refreshes from; the catalogs supply the name and no constant supplies the source. It reads Claude Code's complete install-record listing and the selected Codex home's raw plugin declarations, including disabled entries whose cache or marketplace snapshot is missing. From the Claude Code listing it derives two things: the invocation checkout's project- and local-scope inventory, which selects the bootstrap set and the native-update set, and every other project- or local-scope install record of a cataloged plugin on the machine — one per plugin, scope, and project path — which the plan brings to the target by rewriting its install-record entry. It validates every nonempty catalog-bounded selection contains `spec-tree`, derives empty state as the `spec-tree` bootstrap selection with a warning, and orders names through the committed catalog. Read-only activation observations retain the pre-run declarations for comparison. Selected subsets and agent-definition collisions validate before the first state-changing operation. A missing registration is the bootstrap case: the run registers the source the invocation checkout's own settings declare. No clone exists when that plan is built, so it carries no target; every other checkout's record is reported as unrefreshed with its listed version, the exit is nonzero, and the next run, which finds the registration, brings them to the target.

The plan distinguishes native refresh from bootstrap and recovery. Native refresh updates selected plugin content without activating disabled plugins; activating install or enable commands do not implement routine refresh. The native marketplace refresh moves the registered clone to the head of its source's default branch; that commit is the target, and for each cataloged plugin the target version is its manifest version at that commit and the target install path is the cache directory that version names. For Claude Code, the invocation checkout's own records receive one `plugin update` each at their scope, executed with the invocation checkout as working directory, which fetches the target into the shared plugin cache. Every other project- or local-scope record of a cataloged plugin is brought to the target by a rewrite of its entry in the install-record file — install path, version, and commit — planned as a pure function from the opening listing and the target entries and performed once, atomically, by the single writer at the execution boundary, before the closing listing read the run's postcondition depends on, preserving every entry and field the plan does not set. The rewrite runs no command in any other checkout and does not depend on the record's project directory existing. A record whose plugin the catalog does not carry, or whose scope is neither project nor local, is reported as a warning and left unchanged. A listing entry at project or local scope that names no project path is reported as a listing defect; the run continues and its exit is nonzero. Install and enable are suppressed for every plugin the invocation checkout records at project or local scope; they run only in the bootstrap case, where the checkout records none, and only there do the invocation checkout's own settings matter: unreadable settings stop bootstrap and nothing else. A cataloged plugin that no invocation-checkout record names and whose target version has no cache directory is reported as unrefreshable, its records untouched, and the exit is nonzero; the run never writes the plugin cache itself. An empty Codex home receives a disabled `spec-tree` declaration. Cache recovery preserves existing activation, including explicit home enablement, and never treats an unchanged marketplace snapshot as proof that each selected plugin cache exists. After execution, native state inspection and declaration comparison establish the selected set, activation, and refreshed or pending status of every selected plugin. Unexpected changes are terminal diagnostics, with no snapshot restoration or compensating activation writes. That postcondition is bounded to the invocation checkout and the selected home, whose bootstrap install and enable are the only operations that write an activation entry; a recorded checkout elsewhere receives the install-record rewrite alone, which touches no settings document, so its settings carry no postcondition. The machine-wide refresh carries its own postcondition read: the plan is built from one install-record listing taken in preflight, and after execution the run takes a second listing and compares every project- or local-scope record of a cataloged plugin with the target, reporting each record's version before and after and exiting nonzero when any such record — planned, or written by another session between the two reads — is off the target. The run neither locks the agent's record store nor issues a further update or rewrite; the comparison and the exit code are its complete response. The exit is nonzero when that comparison leaves any record off the target and when the run raises a blocking warning, which is how a condition no record carries — a listing entry with no project path, a bootstrap run with no registered clone, a cataloged plugin whose target version has no cache directory — reaches the exit code.

Persistent Codex inspection and mutation use an explicit selected `CODEX_HOME` and an execution directory outside trusted product configuration discovery. Reading raw home configuration alone is insufficient: the native command's merged configuration must also exclude product overrides. The invocation checkout remains the source of the catalog and generated definitions, independently of the native command's working directory. Every Claude Code command the run executes — marketplace listing and refresh, install-record listing, and the bootstrap and native-update commands — runs with the invocation checkout as its working directory; no command runs in any other checkout.

Pending publication requires established absence of a selected plugin from the registered marketplace source. The report identifies that plugin and continues with the other selected plugins; command failure alone, cache absence, and authentication failure never establish publication absence. Isolated mode treats publication absence as terminal. Generated definition reconciliation consumes only plugin content successfully available from the same installation; a pending plugin retains its prior owned definitions and is reported without claiming a refresh or copying definitions for unavailable skill content.

Codex agent-home placement uses a marketplace ownership record keyed by destination path, owning plugin, and installed-content digest. A plugin's shipped `place_agents.py` entry point may create, replace, or prune only that plugin's recorded definitions; repository installation composes home-selected plugins' entries and performs the distinct marketplace-wide reconciliation, so a recorded definition whose plugin leaves the home selection is pruned with the skills it invokes. Product activation never filters this registry. A recorded definition is replaceable or removable only while its on-disk digest still matches the record; an unrecorded destination whose bytes already equal the desired shipped content is adopted by updating ownership without rewriting the definition, and any other unrecorded or modified destination is a collision left untouched. Before any marketplace, plugin, agent-definition, or ownership-record mutation, planning compares checkout definitions against the skill scope they invoke: byte-identical plugin copies shadowing home skills receive a directed-removal report, changed or unrecognized copies receive a collision report, and either class rejects the complete plan. A checkout that itself carries the invoked skill content remains a coherent placement scope.

Installed subagent discovery uses one fresh non-interactive Codex session against a disposable installation. A typed authentication selection chooses subscription, API, or workspace-token mode; local selection defaults to subscription and CI requires an explicit mode. Credential presence never selects a mode or permits fallback to another billing mode.

Subscription mode resolves the original selected `CODEX_HOME` before redirecting the child environment. After installation, only the disposable home's `auth.json` links to the selected existing file-backed ChatGPT login. The child uses the file credential store and the native CLI owns refresh and persistence through that link. A compatibility preflight with fabricated credentials in temporary homes verifies write-through behavior before the saved login is exposed. Keyring-only, malformed, missing, or non-ChatGPT saved credentials fail with an actionable diagnostic.

Participating verification processes serialize access to the canonical credential file for the credential-use interval within the probe's timeout. File identity, account identity, and link destination are checked before and after use. A detected replacement or account switch fails without restoration or automatic retry. Unrelated CLI processes retain native refresh concurrency semantics; the harness neither controls their locks nor promises to prevent their races. The harness performs no OAuth exchange, saved-home login or logout, or temporary credential-copy restoration.

API and workspace-token modes require `OPENAI_API_KEY` and `CODEX_ACCESS_TOKEN`, respectively, and provision only the disposable home through native login with the credential on stdin. Unrelated credential variables are removed from child environments. One injected Protocol owns process invocation with array arguments, explicit environment, working directory, stdin, and timeout. Captured output and timeout diagnostics are scrubbed against both initial and refreshed credentials before an observation or exception is exposed.

The fresh session reports available subagent names in a harness-owned JSON schema. Its read-out must include the canonical names whose definitions the same installation placed in the disposable home. Installation, login, and session failures are terminal. The harness exposes observations; linked tests own the comparison and every pass/fail predicate.

Native profile-execution evidence is a matrix over the selected agent harnesses and all Standard, Strong, and Fast profiles owned by `outcomeeng.distribution.profiles.AGENT_PROFILES`. An optional --target selects one supported harness; omission selects every supported harness. A row derives its complete native configuration from that registry and materializes its native probe definition beside the installed skill content in one disposable state root. The profile-execution entrypoint extends the repository-installation harness and owns the row lifecycle: isolated installation, configuration capture, native-definition loading capture, parent-session configuration capture, one native subagent invocation, result capture, credential scrubbing, and cleanup. It exposes no verdict. The `just verify-native-profile-execution <artifact-directory>` recipe is the sole execution boundary for that entrypoint and retains one configuration artifact, one loading artifact, and one result artifact for each `<harness>-<profile>` row beneath the caller-selected artifact directory. The configuration artifact identifies the profile-probe definition derived from the central profile owner. The loading artifact identifies the definition discovered from disposable state. The result artifact identifies the parent session separately from its one child invocation and records the child's sanitized result: Claude Code supplies forwarded stream events carrying `parent_tool_use_id`; Codex supplies the parent thread identity through exec JSONL, then lists that parent's active and archived spawned children through the native app-server interface with an explicit subagent source filter and complete pagination. Exactly one listed child permits one thread/read request in the same disposable state. Missing, multiple, malformed, or unrelated child identities produce unusable evidence. Listing pages and the child response are retained. The Codex child-thread record supplies its configured role, recorded model and effort, and completion evidence. Recorded model and effort are configuration evidence, not per-turn execution telemetry. Exec spawn events and parent prose establish none of those properties. A main-session `--agent`, `--model`, or `--profile` selection is retained only as parent-session configuration and never substitutes for the native subagent invocation. Each artifact identifies its row and contains no credential value. The one selected credential channel for a row reaches only the corresponding native CLI boundary. Credential absence, loading failure, or an unusable session result records that row as failed evidence, without a retry, alternate credential channel, profile substitution, or alternate launch mechanism.

## Rationale

Separating declaration parsing, installed-state inspection, scope and collision inspection, validation, plan construction, and external CLI execution makes the exact selected plugin set and every mutation target inspectable before the first write. Persistent mode uses each agent's supported ownership model: Claude Code project and local scope keyed by project path, and Codex's selected home. Catalog ordering gives stable command plans without turning catalog membership into automatic installation. The content-bound ownership record distinguishes files a prior marketplace operation may update from foreign or locally modified files, while the committed catalog gives the repository installer authority to reconcile removed agents and plugins across the marketplace without granting one plugin control over another plugin's namespace; deriving the desired definition set from the selection keeps every placed definition beside skills the same run installed. Rejecting the whole plan on a checkout scope split prevents skill refresh from advancing underneath a shadowing checkout definition. Isolated mode establishes full and subset behavior at the real CLI boundary with persistent installation state isolated and saved-login access limited to the declared credential exception. The subagent-discovery probe exists because the co-location decision rests on the agent loading subagent definitions from its selected home; the app-server protocol lists no user-scope subagent definitions, so a real tool-backed session is the only surface that can answer, and a schema-declared structured result keeps that answer machine-checkable rather than model prose. Deriving the expected set from the same run's placement keeps the discovery oracle independent of the session. A link to the selected credential file lets native refresh persist without introducing a stale temporary-copy restoration; copying refreshable bundles into independent homes would require a second persistence mechanism. The behavior under test is the agent's deterministic subagent registry, and the model inside the probe session is only its schema-constrained read-out channel — the agent exposes that registry through no other surface — so the probe's evidence is a deterministic test scenario over structured output rather than an eval over model judgment. Controlled runners used under `/test` Stage 5 Failure simulation expose first-failure behavior that a successful real install cannot produce reliably, while recording collaborators used under `/test` Stage 5 Interaction protocols expose command order and shape. A closing listing supplied under `/test` Stage 5 Time and concurrency exposes what a real CLI cannot produce on demand: a record another agent session writes between the two listing reads, or an update that leaves a listed version where it was. A configurable fake used under `/test` Stage 5 Combinatorial cost reproduces the one effect of the native update the run observes afterwards — the record's version, commit, and install path in the install-record file — so the generated record cases run without a registered marketplace and a fetch per case, while the real CLI proves the native update itself at `l3`.

## Invariants

- Installation operations preserve their declaration-derived order.
- Every persistent selection, source, and collision inspection completes before any mutation begins.
- An empty persistent selection maps to `spec-tree` plus one warning and disabled activation where no activation is declared; every nonempty selection is valid only when it contains `spec-tree`.
- Catalog ordering never adds an unselected plugin to a persistent plan.
- The first failed operation is terminal for one installation run, except when inspection of the registered source establishes a selected plugin's publication absence in persistent mode; the run reports that plugin as pending publication and continues.
- Only a persistent plan admits that pending-publication carve-out; an isolated plan registers the checkout as the marketplace, so the same absence there is terminal.
- Persistent Codex commands carry the selected `CODEX_HOME` explicitly and execute outside product configuration discovery; product activation cannot change home-wide refresh selection.
- Persistent Claude Code refresh issues exactly one native plugin update for each project- or local-scope record of a cataloged plugin in the invocation checkout, and exactly one install-record entry rewrite for every other project- or local-scope record of a cataloged plugin, its project directory present or not; every other record — outside the catalog or outside project and local scope — is reported and left unchanged; no reinstall stands in for the update and no agent command runs with another checkout as working directory.
- Refresh and recovery preserve pre-run activation; postcondition failure leaves diagnostic state intact without restoring a configuration snapshot.
- A persistent run reads the Claude Code install-record listing exactly twice — once in preflight to plan, once after execution to compare with the target — and issues no update or rewrite the plan did not carry; it exits nonzero when any project- or local-scope record of a cataloged plugin is off the target afterwards.
- The registered marketplace entry carrying the catalog's name is the source the run refreshes from and reports; a missing registration permits bootstrap from the invocation checkout's own declaration.
- Every installation state path used by isolated mode resolves beneath its disposable home; subscription discovery alone may read and refresh the selected saved-login file.
- Every generated Codex agent destination in persistent mode resolves beneath the selected `CODEX_HOME/agents/` directory.
- Every planned overwrite or prune names a marketplace ownership-record entry whose installed-content digest matches the destination's current bytes.
- A plugin placement plan contains only that plugin's recorded definitions; cross-plugin pruning exists only in repository installation's catalog-derived marketplace reconciliation.
- Scope-split and foreign-collision inspection completes before the first marketplace, plugin, agent-definition, or ownership-record mutation.
- Authentication mode is fixed for the run; failed authentication never switches mode.
- The saved-login file is the sole persistent-state exception during subscription discovery.
- Cleanup removes disposable state without traversing the saved-login link.
- Native profile-execution evidence contains exactly one row for each selected harness and central profile, derived from `AGENT_PROFILES` without an independent model, reasoning, or credential inventory.
- Every native profile probe uses a separate disposable state root and invokes one native subagent after isolated installation and native loading complete.
- Every native profile probe retains configuration, loading, and sanitized result artifacts beneath the recipe's caller-selected artifact directory.
- Every Codex native profile probe reads one spawned receiver thread from its disposable state through the native app-server interface and retains its configured role, model, effort, and child completion evidence with the parent-filtered listing and parent thread identity.

## Verification

- ALWAYS: preflight represents selection, activation, registered source, and cache availability separately in immutable typed observations, validating every selected agent before mutation.
- ALWAYS: Codex selection derives from raw selected-home plugin declarations, including disabled and uncached entries, while Claude Code bootstrap selection derives from the invocation checkout's project- and local-scope inventory and Claude Code refresh reach derives from every install record the listing reports.
- ALWAYS: empty selection produces only the `spec-tree` bootstrap plan, preserving declared activation and choosing disabled activation when absent; an empty Codex home declares it disabled.
- ALWAYS: persistent native refresh and cache recovery preserve selection and activation, with post-run observation reporting drift as failure without restoring configuration snapshots.
- ALWAYS: persistent Codex inspection and mutation execute with the selected home outside trusted product configuration discovery; the checkout remains a separate catalog and generated-definition input.
- NEVER: a registered entry the run cannot locate emits a marketplace removal, replacement, or any other state-changing command; the complete plan stops for explicit repair.
- ALWAYS: missing registration, snapshot, and selected plugin cache are distinct recoverable states; a retry preserves declared selection and activation even when the marketplace revision is unchanged.
- ALWAYS: pending publication identifies established absence from the registered source, preserves that plugin's prior owned definitions, and allows only the other selected plugins' refresh to continue.
- NEVER: trusted-product activation filters, generates, or prunes the home subagent registry; shipped plugin placement remains namespace-bounded and marketplace reconciliation remains home-selection-bound.

### Testing

- ALWAYS: explicit authentication modes select their own required credential source and native login mechanism; local default subscription and required CI selection remain independent of credential-variable presence. ([compliance])
- ALWAYS: subscription verification checks native credential write-through compatibility before linking only the saved-login file into disposable state. ([compliance])
- ALWAYS: participating verification processes serialize saved-login use, preserve native refresh writes, and report detected link, file, or account replacement without restoring an earlier copy. ([compliance])
- NEVER: subscription verification migrates a credential store, implements OAuth refresh, or invokes login or logout against the linked home. ([compliance])

- ALWAYS: committed Claude Code and Codex declarations plus selected installation mode are validated at the boundary and converted into frozen typed records before orchestration consumes them ([conformance])
- ALWAYS: command execution avoids shell interpretation and preserves stdout, stderr, and the exit code in a structured result ([compliance])
- ALWAYS: orchestration reports a failed operation with its agent, plugin when applicable, operation name, and structured command result, then executes no later operation unless established publication absence permits the pending-publication result ([compliance])
- NEVER: the pending-publication carve-out applies to an isolated plan, to a non-plugin operation, or to a failure whose result does not report the plugin absent from the marketplace ([compliance])
- ALWAYS: every Claude Code install record maps to exactly one native plugin update at its own scope when it belongs to the invocation checkout and its plugin is cataloged, to exactly one install-record entry rewrite to the target when it is any other project- or local-scope record of a cataloged plugin, or to one warning naming why it is left unchanged — outside the catalog, or outside project and local scope — with no other command for that record ([mapping])
- NEVER: a persistent plan issues an install or enable for a plugin the invocation checkout already records; refresh of a recorded plugin is the native update alone ([compliance])
- ALWAYS: the isolated harness redirects `HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, and `CODEX_SQLITE_HOME` beneath its disposable home for every agent invocation ([compliance])
- ALWAYS: persistent Codex planning places each generated agent definition beneath the selected `CODEX_HOME/agents/` directory and records its destination, owning plugin, and installed-content digest in the marketplace ownership record ([compliance])
- ALWAYS: plugin placement creates, replaces, or prunes only the invoking plugin's recorded definitions, while repository installation reconciles the complete recorded marketplace set against the current committed catalog ([compliance])
- NEVER: placement overwrites or prunes an unrecorded destination, or a recorded destination whose current digest differs from its installed-content digest ([compliance])
- ALWAYS: reconciliation adopts a present destination whose digest equals the desired shipped digest but which no ownership entry records by updating ownership without rewriting the definition, so a run interrupted before its ownership-record write completes cleanly when re-run ([compliance])
- ALWAYS: a scope-split preflight reports byte-identical checkout copies as directed removals and changed or unrecognized checkout definitions as shadowing collisions, rejecting the complete plan before any mutation in either case ([compliance])
- Given a disposable installation and an authenticated fresh session, when the session reports available subagent names, then its structured name set contains every canonical name whose definition that installation placed under the disposable home's `agents/` directory ([scenario])
- NEVER: discovery exposes an initial or refreshed credential in a command argument, returned capture, diagnostic, or exception, or silently skips a selected check when credentials are absent ([compliance])
- ALWAYS: the persistent run's post-execution install-record listing is a planned inspection executed through the same injected runner Protocol as the preflight listing, so one controlled runner supplies both listings and the run performs no listing read outside the plan ([compliance])
- ALWAYS: an install record carries the version the agent's listing reports for it, and the report document names each record's before and after version and the registered source through source-owned field names ([compliance])
- NEVER: the run derives a record's current version from the marketplace cache, a plugin manifest, or an install path; the agent's listing is the only source for what a record holds, and the target is derived only from the refreshed clone's head ([compliance])
- NEVER: a persistent run executes an agent command whose working directory is any checkout other than the invocation checkout ([compliance])
- NEVER: a persistent run exits zero while any project- or local-scope install record of a cataloged plugin in the closing listing lists a version other than the target ([compliance])
