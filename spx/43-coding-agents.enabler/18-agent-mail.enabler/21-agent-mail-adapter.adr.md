# Agent Mail Adapter

One Python 3.13+ standard-library adapter shipped inside `/operate-agent-mail` owns the complete public `am` command grammar for registration, send, listing, read, and acknowledgement, the project-key derivation from the repository's own common Git directory, the message-record field mapping onto the store's fields and back, response validation, and credential scrubbing. It exposes typed importable operations and a versioned JSON CLI; other coding-agents skills invoke `/operate-agent-mail` as a capability and never construct `am` argument vectors, read the store's database, or derive the project key themselves. No mail operation invokes an SPX command, so the capability depends on no SPX command surface. The adapter also carries the raw-command scanner that detects another shipped coding-agents script constructing an `am` command, and that scanner recognizes the command in argument-vector form and in shell-string form alike.

Read state belongs to the store. Listing binds to the store's non-marking listing surface and changes no record's read state; only the read and the acknowledgement change it. Registration sends no name, because the store owns the name vocabulary and assigns the name.

## Rationale

One capability keeps store command knowledge and the record mapping testable and portable while preserving the skill-directory boundary plugin packaging requires. The project key is the repository's common Git directory because that directory is the one identity every checkout of a repository agrees on: a linked worktree, the pool's bare repository, and the pool's main checkout all resolve the same path, and deleting any individual checkout removes none of it. A key that names one checkout makes a repository's mail identity accidental and mortal — the checkout it names can be deleted while the registrations and message records keyed to it remain, and no later read can prove the project belongs to its own repository. The lookup runs without the variables that can make Git answer the location question from something other than the invoking working directory. That effect alone decides membership, never the mechanism producing it: a variable that names a repository directly answers with that repository, and a variable that bounds where Git may discover one hides the repository the working directory belongs to, but those are two known mechanisms rather than the only ones, and any variable with the same effect belongs to the class whether or not it works either way. Git exports `GIT_DIR` into every hook and into the commands it runs itself, so a mail operation invoked from such a context would otherwise key the store to the repository that ran the hook; a caller carrying a ceiling above the operation's own working directory would instead leave it resolving no repository at all. A variable that only widens the search toward the repository genuinely there falls outside the class and is carried through: removing it could prevent no wrong answer, only a right one, and a cross-mount layout every other Git command resolves would answer repository-unresolved for mail alone. Which names Git carries is Git's to say, so the class is the declaration and the adapter's removal list is the enumeration read against Git's own behaviour. Resolving the key inside the adapter also leaves the capability depending on no other command surface, so a retired argument vector elsewhere cannot break every mail operation. The message record carries fields the store lacks — a kind and a correlation — so the adapter maps them onto fields the store does carry, the subject prefix and the thread id, and reads them back, which keeps the record the unit of meaning while the store stays the unit of delivery. The store's thread alphabet is narrower than a correlation: a canonical Change identity carries characters the store rejects in a thread id. Narrowing the record to the store's alphabet would let a store limit shape the record. The adapter therefore encodes such a correlation into the alphabet and decodes it on read. The store renders the encoded form, so the mapping stays a bijection without the record giving up any correlation it can carry.

Read and acknowledge are two operations because the store's two acts differ in who can observe them. A read records, visibly to the recipient alone, that the recipient judged one message. An acknowledgement is a read the sender can observe. A capability offering only the acknowledgement makes every session that wants to record what it judged announce something it did not mean, or keep a private watermark. A watermark advanced past a record that was never read loses that record to its recipient with no signal that it existed. Per-message read state held by the store cannot fail that way: an unjudged record stays unjudged when a later one is judged, and a session that takes over a mail identity inherits the exact unjudged set with no file to hand over. That guarantee holds only while nothing but the read and the acknowledgement changes read state. A listing that marked what it returned would judge every record on the recipient's behalf the moment it was seen, so listing binds to the store's non-marking surface. Its unjudged mode serves routine reading, and its complete form lets a successor read back what its predecessor judged.

Registration returns a token that proves ownership of the name; the adapter removes it from every result because a token in a result reaches conversation transcripts and pane reads. The name itself comes from the store: the store owns the vocabulary it assigns from, so a caller-chosen name would restate a vocabulary the adapter does not own, and the result carries the assigned name verbatim as the identity every later operation addresses.

A recording of an external contract is evidence only while something triggers its recapture. The captured usage and response fixtures are the committed observations of an executed probe against the installed store, and each carries the tool and version that produced it. A pin change or an observed drift therefore has a probe run to recapture from, and a fixture's provenance is inspectable in the fixture rather than only in this record.

The raw-command scanner sits beside the grammar it detects. A home for raw-command detection that the Prowl, herdr, and agent-mail adapters share is a decision above any one adapter, and this record does not pre-empt it. A script can spell a raw command as a shell string as readily as an argument vector, so a scanner that recognized only the vector would pass the violation it exists to catch.

The adapter binds to one store's command surface, so it stays plugin-local under `spx/12-shipped-scripting.adr.md`, whose extraction rule governs its generic logic.

## Invariants

- One source-owned operation registry covers register, send, list, read, and acknowledge; read and acknowledge are distinct operations.
- The list operation binds to the store's non-marking listing surface: its unjudged mode by default, and its complete form when the request carries the all-records option.
- A record's read state changes only through the read or the acknowledgement; no listing, and no other operation, changes it as a side effect.
- A registration request carries no name; the store assigns the name, and the registration result carries the assigned name verbatim.
- One project-key resolver maps the repository's absolute common Git directory, read for the adapter's own working directory, to the project key, or to the repository-unresolved result; it reads no working directory, environment variable, or parent path as a fallback.
- The key is canonical, and the two layers that make it so are separate. The repository lookup runs with every variable removed that can make Git answer the location question from something other than the invoking working directory — the effect deciding membership rather than the mechanism producing it, so naming a repository and bounding where one may be discovered are known mechanisms rather than an exhaustive pair; a variable that only widens the search toward the repository genuinely there is carried through — so it answers from the process's own resolved working directory alone and no value the caller inherited redirects it, neither onto a repository the working directory does not belong to nor away from the one it does; it therefore resolves the physical directory, and a checkout reached through a symlinked route and through its physical route report one directory. The resolver then normalizes that answer textually, to an absolute path carrying no `.` or `..` segment, no repeated separator, and no trailing separator. Canonicality rests on the lookup; the resolver never re-resolves a symlink, so a lookup that returned a non-physical path would surface as one repository with two keys rather than being silently repaired.
- One record mapping is a bijection between a message record and the store fields the adapter writes: `correlation` to the thread id, `kind` to the subject prefix, `sender` to the sender, `recipient` to the recipients, `subject` to the subject remainder, `body` to the body, `ackRequired` to the acknowledgement requirement, and the store-assigned `id` to the record id.
- The correlation-to-thread mapping carries an adapter-owned encoding for a correlation outside the store's thread alphabet, and decoding on read inverts it exactly. Every thread id the adapter writes lies inside the alphabet, and no encoded form equals a correlation the adapter writes unencoded, so the mapping stays a bijection. The store renders the encoded form.
- Every command execution is bounded, argument-vector based, fully reaped before return, and isolated from the adapter request stream.
- Store identities — message ids, thread ids, agent names, timestamps — remain byte-for-byte values from the public response.
- Captured usage and public-response fixtures are the committed observations of the probe that drives every operation against the installed store, and each fixture carries the tool and the version that produced it. The pin for store grammar and responses is `am` 0.3.36. A change to that pin, or a probe run that reports grammar or response drift, invalidates the affected fixtures and requires recapture from a probe run before they serve as oracles. The project key has no captured oracle, because the checkout shapes a real repository takes are the oracle the resolver is read against.
- A registration result never carries the store's registration token.
- An absent `am` executable yields the store-unavailable result; a working directory that resolves to no repository, an absent Git executable, and a Git invocation that reports no absolute common directory each yield the repository-unresolved result. Neither result triggers a fallback.
- The adapter's external programs are the store CLI and Git; no operation's execution path reaches another program.
- A second terminal handback for one coordination reference that carries the same terminal kind with different content is a conflicting handback. The adapter rejects it with a detail naming the content difference, never reporting it as a kind conflict.
- The raw-command scanner recognizes an `am` command in argument-vector form and in shell-string form.

## Verification

- ALWAYS: the list operation maps to the store's non-marking listing surface in unjudged mode, and a list request carrying the all-records option maps to that surface's complete form
- NEVER: an operation other than read or acknowledge changes a record's read state in the store
- ALWAYS: a read request maps to the store's recipient-only read command and an acknowledge request maps to the store's sender-visible acknowledgement command; neither operation maps to the other's command
- ALWAYS: a registration request carries no name, and the registration result carries the name the store assigned, verbatim
- ALWAYS: every captured usage and response fixture is an observation committed by the installed-store probe and names the tool and the version that produced it

### Testing

- ALWAYS: each source-owned operation maps a valid versioned request to the exact `am` argument vector for that operation under the resolved project key ([mapping])
- ALWAYS: a linked worktree, the pool's bare repository, the pool's main checkout, and a symlinked route to one of them each map to one project key, that key being the pool's bare repository directory, and a working directory that is no repository maps to the repository-unresolved result ([mapping])
- ALWAYS: each variable that can make Git answer the location question from something other than the invoking working directory, and the complete set together, maps to no change in the resolved key — a working directory carrying a value that names another repository, or a value that bounds discovery above itself, still maps to its own repository's key, and a working directory that is no repository still maps to the repository-unresolved result. The domain is the set Git's own behaviour confirms moves the answer off the working directory, read from Git rather than from the adapter's removal list ([mapping])
- ALWAYS: public `am` responses map to versioned source-owned results or named command failures without value rewriting ([mapping])
- ALWAYS: every message record maps onto the store fields and back to an equal record, including a record whose correlation lies outside the store's thread alphabet ([property])
- ALWAYS: a terminal handback record maps to exactly one terminal result carrying the complete initiating coordination reference; a matching repeated handback is idempotent, a conflicting terminal kind for one reference is rejected as a kind conflict, and the same terminal kind with different content for one reference is rejected as a conflicting handback whose detail names the content difference ([property])
- NEVER: a registration result carries the registration token the store returns ([compliance])
- ALWAYS: an absent `am` executable maps to the store-unavailable result and a working directory where no program resolves maps to the repository-unresolved result ([mapping])
- NEVER: an operation reaches a program outside the adapter's own command vectors — every operation completes where only those programs resolve ([compliance])
- NEVER: a shipped coding-agents Python script outside `/operate-agent-mail` constructs an `am` command, as an argument vector or as a shell string, or derives a project key from Git state ([compliance])

### Audit

- NEVER: a shipped coding-agents skill outside `/operate-agent-mail` instructs a workflow to construct `am` commands, invoke `am` command help, or read the store's database ([audit])
- ALWAYS: the store subprocess boundary accepts a dependency-injected `CommandRunner` Protocol and the default runner uses null-device stdin, captured output, and a bounded timeout ([audit])
- ALWAYS: tests inject controlled runner implementations only under `/test` Stage 5 exception 1 (failure simulation) or exception 2 (interaction protocols) ([audit])
- ALWAYS: a controlled stand-in placed at the process boundary rather than injected through the runner — an executable on a restricted search path — stands only as exception 2 (interaction protocols) evidence for the boundary itself, naming which programs the adapter may reach; it never stands in for store behavior, which the captured responses own ([audit])
- ALWAYS: `/operate-agent-mail` owns all bundled-script access; composing skills invoke the capability through the skill surface rather than manufacturing a cross-skill filesystem path ([audit])
- NEVER: framework mocks or monkeypatching replace store behavior or the command-runner boundary ([audit])
- NEVER: the adapter owns another workflow's retry, checkpoint, persistence, result interpretation, or continuation decision ([audit])
