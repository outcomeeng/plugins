# Agent Mail Adapter

One Python 3.13+ standard-library adapter shipped inside `/operate-agent-mail` owns the complete public `am` command grammar for registration, send, list, read, acknowledge, and wait, the pass-through of an optional display name on registration, the preservation of the store's position labels beside the message record, the project-key derivation from the repository's own common Git directory, the message-record field mapping onto the store's fields and back, the encoding of correlations the store's thread alphabet rejects, response validation, and credential scrubbing. It exposes typed importable operations and a versioned JSON CLI; other coding-agents skills invoke `/operate-agent-mail` as a capability and never construct `am` argument vectors, read the store's database, or derive the project key themselves. No mail operation invokes an SPX command, so the capability depends on no SPX command surface.

## Rationale

One capability keeps store command knowledge and the record mapping testable and portable while preserving the skill-directory boundary plugin packaging requires. The project key is the repository's common Git directory because that directory is the one identity every checkout of a repository agrees on: a linked worktree, the pool's bare repository, and the pool's main checkout all resolve the same path, and deleting any individual checkout removes none of it. A key that names one checkout makes a repository's mail identity accidental and mortal — the checkout it names can be deleted while the registrations and message records keyed to it remain, and no later read can prove the project belongs to its own repository. The lookup runs without the variables that can make Git answer the location question from something other than the invoking working directory. That effect alone decides membership, never the mechanism producing it: a variable that names a repository directly answers with that repository, and a variable that bounds where Git may discover one hides the repository the working directory belongs to, but those are two known mechanisms rather than the only ones, and any variable with the same effect belongs to the class whether or not it works either way. Git exports `GIT_DIR` into every hook and into the commands it runs itself, so a mail operation invoked from such a context would otherwise key the store to the repository that ran the hook; a caller carrying a ceiling above the operation's own working directory would instead leave it resolving no repository at all. A variable that only widens the search toward the repository genuinely there falls outside the class and is carried through: removing it could prevent no wrong answer, only a right one, and a cross-mount layout every other Git command resolves would answer repository-unresolved for mail alone. Which names Git carries is Git's to say, so the class is the declaration and the adapter's removal list is the enumeration read against Git's own behaviour. Resolving the key inside the adapter also leaves the capability depending on no other command surface, so a change to another command surface cannot break any mail operation.

The message record carries fields the store lacks — a kind and a correlation — so the adapter maps them onto fields the store does carry, the subject prefix and the thread id, and reads them back, which keeps the record the unit of meaning while the store stays the unit of delivery. The store limits a thread id to an alphabet and a length, and a correlation is any text a caller supplies, so the adapter writes a correlation inside the alphabet unchanged and spells every other correlation as a prefixed escape the alphabet admits. The prefix `xc-` marks the escaped form, and a correlation that already begins with it is escaped too, so no escaped form equals a correlation written unchanged and decoding inverts the writing exactly. A thread id the adapter did not write reads back verbatim, because the store may hold threads other writers created. A correlation whose written form exceeds the store's length is refused before any command runs, because truncating it would make two correlations share one thread.

Registration returns a token that proves ownership of the name; the adapter removes it from every result because a token in a result reaches conversation transcripts and pane reads. The store CLI stores the credential at registration and reuses it for the next send from the same identity, and offers no separate credential or token command, so the adapter makes no credential refresh call and the token never travels through a result. The register operation's call sequence is the lookup and the registration call. A position label is a human-readable display name the store records per agent; it travels beside the message record in listed records and send results and never inside it, so the record-to-store bijection and every routing decision stay free of it, and a label, which two agents may share and which changes with its owner, never identifies a target. The adapter registers only the name and label its caller supplies, so each position registers only its own identity.

Reading a message and acknowledging it are two acts. A read is the recipient's private judgment that it has seen one message, visible to the recipient alone; an acknowledgement is the same judgment made visible to the sender. Fusing them in one operation makes every private judgment a notification to the sender, so the adapter keeps them apart and maps each to its own store command, and neither operation stands in for the other. A listing that marked the records it returned would make the act of looking a judgment, so the adapter binds listing to the store's non-marking surface and lets only the read and the acknowledgement change a record's read state. The unjudged form of that surface answers what a recipient has not yet judged, and the complete form answers every record, so a caller asks for either and no listing changes the answer to the next one.

A wait is a bounded read of the requester's own records, never a standing watcher: the caller passes the last store id it handled, the adapter returns the first record above that id or a named result at the timeout, and the run ends. Because the caller owns the cursor, a run that ends at any point loses no record and the adapter holds no state between runs; the wait lists through the complete form so read and unread records alike reach its selection, and it marks none read, so it neither competes with a caller's own judgment nor stands in for one. A listing that cannot reach back to the id could hide records between it and the newest one, so the wait names that case unreachable instead of returning a later record as if it were the first. A wait without a timeout has no end, so the missing timeout is an invalid request before any store command runs, and each store command inside the wait is bounded by the time that remains.

The store reports whether a record requires an acknowledgement and whether it is still owed or given; a caller needs only that the record carries the requirement, so both states read back as one fact and every other status as its absence. The store stamps each agent with an activity timestamp that moves for reasons unrelated to a session's liveness, so no operation derives liveness, staleness, or session state from it. A NUL byte in a text argument cannot cross a process boundary and would end the argument early, so a text argument carrying one is refused before any command runs. Every emitted result, including the failure of an input that does not parse, carries the versioned shape, so a caller parses one envelope whatever happened, and a runner error of any class reaches the caller as a named store-unavailable or command-failed result rather than an unhandled exception.

The adapter binds to one store's command surface, and that surface changes between builds that report one version string. Captured usage and public-response fixtures therefore name the tool and the build that produced them, and the build is pinned by the native binary an attested probe run records: the probe drives every operation against the installed store, and its record is the one home of the pin. A shipped constant would declare a build no run attested, and `am --version` identifies no build. The adapter stays plugin-local under [`spx/12-shipped-scripting.adr.md`](spx/12-shipped-scripting.adr.md), whose extraction rule governs its generic logic.

## Invariants

- One source-owned operation registry covers register, send, list, read, acknowledge, and wait. Read and acknowledge are distinct operations, and no operation keeps the names inbox or receipt.
- A list request carries `agent` and optional `allRecords`, `includeBodies`, and `limit`. A read request and an acknowledge request each carry `agent` and `messageId`. No request carries `unreadOnly`.
- The list operation binds to the store's non-marking listing surface, `am robot inbox`: its unjudged mode, `--unread`, by default, and its complete form, `--all`, when the request carries the all-records option.
- A record's read state changes only through the read or the acknowledgement; no listing, no wait, and no other operation changes it as a side effect.
- A read records, visibly to the recipient alone, that the recipient judged one message, and maps to the store's recipient-only read command, `am mail read`. An acknowledgement is a read the sender can observe, and maps to the store's acknowledgement command, `am mail ack`. Neither operation maps to the other's command.
- A wait request carries an id and an explicit timeout. The adapter lists the requester's records through the complete form of the listing surface, `am robot inbox --all`, so read and unread records alike reach its selection, until the first record whose store id exceeds that id is present or the timeout passes, and returns that record as a listed record or the named timeout result. A listing that cannot reach back to the id returns the named unreachable result, never a later record. Every store command inside a wait is bounded by the time that remains, and a wait without a timeout is an invalid request before any store command runs.
- A wait keeps no cursor, state file, or lock and changes no record's read state; the caller passes the last id it handled, so a run that ends at any point loses no record and the adapter holds no state between runs.
- A listed record whose store acknowledgement status shows an acknowledgement required, whether still owed or given, reads back as `ackRequired` true, and every other status reads back as false.
- A correlation inside the store's thread alphabet — an alphanumeric first character, then letters, digits, `.`, `_`, or `-`, at most 128 characters in all — that does not begin with `xc-` is written as the thread id unchanged. Every other correlation is written as `xc-` followed by its UTF-8 bytes, each byte outside letters, digits, `.`, and `-` spelled as `_` and two lowercase hex digits. Decoding on read inverts it exactly, and a thread id that is no encoded form the adapter writes reads back verbatim. Every thread id the adapter writes lies inside the alphabet, no encoded form equals a correlation the adapter writes unencoded, the store renders the encoded form, and a correlation whose written thread id exceeds 128 characters is rejected as an invalid schema before any command runs.
- Every emitted result carries the versioned result shape, including the failure whose input does not parse, and a runner error of any class maps to the named store-unavailable or command-failed result.
- A text argument carrying a NUL byte is rejected as an invalid schema before any command runs.
- No operation derives liveness, staleness, or session state from the store's per-agent activity timestamp.
- One project-key resolver maps the repository's absolute common Git directory, read for the adapter's own working directory, to the project key, or to the repository-unresolved result; it reads no working directory, environment variable, or parent path as a fallback.
- The key is canonical, and the two layers that make it so are separate. The repository lookup runs with every variable removed that can make Git answer the location question from something other than the invoking working directory — the effect deciding membership rather than the mechanism producing it, so naming a repository and bounding where one may be discovered are known mechanisms rather than an exhaustive pair; a variable that only widens the search toward the repository genuinely there is carried through — so it answers from the process's own resolved working directory alone and no value the caller inherited redirects it, neither onto a repository the working directory does not belong to nor away from the one it does; it therefore resolves the physical directory, and a checkout reached through a symlinked route and through its physical route report one directory. The resolver then normalizes that answer textually, to an absolute path carrying no `.` or `..` segment, no repeated separator, and no trailing separator. Canonicality rests on the lookup; the resolver never re-resolves a symlink, so a lookup that returned a non-physical path would surface as one repository with two keys rather than being silently repaired.
- One record mapping is a bijection between a message record and the store fields the adapter writes: `correlation` to the thread id through the correlation encoding, `kind` to the subject prefix, `sender` to the sender, `recipient` to the recipients, `subject` to the subject remainder, `body` to the body, `ackRequired` to the acknowledgement requirement, and the store-assigned `id` to the record id.
- A registration request carries an optional display name that the adapter passes to the store as `display_name`; an absent display name passes none.
- The store's labels — `sender_display_name` on listed records with and without bodies and on send results, and `to_display_names` as the mapping from each recipient stable name visible to the reader to its label — pass through verbatim, null included, beside the message record; no label enters the message record or its mapping.
- After a successful registration the next send authenticates through the credential the store CLI stores at registration; the adapter makes no credential refresh call, and no result carries the registration token.
- Every target resolves by stable name or store id; no operation selects, routes, or addresses by a label.
- Every command execution is bounded, argument-vector based, fully reaped before return, and isolated from the adapter request stream.
- Store identities — message ids, thread ids, agent names, timestamps — remain byte-for-byte values from the public response, except that a thread id the adapter wrote in its encoded form reads back as the correlation it encodes.
- Captured usage and public-response fixtures are the committed observations of the probe that drives every operation against the installed store, and each fixture names the tool and the build that produced it. A change to the build pin, or a probe run that reports grammar or response drift, invalidates the affected fixtures and requires recapture from a probe run before they serve as oracles. The project key has no captured oracle, because the checkout shapes a real repository takes are the oracle the resolver is read against.
- The build pin is the native `am` binary the attested installed-store probe run records, named by the Agent Mail source commit it was built from and the binary's SHA-256. `am --version` identifies no build, because one version string covers builds with and without the label fields, and the probe record is the pin's one home.
- A registration result never carries the store's registration token.
- A second terminal handback for one coordination reference that carries the same terminal kind with different content is a conflicting handback, rejected with a detail naming the content difference, never reported as a kind conflict.
- An absent `am` executable yields the store-unavailable result; a working directory that resolves to no repository, an absent Git executable, and a Git invocation that reports no absolute common directory each yield the repository-unresolved result. Neither result triggers a fallback.
- The adapter's external programs are the store CLI and Git; no operation's execution path reaches another program.
- The raw-command scanner recognizes an `am` command in argument-vector form and in shell-string form.

## Verification

- ALWAYS: a list request maps to the store's non-marking listing surface in its unjudged mode, and a list request carrying the all-records option maps to that surface's complete form
- ALWAYS: a read request maps to the store's recipient-only read command and an acknowledge request maps to the store's acknowledgement command, each for one message id, and neither request maps to the other's command
- NEVER: a list, a wait, or any operation other than the read and the acknowledgement changes a record's read state
- ALWAYS: a wait request carrying an id and a timeout maps to the first record addressed to the requester whose store id exceeds that id, read or unread, listed through the complete form of the listing surface, to the named timeout result when none is present before the timeout, and to the named unreachable result when the listing cannot reach back to the id
- NEVER: a wait request without a timeout runs a store command, and no store command inside a wait outlives the timeout
- NEVER: a wait keeps a cursor, state file, or lock
- ALWAYS: a listed record whose store acknowledgement status shows an acknowledgement required, whether still owed or given, reads back as `ackRequired` true, and every other status reads back as false
- ALWAYS: every correlation round-trips through the adapter's encoding and decoding to itself; every thread id the adapter writes lies inside the store's thread alphabet; no encoded form equals a correlation the adapter writes unencoded; and a thread id that is no encoded form the adapter writes reads back verbatim
- NEVER: a send whose correlation's written thread id exceeds 128 characters reaches a store command; the request is rejected as an invalid schema first
- ALWAYS: every emitted result carries the versioned result shape, including the failure whose input does not parse, and a runner error of any class maps to the named store-unavailable or command-failed result
- NEVER: a text argument carrying a NUL byte reaches a store command; the request is rejected as an invalid schema first
- NEVER: an operation derives liveness, staleness, or session state from the store's per-agent activity timestamp
- ALWAYS: for every operation, the argument vector the adapter builds is accepted by the installed store, and every response the adapter parses is a shape that store emits, as the attested installed-store probe run records
- ALWAYS: each captured usage and public-response fixture names the tool and the build that produced it, and the build it names is the build the installed-store probe run records
- ALWAYS: a second terminal handback for one coordination reference that carries the same terminal kind with different content is rejected as a conflicting handback whose detail names the content difference
- NEVER: a shipped coding-agents Python script outside `/operate-agent-mail` constructs an `am` argument vector or a shell-string `am` command, or derives a project key from Git state
- ALWAYS: a read records, visibly to the recipient alone, that the recipient judged one message, and establishes nothing about the message's content
- ALWAYS: an acknowledgement is a read the sender can observe, and establishes no agreement, ownership, authorization, or acceptance of a proposal

### Testing

- ALWAYS: each source-owned operation maps a valid versioned request to the exact `am` argument vector for that operation under the resolved project key ([mapping])
- ALWAYS: a linked worktree, the pool's bare repository, the pool's main checkout, and a symlinked route to one of them each map to one project key, that key being the pool's bare repository directory, and a working directory that is no repository maps to the repository-unresolved result ([mapping])
- ALWAYS: each variable that can make Git answer the location question from something other than the invoking working directory, and the complete set together, maps to no change in the resolved key — a working directory carrying a value that names another repository, or a value that bounds discovery above itself, still maps to its own repository's key, and a working directory that is no repository still maps to the repository-unresolved result. The domain is the set Git's own behaviour confirms moves the answer off the working directory, read from Git rather than from the adapter's removal list ([mapping])
- ALWAYS: public `am` responses map to versioned source-owned results or named command failures without value rewriting ([mapping])
- ALWAYS: the store's labels — `sender_display_name` on listed records with and without bodies and on send results, null included, and `to_display_names` as the mapping from each visible recipient stable name to its label — map verbatim beside the message record, and a registration request's optional display name maps to the store's `display_name` ([mapping])
- ALWAYS: every message record maps onto the store fields and back to an equal record ([property])
- NEVER: an operation selects, routes, or addresses a target by a label — the stable name or the store id selects every target ([compliance])
- NEVER: a registration result carries the registration token the store returns ([compliance])
- ALWAYS: an absent `am` executable maps to the store-unavailable result and a working directory where no program resolves maps to the repository-unresolved result ([mapping])
- NEVER: an operation reaches a program outside the adapter's own command vectors — every operation completes where only those programs resolve ([compliance])

### Audit

- NEVER: a shipped coding-agents skill outside `/operate-agent-mail` instructs a workflow to construct `am` commands, invoke `am` command help, or read the store's database ([audit])
- ALWAYS: the store subprocess boundary accepts a dependency-injected `CommandRunner` Protocol and the default runner uses null-device stdin, captured output, and a bounded timeout ([audit])
- ALWAYS: tests inject controlled runner implementations only under `/test` Stage 5 exception 1 (failure simulation) or exception 2 (interaction protocols) ([audit])
- ALWAYS: a controlled stand-in placed at the process boundary rather than injected through the runner — an executable on a restricted search path — stands only as exception 2 (interaction protocols) evidence for the boundary itself, naming which programs the adapter may reach; it never stands in for store behavior, which the captured responses own ([audit])
- ALWAYS: `/operate-agent-mail` owns all bundled-script access; composing skills invoke the capability through the skill surface rather than manufacturing a cross-skill filesystem path ([audit])
- NEVER: framework mocks or monkeypatching replace store behavior or the command-runner boundary ([audit])
- NEVER: the adapter owns another workflow's retry, checkpoint, persistence, result interpretation, or continuation decision ([audit])
