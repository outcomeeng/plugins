# Installed Store

The protocol lives at `probes/installed-store/probe.md`, the target of the assertion's `[probe]` tag. Working runs stay in an ignored `runs/` inside this directory; every attested run retains at least one inspectable artifact beside this file.

## Intent

An operator relying on the agent-mail adapter expects every operation to reach the store through an argument vector the installed `am` accepts, and expects every response the adapter parses to be a shape that `am` emits. The uncertainty is grammar and response drift: one `am` version string covers builds with different command grammars and different response fields, so the adapter's argument vectors and parsers can disagree with the installed build while every deterministic test passes against captured fixtures. The probe drives each operation against the installed store, and its attested run is the one home of the build pin and the source of every captured usage and public-response fixture.

## Environment and preconditions

- The installed native `am` is the build under test. The run records the build as the installed CLI reports it: the path of the executable the adapter invokes, `am --version`, and `am capabilities`. The pin is the version string the CLI reports, because the CLI reports no source commit; a run that finds a source commit in the CLI's output records it with the version.
- The store is isolated by project key only: a scratch mail project whose key the adapter resolves from a scratch Git repository outside the repository under test, at a path no earlier run used, a writable store, and no foreign records under that key. A repository removed and created again at the same path keeps its key, and the store keeps every record under it. The installed `am` ignores environment overrides of its store, so the run writes to the installed store under the scratch project key and touches no record under any other key.
- Three positions with distinct stable names exist: a sender, a recipient, and a second recipient. Each registers through the adapter with its own label. A fourth stable name, an observer, registers with no label. A fifth, the bulk recipient, registers with its own label.
- The adapter runs from the sources of the committed head under test, through `python3 "${CLAUDE_SKILL_DIR}/scripts/agent_mail.py" run` for each request operation, with each request submitted on its standard input.
- No step constructs a raw `am` command except the observation steps that record the build, capture usage text, and read the store's own surfaces: its agent listing, its acknowledgement listing, a page of delivery events, and its single-message read.

## Protocol

1. Record the build: the path of the executable the adapter invokes, its `am --version` output, and its `am capabilities` version and schema, and record whether the CLI reports a source commit.
2. Capture the usage text of every store command the adapter builds an argument vector for, from the installed `am`, and retain each as a fixture naming the tool and the build recorded in step 1.
3. Register the sender, the recipient, and the second recipient through the adapter's register operation, each with a label. Record that each result is `succeeded` and that the adapter accepted every argument it passed.
4. Register the observer through the register operation with no label, then list the registrations through the adapter's registrations operation. Record the argument vector, that the store accepted it, that the result is `succeeded`, that it lists the sender, the recipient, the second recipient, and the observer, each with the label it registered and the observer's label `null`, and that the store's raw listing writes the label of each labelled registration and none for the observer. Retain the store's raw listing as the agent-listing response fixture.
5. Send one record from the sender to the recipient with an acknowledgement required, one record with an acknowledgement required whose correlation lies outside the store's thread alphabet, and one record to the second recipient. Record that each is `succeeded`, that the store assigned an id, and that the outside-alphabet correlation round-trips through the stored thread id.
6. List the recipient's records without options. Record the argument vector, that the store accepted it, that every listed record is unread, the response shape each record carries, and that each record sent with an acknowledgement required reads back with `ackRequired` true.
7. List the recipient's records with the all-records option, with bodies, and with a limit. Record that the store accepted each vector and that the response shape parses.
8. Wait for the recipient with an `afterId` below the first sent id and a short timeout. Record the `received` outcome. Wait again with an `afterId` above the last sent id and record the `timeout` outcome.
9. Register a fifth stable name, the bulk recipient, with a label, and send it 1001 records from the sender. List its records in the complete form with a limit of 1000, then wait for it with an `afterId` one below its first record and a timeout of 120 seconds. Record that the full listing holds 1000 records, every one past `afterId`, that the wait returns `received` with the first record sent to the bulk recipient, and that the result's response is the store's single-message read. Retain the store's raw page of the recipient's delivery events with a limit of 2 as the events-page response fixture, and the wait's response as the single-message-read response fixture.
10. List the recipient's records unjudged, then again, and record that neither listing, nor any wait, changed any record's read state. Read the recipient's newest record through the store's single-message read, list the recipient's records unjudged again, and record that the record it read still lists as unread.
11. Read the first record as the recipient through the adapter's read operation. Record that the store accepted the vector, that the read state of that record changed for the recipient, and that the store's acknowledgement listing for the recipient shows that record still pending.
12. Acknowledge the second record as the recipient through the adapter's acknowledge operation. Record that the store accepted the vector and that the store's acknowledgement listing for the recipient shows that record acknowledged.
13. List the recipient's records unjudged and with the all-records option. Record that the read record and the acknowledged record leave the unjudged listing and remain in the complete listing, and that a record whose acknowledgement status is owed or given reads back with `ackRequired` true.
14. Submit a request carrying a text argument with a NUL byte, a correlation whose written thread id exceeds 128 characters, and a request that does not parse. Record that each is rejected before any store command runs, with the versioned result shape.
15. Retain the request, the adapter result, and the store's raw response for every step as structured output beside this file, with the fixtures from steps 2, 4, and 9.

## Verdict

`passed`. Every operation, the registrations listing included, reached the store through an argument vector the installed `am` accepted, and every response shape parsed. A wait whose complete listing of 1000 records did not reach back to its id paged the delivery events and returned the first record past the id through the single-message read, and that read left the record's read state as it was. The registrations listing reads each label back verbatim and an unlabelled registration back as `null`. A record sent with an acknowledgement required reads back with `ackRequired` true while still owed (`required`), after a read (`pending`), and after acknowledgement (`acked`). The verdict holds for the build pinned by the version string `am 0.3.36` alone.

## Limitations

The protocol exercises one installed `am` build and one store under a scratch project key. The installed `am` ignores environment overrides, so the isolated-store precondition holds by project key only: the run writes to the installed store, and the store holds records under other keys the run does not read or change; store ids are global, so the bulk recipient's 1001 records span more than 1001 ids. The CLI reports no source commit, so the build pin is the version string `am 0.3.36` alone, and one version string covers builds that differ in grammar and response fields; the binary's SHA-256 is not recorded. The run reads acknowledgement state through the store's `list-acks` command, and read state through the adapter's unjudged listing. It does not exercise a wait that pages more than one page of delivery events, a wait whose delivery events do not reach back to its id, a store command that reaches its bound, concurrent senders, a registration refused by the store's name rules, or a runner failure class such as an absent binary; the deterministic tests cover those against the fixtures the run captures. The single-message read carries no label fields, so a wait that finds its record through the delivery events returns no label in its response.
