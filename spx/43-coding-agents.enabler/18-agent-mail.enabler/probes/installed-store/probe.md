# Installed store

## Intent

The adapter decision binds each of the five mail operations — registration, send, listing, read, and acknowledgement — to one command of the agent-mail store, and the adapter parses what that command answers. The captured usage and response oracles the node's deterministic evidence reads are recordings of that store; a recording stays evidence only while an executed observation of the store the machine actually carries backs it. This probe settles whether the installed store accepts the argument vector each operation is bound to and emits the response shape the adapter parses, and it supplies the provenance — tool, version, argument vector, exit code, and verbatim output — every captured usage and response fixture is recaptured from.

The uncertainty it exposes is the one the node already paid for once: captured artifacts pinned behind the installed store went on asserting a listing behaviour the store had changed, while the deterministic evidence stayed green.

## Environment and preconditions

- The `am` command line of the agent-mail store is on the search path; its resolved installation and `am --version` are recorded before any other step.
- A disposable Git repository created for the run with `mktemp -d` under `$TMPDIR`, outside every product checkout. Its project key is the adapter's own derivation, read by running the adapter's `project-key` form with that repository as the working directory. Every `am` invocation that takes a project key uses that key and no other.
- Every `am` invocation runs with the disposable repository as its working directory and with `AGENT_MAIL_PROJECT`, `AGENT_MAIL_AGENT`, `AGENT_NAME`, and `AGENT_MAIL_SENDER_TOKEN` removed from its environment, so no inherited value selects another project, agent, or credential.
- The store's database is never read directly; every observation comes from the `am` command line.
- Argument vectors follow the adapter's construction form: the project key as a separate `--project <key>` pair, every free-text option attached as `--option=value`, and `--json` on the commands whose response the adapter parses as JSON.

## Protocol

Each `am` invocation below is recorded as one JSON envelope carrying `tool`, `version`, `observedAt`, `argv`, `exitCode`, `stdout`, and `stderr`. Before an envelope is written, every JSON field of the output whose name contains `token` is replaced by `REDACTED-<field-name>` — a response carrying such a field is then re-rendered with two-space indentation — and every redacted value is replaced wherever else it appears in the output. Working envelopes go to an ignored `runs/<run-id>/` directory beside this file.

1. Record `command -v am`, the installation it resolves to, and `am --version`.
2. Create the disposable repository with `mktemp -d` under `$TMPDIR`, run `git init` in it, and derive its project key `K` with the adapter's `project-key` form run from that repository.
3. Capture the usage text of every command the five operations bind to: `am agents register --help`, `am mail send --help`, `am robot inbox --help`, `am mail read --help`, and `am mail ack --help`; and, as context for those bindings, `am mail --help`, `am mail inbox --help`, `am agents --help`, `am agents list --help`, `am robot --help`, and `am robot message --help`.
4. Registration: run `am agents register --project K --program=claude-code --model=opus --task=<text> --json` twice, supplying no name. Record the name the store assigns to the first as the sender `S` and to the second as the recipient `R`. Run `am agents list --project K --json`.
5. Send: run `am mail send --project K --from=S --to=R --thread-id=probe-installed-store --subject=<[kind] subject> --body=<text> --ack-required --json` for one message `A`, and the same without `--ack-required` for one message `P`. Then run the same send with `--thread-id=outcomeeng/changes#132`, a canonical Change identity used as a correlation.
6. Listing, unjudged: run `am robot inbox --project K --agent=R --json`, then the same with `--unread`, then with `--unread --include-bodies`. Record the sender's view of `P` with `am robot message --project K --agent=S <P> --json`.
7. Read: run `am mail read --project K --agent=R <P>`. Repeat the unjudged listing and the sender's view of `P`.
8. Acknowledgement: run `am mail ack --project K --agent=R <A>`. Repeat the unjudged listing, record the sender's view of `A`, and run the complete listing `am robot inbox --project K --agent=R --all --json`.
9. Failure shape: run `am mail read --project K --agent=S <P>`, a read by an agent that is no recipient of `P`.
10. Run `am agents list --project K --json` again and compare each agent's `last_active_ts` with the value step 4 recorded.
11. Confirm that no redacted value occurs in any envelope, copy the retained envelopes beside this file, and remove the disposable repository.

## Verdict

`passed` — against the argument vectors the adapter decision assigns to the five operations. The installed `am 0.3.36`, the release the decision pins, accepted every one of them: a nameless registration that returns the assigned name, a send carrying every record field, the non-marking listing in its unjudged default and `--unread` forms and in its `--all` complete form, the recipient-only `mail read`, and the sender-visible `mail ack`. Each response is one of the shapes recorded above — a JSON agent object, a JSON message object, a JSON listing envelope with an `inbox` array, a one-line text confirmation for read and acknowledgement, and, on failure, a nonzero exit with the store's error on stderr. The listing marked nothing read across six runs; only the read and the acknowledgement changed read state; the read left the sender's view unchanged while the acknowledgement changed it; and the store rejects a canonical Change identity as a thread id, the premise of the adapter's correlation encoding.

Actor provenance comes from the verification run, never from this prose.

## Limitations

- The adapter at head `dc9db09166ebc0658f577d7297f3d3ca389ff98e` still builds the four-operation grammar — a registration that sends a name, no read operation, and a listing without the complete form — so this run drove the vectors the decision assigns in the adapter's construction form rather than vectors the adapter emitted. A change to the adapter invalidates this result; the next run drives each operation through the adapter's own request form.
- No encoded correlation was sent, because the adapter's encoding does not exist yet; the run established only that the raw identity is rejected and what alphabet and length the store admits.
- `--limit`, `--urgent`, and `--ack-overdue` on the listing, a repeated read or acknowledgement, an acknowledgement of an already-read record, and re-registration of an existing name were not exercised.
- Visibility of a read to the sender was observed through `robot message` alone; the other surfaces that render a message to its sender were not exercised.
- Whether `mail inbox` marks what it returns was not exercised; no operation binds to it.
- The activity-timestamp observation spans about one minute of one store release on one machine, with the store's default contact policy auto-accepting the first send.
