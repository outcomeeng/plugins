# Installed store

## Intent

The adapter decision binds each of the five mail operations — registration, send, listing, read, and acknowledgement — to one command of the agent-mail store, and the adapter parses what that command answers. The captured usage and response oracles the node's deterministic evidence reads are recordings of that store; a recording stays evidence only while an executed observation of the store the machine actually carries backs it. This probe settles whether the installed store accepts the argument vector the adapter builds for each operation and emits the response shape the adapter parses, and it supplies the provenance — tool, version, argument vector, exit code, and output — every captured usage and response fixture is recaptured from.

The uncertainty it exposes is the one the node already paid for once: captured artifacts pinned behind the installed store went on asserting a listing behaviour the store had changed, while the deterministic evidence stayed green.

## Environment and preconditions

- The `am` command line of the agent-mail store is on the search path; its resolved installation and `am --version` are recorded before any other step.
- The adapter is `src/plugins/coding-agents/skills/operate-agent-mail/scripts/agent_mail.py` at a recorded commit, and the file in the working tree equals the blob that commit carries.
- A disposable Git repository created for the run with `mktemp -d` under `$TMPDIR`, outside every product checkout. The adapter derives its project key itself: every adapter invocation runs with that repository as its working directory, so the key is the adapter's own derivation and no step supplies one.
- Every adapter invocation runs with `AGENT_MAIL_PROJECT`, `AGENT_MAIL_AGENT`, `AGENT_NAME`, and `AGENT_MAIL_SENDER_TOKEN` removed from its environment, so no inherited value selects another project, agent, or credential.
- The store's database is never read directly, and the store is reached only through the adapter's `run` request form; `am --version` is the one direct `am` invocation.

## Protocol

1. Record `command -v am`, the installation it resolves to, and `am --version`. Confirm the adapter file's blob equals the one the recorded commit carries.
2. Create the disposable repository with `mktemp -d` under `$TMPDIR` and run `git init` in it. Run the adapter's `project-key` form from that repository and record the key `K` it derives.
3. Prepend to the search path a directory, created with `mktemp -d` under `$TMPDIR`, that holds a transparent recorder named `am`. The recorder runs the resolved `am` with the same arguments, passes standard input, output, and error through without reading them, and appends only the argument vector and exit code to a log. The run stops if a recorded vector carries a `--project` other than `K`, or a successful result names another project key.
4. Each step below is one versioned request `{"schemaVersion": 1, "operation": …, "arguments": …}` on standard input to `python3 agent_mail.py run`, working directory the disposable repository. Each is recorded as one JSON envelope carrying `tool`, `adapterCommit`, `store` (tool and version), `observedAt`, `cwd`, `request`, `storeInvocations` (the recorder's vectors and exit codes for that request), `adapterExitCode`, the adapter's `result`, `adapterStderr`, and `redactedFields` — before an envelope is written, any result field whose name contains `token` is replaced by `REDACTED-<field-name>` and named there. Working envelopes go to an ignored `runs/<run-id>/` directory beside this file.
5. Registration: `register` twice with `program`, `model`, and `task`, supplying no name. The first assigned name is the sender `S`, the second the recipient `R`.
6. Send three records from `S` to `R`: kind `question` with `ackRequired` true under correlation `probe-installed-store` (message `A`); kind `fact` with `ackRequired` false under the same correlation (message `P`); and kind `order` with `ackRequired` false under correlation `outcomeeng/changes#132`, a canonical Change identity outside the store's thread alphabet (message `E`).
7. Listing, unjudged: `list` for `R` with no option, then with `includeBodies` true, then with `limit` 1.
8. Read: `read` of `P` as `R`, then `list` for `R`.
9. Acknowledgement: `acknowledge` of `A` as `R`, then `list` for `R`, then `list` with `allRecords` true, then with `allRecords` and `includeBodies` true.
10. Failure shape: `read` of `P` as `S`, an agent that is no recipient of `P`.
11. Confirm that no envelope carries a field or value naming a token, and copy the retained envelopes to `adapter-run-<run-id>/` beside this file. The disposable repository and the recorder directory are left in place and their paths recorded.

## Verdict

`passed` — for every operation, the installed `am 0.3.36` accepted the argument vector the adapter built from its own versioned request, and every response the adapter parsed is a shape that store emitted. Nameless registration returned the assigned name, which the adapter carried verbatim and without the registration token. Send accepted every record field, including the encoded thread id `xc-outcomeeng_2fchanges_23132`, and the listing decoded it back to `outcomeeng/changes#132`. The non-marking listing answered in its unjudged mode, with bodies, with a limit, and in its complete form, and three unjudged listings left every record unjudged. The recipient-only read and the acknowledgement each removed exactly their record from the unjudged set, and each returned the one-line text the adapter carries as `output`. The non-recipient read reached the adapter's `command-failed` result carrying the store's exit code and error verbatim.

Actor provenance comes from the verification run, never from this prose.

## Limitations

- The run reached the store only through the adapter's operations, which bind no agent listing and no sender-side message view. Sender-side visibility of a read versus an acknowledgement, and the store's never maintaining `last_active_ts`, rest on the earlier run's observations of the same release.
- The encoding was exercised with one correlation, which escapes `/` and `#`. A non-ASCII correlation, one whose encoded form reaches the 128-character limit, and one that itself begins with the `xc-` prefix were not sent.
- With `limit` 1 the store returned 2805 while the unlimited listing ranks 2803 first, so a limited listing is not the first rows of the unlimited order. Which rows a limited listing selects was not characterized further, and the adapter makes no claim about it.
- The run removed `AGENT_MAIL_PROJECT`, `AGENT_MAIL_AGENT`, `AGENT_NAME`, and `AGENT_MAIL_SENDER_TOKEN`. The adapter's default runner passes its caller's environment to `am` unchanged. Every vector names its project and agent or sender explicitly, so the store's documented fallbacks for those do not apply. Send under an inherited `AGENT_MAIL_SENDER_TOKEN`, which the store's usage says it reads to prove ownership of `--from`, was not observed.
- A repeated read or acknowledgement, an acknowledgement of an already-read record, and a listing by an agent holding no records were not exercised.
- The failure detail carries the store's failure envelope verbatim — storage paths, process id, binary path — and no credential. The adapter passes it through without rewriting, as its response contract requires.
- The observation covers one store release on one machine, with the store's default contact policy auto-accepting the first send and generating record 2802.
- A change to the adapter's command grammar, record mapping, or response parsing, or to the store pin, invalidates this result; the next run repeats this protocol against the changed adapter.
