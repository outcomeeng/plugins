# TypeScript Workflow

PROVIDES operational TypeScript workflows for implementation, remediation, code review, test review, and architecture review
SO THAT TypeScript projects using spec-tree
CAN turn specs, decisions, and test standards into source changes that survive adversarial audit

## Assertions

### Compliance

- ALWAYS: TypeScript implementation work starts from complete spec-tree context, governing ADRs/PDRs, and lower-index TypeScript standards — code follows declared product truth rather than local precedent ([review])
- ALWAYS: TypeScript coding workflows distinguish discovery from authority — code search locates artifacts to reuse, while specs, decisions, local instructions, and skills decide how the work is done ([review])
- ALWAYS: implementation and remediation workflows keep source changes aligned with TypeScript architecture standards, product validation commands, and TypeScript test standards — lower-index enablers provide the rules this workflow consumes ([review])
- ALWAYS: TypeScript code uses strict static types, typed boundaries for unknown input, source-owned vocabulary, and injected side-effect dependencies — source modules expose contracts that callers and tests can observe without replacement mocks ([review])
- ALWAYS: TypeScript test changes load the TypeScript testing standard and route evidence through the selected assertion type and execution level — implementation workflows do not redeclare testing policy locally ([review])
- ALWAYS: TypeScript audit and remediation workflows run repository-canonical validation, inspect behavior through source comprehension and evidence quality, update every affected artifact in the same concern, and rerun verification before reporting readiness ([review])
- NEVER: preserve legacy aliases, compatibility shims, parallel APIs, or style-only approvals — TypeScript artifacts satisfy the governing spec, use the active source contract, and meet the evidence model that applies to them ([review])
