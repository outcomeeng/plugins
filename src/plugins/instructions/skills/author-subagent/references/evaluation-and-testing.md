<evidence_design>

1. Read the governing assertion and identify the real subject.
2. Use deterministic tests for parsing, generation, configuration validation,
   namespace mapping, and installation behavior.
3. Use the owning verification workflow for semantic judgments and execution acceptance.
4. Select cases from the complete supported profile domain and from the behavior's
   actual failure boundaries.
5. Keep expected results independent of the implementation being exercised.

</evidence_design>

<native_loading>

Use the owning product's disposable installation workflow. Preserve each generated
definition, the native loader's result, and the exact installed role. Inspect the
complete configuration, including a control that is intentionally absent.

A running session may retain definitions loaded before installation changed.
Use the workflow's fresh-session boundary when verifying a newly installed definition.

</native_loading>

<minimal_execution>

Prepare one minimal target that the configured role's skill can interpret without an
author-written context packet. The owning workflow performs one native launch and
retains its actual response. Inspect that response against the declared result contract.

Keep loading evidence and execution evidence distinct: a parsed file establishes no
successful task execution, and a task response alone establishes no agreement between
the selected profile and the loaded native configuration.

</minimal_execution>

<retained_record>

Record the exact subject revision, native configuration, configured role, supplied
target, observed load result, launch result, and final response. Preserve errors at
their actual boundary. The independent verifier reads these artifacts and the governing
requirements to produce its verdict.

For comparative quality or cost work, use the owning product's approved case set and
budget. A role's existing profile assignment supplies no comparative evidence.

</retained_record>
